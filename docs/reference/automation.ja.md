# スクリプトから kortopi を実行する

kortopi が人の手を離れて動く場所は3つある。デプロイのとき、プルリクエストのチェック、定期的なジョブである。
このページは、それぞれの実行の形と、スクリプトが頼れることを示す。
コマンドは [kortopi plan](plan.ja.md)・[kortopi apply](apply.ja.md)・[kortopi export](export.ja.md) のものである。

## スクリプトが頼れること

- 標準出力には、`kortopi plan` と `kortopi apply` の計画と、apply が書いたものの行が出る。標準エラー出力には、`kortopi: <message>` の形のエラーが1行ずつ出る。例外は接続の失敗で、接続の試みごとにも1行を出す（[kortopi plan](plan.ja.md#データベースへの接続)）。`note: <message>` の形の注記、別の apply を待つ apply の行、コミットが始まったあとに来た割り込みの行もここに出る。
- 計画はデータベースを変えない。そのため、何度でも実行できる。
- 適用済みの宣言の apply は何も変えず、空の計画を出す。失敗した apply は何も変えていない。例外は、コミットの結果が分からないとエラーが告げる場合で、そのときは `kortopi plan` で状態を確かめる。データベースやファイルでのエラーのあとは、標準エラー出力の最後の行が `kortopi: nothing was changed` になる。apply がシーケンスを進めたあとでコミットが失敗したときは、その行に `but the sequences that the apply had moved before its commit, ...` が続く。ロールバックはシーケンスを戻さないからである（[kortopi apply](apply.ja.md#シーケンス)）。フラグの誤りのあとは、代わりにコマンドの使い方が出力の最後に来る。そのため、apply はどんな失敗のあとでも、もう一度実行できる。
- 接続の設定は、libpq の環境変数から読む（[kortopi plan](plan.ja.md#データベースへの接続)）。パスワードのフラグはない。パイプラインのシークレットから `PGPASSWORD` に渡すか、パスワードファイルに書く。

| コマンド | 0 | 1 | 2 |
|---|---|---|---|
| `kortopi plan` | 計画を立てた | 計画が失敗した | 使わない |
| `kortopi plan --exit-code` | 適用するものがない | 計画が失敗した | 計画が空でない |
| `kortopi apply` | apply がコミットした、または変えるものがなかった | apply が失敗した | 使わない |
| `kortopi export` | すべてのファイルを書いた | 書き出しが失敗した | 使わない |

パイプラインは、終了コードと標準エラー出力の最後の行で結果を見分ける。

- `kortopi plan --exit-code` の 2：計画が空でない。計画をレビューに見せるか、ずれを報告する。
- 1 で、最後の行が `kortopi: nothing was changed` か、それにシーケンスを挙げたもの：エラーが示すものを直して、もう一度実行する。
- 1 で、コミットの結果が分からないというメッセージ：`kortopi plan` でコミットされたかどうかを確かめ、されていなければもう一度 apply する（[kortopi apply](apply.ja.md#出力の読み方)）。
- 1 で、最後がコマンドの使い方：フラグを直す。
- `kortopi export` の 1：エラーは、書き出しが書いたファイルを挙げるか、何も書かなかったと告げるか、何かを書く前に書き出しが見つけた誤りである（[kortopi export](export.ja.md#出力とエラー)）。
- 128 より大きい値（SIGKILL なら 137）：kortopi が自分のセッションを終える前に、シグナルが kortopi を終わらせた。そのセッションはサーバーに残り、ロックを持ち続けることがある（[途中で途切れた実行](#途中で途切れた実行)）。kortopi は SIGINT と SIGTERM を受け止め、そのあとは 1 で終わる。

## デプロイのとき

行は、同じデプロイの中で、スキーマのあとに適用する。

```sh
export PGHOST=db.example.test PGDATABASE=app PGUSER=app_owner
export PGPASSWORD="$APP_OWNER_PASSWORD"
kortopi apply --dir data --lock-timeout 10s
```

- apply は、デプロイのスキーマの変更がコミットしてから始める。apply が始まったあとに宣言したテーブルを変える変更があれば、apply は何も書き込む前に終了コード 1 で止まる。テーブルを書き換えるか空にする変更、テーブルを置き換える変更、パーティションをアタッチかデタッチする変更である。そのときは、もう一度実行する（[kortopi plan](plan.ja.md#実行中のスキーマの変更)）。
- apply は、宣言したテーブルを所有するロールか、[apply に要るもの](apply.ja.md#apply-に要るもの)を持つロールで実行する。スキーマごとに所有者のロールがあるなら、スキーマごとに1回、`--schema` を付けて apply を実行する。そのとき、テーブルが両方向に参照し合う2つのスキーマは、互いを要する新しい行を、両方を書けるロールによる1回の apply か、2回のデプロイでしか受け取れない（[kortopi apply](apply.ja.md#スキーマごとの-apply)）。
- `--lock-timeout` で apply にロック待ちの上限を与える。与えなければ、宣言したテーブルや書く行のロックをほかのセッションが持っている間、apply は際限なく待ち、デプロイもそれを待つ。与えれば、apply はそう告げるエラーを出して止まり、何も変えない（[kortopi plan](plan.ja.md#ロックを待つとき)）。`PGOPTIONS` ではなくフラグを使う。トランザクションモードのコネクションプーラーの後ろでは `PGOPTIONS` がサーバーに届かず、実行は接続に失敗するか、上限なしに待つ（[接続の設定](plan.ja.md#接続の設定)）。
- ジョブをキャンセルする実行役は、kortopi に SIGTERM か SIGINT を送る。コミットの前なら、kortopi は文のキャンセルをサーバーに求め、ロールバックし、5秒以内に終了コード 1 で終わる。削除のあとの検査の最中なら、2つ目のセッションも終えるので、10秒以内に終わる。最後の行は `kortopi: nothing was changed` である。セッションが終わったという応答がその間にサーバーからなかったときは、その前の行が、セッションを `pg_stat_activity` で見つけて終わらせる方法を伝える。コミットが始まっていれば、kortopi は応答を待つことを伝え、2度目のシグナルで結果の分からないメッセージとともに待つのをやめる。そのときは `kortopi plan` を実行する。それより早くプロセスを強制終了する実行役では、結果はサーバーが決める（[kortopi apply](apply.ja.md#apply-に割り込む)）。セッションも、サーバーが終わらせるまで残る（[途中で途切れた実行](#途中で途切れた実行)）。
- 終了コード 1 は、apply が何も変えなかったことを示す。例外は、コミットの結果が分からないとエラーが告げる場合である。直したあとで、デプロイは apply をもう一度実行できる。
- 削除の扱いは、パイプラインごとに決める。`--allow-delete` がなければ、apply はモード `sync` のテーブルが失うべき行を残し、`Not deleted: ...` の行でそう告げ、0 で終わる。`--allow-delete` があれば、`--max-delete`（既定は 100 行）の範囲でそれらを削除する。この上限は、削除する行と、外部キーがそれと一緒にすべての段で消すか変える行をすべて数える（[kortopi apply](apply.ja.md#削除の安全策)）。上限は、宣言の行だけでなく、パイプラインの削除がそれを参照するテーブルで消し、変える行も見て決める。行が削除されたときにほかのテーブルの行を消すか変えるトリガーは、削除をする apply を止める。ただし、`kortopi.toml` の `allow_unplanned_changes` がそのトリガーの変えるテーブルを挙げれば止めない。そのとき apply は、データベースがそのテーブルで数えた削除を上限に数える。その数は、`Applied:` のあとの `Unplanned changes in` で始まる行が伝える（[kortopi apply](apply.ja.md#計画を超えて変わってよいテーブル)）。行を残したデプロイを失敗にしたければ、apply のあとで `kortopi plan --exit-code` を実行する。どちらの場合も、パーティションテーブルでないテーブルに削除する行が計画にあれば、apply には既定のとおり on の `track_counts` が要る（[kortopi apply](apply.ja.md#track_counts)）。削除をする apply は、削除のあとに2つ目の接続を開き、削除が着くテーブルのスキーマを今のものと比べる。apply の実行中にほかのセッションがそれを変えていれば、コミットの前に止まる。そのため、その接続のための空いた接続枠が要り、デプロイのスキーマの変更は apply を始める前にコミットしておく（[kortopi apply](apply.ja.md#apply-の実行中にスキーマが変わったとき)）。
- apply は、コミットの前に、その実行の宣言したすべてのテーブルをもう一度比べる。書き込みのあとでデータベースが宣言と違う値や行を持てば、何も変えずに失敗する。宣言した値を書き換えるトリガーは、そうした違いを生む（[kortopi apply](apply.ja.md#コミット前の比較)）。`--allow-delete` がなければ、宣言にない行をモード `sync` のテーブルから書き込みが消したときや、そうした行を足したときにも失敗する。一方が他方の代わりになったときも同じである。宣言した値を書き換えるトリガーを持つテーブルでは、そのテーブルが保存するとおりの値を宣言が持つまで、そうした apply はどれも失敗する。コミットした apply の直後の計画にも、次のものはまだ現れうる。
  - `--allow-delete` がないときに apply が省いた削除。
  - 削除のない apply のあとでは、コミットまで遅らせた制約トリガーが変えたもの。そこでは比較のあとに働く。削除をする apply は、そうしたトリガーを検査の前に動かす。
  - `--schema` を付けたときの、ほかのスキーマの宣言したテーブル。その実行は、自分の書き込みがそれを変えても比べない。
  - apply のスナップショットより後にほかのセッションが書いたもの。apply の実行中でもコミットのあとでも同じである。kortopi のロックが分けるのは2つの apply であり、アプリケーションではない。

  モード `insert` のテーブルのキー以外の値は、apply も計画も比べない。
- 識別列や `serial` の列に明示的な値を書く apply は、コミットの直前に、その列のシーケンスを書いた値の先へ進める。アプリケーションが次にそのどれかを取らないようにするためであり、`Applied:` のあとでそれを伝える（[kortopi apply](apply.ja.md#シーケンス)）。シーケンスの `SELECT` と `UPDATE` があれば、どの進め方もできる。その進め方に要る権限がなければ、apply は行を書いてシーケンスを残し、付与するものを標準エラー出力の注記で伝え、終了コード 0 で終わる。ほかのセッションが 5 秒を超えてシーケンスのロックを持つときも同じである。シーケンスを進める apply は、コミットまで遅らせた制約を、最初に進める直前で確かめる。そのため、失敗する制約は、どのシーケンスも進める前に apply を止める。
- スキーマにない宣言済みのテーブルや列があれば、apply は止まり、何も変えない（[kortopi apply](apply.ja.md#データベースにないテーブルや列)）。apply の前に `--no-pending` を付けた計画を置くと、同じ名前で止まり、それを宣言したファイルを挙げる。ただし、apply にない検査を足すわけではない。

## 変更を取り消す

宣言の変更を取り消すときは、そのコミットを revert し、revert したファイルを apply する。変更がモード `sync` のテーブルに行を足していたなら、`--allow-delete` を付ける。
apply は、宣言した行を前の宣言に戻す。それは、前のデータベースに戻すことではない。

- 変更が更新した値は元に戻る。
- 変更が削除した行は、新しい行として戻る。データベースはその行に、新しく振った ID と、作成した時刻のように宣言が挙げない列の既定値を与え、apply は `on_insert` の値をあらためて与える。外部キーなしで古い ID を持つ行は、何も指さなくなる（[kortopi export](export.ja.md#生成される-id-の代わりの自然キー)）。
- 削除が外部キーを通じて変えたか消したほかのテーブルの行は、削除が残したままになる。`ON DELETE SET NULL` が NULL にした参照がその例である。revert の計画は、それらを示さない。
- 変更がモード `upsert` か `insert` のテーブルに挿入した行は残る。計画は、それを宣言にない保存された行として数える（[kortopi plan](plan.ja.md#宣言にない保存された行)）。

ある試験では、変更が方針 `flexible` の名前を変え、方針 `strict` を削除し、モード `upsert` のテーブルに設備 `spa` を足した。`strict` の削除は、2つの予約の参照を NULL にした。revert の apply は、次のように出力した。

```text
bk.policies (sync, key: code)
  + code=strict  name=Strict
  ~ code=flexible  name: "Flexible (no fee)" -> Flexible
  1 to insert, 1 to update, 0 to delete

bk.amenities: 1 stored row is not declared, which mode upsert does not delete

Plan: 1 to insert, 1 to update, 0 to delete in 2 tables.
Not declared: 1 stored row in 1 table, which mode upsert does not delete.

Applied: 1 inserted, 1 updated, 0 deleted.
```

`strict` は、ID 2 ではなく 3 と、新しい `created_at` で戻った。2つの予約は NULL のままで、`spa` は残った。
kortopi が戻すのは宣言が持つものだけである。

## プルリクエストで

その環境の認証情報を渡すつもりのない人が作った変更なら、そのプルリクエストのチェックから実際の環境に接続させてはならない。フォークからのプルリクエストの作者がその例である。
変更は、宣言も、チェックのスクリプトそのものも書き換えうる。

代わりに、コンテナの PostgreSQL のような、チェック用の使い捨てのデータベースに、プルリクエストのスキーマを適用して宣言を検査する。

```sh
# The schema of the pull request is applied to the scratch database first.
kortopi plan --dir data --no-pending
kortopi apply --dir data --allow-delete
kortopi plan --dir data --exit-code
```

- 1つ目の計画は、宣言が持つものをチェックのログに出す。スキーマは適用済みなので、スキーマの変更を待つものはないはずである。`--no-pending` があれば、綴りを誤った名前のように、スキーマにない宣言済みのテーブルや列は、ここでチェックを失敗させる。そのエラーは、それを宣言したファイルを挙げる（[kortopi plan](plan.ja.md#スキーマを適用済みのとき)）。
- apply は、デプロイと同じように行を書く。計画が検査しないものは、ここで失敗になる。`CHECK` 制約や宣言にない行への外部キーのように制約が拒む値と、トリガーが宣言と違うものにした値や行である。後者は、apply がコミットの前にテーブルをもう一度比べて見つける。
- 最後の計画は 0 で終わらなければならない。それ以外なら、apply がデータベースを宣言どおりにできなかったことを示す。たとえば、削除のない apply では、コミットまで遅らせた制約トリガーがその比較のあとに働き、原因になりうる。宣言したすべてのテーブルを読むように、この計画には `--schema` を付けない。
- 使い捨てのデータベースには残すべきものがないので、ここでの `--allow-delete` には何の害もない。
- チェックは、デプロイのロールで実行する。ロールは使い捨てのデータベースに作り、プルリクエストのスキーマが付与する権限を与える。apply は、デプロイが apply で使うロールで実行する。デプロイがスキーマごとに `--schema` を付けて実行するなら、チェックもそうする。計画は、ずれの検出のロールで実行する。スーパーユーザーや、すべてのテーブルの所有者で実行するチェックは、権限の不足でデプロイが拒む宣言を通してしまう。

  ```text
  kortopi: an apply needs SELECT on table billing.currencies, and the role "deployer" lacks it: grant the role SELECT on the table
  ```

- マージの結果をチェックする。同じキーの行をそれぞれ足す2つのプルリクエストは、どちらもチェックを通る。行がファイルの離れた位置にあれば、Git は衝突なしにそれらをマージする。そのマージの計画は、2つの行が持つキーで止まる（[宣言のファイル](declaration.ja.md#2つの行が持つキー)）。チェックは、プルリクエストとベースをマージした結果で実行し、マージの前にベースが進んだらもう一度実行する。

マージで何が変わるかをレビューする人に見せるための、実際の環境に対する計画は、信頼できる実行に置く。メンテナーが始める実行などである。ロールは、[計画のセッションに要るもの](plan.ja.md#セッションに要るもの)を持ち、`UPDATE` のような宣言したテーブルを変える権限を持たないものにする。

## 定期的なずれの検出

ジョブがデータベースを main ブランチの宣言と比べ、計画をログに出して、3つの結果を終了コードで見分ける。

```sh
status=0
kortopi plan --dir data --exit-code > plan.txt || status=$?
cat plan.txt
case "$status" in
  0) echo "there is nothing to apply" ;;
  2) echo "the database has drifted from the declaration" ;;
  *) echo "the check failed" ;;
esac
if grep -q '^Not declared:' plan.txt; then
  echo "tables of mode upsert or insert hold stored rows that the declaration lacks"
fi
```

- 終了コード 2 になるのは、挿入・更新・削除する行か、スキーマの変更を待つテーブルや列が1つでもあるときである。つまり、計画が空でないときである。
- 計画の実行中に、別のチームが宣言したテーブルを変えるスキーマの変更をコミットすることがある。テーブルを書き換えるか空にする変更、テーブルを置き換える変更、パーティションをアタッチかデタッチする変更である。そのとき計画はずれを報告せず、終了コード 1 で失敗する。計画はそのテーブルをスナップショットのとおりに読めず、書き換えられたテーブルは空に見えてしまうからである。検出が失敗したのであり、次の実行では通る（[kortopi plan](plan.ja.md#実行中のスキーマの変更)）。
- モード `insert` のテーブルはキーだけで比べるので、その行の値が変わっても、ずれにはならない。
- モード `upsert` か `insert` のテーブルが持ち、宣言にない保存された行も、ずれにはならない。そのモードはその行をどれも削除しないので、それは計画の変更ではないからである。計画は、各テーブルの行と、`Not declared:` から始まる行によってそれを数える。ジョブは上のようにその行を探す（[kortopi plan](plan.ja.md#宣言にない保存された行)）。そうした行で検査を失敗させたいときは、テーブルにモード `sync` を与える。その削除する行は終了コード 2 になる。
- ロールには、プライマリで、[計画のセッションに要るもの](plan.ja.md#セッションに要るもの)が要る。
- `|| status=$?` は、`set -e` のシェルが終了コード 2 で止まらないようにする。`grep` が行を見つけないときも、シェルは止まらない。その `grep` は `if` の条件だからである。
- 失敗した計画はエラーを標準エラー出力へ出す。ジョブのログは、そのエラーもそのまま含む。

## レビューしたスクリプトのための SQL としての計画

データベースをレビューしたスクリプトだけで変えるチームは、計画を SQL として受け取り、レビューして、1つのトランザクションで実行する。

```sh
kortopi plan --dir data --format sql > rows.sql
psql --single-transaction -v ON_ERROR_STOP=1 -f rows.sql
```

- スクリプトは、1つのデータベースの、ある時点での差分である。計画が読んだデータベースに対して、計画のすぐあとに実行する（[kortopi plan](plan.ja.md#計画を-sql-として出力する)）。
- 削除はコメントであり、誰かがコメントの印を外したときだけ実行される。
- スクリプトは、明示的な値を書く列のシーケンスで終わる。計画したロールによる apply と同じく、スクリプトが動くときにシーケンスを書いた値の先へ進める文を置く。そのロールが読めないか進められないシーケンスには、その文をコメントにして理由の下に置く。計画したロールでスクリプトを実行すれば、シーケンスで失敗しない（[kortopi plan](plan.ja.md#スクリプトの読み方)）。
- `--exit-code` は、テキストと同じく `--format sql` でも働く。計画が空でなければ終了コードは 2 である。
- スクリプトは1つの文で1つの行を更新する。apply は、テーブルの行を1つの文で更新する。テーブルのすべての行が変わったところで初めて成り立つ変更は、apply では通り、スクリプトでは失敗する。一意キーの値を2つの行で入れ替える変更がその例である（[kortopi plan](plan.ja.md#スクリプトがしないこと)）。
- スクリプトは、apply のようにコミットの前にテーブルをもう一度比べることはしない。そのため、宣言した値をトリガーが書き換えれば、その書いたものがコミットされる。スクリプトのあとの `kortopi plan --exit-code` は、コメントのまま残った削除と、そうした値を示す。宣言にない保存された行も数え直すが、それ自体は終了コードに表れない。

## ジョブとサーバー

kortopi を動かすジョブには、実行ごとのロール（[kortopi plan](plan.ja.md#セッションに要るもの)・[kortopi apply](apply.ja.md#apply-に要るもの)）のほかに、この節の述べるものが要る。

### チェックアウト

データのディレクトリは、コミットしたときのバイトのままチェックアウトする。
`core.autocrlf=true` の Git のように行の終わりを変換すると、改行を持つ値がすべて変わる。そのチェックアウトからの計画はその変更を示し、apply はその変更を書く。
データのディレクトリのファイルは、`.gitattributes` で変換から外す（[宣言のファイル](declaration.ja.md#行の終わりと-git)）。

### メモリ

SQL ファイルを読む実行は SQL のパーサを起動し、パーサはファイルの大きさにかかわらずメモリを要する（[宣言のファイル](declaration.ja.md#文字コードと大きさ)）。
次の表の宣言のそれぞれについて、コミット c58064e の kortopi の arm64 向け Linux バイナリで、PostgreSQL 18.7 に対して計画を立てた。実行したコンテナには行ごとのメモリの上限を与え、それを超えるスワップは与えなかった。

| 宣言 | メモリの上限 | 結果 |
|---|---|---|
| 3行、122 バイトの SQL ファイル1つ | 272 MiB | 強制終了、終了コード 137 |
| 3行、122 バイトの SQL ファイル1つ | 280 MiB | 計画、終了コード 0 |
| 同じ行の CSV ファイル1つ | 16 MiB | 計画、終了コード 0 |
| 200,000 行、25 MB の SQL ファイル1つ | 1.5 GiB | 強制終了、終了コード 137 |
| 200,000 行、25 MB の SQL ファイル1つ | 4 GiB | 計画、終了コード 0、最大 1.8 GiB |

- SQL ファイルを読むジョブには 300 MiB 以上を、大きな SQL ファイルならさらに多くを与える。または、テーブルを CSV ファイルで宣言する。kortopi は CSV ファイルを解析しない。
- 計画と apply は、計画の行をメモリに保つ。そのため、使うメモリは変わる行の数とともに増える。arm64 の macOS 向けバイナリで、PostgreSQL 18.7 に対して、ほかの作業の負荷があるマシンで計測した。CSV ファイルで行を宣言したテーブルで、最大の常駐メモリは次のとおりだった。

  | 実行 | 100,000 行 | 1,000,000 行 |
  |---|---|---|
  | 計画、どの行も変わらない | 14 MiB | 13 MiB |
  | 計画、すべての行が変わる | 78 MiB | 375 MiB |
  | apply、すべての行が変わる | 75 MiB | 455 MiB |

  大きな変更を apply するジョブには、パーサの分とは別に、そのためのメモリを与える。
- メモリのためにシステムが強制終了した実行は、何も出力しない。出力する機会がないからである。シェルは終了コード 137 を報告し、これはシグナル SIGKILL を表す。そう終わったジョブでは、メモリを確かめる。

### 接続

- `PGCONNECT_TIMEOUT` を 10 秒などに設定する。ないときは、何も応答しないホストへの試みがオペレーティングシステムの許すだけ待つ。ある試験では約 150 秒だった（[接続の設定](plan.ja.md#接続の設定)）。
- `PGHOST` にホストの一覧を書くときは、計画と apply に `PGTARGETSESSIONATTRS=read-write` を設定する。どちらもプライマリを要するからである（[接続の設定](plan.ja.md#接続の設定)）。
- 削除をする apply は、削除のあとに2つ目の接続を開く。そのため、`max_connections`、ロールの接続数の上限、コネクションプーラーのプールのそれぞれで、その apply に2つの接続枠を見込む（[kortopi apply](apply.ja.md#apply-に要るもの)）。

### 時間の制限

- `--lock-timeout` は、ほかのセッションが持つロックを実行が待つ時間の上限を、待つたびに与える。別の apply を待つときもそうである。デプロイが待つ実行には、どれにもこれを与える（[ロックを待つとき](plan.ja.md#ロックを待つとき)）。
- セッション・ロール・サーバーの `statement_timeout` は、理由を問わず、長くかかりすぎた文を終わらせる。kortopi にはそのフラグがなく、それが文を終わらせたときはエラーがそう告げる（[ロックを待つとき](plan.ja.md#ロックを待つとき)）。
- `idle_in_transaction_session_timeout` は、トランザクションの中でクライアントを長く待ちすぎたセッションを終わらせる。途中で途切れた実行のセッションがそうなる（[途中で途切れた実行](#途中で途切れた実行)）。

### 途中で途切れた実行

kortopi がエラーや割り込みで自分から止めた実行は、トランザクションをロールバックし、サーバーのセッションを終える（[kortopi apply](apply.ja.md#apply-に割り込む)）。
それ以外の形で止まった実行は、セッションをサーバーに委ねる。SIGKILL で強制終了されたジョブ、止まったマシン、切れたネットワークがそうである。
セッションはサーバーが終わらせるまでトランザクションを保ち、それとともに、2つの apply を分ける kortopi のロックと、実行が読み書きしたテーブルや行のロックを持ち続ける。
2つ目の apply はそのロックを待ち、ロック待ちの上限で止まる。そのエラーは、セッションを見つけて終わらせる方法を告げる（[2つの apply を同時に動かす](apply.ja.md#2つの-apply-を同時に動かす)）。

Linux の PostgreSQL 18.7 に対する試験で、サーバーの設定を既定のままにして、ほかのセッションが持つ行を apply に待たせ、その間にクライアントをいなくした。

- マシンを動かしたまま kortopi を SIGKILL で強制終了したときは、セッションはその行を待ち続け、ほかのセッションがコミットして文が終わったところで終わった。
- クライアントのネットワークを切ったときは、セッションは行が空いたところで文を終え、そのあと `idle in transaction` で kortopi のロックを持ったままクライアントを待った。試験が見ていた1分あまりの間、ずっとそうだった。2つ目の apply はそれを待ち、`--lock-timeout` で止まった。

次のサーバーの設定は、そうしたセッションをより早く終わらせる。試験では、初めの2つを `ALTER ROLE ... IN DATABASE ... SET` で apply のロールに、残りを `ALTER SYSTEM` でサーバーに設定した。

| 設定 | 終わらせるもの | 試験の結果 |
|---|---|---|
| `idle_in_transaction_session_timeout` | トランザクションの中で、設定より長くクライアントを待ったセッション | `5s` は、切れたネットワークの先のセッションを文の 5 秒後に終わらせ、次の apply が動いた。 |
| `client_connection_check_interval` | クライアントが接続を閉じた文。文の実行中に、サーバーはこの間隔でそれを確かめる | `1s` は、強制終了した kortopi の文を、行を待っている間に終わらせた。これだけでは、切れたネットワークに気付かなかった。 |
| `tcp_keepalives_idle`、`tcp_keepalives_interval`、`tcp_keepalives_count` | 確認応答を待つデータがサーバー側にない間に送るプローブに、クライアントが応答しない接続 | `5`・`2`・`3` は、`1s` の `client_connection_check_interval` とともに、切れたネットワークの先の文を、行を待っている間に終わらせた。これらだけでは、切れたネットワークの先で文を終えてクライアントを待つセッションを終わらせなかった。その応答を、クライアントは確認応答しなかったからである。 |
| `tcp_user_timeout` | 送ったデータが、設定のミリ秒より長く確認応答を待つ接続 | `10000` は、そのセッションを文の約 10 秒後に終わらせた。 |

- `idle_in_transaction_session_timeout` は、これらのどの形でクライアントがいなくなっても、文が終わったあとでそのセッションを終わらせる。ただし、この設定には、実行が自分の文と文の間で止まる時間を超える余裕が要る。計測した最も長い停止は、変更のある 100,000 行の計画と apply で 2.3 秒、変更のある 1,000,000 行の計画で 3.1 秒、apply で 5.0 秒だった。計測したマシンには、ほかの作業の負荷があった。最大の実行に余裕を持たせた値を、デプロイのロールに設定する。
- そうしたセッションは、手で終わらせることもできる。`pg_stat_activity` で `application_name` が `kortopi` のセッションを見つけ、`pg_terminate_backend` で終わらせる。`PGAPPNAME` がほかの名前を挙げていれば、その名前で探す。
- 応答しなくなったサーバーには、kortopi 自身が自分のプローブで気付く（[接続の設定](plan.ja.md#接続の設定)）。
