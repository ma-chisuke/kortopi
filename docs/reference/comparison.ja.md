# 値の比べ方

kortopi は、ファイルのテキストをデータベースと比べることはしない。
宣言したテーブルごとに、本物の列と同じ型の列を持つ一時テーブルを作り、宣言したすべての値を PostgreSQL にそこへ読み込ませ、2つのテーブルを SQL で比べる。
このページは、宣言の値と保存されている値をいつ等しいとするか、PostgreSQL がどの設定のもとで値を読むか、計画が何を検査しないかを説明する。

ファイルそのものは[宣言のファイル](declaration.ja.md)に、出力は [kortopi plan](plan.ja.md) にある。

## 2つの値が等しいとき

- 2つの値は、両方が NULL のとき、または、どちらも NULL でなく列の型の等価性が等しいとするときに等しい。
- NULL と値は、常に違う。空文字列は値であり、NULL ではない。
- 等価性は、PostgreSQL が並べ替えと一意インデックスでその型に使うものである。型の既定の B-tree 演算子クラスの等価性を使い、なければ既定のハッシュ演算子クラスの等価性を使う。
- ドメインは、基本の型として比べる。配列は要素ごとに、複合型は列ごとに比べる。
- 拡張の型は、その型自身の規則で比べる。PostgreSQL に付いてくる拡張 `citext` は大文字と小文字を無視し、`hstore` は組の順番を無視する。
- テキストは、列の照合順序のもとで比べる。大文字と小文字を無視する非決定的な照合順序では、`abc` と `ABC` は等しい。
- `json` は自分の等価性を持たないので、`jsonb` として比べる。
- `xml` や `point` のように等価性を持たない型は、テキストをバイト単位で比べる。そうした型を含む配列や複合型も同じである。
- 照合キーの列も同じように比べ、行はキーの型の順に並べる。`integer` のキーなら、`9` は `10` より前に来る。そのため、キーの列の型には等価性と B-tree の順序が要る。`xid` のように、等価性がハッシュの演算子クラスからしか得られない型は、キーの列にできない。

計画は値を、次の節の設定のもとで PostgreSQL がテキストとして出力するとおりに表示する。

## セッションの設定

計画は、トランザクションの中で次の設定を固定する。ロール・データベース・環境が何を設定していても変わらない。
これらの設定は、ファイルの値を PostgreSQL がどう読み、計画がどう表示するかを決める。そのため、1つの宣言がどこでも同じ意味になる。

| 設定 | 値 | ファイルにとっての意味 |
|---|---|---|
| `search_path` | `pg_catalog` | `pg_catalog` の外の型へのキャストには、スキーマを書く。`'ok'::mood` ではなく `'ok'::facility.mood` と書く。 |
| `TimeZone` | `UTC` | オフセットのない `timestamptz` は UTC として読み、どの時点も `+00` 付きで表示する。 |
| `DateStyle` | `ISO, MDY` | `11/19/2026` は11月19日であり、日付は `2026-11-19` と表示する。 |
| `IntervalStyle` | `postgres` | 期間は `1 day 02:00:00` と表示する。 |
| `standard_conforming_strings` | `on` | `'...'` の中のバックスラッシュは、ふつうの文字である。エスケープは `E'...'` に書く。 |
| `client_encoding` | `UTF8` | ファイルは UTF-8 として読む。 |
| `extra_float_digits` | `1` | 浮動小数点数は、読み戻すと同じ値になる最短のテキストで表示する。 |
| `bytea_output` | `hex` | `bytea` は `\x...` と表示する。 |
| `xmloption` | `content` | `xml` の値は、`pg_dump` が書くのと同じく、文書全体ではなく内容として読む。 |
| `lc_monetary` | `C` | `money` の値は、C ロケールの形で読み、表示する。どの環境でも同じである。 |
| `row_security` | `off` | 行単位セキュリティのポリシーが絞り込む問い合わせは、少ない行を返さずに失敗する（[kortopi plan](plan.ja.md#セッションに要るもの)）。 |

## 型ごとの比べ方

例の1列目は、保存されている値と等しくなる値であり、計画には変更が出ない。
2列目は、変更が計画の行でどう表示されるかを `column: stored -> declared` の形で示す。

| 型 | 等しい（変更なし） | 変更の表示 |
|---|---|---|
| `numeric` | `1.0`・`1.00`・`1.000`、`100` と `1e2` | `1.0 -> 1.5` |
| `numeric(10,2)` | `1.5`・`1.500`・`1.504`（型が入力のときに `1.50` へ丸める） | `1.50 -> 2.00` |
| `double precision` | `0.1`・`1e-1`・`0.10`、`NaN` と `NaN` | `0.1 -> 0.2` |
| `text`、`varchar(n)` | 同じ文字の並び | `ab -> "ab "`（末尾の空白も変更になる） |
| `char(n)` | `ab`・`ab`・`ab`（末尾の空白は数えない） | `ab -> abc`（詰め物の空白なしで表示） |
| `timestamptz` | 同じ時点：`2026-11-19 09:00:00+09`・`2026-11-19 00:00:00+00`・`2026-11-19T00:00:00Z`・`2026-11-19 09:00:00 Asia/Tokyo`、UTC として読む `2026-11-19 00:00:00` | `"2026-11-19 00:00:00+00" -> "2026-11-19 01:00:00+00"` |
| `timestamp` | `2026-11-19 09:00` と `2026-11-19T09:00:00`（入力のオフセットは無視する） | `"2026-11-19 09:00:00" -> "2026-11-19 09:00:01"` |
| `date` | `2026-11-19`・`11/19/2026`・`20261119` | `2026-11-19 -> 2026-11-20` |
| `time` | `09:00`・`09:00:00.000`・`9:00 AM` | `09:00:00 -> 09:00:01` |
| `interval` | `1 hour`・`60 minutes`・`PT1H`、`1 day`・`24 hours`・`24:00:00` | `"1 day" -> "2 days"` |
| `boolean` | `true`・`TRUE`・`t`・`yes` | `true -> false` |
| `uuid` | 大文字でも小文字でも、波かっこがあってもなくても同じ値 | 新しい値を小文字で表示 |
| `bytea` | `\x6869` と、バイト列として読んだ `hi` | `\x6869 -> \x6870` |
| `jsonb` | キーの順番と空白だけが違う同じ文書 | `"{\"a\": 1, \"b\": {\"c\": 2}}" -> "{\"a\": 1, \"b\": {\"c\": 3}}"`。配列の順番は意味を持つ：`"[1, 2]" -> "[2, 1]"` |
| `json` | `jsonb` と同じ | 書いたとおりに表示：`"{\"a\": 1}" -> "{\"a\":2}"` |
| 配列 | `{1,2,3}`・`{1, 2, 3}`・`ARRAY[1, 2, 3]` | `{1,2,3} -> {3,2,1}`、`{1,2} -> {1,NULL}`、`{NULL} -> "{\"NULL\"}"` |
| enum | 同じラベル | `ok -> happy` |
| ドメイン | 基本の型と同じ | `abc -> xyz` |
| 複合型 | `(1,x)` と `ROW(1, 'x')` | `(1,x) -> (1,y)` |
| 範囲 | `int4range` の `[1,5)` と `[1,4]` | 新しい範囲を正規の形で表示 |
| `xml` | 同じテキスト | `"<a x=\"1\">t</a>" -> "<a  x=\"1\">t</a>"`（属性の間の空白の違いも変更になる） |
| `point` | PostgreSQL が同じ点として読む `(1,2)` と `( 1 , 2 )` | `(1,2) -> (1,3)` |

SQL ファイルでは、`date '2026-11-19'` や `'hi'::pg_catalog.bytea` のように列の型へキャストした値は、キャストのない値と同じに読む。
最後の列の引用符とエスケープは、計画の表示のものである。値は、空白・`=`・引用符を含むときに二重引用符で囲む（[kortopi plan](plan.ja.md#値と名前)）。

## NULL と空文字列

| | CSV ファイル | SQL ファイル |
|---|---|---|
| NULL | 2つのコンマの間に何もない：`1,,x` | `NULL` |
| 空文字列 | `""` | `''` |
| 文字列の `NULL` | `NULL` | `'NULL'` |

計画は NULL を `NULL` と表示する。空文字列は `""`、文字列の `NULL` は `"NULL"` のように、引用符で囲んで表示する。

## 計画が宣言の行で検査すること

PostgreSQL が行を読み込むとき、どの値も列に合う必要がある。合うかどうかは、型、`varchar(3)` の長さのような型修飾子、ドメインの制約で決まる。
合わない値は、PostgreSQL のエラーとファイルの行を示して計画を止める。

テーブルを読み込んだあと、比べる前に、計画は宣言の行を検査する。

- 2つの行が同じキーを持たないこと。エラーは、繰り返されたキーを10個まで、それぞれの出現回数とともに挙げる。
- キーの列に NULL を持つ行がないこと。
- テーブルが `NOT NULL` とする宣言した列に、NULL を持つ行がないこと。その行を適用すると失敗するからである。エラーは、列ごとに5行までのキーを挙げる。モード `insert` では、挿入する行だけを検査する。適用は、ほかの行を書かないからである。
- 日付や時刻の型の列に、`now`・`today`・`tomorrow`・`yesterday` を持つ行がないこと。大文字と小文字は問わない。対象の型は、その型そのもの・その上のドメイン・その配列・その範囲と複数範囲である。PostgreSQL はこれらの語を読んだ時点として読むので、値が計画ごとにデータベースと違ってしまう。PostgreSQL は語を日付に変えてしまうので、計画はその前に、そうしたテーブルの行をもう一度テキストとして読み込んで調べる。複合型のフィールドの中は見ず、SQL ファイルではキャストを済ませた値を見る（[宣言のファイル](declaration.ja.md#値)）。

すべてのテーブルを比べたあと、計画は、挿入する行が値の要るどの列にも値を得られることを検査する。

- `NOT NULL` で既定値がなく、宣言が挙げない列は、新しい行で値を得られない。そのため、挿入する行を適用すると失敗する。計画は、挿入する行のあるテーブルごとにそうした列を報告し、すべてのテーブルをまとめて報告する。ここでの既定値とは、列かそのドメインの既定値、`serial`、識別列、生成列である。

計画は、宣言した列もテーブルと照らし合わせる。

- ほかの列から値を計算する生成列は、宣言できない。
- `GENERATED ALWAYS` の識別列は、照合キーの一部としてだけ宣言できる。更新ではその値を変えられないからである。

## 計画が検査しないこと

一時テーブルは本物の列の型を持つが、本物のテーブルの制約は何も持たない。
そのため、計画は次のことを検査しない。

- テーブルの `CHECK` 制約
- 外部キー
- 照合キー以外の一意キー
- トリガーと、書き込みの権限
- データベースにまだないテーブルや列の値

これらは、行を適用したときに見つかる。
マージの前にこれらを見つける方法は、ADR-0016 にある。CI で、使い捨ての PostgreSQL に新しいスキーマを適用し、続けて行を適用する。
`kortopi apply` は、まだできていない。

これらの決まりの理由は、[ADR-0009](../adr/ADR-0009-let-postgresql-interpret-declared-values.ja.md) と [ADR-0023](../adr/ADR-0023-compare-values-with-the-equality-of-their-type-in-pinned-settings.ja.md) にある。
