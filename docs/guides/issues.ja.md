# issue を書く

kortopi の issue は、1つの問題を記録する。書いた人以外の誰かがそれを再現し、直し、直ったことをあとで確かめられるようにするためである。
このガイドは、issue を出す人（人かコーディングエージェント）と、issue をトリアージして閉じるメンテナーに向けたものである。
`.github/ISSUE_TEMPLATE/` のフォームが issue の種類ごとに欄を求め、スキル `write-issue` がコーディングエージェントに手順を示す。
理由は ADR-0041 にある。

## 出す前に

- 同じ問題の issue を、開いているものも閉じたものも探す。`gh issue list --repo ma-chisuke/kortopi --state all --search "<words>"` を使う。見つかったら、新しく開かずに、知っていることをその issue に足す。
- 脆弱性は、`SECURITY.md` のとおり非公開で報告する。issue には書かない。
- 不具合は、出す前に、リリースか `main` の特定のコミットで再現する。
- 英語で書く。issue は公開され、対訳を持たない。次に同じ問題に出会う人は英語で検索し、issue を直すプルリクエストとコミットも英語である（ADR-0003）。

## 1つの issue に1つの問題

1つの issue には、1つの問題だけを置く。そうすれば、タイトルでその問題を名指しでき、1つのプルリクエストで閉じられる。

同じ種類の小さな問題がいくつかあるとき（誤った方へ導くメッセージや、1つのページの抜けなど）は、タスクリストにして1つの issue にまとめてもよい。
そのときは、各項目が1つの問題を、そのメッセージや文とともに過不足なく述べ、ほかの項目とは別に直してチェックを付けられるようにする。
議論や独自の設計が要る項目は、別の issue に移し、元の項目からそこへリンクする。

## タイトル

- タイトルには、何をすべきかではなく、何が起きるかを書く。「Fix the count of --max-delete」ではなく、「Only the first level of ON DELETE CASCADE counts against --max-delete」とする。
- 1つの文で書き、最後にピリオドを付けない。その問題に出会った人が検索に使う語、つまりコマンド・フラグ・モード・型・メッセージの語を使う。
- `[Bug]` のような接頭辞は付けない。種類はラベルが示す。
- 提案のタイトルは、いまはできない作業を名指しする。たとえば「Rows that only one environment has cannot be told apart in a table of mode sync」である。文書の変更のタイトルは、ページの誤りや抜けを名指しする。「The reference does not warn that a line-ending conversion of Git changes CSV values」がその例である。

## 本文

各種類のフォームが欄を決め、欄のラベルが issue の見出しになる。
`gh issue create --body` で書く issue も、同じ見出しを同じ順に使う。そうすれば、同じ種類の issue はどれも同じように読める。

### 不具合

- 最初にバージョンを書く。kortopi のバージョンは `kortopi version` の出力のとおりに、PostgreSQL のバージョンは `SELECT version()` の出力のとおりに書く。宣言した値を読んで比べるのは PostgreSQL なので（ADR-0009、ADR-0023）、同じファイルでも、バージョンが違えば別の計画になりうる。バージョンを特定できない不具合は、直ったことを示せない。ソースからビルドしたバイナリは、ビルドに使ったコミットを出力する。
- 再現は、その不具合を示す最小の例にし、issue の中だけで完結させる。テーブルとその行を作る SQL、データのディレクトリの各ファイルとそのパス、`kortopi.toml`、接続の設定を含むコマンドを書く。ほかの人が、同じバージョンの PostgreSQL の空のデータベースに対して、これを実行する。報告者のマシンや非公開のリポジトリにしかないファイルがあると、その人は何も実行できない。
- 例を小さくするには、テーブル・列・行・フラグを1つずつ取り除き、それでも不具合が出るなら取り除いたままにする。行が多いときは、行を生成する SQL を書く。たとえば `generate_series` を使うクエリである。
- 2つ目のセッションが要る不具合（計画の実行中に別の文を実行する場合など）は、両方のセッションの文と、その手順の順序を書く。
- 再現は、修正を固定するテストになる。そのため、issue には、そのテストに要るものをすべて書く。

このリポジトリのチェックや道具の不具合（`make` のターゲットや CI のジョブなど）にも、不具合のフォームを使う。
kortopi のバージョンにはチェックアウトのコミット（`git rev-parse --short HEAD`）を書き、PostgreSQL のバージョンには、サーバーが関わらなかったなら「none」と書く。コマンドには `make` のコマンドを書く。

### 出力

- 出力は、テキストとしてコードブロックに引用する。スクリーンショットにはしない。テキストなら、検索でき、テストにコピーでき、直したバージョンの出力と比べられる。
- kortopi のメッセージは、出力されたとおりに接頭辞 `kortopi:` ごと引用し、終了コードも書く。
- 出力は大事な行だけに切り詰める。切った箇所ごとに `[40 lines cut]` のような印を付け、切ったことを書く。

### issue に決して書かないもの

issue は作った時点で公開され、GitHub はその本文を、リポジトリをウォッチしている人への通知に載せて送る。そのため、あとで編集しても、何も取り消せない。

- パスワード、トークン、パスワードを含む接続文字列。issue に載った秘密情報は、もう秘密ではない。秘密情報を変えてから、issue から消す。
- 実際のデータ。実際の環境の行と、そのホスト・データベース・ロールの名前である。同じことを示す行を作り、ホストには `db.example.test` のような仮の名前を書く。
- kortopi と比べるための、ほかの製品の名前。kortopi に何を期待したか、それはなぜかを書く。
- 顧客の名前と、非公開のリポジトリの名前。

## ラベル

各フォームはその種類のラベルを付けるので、どの issue にも、その3つのどれかが付く。
ほかのラベルは、当てはまるときにメンテナーが付ける。

| ラベル | ここでの意味 | 付けるもの |
|---|---|---|
| `bug` | kortopi またはこのリポジトリのチェックが、文書や記録が否定することをする。または、どの利用者も望まないことをする。誤った計画、残るはずの行の変更、失敗した実行、誤った方へ導くメッセージなどである。 | 不具合のフォーム |
| `documentation` | kortopi は設計どおりに動くが、ページが誤っているか、わかりにくいか、読者に必要なことを欠いている。 | 文書のフォーム |
| `enhancement` | 設計のままの kortopi が扱えない作業、またはうまく扱えない作業である。 | 提案のフォーム |
| `duplicate` | 同じ問題を、別の issue が扱っている。その issue へのリンクを付けて閉じる。 | メンテナー |
| `wontfix` | メンテナーが、kortopi を変えないと決めた。理由（多くは記録）を付けて閉じる。 | メンテナー |
| `invalid` | kortopi の問題ではない。たとえば、サーバーやその構成の問題である。理由を付けて閉じる。 | メンテナー |
| `question` | issue が、作成者の答えを待っている。 | メンテナー |
| `good first issue` | 小さく、直し方がわかっていて、コードに初めて触れる人に向く。 | メンテナー |
| `help wanted` | メンテナーが、プルリクエストを歓迎する。 | メンテナー |
| `accessibility` | 障害のある人にとっての障壁である。たとえば、スクリーンリーダーでは追えない出力である。 | メンテナー |

ラベル `dependencies` と `security` は、依存を更新するボットのプルリクエストのものであり、issue には付けない。

## issue をトリアージする

issue が届いたら、メンテナーは次のことをする。

1. issue に決して書かないものを消し、載った秘密情報を変えるよう作成者に頼む。脆弱性を明かしている issue は、非公開のセキュリティアドバイザリに写してから削除する。
2. issue が挙げるバージョンで再現を動かし、次に `main` で動かす。不具合が出ないときは、足りないものを尋ね、`question` を付ける。
3. タイトルは何が起きるかを書いたものへ、ラベルは種類に合うものへ直す。
4. いくつもの問題を含む issue を分ける。大きくなったタスクリストの項目は、別の issue に移す。

## issue を閉じる

- issue は、それを直すプルリクエストが閉じる。そのプルリクエストは、修正を固定するテストを含む。変更がなければ失敗し、変更があれば通るテストで、再現から作る。文書の変更にはテストは要らず、変えたページが修正である。
- プルリクエストの説明には、閉じる issue を1行に1つずつ `Closes #52` と書く。GitHub はプルリクエストと issue をリンクし、プルリクエストが `main` へマージされたときに issue を閉じる。
- コミットメッセージとプルリクエストのタイトルには、`#52` も閉じるキーワードも書かない。スカッシュマージは、タイトルと各コミットのメッセージを `main` 上のコミットに書き、説明は書かない。そのため、説明の行は、プルリクエストから一度だけ issue を閉じる。コミットメッセージに `#52` があると、リベースのあとなど、コミットが新しいハッシュでプッシュされるたびに、issue のイベントが増える。そこにキーワードがあると、issue はプルリクエストからではなく、コミットそのものから閉じられる。変更の理由を述べるのにコミットメッセージが issue を挙げる必要があるときは、`(issue 52)` のように言葉で書く。
- タスクリストの1項目を直すプルリクエストは、`Part of #52` と書いて項目を挙げる。最後の項目のプルリクエストは `Closes #52` と書く。メンテナーは、各項目のプルリクエストがマージされるたびに、その項目にチェックを付ける。
- 直さない issue は、理由を述べるコメントを付けて「not planned」として閉じる。理由は、重複する issue、別の判断をした記録、または再現が不具合を示さなかったことである。

## 修正を含むバージョンを示す

プルリクエストがマージされたら、メンテナーは issue のマイルストーンを、修正を含むことになるバージョン（`v0.3.0` など）にする。
すると、`gh issue list --repo ma-chisuke/kortopi --milestone v0.3.0 --state closed` が、そのリリースで直るものを一覧にする。
リリースが別の番号になるときは、メンテナーはリリースの前にマイルストーンの名前を変える。そうすれば、そこに含まれるすべての issue が一度に正しくなる。
メンテナーは、リリースを公開したときにマイルストーンを閉じる。
