# GitHub のリポジトリを設定する

このリポジトリの決まりには、ファイルではなく GitHub 上のリポジトリの設定にあるものがある。
CI が `main` を守れるのはルールセットが CI のチェックを必須にしている場合だけであり、Renovate が更新をマージできるのはリポジトリが自動マージを許している場合だけである。
スクリプト `tools/github/apply-settings.sh` がこれらの設定を書き込む。設定をスクリプトに置くことで、プルリクエストでレビューでき、いつでも適用し直せる。
このガイドは、スクリプトを実行するメンテナーと、リポジトリがなぜこう設定されているのかを知りたい人に向けたものである。
スクリプトの実行方法、各設定の意味、スクリプトにはできない1つの作業（Renovate のインストール）を説明する。

## 設定を適用する

リポジトリの管理者としてログインした `gh` が必要である。
スクリプトは `make` から実行する。`make` が、固定したバージョンの `gh` と `jq` を `PATH` に入れる（ADR-0004）。

```sh
make github-settings                        # ドライラン：違いを表示するだけで、何も変えない
make github-settings APPLY=1                # 違う設定を変える
make github-settings REPO=<owner>/<name>    # 今いるリポジトリ以外を対象にする
```

出力の各行は1つの設定を表す。

- `ok` は、その設定がすでに望む値であることを表す。
- `change` は、今の値と望む値を表示する。`APPLY=1` を付けると、望む値を書き込む。
- `note` は、スクリプトでは変えられないことを伝える。

スクリプトは書き込む前にすべての設定を比べる。そのため、`APPLY=1` で2回目を実行すると、変える設定は見つからない。
メンテナーは、GitHub にリポジトリができた時点でスクリプトを実行し、スクリプトを変えるたびにもう一度実行する。

## スクリプトが変える設定

### リポジトリ

| 設定 | 値 | 理由 |
|---|---|---|
| テンプレートリポジトリ | オフ | kortopi は利用者がインストールして使うプログラムであり、新しいリポジトリを作るときの出発点ではない。 |
| トピック | `postgresql`、`master-data`、`cli` など | 利用者はトピックから kortopi を見つける。 |
| マージの方法 | スカッシュだけ | どのプルリクエストも `main` では1つのコミットになり、履歴は一直線のまま保たれる。 |
| スカッシュのコミットメッセージ | プルリクエストのタイトルと、そのコミットのメッセージ | タイトルは `main` 上のコミットの件名になる。そのため CI は、タイトルが Conventional Commit の形かどうかを確かめる（`make lint-pr-title`）。手元の各コミットについては `commit-msg` フックが同じことを確かめる。 |
| マージ後のブランチ削除 | オン | マージしたブランチはもう使わない。 |
| 自動マージ | 許可 | Renovate は、パッチ、ダイジェスト、固定の更新を、必須チェックが通った時点でマージする。 |

### デフォルトブランチのルールセット

ルールセット `main` はデフォルトブランチに適用され、管理者を含めて誰も迂回できない。

- 変更はすべてプルリクエストを通る。承認のレビューは求めない。kortopi のメンテナーは1人であり、自分のプルリクエストを自分で承認できないからである。
- チェック `check` が成功しなければならず、その結果は GitHub Actions から届いたものでなければならない。`check` は `.github/workflows/ci.yml` の最後のジョブである。CI のほかのジョブをすべて待ち、そのどれかが失敗するか取り消されると失敗する。CI に新しいジョブを足すときは `check` の `needs` に加えるので、ルールセットは変わらない。
- 履歴は一直線で、プルリクエストはスカッシュでだけマージできる。
- 誰もこのブランチに強制プッシュできず、削除もできない。

ルールセットは、マージの前にブランチが `main` に追いついていることを求めない。求めると、何かがマージされるたびに、Renovate のものを含む開いているプルリクエストがすべてリベースを待つことになる。

### リリース

タグ `v*` がリリースを始める。タグが指すコミットを、`.github/workflows/release.yml` がビルドし、構成証明を作り、公開する（[リリースのガイド](release.ja.md)、ADR-0030）。

| 設定 | 値 | 理由 |
|---|---|---|
| ルールセット `release-tags` | タグ `v*` を作成・移動・削除できるのは管理者だけ | そうしたタグをプッシュするとリリースが始まるので、リリースを始められるのをメンテナーだけにする。リリースのワークフローも、タグが `main` 上にあり、そのコミットで CI が成功したことを確かめる。 |
| 変更不可リリース | オン | 公開したリリースのアセットは誰も変えられず、リリースがあるあいだはそのタグも誰も移動・削除できない。GitHub はリリースの構成証明に署名し、`gh release verify` がそれを確かめる。タイトルとノートは編集できる。 |

最初のリリースの前に両方を適用する。変更不可リリースが無効なあいだに公開したリリースは、変更できるままになる。

### セキュリティ

| 設定 | 値 | 理由 |
|---|---|---|
| シークレットスキャンとプッシュ保護 | オン | 既知の種類の秘密情報を含むプッシュを GitHub が拒む。`make check` もコミットの前に gitleaks で秘密情報を探す。 |
| 脆弱性の非公開報告 | オン | `SECURITY.md` は、これを通じて報告するよう求めている。GitHub はこの機能を公開リポジトリにだけ提供する。 |
| Dependabot アラート | オン | GitHub の依存関係グラフが把握する依存パッケージについて、既知の脆弱性を GitHub が知らせる。 |
| Dependabot セキュリティアップデート | オフ | 修正は Renovate が提案する。ほかの更新と同じコミットメッセージで、同じチェックを通る。 |
| コードスキャンの既定の設定 | オフ | 代わりに `.github/workflows/codeql.yml` が CodeQL を実行する。この2つは同時には動かない。 |

### GitHub Actions

| 設定 | 値 | 理由 |
|---|---|---|
| アクションをコミットの完全な SHA で固定する | 必須 | タグやブランチは後から別のコードを指すことがあるが、コミットの SHA はそうならない（ADR-0005）。タグやブランチでアクションを参照するワークフローを GitHub が拒む。`make check` も同じことを確かめる（pinact、ghalint）。 |
| `GITHUB_TOKEN` の既定の権限 | 読み取り | 各ジョブが必要な権限を自分で求める。 |
| GitHub Actions によるプルリクエストの作成と承認 | 不可 | プルリクエストを開くワークフローも、承認するワークフローもない。プルリクエストに書き込める権限を持つジョブでも、プルリクエストを開くことも承認することもできない。`coverage` はコメントのためにこの権限を持つジョブである。 |

## Renovate を入れる

リポジトリに [Renovate の GitHub App](https://github.com/apps/renovate) をインストールする。
Renovate は `renovate.json` を読み、毎週月曜日に、更新ごと、または更新のグループごとに1つのプルリクエストを開く（ADR-0005）。

- リリースから3日待つ。pnpm と uv も同じだけ待つ。
- パッチ、ダイジェスト、固定の更新は、`check` が通ればそのままマージされる。マイナーとメジャーの更新は人がレビューする。
- セキュリティの修正は、予定を待たずにすぐ届く。
- ロックファイルは毎月1日に更新する。
- Dependency Dashboard の issue に、保留中の更新がすべて並ぶ。

Renovate は `mise.toml` と一緒に `mise.lock` も更新する。
Renovate のプルリクエストが `mise.toml` を変えて `mise.lock` を変えていないと、CI は `mise.lock` にある道具をインストールするステップで失敗する。
その場合は、そのプルリクエストのブランチをチェックアウトし、`make tools-lock` を実行して、結果をプッシュする。

pnpm と uv は、リリースから3日たっていないバージョンを拒む。今日リリースされたセキュリティの修正も例外ではない。
そうした修正をすぐ取り込むには、そのパッケージを `pnpm-workspace.yaml`（`minimumReleaseAgeExclude`）か `pyproject.toml`（`exclude-newer-package`）で決まりから外す。
リリースから3日たったら、その例外を消す。
