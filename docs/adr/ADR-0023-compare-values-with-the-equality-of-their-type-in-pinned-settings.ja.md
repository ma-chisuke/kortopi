# ADR-0023: 値は列の型の等価性で比べ、セッションの設定は固定する

## 背景と課題

ADR-0009 は、宣言したすべての値を PostgreSQL が列の型で一時テーブルに読み込み、差分を SQL で求めることを決めた。
細部は plan の実装に任せていた。小数点以下の桁数の違う numeric、`timestamptz`、`jsonb` のキーの順番、配列、enum、NULL と空文字列をどう比べるかである。

2つの値の型がそろっても、SQL には「等しいか」への答えがいくつもあり、その答えは食い違う。
演算子 `=` は、セッションが検索パスを通して探す。`json`・`xml`・`point` のように、等価性をまったく持たない型もある。
PostgreSQL が値を出力したテキストは、型が無視する違いを残す。たとえば numeric の桁数（`1.0` と `1.00`）や、拡張が持つ大文字と小文字を区別しないテキスト型の大文字と小文字である。
拡張の型は、その演算子を拡張のスキーマに置く。

値の読まれ方も、セッションの設定に左右される。
オフセットなしで書いた `timestamptz` がどの時点になるかは `TimeZone` が決め、`01/02/2026` が1月か2月かは `DateStyle` が決める。
文字列の中のバックスラッシュの意味は `standard_conforming_strings` が決め、キャストがどの型を指すかは `search_path` が決める。
`xml` や `money` の値の読み方を変える設定もある。`row_security` は、ポリシーが絞り込む問い合わせを失敗させるか、少ない行を返させるかを決める。
ロールやデータベースは、`ALTER ROLE ... SET` や `ALTER DATABASE ... SET` でどれも設定できる。そのため、同じファイルが CI と本番で違う値を意味しうる。
読む時点に左右される値もある。PostgreSQL は、日付や時刻の列の `now`・`today`・`tomorrow`・`yesterday` を、読んだ時点として読む。

ADR-0012 は、選んだ照合キーが「UNIQUE 制約の対象となる」ことを求めるが、何がそれにあたるかは決めていない。
一意インデックスは、比べ方と食い違うことがある。インデックスは、列とは違う照合順序や、型の既定とは違う演算子クラスを使える。そのとき、どの2つの値を同じとみなすかについて、インデックスと計画の考えが食い違う。

比べようのない宣言の行や、適用で拒まれる行もある。同じキーを持つ2つの行、キーの列の NULL、テーブルが NOT NULL とする列の NULL である。
一時テーブルは本物の列の型を持つが、制約はまったく持たない（ADR-0009）。そのため、こうした行もエラーなしに読み込める。

宣言の値と保存されている値は、いつ等しいとするか。値は、どの設定のもとで読むか。

## 判断の基準

- 列の型が等しいとみなす2つの値を、違うと報告しない（ADR-0009）。
- 照合キーは、テーブルの中でキーを一意に保つのと同じ等価性で行を組にする（ADR-0012）。
- `=` を持たない型や、自分のスキーマにある拡張の型を含め、どの型でも比べられる。
- 1つの宣言は、どの環境でも、どのロールでも同じ値を意味する。
- 照合できない宣言の行・ほかの宣言の行と照合先が重なる宣言の行・適用で拒まれる宣言の行は、計画が報告する。

## 検討した選択肢

- カタログから得た各列の型の等価性で比べ、セッションの設定を固定する
- 各値のテキストで比べ、セッションの設定を固定する
- セッションが解決した演算子 `=` で比べ、セッションの設定を固定する
- 各列の型の等価性で比べ、セッションの設定は環境に任せる

## 決定

採用：「カタログから得た各列の型の等価性で比べ、セッションの設定を固定する」。型自身と同じように、その型の一意インデックスが使う演算子で2つの値を比べられるからである。また、設定を固定すれば、1つのファイルがどこでも同じ値の集まりを意味する。

決まりは次のとおりである。

2つの値の比べ方について。

- 列の2つの値は、両方が NULL のとき、または、どちらも NULL でなく列の型の等価演算子が等しいとするときに等しい。NULL と値は違う。空文字列は、NULL と違う値である。
- 演算子は、PostgreSQL 自身がその型について見つけるものである。既定の B-tree 演算子クラスの等価性を使い、なければ既定のハッシュ演算子クラスの等価性を使う。探す対象は、型そのもの、その型からバイナリ変換できる型、配列・enum・範囲・複数範囲・複合型を受け持つ多相の演算子クラスである。kortopi は、型の名前の一覧ではなくカタログからこれを読む。
- ドメインは、基本の型の等価性で比べる。配列は要素が等価性を持つとき、複合型はすべての列が等価性を持つときに、等価性を持つ。
- セッションの検索パスは `pg_catalog` だけなので、kortopi は演算子をスキーマ付きで `OPERATOR(<schema>.<op>)` と書く。そのため、拡張の型はその型自身の規則で比べる。大文字と小文字を区別しないテキスト型なら、大文字と小文字を無視する。
- 比べるときは、列の照合順序を使う。一時テーブルの列は、その照合順序を写し取る。大文字と小文字を無視する非決定的な照合順序では、`abc` と `ABC` は等しい。
- `json` は等価性を持たないので、`jsonb` として比べる。
- ほかの等価性を持たない型は、テキストをバイト単位で比べる。`xml`、`point`、`json` の配列、`point` の列を持つ複合型などがこれにあたる。
- 照合キーも同じ演算子で比べ、計画の行は照合キーで並べる。等価性を持たない型のキーの列はエラーである。そのキーでは行を照合できないからである。`xid` のように B-tree の順序を持たない型のキーの列もエラーである。そのキーでは行を並べられないからである。
- 値は、固定した設定のもとで PostgreSQL がテキストとして出力するとおりに表示する。

何をキーとみなすかは、次のとおりである。これで、ADR-0012 の「UNIQUE 制約の対象となる」が正確になる。

- 選んだキーは、主キーの列か、1つの一意キーの列そのものである。順番は問わない。一意キーの列とほかの列を合わせたものや、一意キーの列の一部は、キーではない。
- 一意キーとは、`UNIQUE` 制約か、次の条件を満たす一意インデックスである。有効であること・部分インデックスでないこと・遅らせられないこと・キーの列に式を含まないことである。
- インデックスは、主キーのものも含め、キーのどの列についても列の照合順序と既定の演算子クラスを使うときだけ、キーとみなす。そうでなければ、計画が1つとみなす2つの行をインデックスが持てたり、計画が組にする2つの行をインデックスが区別したりする。そのため、照合があいまいになりうる。
- ADR-0012 のとおり、キーのどの列も NOT NULL である。

どの計画もトランザクションの中で次の設定を固定する。ロール・データベース・環境が何を設定していても変わらない。

| 設定 | 値 | 固定されること |
|---|---|---|
| `search_path` | `pg_catalog` | キャストは、ファイルに書いた型を指す。`pg_catalog` の外の型は、`pg_dump` と同じようにスキーマ付きで書く。 |
| `TimeZone` | `UTC` | オフセットのない `timestamptz` は UTC として読み、どの時点も `+00` 付きで表示する。 |
| `DateStyle` | `ISO, MDY` | `11/19/2026` はどこでも同じ日になり、日付は `2026-11-19` と表示する。 |
| `IntervalStyle` | `postgres` | 期間は `1 day 02:00:00` と表示する。 |
| `standard_conforming_strings` | `on` | `'...'` の中のバックスラッシュは、ふつうの文字である（ADR-0022）。 |
| `client_encoding` | `UTF8` | ファイルは UTF-8 として読む。 |
| `extra_float_digits` | `1` | 浮動小数点数は、読み戻すと同じ値になる最短のテキストで表示する。 |
| `bytea_output` | `hex` | `bytea` は `\x...` と表示する。 |
| `xmloption` | `content` | `xml` の値は、`pg_dump` が書くのと同じく、文書全体ではなく内容として読む。 |
| `lc_monetary` | `C` | `money` の値は、C ロケールの形で読み、表示する。どの環境でも同じである。 |
| `row_security` | `off` | 行単位セキュリティのポリシーが絞り込む問い合わせは、少ない行を返さずに失敗する（ADR-0024）。 |

よく使う型については、テストで固めたとおり、次のようになる。

- `numeric`：`1.0` と `1.00` は等しい。`numeric(10,2)` は入力のときに丸めるので、宣言の `1.504` は保存されている `1.50` と等しい。
- `timestamptz` は時点を比べ、宣言が書いたオフセットには左右されない。`timestamp` の列は、入力のオフセットを無視する。
- `interval`：`1 day` と `24 hours` は等しい。
- `jsonb` は、キーの順番と空白を無視する。`json` も同じように比べるが、書かれたとおりに表示する。
- 配列は要素ごとに比べ、順番は意味を持つ。
- enum はラベルで、ドメインは基本の型で比べる。
- `char(n)` は末尾の空白を無視し、詰め物の空白なしで表示する。`varchar` は末尾の空白を残す。
- `uuid` は大文字と小文字を無視する。`boolean` は `t`・`true`・`yes` など、PostgreSQL の受け付ける書き方を受け付ける。
- `xml` はテキストで比べる。そのため、属性の間の空白が違えば差分になる。
- CSV では、引用符のない空の欄は NULL であり、`""` は空文字列である。引用符のない `NULL` や `\N` は、その文字列である。

テーブルを読み込んだあと、比べる前に、計画は宣言の行の次の誤りを報告する。

- 同じキーを持つ2つの宣言の行。エラーは、そうしたキーを10個まで、それぞれの出現回数とともに挙げる。
- 照合キーの列の NULL。エラーは行の数を示す。
- テーブルが NOT NULL とする比べる列の NULL。その行を適用すると失敗するからである。エラーは、列ごとに5行までのキーを挙げる。CSV ファイルなら、引用符のない空の欄が NULL になることも伝える。モード `insert` では、挿入する行だけを検査する。適用は、ほかの行を書かないからである。
- 型が日付や時刻の型である列の `now`・`today`・`tomorrow`・`yesterday`。大文字と小文字は問わない。対象の型は、その型そのもの・その上のドメイン・その配列・その範囲と複数範囲である。こうした値は、計画のたびにデータベースと違ってしまう。型付きの読み込みは語を日付に変えてしまう。そこで kortopi は、その前に、そうしたテーブルの行をもう一度テキストとして読み込む。そして、列ごとに5つまでのキーを値とともに挙げる。`text` などのほかの型の列は、これらの語を持ってよい。

識別列と生成列について。

- ほかの列から値を計算する生成列は、宣言できない。
- `GENERATED ALWAYS` の識別列は、照合キーの一部としてだけ宣言できる。新しい行はその値を持てるが、更新ではその値を変えられないからである。

これらの語の検査には限りがある。複合型のフィールドの中は見ない。SQL ファイルでは、キャストを済ませた値を見る。そのため、SQL を読む処理が日付の型と知らない `date` の上のドメインへのキャスト（ADR-0022）は、検査が見る前に `'today'` を日付に変えてしまう。

計画は、テーブルのほかの制約を検査しない。CHECK 制約、外部キー、照合キー以外の一意キー、宣言が挙げない列の NOT NULL である。
これらは適用で見つかる。たとえば、CI で使い捨ての PostgreSQL に適用すればよい（ADR-0016）。
一時テーブルの各列の型は、型修飾子とドメインも含む。そのため、`varchar(n)` の長さ、`numeric(p,s)` の桁数、ドメインの制約は、行を読み込むときに効く。

### 結果

- 良い点：型が等しいとみなす値は、決して変更として現れない。numeric の桁数、時点のオフセット、`jsonb` のキーの順番、`uuid` の大文字と小文字は、差分にならない。
- 良い点：照合キーは、型の一意インデックスと同じように行を組にする。拡張の型でも同じである。
- 良い点：等価性を持たない型も含め、どの型でも比べられる。
- 良い点：`ALTER ROLE` や `ALTER DATABASE` が何を設定していても、1つのファイルは CI でも本番でも同じ値を意味する。
- 良い点：NOT NULL で適用が失敗する宣言や、照合があいまいになる宣言では、計画が行のキーを示して失敗する。
- 良い点：宣言は、計画を立てる日によって変わる値を持たない。
- 悪い点：何が等しいかは型が決めるので、意外な結果にもなる。`numeric(10,2)` の列に宣言した `1.504` は `1.50` と比べて変更にならず、大文字と小文字を区別しないテキスト型では大文字と小文字の変更が現れない。
- 悪い点：等価性を持たない型はテキストで比べる。そのため、属性の間の空白だけが違う2つの `xml` の値も変更として現れる。
- 悪い点：SQL ファイルのキャストでは、`pg_catalog` の外の型をスキーマ付きで書く。`'ok'::facility.mood` は通るが、`'ok'::mood` は通らない。
- 悪い点：チームのデータベースが別のタイムゾーンで動いていても、オフセットなしで書いた `timestamptz` は UTC になる。
- 悪い点：列とは違う照合順序を使う一意インデックスや、`text_pattern_ops` のような演算子クラスを使う一意インデックスは、キーとみなさない。そうして作った主キーも同じである。そうしたテーブルには別のキーが要り、なければ計画はキーがないと報告する。
- 悪い点：日付や時刻の型の列を持つテーブルは、語の検査のためにテキストとしてもう一度読み込む。そのぶん、対象のデータベースの仕事が増える。

### 確認の方法

- `internal/postgres` の結合テストで、この決定を確かめる。結合テストは、`make check-all` で PostgreSQL 15〜18 に対して実行する。`TestCompareTypes` は、この記録が挙げた型ごとに CSV と SQL から値を読み込む。そして、保存されている値と違う書き方の値で変更が出ないことと、値を変えれば記録のとおりに表示される更新が出ることを確かめる。
- `TestEqualityOfExtensionTypes` で、拡張の型の演算子を使うことを確かめる。`TestSessionSettings` で、データベースが別の値を設定しても設定が固定されることを確かめる。`TestCSVDetails` で、CSV の規則を確かめる。
- 宣言の行の誤りは、`TestDiffDuplicateKeys`・`TestDiffNullKey`・`TestDiffNotNull`・`TestDiffNotNullAccepts` で確かめる。`TestNotNullOnlyForRowsToInsert` と `TestRelativeTimes` でも確かめる。`internal/plan` の単体テストで、識別列と生成列の決まりを確かめる。
- ADR-0012 が挙げる選んだキーのエラーは、ADR-0012 が言う結合テストではなく、`internal/plan` の単体テスト（`TestBuildErrors`）で確かめる。主キーでも一意キーでもないキー、NULL になりうるキーの列、どちらのキーもないテーブルのエラーである。このテストは、テーブルを偽のデータベースから計画に渡す。カタログが何を報告するかは、結合テストで確かめる。`TestDescribe` は主キーと一意キーを、`TestDescribeKeysThatMatchAsAPlanDoes` は照合順序と演算子クラスの決まりを確かめる。`TestDiffChosenUniqueKey` は選んだキーでの照合を、`TestDiffKeyWithoutOrdering` は B-tree の順序のないキーの列を確かめる。

## 選択肢の長所と短所

### カタログから得た各列の型の等価性で比べ、セッションの設定を固定する

- 良い点：型が並べ替えと一意インデックスのために定める等価性そのものである。
- 良い点：`jsonb` とテキストを代わりに使うので、どの型でも比べられる。
- 悪い点：kortopi は、PostgreSQL と同じようにカタログから演算子を探す必要があり、そのための問い合わせが1つ増える。

### 各値のテキストで比べ、セッションの設定を固定する

- 良い点：単純で、どの型にも使える。
- 悪い点：テキストは、型が無視する違いを残す。`numeric` の `1.0` と `1.00`、`interval` の `1 day` と `24:00:00`、大文字と小文字を区別しないテキスト型の大文字と小文字は、表示が違う。そのため、こうした値では計画が空にならない。
- 悪い点：照合キーが、テーブルの一意インデックスとは違うやり方で行を組にしてしまう。

### セッションが解決した演算子 `=` で比べ、セッションの設定を固定する

- 良い点：人が SQL で書くとおりの比べ方である。
- 悪い点：`json`・`xml`・`point` には `=` がないので、そうした列の計画は失敗する。
- 悪い点：検索パスを `pg_catalog` に固定すると、`=` は拡張の型の演算子を見つけられない。暗黙のキャストを通して別の型の演算子を使うこともありうる。大文字と小文字を区別しないテキスト型なら、`text` として大文字と小文字を区別して比べてしまう。

### 各列の型の等価性で比べ、セッションの設定は環境に任せる

- 良い点：データベースを1つのタイムゾーンで動かすチームは、オフセットなしの `timestamptz` をそのタイムゾーンで書ける。
- 悪い点：同じファイルが、CI と本番で違う時点・日付・文字列を意味しうる。すると、プルリクエストの計画とデプロイで適用されるものが食い違う。
- 悪い点：キャストの型を、ロールによって違う検索パスで探すことになる。
