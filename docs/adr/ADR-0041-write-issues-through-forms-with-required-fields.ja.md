# ADR-0041: issue は、必須の欄を持つフォームで書く

## 背景と課題

kortopi は公開されており、利用者は issue で、うまくいかなかったことやできないことを報告する。
kortopi の不具合は、本番のデータベースの行を変えうる。そのため報告は、書いた人以外の誰かが不具合を再現し、修正を固定するテストを書き、あとで修正が保たれていることを確かめられるものでなければならない。

それには、説明だけでは足りない。
宣言した値を読んで比べるのは PostgreSQL である（ADR-0009、ADR-0023）。そのため、同じファイルでも、サーバーのバージョンが違えば別の計画になりうる。また、実行の結果はフラグと接続の設定にも左右される。
したがって、不具合の報告には、kortopi のバージョン、PostgreSQL のバージョン、接続を含むコマンド、不具合を示すテーブル・行・ファイルが要る。

issue #19 から #49 は、フォームなしで書かれた。その多くは、v0.2.0 を一通り使ったときに見つかったものである。
これらは、kortopi のリリースと PostgreSQL のメジャーバージョンを最後の行に書いているが、サーバーのマイナーバージョンは書いていない。
テーブルの SQL やデータのディレクトリのファイルを載せたものは少ない。そのため再現は、説明をもとにそれらを組み立てる作業で始まる。
コーディングエージェントも、利用を模擬した試行やレビューから issue を書く。エージェントが `gh` で書く issue は、ブラウザのどのページも通らない。

人がブラウザで書いても、エージェントが `gh` で書いても、どの報告も再現して閉じるのに要るものを含むようにするには、kortopi の issue をどう書けばよいか。

## 判断の基準

- ほかの人が、作成者へ尋ねることなく、不具合の報告だけを頼りに空のデータベースで不具合を再現できる。
- 再現に要る欄を、うっかり抜かせない。
- コーディングエージェントが `gh` で書く issue が、人がブラウザで書く issue と同じように読める。
- リポジトリのほかの部分と同じく、できるところはプログラムが形を検査する（ADR-0002、ADR-0004）。
- 新しくインストールするもの、固定するもの、支払うものがない。

## 検討した選択肢

- 自由記述とガイド
- issue の種類ごとの Markdown のテンプレート
- 必須の欄を持つ issue のフォーム、ガイド、スキル

## 決定

採用：「必須の欄を持つ issue のフォーム、ガイド、スキル」。GitHub は必須の欄が空のフォームを送信させず、同じ種類の報告をどれも同じ見出しのもとに表示する。エージェントも `gh` で同じ見出しを書ける。しかも、リポジトリがすでに固定しているスキーマのチェックで、フォームを検証できるからである。

決まりは次のとおりである。

- `.github/ISSUE_TEMPLATE/` に3つのフォームを置き、それぞれにその種類のラベルを付ける。不具合（`bug`）、文書の変更（`documentation`）、提案（`enhancement`）である。
- 不具合のフォームは、kortopi のバージョン、PostgreSQL のバージョン、kortopi の実行のしかた、issue の中で完結する再現、起きたこと、期待したことを必須にする。kortopi とサーバーのあいだにあるもの、OS とアーキテクチャ、影響、回避策は、任意の欄で尋ねる。報告者は、報告にパスワードも、パスワードを含む接続文字列も、実際のデータもないことを確かめる。
- 文書のフォームは、ページとその節、ページの記述やその抜け、読者が知る必要のあったこと、ページのバージョンを必須にする。
- 提案のフォームは、具体的な例を添えた作業と、代わりにしていることを必須にする。考えは任意の欄で尋ね、作業のほうが考えより大事だと述べる。メンテナーは、その作業を別のやり方で扱うことがあるからである。
- 空の issue は無効にする（`config.yml`）。そのため、報告者はみなフォームを通る。それでも GitHub は、リポジトリに書き込める人には空の issue を出せるようにしている。また、`gh issue create` と依存を更新するボットが使う API は、どんな本文でも受け付ける。
- 新しい issue のテンプレートの選択画面は、脆弱性の非公開報告へリンクする。`SECURITY.md` がこれを求め、`make github-settings` がこれを有効に保つ。
- `gh` で書く issue は、送信したフォームを GitHub が表示するのと同じく、そのフォームの見出しをフォームの順に持つ。
- issue は英語で書く。issue は公開され、対訳を持たない。issue に応えるプルリクエストとコミットも英語である（ADR-0003）。
- issue を直すプルリクエストは、説明に `Closes #N` と書いて issue を閉じ、修正を固定するテストを含む。コミットメッセージは、`#N` で issue を参照しない。issue には、修正を含むことになるバージョンのマイルストーンを付ける。
- `docs/guides/issues.md` は、issue の書き方・トリアージのしかた・閉じ方を述べ、スキル `write-issue` は、コーディングエージェントに手順を示す。issue を作ると公開されるので、エージェントが issue を作るのは、依頼した人か作業の指示が求めたときだけである。

### 結果

- 良い点：ブラウザでは、バージョンと再現のない不具合の報告を送信できない。メンテナーは、説明ではなく SQL とファイルから始められる。
- 良い点：誰が書いても、同じ種類の issue はどれも同じ見出しを持つ。そのため、issue を欄ごとに読み、比べられる。
- 良い点：フォームはリポジトリのファイルである。フォームの変更はプルリクエストでレビューされ、`make check` がフォームを検証する。
- 良い点：スカッシュマージは、プルリクエストの説明を `main` 上のコミットに含めない。そのため、閉じる行はプルリクエストから一度だけ働き、issue は、それを直したプルリクエストとそのテストにリンクする。
- 悪い点：必須の欄には何でも書ける。フォームが確かめるのは欄が空でないことであり、再現が不具合を再現することではない。トリアージでは、やはり再現を動かす必要がある。
- 悪い点：フォームは、空の入力欄より多くを報告者に求める。そのため、不具合に出会っても報告しない人が出る。
- 悪い点：`gh` で書く issue にフォームを守らせるものはない。API がどんな本文でも受け付けるからである。そうした issue の欄がそろうかどうかは、スキルとレビューしだいである。
- 悪い点：スキーマのチェックが見るのは、フォームの構造であって意味ではない。同じ ID の欄が2つあっても、誤ったことを求める説明があっても、チェックは通る。
- 悪い点：PostgreSQL を使わない、このリポジトリのチェックの不具合も、不具合のフォームに合わせる必要がある。PostgreSQL のバージョンには「none」と書く。
- 悪い点：英語を書かない報告者にも、英語で書くよう求める。

### 確認の方法

- `make check` は `lint-schema` を実行する。これは、各フォームを issue のフォームのスキーマで検証し、`config.yml` を選択画面のスキーマで検証する。どちらのスキーマも固定した道具に同梱されているので、このチェックはネットワークを使わない。`lint-yaml` と `fmt-check-prettier` は、ほかの YAML のファイルと同じく、フォームの YAML を検査する。
- `make check-all` は自己テストを実行する。そのケース `lint-schema (issue-forms)` は、ラベルのない欄を持つフォームと、空の issue の設定が真偽値でない選択画面とで、このチェックが失敗することを示す。
- 残りはレビューが確かめる。フォームは、この記録の挙げるものを求めているか。`gh` で書いた issue は、そのフォームに従っているか。issue に、ガイドの禁じるものはないか。プルリクエストは、説明から issue を閉じ、テストを含んでいるか。issue には、マイルストーンが付いたか。

## 選択肢の長所と短所

### 自由記述とガイド

- 良い点：報告者は、知っていることを好きな順に書ける。保守が要るのはガイドだけである。
- 悪い点：書いている時点で、バージョンや再現を求めるものがない。そのとき何が抜けるかは、issue #19 から #49 が示している。
- 悪い点：issue ごとに構造が違うので、読者は、期待した振る舞いやバージョンを毎回違う場所で探す。

### issue の種類ごとの Markdown のテンプレート

- 良い点：見出しが最初からそろっている。Markdown のファイルは、書くのも読むのも簡単である。
- 悪い点：テンプレートは、報告者が消すことも、そのまま残すこともできるテキストである。見出しだけで中身のない報告も送信できる。
- 悪い点：テンプレートに当てはまるスキーマはない。そのため、ガイドが挙げるものをテンプレートがまだ求めているかどうかは、レビューでしか確かめられない。

### 必須の欄を持つ issue のフォーム、ガイド、スキル

- 良い点：必須の欄を埋めないと、報告を送信できない。GitHub は、どの報告もフォームの欄のラベルのもとに表示する。
- 良い点：リポジトリが固定しているスキーマのチェックの道具は、issue のフォームと選択画面のスキーマを同梱している。そのため、フォームのために新しい道具は要らない。
- 悪い点：フォームは GitHub の機能である。別のホストへ移れば、`.github/` のほかのものと同じく、フォームも持っていけない。
- 悪い点：GitHub が必須の欄を守らせるのは、ブラウザで、しかも公開リポジトリでだけである。
