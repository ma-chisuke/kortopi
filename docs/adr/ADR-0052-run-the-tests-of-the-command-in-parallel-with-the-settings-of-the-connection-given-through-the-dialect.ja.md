# ADR-0052: コマンドのテストを並列に実行し、接続の設定は DB ごとの部品を通して渡す

## 背景と課題

結合テストは、テスト自身が起動するコンテナの PostgreSQL 15・16・17・18 に対して動き（ADR-0019）、`make check-all` で実行される。
その時間は変更のたびに延びてきた。メモリ 8 GB の arm64 のノート PC では、`make check-all` に 840 秒から 1,050 秒かかった。ほかのジョブが動いている間に、パッケージ `cmd/kortopi` だけでテストバイナリの時間の上限 20 分を超えたこともある。CI のジョブ `full` は 7〜9 分から 12〜13 分に延びた。

`internal/postgres` のテストは、すでに並列に動いていた。どのテストも、そのサーバーごとのサブテストも、`t.Parallel` を呼ぶ。
コマンドのテスト（`cmd/kortopi`）は、1つずつ順に動き、各テストの 4 つの版も順に動いていた。
これらのテストは、パスワードなどの接続の設定を libpq の環境変数（`PGPASSWORD`・`PGSSLMODE`・`PGCONNECT_TIMEOUT`・`PGOPTIONS`）として `t.Setenv` でコマンドに渡していた。
環境変数はプロセスに属し、すべてのテストがそれを共有する。そのため Go は、並列に動くテストでの `t.Setenv` を拒む。
ノート PC では、コマンドのテストはそれだけで 240 秒から 370 秒かかり、その間マシンはほとんど空いていた。そして `make check-all` でいちばん長い一続きの処理になっていた。

サーバー上の文を測ると、テスト自身にもう1つの費用が見つかった。
`pgtest.DB.Objects` は、コマンドを実行するたびにその前後でデータベースのオブジェクトを並べる。実行が何も残さなかったことをテストが示すためである（ADR-0010）。この関数は、テンプレートデータベースのおよそ 5,000 のオブジェクトすべての名前を `regprocedure` と `regoperator` で書いていた。
テストの負荷の下で、1回の呼び出しに PostgreSQL 15 では 250 ミリ秒、ほかの版では 40 ミリ秒ほどかかった。コマンドのテストの文のなかでもっとも高くつき、PostgreSQL 15 では、サーバーがそれらの文に費やした時間全体の半分を超えた。

コマンドが設定を環境変数から読むなかで、コマンドのテストをどうやって並列に動かすのか。そして、テストが確かめることを減らさずに、どの費用を払わずに済ませられるのか。

## 判断の基準

- どのテストも、これまでどおりサポートするすべての版に対して `-race` と `-shuffle=on` で動き、失敗したテストは版の名前を示す。
- コマンドが利用者に対してすることは変えない。コマンドは、これまでどおりドライバを通して環境変数を読む。
- 環境変数の読み取りは、テストで確かめ続ける。
- どのテストも確かめることを減らさない。時間への依存も、これまでより増やさない。
- テストは、自身が起動したサーバーだけに対して動く（ADR-0019）。
- 同時に動くテストは、メモリ 8 GB のノート PC のメモリにも、サーバーの接続数にも収まる。
- CI のワークフローは、これまでどおり `make` だけを呼ぶ（ADR-0004、ADR-0005）。

## 検討した選択肢

- テストでは接続の設定を DB ごとの部品に渡し、コマンドのテストを並列に動かす
- `TestMain` で環境変数を一度だけ設定し、テストを並列に動かす
- テストごとにコマンドを別のプロセスとして動かし、それぞれに環境変数を与える
- コマンドのテストは順に動かしたまま、専用の make のターゲットで動かす

## 決定

採用：「テストでは接続の設定を DB ごとの部品に渡し、コマンドのテストを並列に動かす」。コマンドのどのテストも、自分のパスワード・ロール・オプションを持ったまま並列に動ける。しかもコマンドは、利用者のときと同じコードを通って同じドライバに届く。

決まりは次のとおりである。

- PostgreSQL の DB ごとの部品は、`password`・`sslmode`・`connect_timeout`・`options` のような libpq のキーワードで接続の設定を持つ。セッションは、それを libpq の環境変数と同じように、その代わりとして受け取る。kortopi がドライバに渡す接続文字列では、この設定がフラグより前に来る。そのためフラグがこの設定に優先し、この設定は環境変数に優先する。コマンドはこの設定を一切しない。設定するのは `postgres.WithSettings` だけで、この関数はビルドタグ `integration` のときだけビルドされるファイルにある。したがって利用者が受け取るバイナリには、この設定をする手段がない。
- コマンドのテストは、利用者なら環境変数で与える設定を、自分の `e2e` を通してコマンドに渡す。スーパーユーザーには `connect`、テストのロールには `connectAs`、`PGOPTIONS` が与えるものには `withOptions` を使う。コマンドは、この設定を持つ DB ごとの部品を登録したものを使って動き、テストはプロセスの環境変数に手を触れない。
- コマンドのテストは、どれも並列に動く。テスト自身が `t.Parallel` を呼び（`eachServer`）、サーバーごとのサブテストも、その中で自分のデータベースを持つサブテストも同じく呼ぶ。
- 環境変数の読み取りを主題とするテストは、環境変数を設定し、順に動かしたままにする。`TestSettingsFromTheEnvironment`（環境変数のパスワードでの接続も確かめる）と `TestPlanCommandConnectionErrors` である。Go はパッケージの順に動くテストをすべて終えてから並列のテストを進めるので、並列のテストがこれらの環境変数を見ることはない。
- `pgtest.DB.Objects` は、データベースの作成後にできたオブジェクト（OID が 16384 以上）を、これまでどおり名前で並べる。テンプレートデータベースのオブジェクトは1行にまとめ、その数と、それらを名指す列のダイジェストを示す。テンプレートのオブジェクトがどれか追加・削除・改名されればこの行が変わる。これまでそのオブジェクトの名前の行が変わったのと同じである。`TestObjectsSeeEveryChange` が、各版でそれを確かめる。
- `internal/postgres` のテストがヘルパー `session` と `applySession` で開くセッションは、テストのコンテキストからキャンセルだけを除いたもの（`runContext`）で動く。Go は、クリーンアップの前にテストのコンテキストをキャンセルする。実行がキャンセルされたセッションは割り込まれたものとして閉じ、サーバーのロールバックを最大 5 秒しか待たない。そのため混んだノート PC では、確認をすべて通った2つのテストが、この閉じる処理で失敗した。割り込みのテストは、それぞれ自分のコンテキストをキャンセルする。
- パッケージの中で同時に動くテストの数は、`go test` の既定値である `GOMAXPROCS` とする。ノート PC では 8、CI のランナーでは 4 である。1つのテストが持つ接続は、スーパーユーザーのもの、コマンドの1つか2つ、ときにロックを持つための1つだけである。1つのサーバーで同時に開いていた接続は最大でも 15 で、上限の 300 には遠く及ばない。上限を上げてもノート PC では速くならない。並列に動くコマンドのテストは、1つで動くときの 4〜5 倍の時間がかかっており、速さを決めているのはスロットの数ではなく、サーバーとマシンのメモリである。
- 結合テストは、パッケージを1つずつ動かす（`make/go.mk` の `go test -p 1`）。`cmd/kortopi` と `internal/postgres` はそれぞれ自分の 4 つのサーバーを起動する。テストバイナリは、データ競合の検出器を有効にしてテストを並列に動かすと、1.1〜1.4 GB を使う。ほかのプログラムがすでにメモリを埋めているメモリ 8 GB のノート PC で両方を同時に動かすと、激しくスワップした。`cmd/kortopi` は 85 秒ではなく 933 秒かかり、コマンドの実行がテストの時間の上限を超えた。`TestLockTimeoutCommand` は、10 秒までを許すところで 12 秒の実行を見た。1つずつ動かすと、2つのパッケージは 85 秒と 264 秒、ターゲット全体で 368 秒かかり、すべて通った。テストバイナリごとの 20 分の上限は変えない。

ほかの変更を見送った根拠となる測定は次のとおりである。

- どのテストも、自分のデータベースを作り、終わると削除する。`DROP DATABASE` はサーバーにチェックポイントを書かせてそれを待つので、高くつくように見えた。2,000 行のテーブルを1つ持つデータベース 192 個を並列に扱うベンチマークで、テストの時間の中央値を比べた。各テストの最後に削除すると 0.24〜0.30 秒、どのテストも待たない 16 個ずつの一括の削除にすると 0.94 秒、削除しないと 0.62 秒だった。削除しないと、残ったデータベースの書き換えたページを書き出さなければならないからである。削除はこれまでどおりとする。
- `CREATE DATABASE ... STRATEGY FILE_COPY` は、サーバーにチェックポイントを2回書かせる。既定の `WAL_LOG` では1回も書かない。単独では速かったが、テストの負荷の下では遅くなる。既定のままとする。
- データディレクトリを `tmpfs` に置いても、ベンチマークの変化はばらつきの範囲に収まった。しかも、ノート PC がほかのコンテナと共有する 4 GB の仮想マシンのメモリを使ってしまう。

### 結果

- 良い点：コマンドのテストが長い一続きの処理でなくなる。1つのテストの 4 つの版も、テストどうしも、同時に動く。
- 良い点：コマンドは同じ関数 `Connect` を通り、テストが足す設定を除いて同じ接続文字列でドライバに届く。環境変数の読み取りには、それ専用のテストが残る。
- 良い点：サーバーがテストの確認に費やす時間が減る。PostgreSQL 15 でもっとも減る。
- 悪い点：コマンドのテストは `t.Setenv` を呼んではならない。Go がそれを止めるのは、テストが並列であるときの実行時だけである。
- 悪い点：PostgreSQL の DB ごとの部品が、テストだけが設定するフィールドを持つ。テストの接続文字列は、フラグより前に来る設定の分だけ、利用者のものと異なる。
- 悪い点：テンプレートデータベースのオブジェクトの変化は、ダイジェストの変化として現れ、オブジェクトもその種類も名指さない。その場合、テストは自分で問い合わせて変化したものを探す必要がある。
- 悪い点：同時に動くテストはサーバーとマシンを共有するので、どのテストも単独のときより長くかかる。混んだマシンでは、同時に動くテストの数ほどには速くならない。
- 悪い点：2つのパッケージは重ならなくなる。CI のランナーのようにメモリに余裕のあるマシンでは、ターゲットの時間は、長いほうのパッケージの時間ではなく、2つの合計に近くなる。

### 確認の方法

- Go は、`t.Setenv` を呼ぶテストが、またはその親のテストが並列に動くとき、そのテストを失敗させる。そのため環境変数を設定するコマンドのテストは、順に動かさない限り失敗する。そうしたテストを環境変数が主題のものに限ることは、レビューで守る。
- `internal/postgres` の `TestOptionsConnString` と `TestOptionsConnConfig` は、設定がフラグより前に来て、環境変数に優先し、フラグには譲ることを確かめる。`TestDialectOpen` は、`Open` が設定を受け渡すことを確かめる。
- `make/go.mk` の `GO_INTEGRATION` は、`make test-go-integration` と `make coverage` のために `-p 1` を持つ。
- `internal/postgres` の `TestObjectsSeeEveryChange` は、`make check-all` で各版を相手に、オブジェクトの一覧が変化の種類ごとに変わることを確かめる。テストのオブジェクトの変化も、テンプレートデータベースのオブジェクトの変化も対象である。

## 選択肢の長所と短所

### テストでは接続の設定を DB ごとの部品に渡し、コマンドのテストを並列に動かす

- 良い点：各テストが、並列に動きながら、自分のパスワード・ロール・オプションを持てる。
- 良い点：コマンドはこれまでどおりテストのプロセスの中で動くので、テストはコマンドに割り込み、書いたものを読める。
- 悪い点：DB ごとの部品のフィールドを接点とし、バイナリはそれを一切設定しない。

### `TestMain` で環境変数を一度だけ設定し、テストを並列に動かす

- 良い点：kortopi のコードは変わらない。
- 悪い点：テストは異なるパスワードとオプションを持つ異なるロールで接続する。1つの環境変数では、それらを同時に与えられない。
- 悪い点：テストバイナリ全体の環境変数にあるパスワードは、ホストを省いたどの接続にも届いてしまう。`pgtest.Main` が libpq の環境変数を取り除くのは、まさにそれを防ぐためである。

### テストごとにコマンドを別のプロセスとして動かし、それぞれに環境変数を与える

- 良い点：バイナリもその環境変数も、利用者のものとまったく同じになる。
- 悪い点：テストは、動いているコマンドへの割り込み、2回目の割り込み、出力の読み取りを行う。プロセスを相手にすると、これらは遅くなる。しかも、時間の影響を受けずに行うことが難しくなる。
- 悪い点：`-race` でバイナリをビルドし、数百を超える実行のたびにそれを起動する費用は、テストが節約する時間を上回る。

### コマンドのテストは順に動かしたまま、専用の make のターゲットで動かす

- 良い点：テストは変わらない。
- 悪い点：コマンドのテストは、これまでと同じ長さの一続きの処理のままである。しかも専用のターゲットを `internal/postgres` のターゲットと並べて動かせば、サーバーを持つ2つのパッケージが同時にマシンに載る。
