# ADR-0047: スナップショットのあとにほかのセッションが書き換え、置き換え、パーティションを変えたテーブルを読んだ実行は止める

## 背景と課題

計画・apply・書き出しは、`REPEATABLE READ` の1つのトランザクションで動き、その最初の文がスナップショットを取る（ADR-0024、ADR-0026）。
宣言したテーブルのロックは、そのテーブルを読むまで取らない。読むのは、カタログを読んだあとである。
その間にほかのセッションがコミットしたスキーマの変更は、テーブルの読み取りには見え、スナップショットには見えない。

テーブルを書き換える `ALTER TABLE` の形（`ALTER COLUMN ... TYPE` や、揮発性の既定値を持つ `ADD COLUMN` など）と `TRUNCATE` は、テーブルに新しいストレージを与える。その行には、変更をしたトランザクションが記録される。
これらは MVCC に対して安全でない。変更より前のスナップショットを持つトランザクションには、新しいストレージは空に見える。
issue 45 では、あるセッションが `geo.postal_codes` をロックし、計画がスナップショットを取って最初の読み取りでそのロックを待った。そのあと、そのセッションが列の型を変えてコミットした。
計画は宣言したすべての行を欠けていると示し、`--exit-code` は 2 で終わった。存在しないずれである。同じ状況の apply は同じ計画を出力し、重複キーで失敗した。
書き出しは、行のないファイルを書いて 0 で終わった。
リファレンスは、スキーマの変更がロックを持つ間は計画が待つと書いていたが、そのとき結果が誤ることは書いていなかった。

PostgreSQL 15 から 18 では、読み取りに見えてスナップショットに見えないほかの変更でも同じことが起きる。

- ほかのセッションが削除して作り直したテーブルや、名前を変えて別のテーブルに置き換えたテーブルは、名前で読む。そのため読み取りは新しいテーブルを見つけ、スナップショットにはその行が見えない。
- ほかのセッションがデタッチしたパーティションは、パーティションテーブルの読み取りから消え、その行が欠ける。アタッチしたパーティションは、スナップショットがそこに見せる行とともに読まれる。それはスナップショットの時点でテーブルが持っていなかった行である。
- 削除の波及をたどる処理が読むテーブル（ADR-0039）は、宣言にあるとは限らない。それが書き換えられると空に見え、計画は削除が実際より少ない行にしか着かないと示す。

実行は、読んだテーブルがスナップショットのテーブルでないことをどう知り、そのとき何をするのか。

## 判断の基準

- 計画が報告するずれは本物のずれであり、失敗した計画がずれに見えることはない。`--exit-code` が 2 で終わるのは、データベースが持つ違いのときだけである。
- 実行が読むのは、そのスナップショットが持つものである。そうできないときは、実行がそう伝え、何も変えない。
- 実行には、ADR-0024・ADR-0039・ADR-0026 の権限より多くは要らない。計画と apply は、宣言したテーブルを、宣言した列だけに対する `SELECT` で読む。
- kortopi は一時テーブルのほかに何も作らず（ADR-0010）、計画は何も変えない（ADR-0016）。
- 確認の負担は、読み取りに比べて小さい。テーブルの行を読まず、待ちもしない。

## 検討した選択肢

- 各テーブルを初めて読んだあとに、スナップショットでのテーブルのストレージとサーバーが今使うストレージを比べ、違えば止める
- スナップショットを取る文より前に、宣言したテーブルをロックする
- ストレージが違えば、新しいスナップショットを取ってやり直す
- リファレンスに任せる：スキーマの変更は kortopi の実行の前にする

## 決定

採用：「各テーブルを初めて読んだあとに、スナップショットでのテーブルのストレージとサーバーが今使うストレージを比べ、違えば止める」。実行はテーブルを一度読むと、終わるまでそうした変更をすべて締め出すロックを持つ。そのため、最初の読み取りの直後の確認で結果が確定する。しかも権限は要らず、実行がすでに取るロックのほかにロックも要らず、カタログの問い合わせ1つで済む。

決まりは次のとおりである。

比べるもの：

- テーブルのストレージとは、その行を持つリレーションの集まりであり、それぞれにファイルがある。テーブル自身か、パーティションテーブルならテーブルを読んだときに見つかるすべての段のパーティションである。パーティションテーブルは、自分のストレージを持たない。
- スナップショットでのストレージ：トランザクションの中で `pg_inherits` と `pg_class` を問い合わせる。この問い合わせはスナップショットのカタログを見る。起点はスナップショットのカタログがテーブルに与える OID であり、各リレーションの `relfilenode` を読む。
- サーバーが今使うストレージ：実行の文がテーブルを呼ぶ名前に対する `to_regclass`、そのリレーションの `pg_partition_tree`、それぞれの `pg_relation_filenode` である。これらの関数は最新のカタログを読む。セッションは、リレーションのロックを持てば最新のカタログを読む。PostgreSQL 15 から 18 で、スナップショットと読み取りの間に変更がコミットしたあとに確かめた。トランザクションの中で `pg_class` を問い合わせて返る `relfilenode` はスナップショットのものであり、`pg_relation_filenode` は新しいものを返した。
- 名前が今は別のリレーションを指すか、どれも指さないとき、あるリレーションのファイルがスナップショットと今とで違うとき、リレーションの集まりが違うとき、実行は止まる。

比べる時点：

- 計画と apply では、宣言した各テーブルの比較の直後である。比較の最初の文がテーブルを読む。宣言の行の一時テーブルを作る文が、列の型をそのテーブルから取るからである（ADR-0009）。最初の読み取りは `ACCESS SHARE` を取る。テーブルに新しいストレージを与えるか置き換える変更は、どれもこれと衝突する。そうした変更は、どれも `ACCESS EXCLUSIVE` を取る。テーブルを書き換える `ALTER TABLE` の形、`TRUNCATE`、`VACUUM FULL`、`CLUSTER` がそうである。`DROP TABLE`、`ALTER TABLE ... RENAME`、`DETACH PARTITION`、`CREATE TABLE ... PARTITION OF` も同じである。そのため、最初の読み取りのあとにストレージは変わらず、確認は1回で足りる。
- テーブルの比較が失敗したときも、そのテーブルのセーブポイントをロールバックしたあとに確認をし、その確認のエラーが比較のエラーに代わる。テーブルを書き換えた変更は、列の新しい型のように、比較の文を失敗させうる。なくなったテーブルは、読み取りを `relation does not exist` で失敗させる。割り込みのあとには確認をしない。
- 削除の波及をたどる処理（ADR-0039）のあとごとに、その処理がどの段で読んだ参照元のテーブルもすべて確かめる。計画と apply の最初のたどる処理と、apply が削除の直前にするもう1回のたどる処理である。たどる処理もセーブポイントの中で動く。確認は、上と同じく、たどる処理の成否を問わずそのあとに続く。
- 書き出しでは、各テーブルを読んだあと、書き出しがどのファイルを置く前にも確かめる。行は一時ファイルで待ち、書き出しが失敗すればそのファイルは消える（ADR-0028）。
- `ATTACH PARTITION` はパーティションテーブルに `SHARE UPDATE EXCLUSIVE` を取る。`ACCESS SHARE` はこれを締め出さないので、確認のあとにパーティションがアタッチされることはありうる。それでも、実行が読んだ行はそのスナップショットのものである。apply は書き込みとコミット前の比較（ADR-0042）でテーブルをもう一度読み、そうした行を計画が示さなかった行として見つける。

実行がすること：

- 終了コード 1 で止まる。`--exit-code` があっても同じである。このエラーはずれではない。計画は計画を出さず、apply は何も書き込まず、書き出しはファイルを書かない。
- エラーは、テーブルと起きたことを挙げ、実行の読んだものがテーブルの持つものでない可能性を伝え、もう一度実行すること、スキーマの変更は kortopi の実行の前にすることを伝える。

  ```text
  kortopi: another session rewrote or truncated table geo.postal_codes after the plan began, so what the plan read from the table may not be what it holds: nothing was changed: run the plan again, and make schema changes before a run of kortopi, not during one
  ```

  最初の部分は、次のどれかである。

  - `rewrote or truncated table <table>`
  - `rewrote or truncated partition <partition> of table <table>`
  - `dropped, renamed, or replaced table <table>`
  - `detached or dropped a partition of table <table>`
  - `attached or created a partition of table <table>`

  apply は、ほかのエラーと同じく `nothing was changed` を最後の行に任せる。書き出しは `no file was written` を足す。たどる処理のエラーは `follow the foreign keys that reference the rows to delete:` で始まる。書き出しのエラーは `export table <table> into <file>:` で始まる。
- `VACUUM FULL`・`CLUSTER`・`ALTER TABLE ... SET TABLESPACE` も、テーブルに新しいストレージを与えるが、スナップショットに見える行を保つ。これらは MVCC に対して安全であり、テーブルを読んだ実行は、テーブルが持つとおりの行を読んでいる。カタログの上ではこれらを書き換えと区別できないので、これらのあとでも実行は止まる。これらで止まった実行は、もう一度実行すれば通る。しかも、kortopi の実行中にこれらが動くことはまれである。

負担：

- 計画か apply が比べる宣言したテーブルごとに1つ、たどる処理ごとに1つ、書き出しが読むテーブルごとに1つの、カタログの問い合わせである。テーブルの行は読まない。`pg_partition_tree` は、パーティションテーブルのパーティションに `ACCESS SHARE` を取るが、それはテーブルの読み取りがすでに取っている。
- 呼ぶ関数はテーブルへの権限を要しないので、宣言した列だけに対する `SELECT` を持つロールでも確認できる。

確かめないもの：

- ストレージを変えない変更は、確認には見えない。スナップショットのあとにほかのセッションが列を削除すると、読み取りは `column s.lat does not exist` のような PostgreSQL のエラーで失敗する。ほかのセッションが宣言した列を追加すると、スナップショットのテーブルのとおり、その列はスキーマの適用後に決まるものとして示され、`--exit-code` で数えられる。宣言が挙げない列を書き換えなしに追加しても、何も変わらない。
- スナップショットのあと、実行がカタログを読む前に、ほかのセッションがテーブルを削除すると、カタログの読み取りが、原因を示さないエラーで失敗する。スナップショットのカタログは、最新のカタログがもう権限を知らないリレーションを挙げるからである。
- 確認するテーブルは、実行が読むものである。実行の宣言したテーブル、そのパーティション、たどる処理の参照元のテーブルである。宣言したパーティションの上にあるパーティションテーブルは、たどる処理がそのパーティションの行のためだけに読むもので、確かめない。そのほかのパーティションは、たどる処理が数える行を1つも持たない。

これは、トランザクションが1つのスナップショットを見るとした ADR-0024・ADR-0026 を細かくする。スキーマの変更がスナップショットのあと、テーブルの最初の読み取りの前にコミットすると、読み取りにはその変更が見える。これまで、そうした変更は、テーブルが一度も持たなかった状態でそれを実行に読ませていた。今は実行を止める。

### 結果

- 良い点：スキーマの変更に出会った `--exit-code` 付きの計画は、テーブルのすべての行が欠けていると終了コード 2 で報告する代わりに、そう伝えるエラーとともに終了コード 1 で失敗する。
- 良い点：スキーマの変更に出会った apply は、行のせいにする重複キーで失敗する代わりに、原因を挙げるエラーとともに、どの書き込みよりも前に止まる。書き出しは、空のファイルを書いて終了コード 0 で終わることがなくなる。
- 良い点：削除の波及をたどる処理は、書き換えられたテーブルを空として数えなくなる。そう数えると、削除の波及が実際より小さく見えていた。
- 良い点：確認には、読み取りが要るもののほかに権限もロックも要らず、テーブルごとにカタログの問い合わせ1つで済む。
- 悪い点：実行がロックを待つ間に、宣言したテーブルか、たどる処理が読むテーブルに `VACUUM FULL`・`CLUSTER`・`ALTER TABLE ... SET TABLESPACE` がされると、実行は止まる。実行が読んだのはテーブルが持つとおりの行であってもそうなる。
- 悪い点：スキーマの変更に出会った実行は、今も失敗し、もう一度実行しなければならない。確認は変更を見つけるが、避けはしない。
- 悪い点：スナップショットのあとに削除された列と、実行がカタログを読む前に削除されたテーブルは、今も PostgreSQL かドライバーのエラーで失敗する。そのエラーは、ほかのセッションがスキーマを変えたことを伝えない。

### 確認の方法

- `internal/postgres` の単体テストは、2つのリレーションの集まりから下す判断とエラーを確かめる：`TestStorageChange` と `TestStorageError`。
- `make check-all` で PostgreSQL 15 から 18 に対して動く `internal/postgres` の結合テストは、セッションのスナップショットのあとに、別の接続からスキーマを変える：
  - `TestPlanOfATableChangedAfterTheSnapshot`：次のものは計画を止める。新しい型がテーブルを書き換える列と、揮発性の既定値で追加した列である。`TRUNCATE` と `VACUUM FULL` も止める。削除して作り直したテーブルと、名前を変えて別のテーブルを置いたテーブルも止める。空にしたパーティション、列の型を変えたパーティションテーブル、デタッチしたパーティション、アタッチしたパーティションも止める。書き換えなしに追加した列は止めない。
  - `TestApplyAndExportOfATableRewrittenAfterTheSnapshot`：apply はどの書き込みよりも前に止まり、行はそのまま残る。書き出しは止まる。
  - `TestWalkOfATableRewrittenAfterTheSnapshot`：たどる処理が、書き換えのあとに読む参照元のテーブル。
- `cmd/kortopi` の `TestTableRewrittenDuringARunCommand` は、issue 45 の再現を各バージョンに対して動かす。ほかのセッションがテーブルをロックし、`--exit-code` 付きの計画、apply、書き出しが最初の読み取りで待ち、そのあとそのセッションが列の型を変えてコミットする。どのコマンドも、そのエラーとともに終了コード 1 で終わり、テーブルは行を保ち、あとの計画は変えるものを見つけない。確認がなければ、同じテストは issue のとおりに終わる。

## 選択肢の長所と短所

### 各テーブルを初めて読んだあとに、スナップショットでのテーブルのストレージとサーバーが今使うストレージを比べ、違えば止める

- 良い点：読み取りに見えてスナップショットに見えない変更のうち、テーブルに新しいストレージを与えるもの、テーブルを置き換えるもの、パーティションを変えるものについて正確であり、権限も要らない。
- 良い点：たどる処理のテーブルも確かめる。実行は、そのテーブルをスナップショットのカタログを通してしか見つけられない。
- 悪い点：テーブルに新しいストレージを与えても行を保つ変更のあとでも止まる。カタログの上では、それを区別できない。

### スナップショットを取る文より前に、宣言したテーブルをロックする

- 良い点：書き換えは実行を待つか、実行がスナップショットより前に書き換えを待つことになる。そのため、実行はどのテーブルもスナップショットが持つとおりに読む。
- 悪い点：`LOCK TABLE` にはテーブル全体への権限が要る。`ACCESS SHARE` には `SELECT` が要り、ほかに `UPDATE`・`DELETE`・`TRUNCATE`、PostgreSQL 17 からは `MAINTAIN` でもよい。計画と apply が受け入れる、宣言した列だけに対する `SELECT` を持つロール（ADR-0024、ADR-0037）は、PostgreSQL 15 から 18 で `permission denied for table` を受ける。この決定のために手で試して確かめた。
- 悪い点：計画は、カタログを読む前にテーブルを挙げなければならない。しかも `LOCK TABLE` は、データベースにまだないテーブルで失敗する。計画は、そうしたテーブルをスキーマの変更を待つものとして示す（ADR-0016）。
- 悪い点：削除の波及をたどる処理が読むテーブルは、カタログから見つける。カタログの問い合わせはスナップショットで読むので、それより前にそれらのテーブルはロックできない。

### ストレージが違えば、新しいスナップショットを取ってやり直す

- 良い点：利用者は、エラーの代わりに計画を得る。
- 悪い点：実行中のスキーマの変更は、知っておく価値がある。両方を同時に動かすデプロイは、手順の順序が崩れている。
- 悪い点：新しいスナップショットは、一連のスキーマの変更の次の変更に出会いうる。しかも apply は、そのたびに宣言の行を読み込み直し、ロックを取り直す。

### リファレンスに任せる：スキーマの変更は kortopi の実行の前にする

- 良い点：kortopi では何も変わらない。
- 悪い点：定期的なずれの検出は、別のチームがいつスキーマを変えるかを選べない。しかも、テーブルが欠けているという報告は、本当に行が失われた場合と区別できない。
