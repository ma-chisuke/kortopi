# ADR-0031: パーティションが二重に宣言する行と、データベースの名前と空白か大小だけが違う名前で止まり、モード insert が比べない値について一致を主張しない

## 背景と課題

あるチームが、文脈ごとに1つのスキーマを持つアプリケーションで kortopi を試した。
計画の結果のうち3つが誤っていたのに、それを告げるエラーはなかった。

- パーティションとそのパーティションテーブルを、まとめて書き出し、計画し、適用した。パーティションの行はそのパーティションテーブルの行でもあり、計画はパーティションテーブルを全体として読む（ADR-0024）。そのため、宣言はそれらの行をそれぞれ2回持っていた。計画は挿入する行をそれぞれ2回示し、apply は文の件数の検査（ADR-0026）で失敗した。そのエラーはトリガーを原因に挙げていた。
- CSV の見出しの行が、列 `name` を `name` や `Name` と書いていた。この列は、スキーマの変更を待つ列として示された（ADR-0016）。計画は通り、この列は比べられなかった。ADR-0016 は、綴りを誤った名前が適用待ちの名前と同じに見えることを受け入れ、その誤りを使い捨ての PostgreSQL での実行とレビューに委ねている。
- モード `insert` のテーブルは、欠けている行を得るだけである（ADR-0013）。そのため計画は、ほかの行の値を比べない。それでも空の計画は `The database matches the declaration.` と表示していた（ADR-0024）。実際には、宣言した値の1つが保存されている値と違っていた。

計画はこうした宣言をどう扱い、空の計画は何を主張してよいのか。

## 判断の基準

- 計画は、同じ行を2回示さない。データベースにある名前を、スキーマの変更を待つ名前として示さない。
- スキーマの変更を待つテーブルや列は、引き続き宣言できる（ADR-0016）。それを足すプルリクエストも、計画を得る。
- 出力は、kortopi が検査したことだけを述べる（ADR-0024）。
- 検査に新しい権限は要らず、カタログへの問い合わせは多くても1つ増えるだけである。

## 検討した選択肢

- カタログの示す誤りでは止まり、計画が比べたことだけを主張する
- 振る舞いを変えず、これらの場合を文書に書く
- フラグで、すべての適用待ちの名前をエラーにする
- モード insert のテーブルの値も比べる

## 決定

採用：「カタログの示す誤りでは止まり、計画が比べたことだけを主張する」。これらの誤りは、どれも計画がすでに読むカタログに表れる。スキーマの変更を待つ名前は引き続き使える。出力も、データベースでの作業を増やさないまま正しく保てるからである。

決まりは次のとおりである。

パーティションについて。

- カタログは、パーティションについて、その上にあるパーティションテーブルを、どの深さのものも報告する。
- 宣言がパーティションと、その上にあるパーティションテーブルを宣言していれば、計画と apply は、そうした組ごとにエラーを出して止まる。エラーは両方のテーブルと両方のファイルを挙げ、どちらか一方だけを宣言するよう告げる。このエラーは、計画がどの行も読み込む前にまとめて報告する誤りの1つである（ADR-0024）。
- パーティションと、その上にあるパーティションテーブルを指定した書き出しは、何も書かない。データのディレクトリがすでにパーティションテーブルを宣言しているパーティションを指定した書き出しも、同じである。`--table` で、または `--schema` を通じて指定したパーティションテーブルのパーティションを、データのディレクトリがすでに宣言している場合も、同じである。そのエラーがそう告げる。この最後の場合のため、カタログはパーティションテーブルのパーティションも報告する。`--schema` は、パーティションを単独では指定しない（ADR-0028）。
- パーティションだけ、パーティションテーブルだけなら、これまでどおり宣言できる。
- 別のテーブルを継承するテーブルは、パーティションではない。計画と apply は、ふつうのテーブルを `ONLY` で読み書きする（ADR-0024、ADR-0026）。そのため、テーブルとそれを継承するテーブルは別々の行の集まりを持ち、両方を宣言できる。

空白か大小だけが違う名前について。

- 宣言した列がテーブルになく、宣言した名前の前後の空白を取り除き、大小を同一視するとテーブルの列と等しいなら、エラーである。エラーは、ファイルと、ファイルが書いたとおりの列名と、テーブルの列を挙げる。列名は引用符で囲み、空白が見えるようにする。こうした列は、もはやスキーマの変更を待つ列としては示さない。
- 宣言したテーブルがデータベースになく、データベースに、スキーマと名前がこの意味で宣言と等しいテーブルがあるなら、エラーである。そうしたテーブルはないが、宣言したスキーマとこの意味で等しいスキーマがあるなら、エラーはそのスキーマを挙げる。宣言したスキーマがそのとおりの名前で存在するなら、そのスキーマのテーブルだけを数え、ほかのスキーマは数えない。存在するスキーマへの新しいテーブルは、スキーマの変更を待っていることが十分ありうるからである。これらの名前は、存在しない宣言済みのテーブルについてだけ、カタログへの1つの問い合わせで探す。空白を取り除くのは宣言した名前だけであり、両側を照合順序 `"C"` での `lower()` で比べる。この照合順序は ASCII の文字の大小だけを同一視する。
- データベースにないそのほかの名前は、ADR-0016 が決めたとおり、引き続きスキーマの変更を待つ。すべての適用待ちの名前をエラーにするフラグは、この記録には含めない。
- これは ADR-0016 と ADR-0024 を細かくする。その決まりは、データベースにない宣言済みのテーブルや列を、スキーマの適用後に決まるものとして示す。今後は、データベースの名前と空白か大小だけが違う名前はエラーになる。ADR-0016 は、綴りを誤ったテーブル名や列名が、スキーマの変更を待つ名前と同じに見えることを結果に挙げている。今後それが当てはまるのは、空白と大小のほかにも違いのある名前だけである。

空の計画について。

- 計画のどのテーブルもモード `insert` でなければ、空の計画は、ADR-0024 が決めたとおり `No changes. The database matches the declaration.` と表示する。
- 計画にモード `insert` のテーブルがあれば、空の計画は `No changes. There is nothing to apply.` と表示し、2行目にモード `insert` のテーブルを挙げて、それらをキーだけで比べると述べる。挙げる名前は5つまでとし、残りは数で示す。問い合わせは増えない。
- SQL としての計画（ADR-0029）は、これらの行をコメントとして書く。1行目は `-- No changes: there is nothing to do.` である。
- これは ADR-0024 を細かくする。ADR-0024 は、空の計画を1行としている。ADR-0029 も細かくする。ADR-0029 は、空のスクリプトをコメント1行としている。
- ADR-0021 も細かくする。ADR-0021 では、`plan --exit-code` の終了コード 0 はデータベースが宣言と一致していることを意味する。今後は、適用するものがないことを意味する。モード `insert` のテーブルについては、すでにある行の値について何も言わない。plan のヘルプもそう述べる。

### 結果

- 良い点：パーティションが二重に宣言する行では、選ぶべき2つのファイルを示して計画が止まる。件数で失敗してトリガーのせいにする apply にはならない。
- 良い点：見出しの行でいちばんありがちな誤り、つまりコンマのあとの空白と大小の違う名前で、その誤りを入れたプルリクエストの計画が止まる。
- 良い点：空の計画が、値を比べていないテーブルについて、データベースが宣言と一致しているとは言わなくなる。
- 悪い点：`sort_order` を `sortorder` と書いたときのように、空白と大小のほかにも違いのある綴りの誤りは、引き続きスキーマの変更を待つ列に見える。それは使い捨ての PostgreSQL での実行が見つける（ADR-0016）。
- 悪い点：照合順序 `"C"` での `lower()` は、ASCII の文字の大小しか同一視しない。そのため、ほかの文字の大小だけが違う名前のテーブルは、引き続きスキーマの変更を待つ。列は kortopi の中で、すべての文字の大小を同一視して比べる。
- 悪い点：`--schema` で絞った計画は、そのスキーマの宣言済みのテーブルしか見ない。そのため、2つのスキーマにまたがるパーティションとパーティションテーブルは、一方だけを指定した実行を通ってしまう。
- 悪い点：既存のテーブルと大小だけが違う名前の新しいテーブルは、そのスキーマがそのとおりの名前で存在しない限り、スキーマの変更がそれを作るまで宣言できない。
- 悪い点：既存の列と大小か前後の空白だけが違う名前の新しい列は、適用待ちとして宣言できない。スキーマの変更がそれを作るまでエラーになる。
- 悪い点：空の計画に2つの形ができるので、出力を読むスクリプトは両方を受け付ける必要がある。

### 確認の方法

- `internal/plan` の単体テストが、エラーと空の計画を確かめる。エラーは `TestBuildPartitionDeclaredWithItsParent`・`TestBuildNearNames`・`TestBuildErrors` が確かめる。空の計画は、`TestRender` のゴールデンファイル `no_changes_insert.golden` と `no_changes_insert_many.golden` が確かめる。`internal/script` の `TestWrite` がスクリプトを（`empty_with_mode_insert.golden`）、`internal/export` の `TestRunErrors` が書き出しを確かめる。
- 残りは、`make check-all` で PostgreSQL 15 から 18 に対して実行する結合テストが確かめる。`internal/postgres` では、`TestDescribe` がカタログの報告を検査する。2つの深さでのパーティションの上にあるパーティションテーブル、別のテーブルを継承するテーブル、大小の違う名前である。`cmd/kortopi` の `TestPartitionsAndInheritance` は、パーティションとそのパーティションテーブルについて、また別のテーブルに継承されるテーブルについて、plan・apply・export を実行する。`TestPlanCommand` は、大小の違う見出しとファイル名を計画する。

## 選択肢の長所と短所

### カタログの示す誤りでは止まり、計画が比べたことだけを主張する

- 良い点：それぞれの誤りが、それを入れた場所で計画を止め、代わりに何を書くかを示す。
- 悪い点：存在しない宣言済みのテーブルがあると、カタログへの問い合わせが1つ増え、空の計画に2つ目の形ができる。

### 振る舞いを変えず、これらの場合を文書に書く

- 良い点：これらの場合を知っているチームにとっては、何も変わらない。
- 悪い点：apply が拒む宣言や、列を管理しないままにする宣言を、計画が通してしまう。その出力は、検査していない一致を主張する。

### フラグで、すべての適用待ちの名前をエラーにする

- 良い点：フラグを付けた場所、たとえばデプロイのときには、すべての綴りの誤りで失敗する。
- 悪い点：適用待ちの名前がよく現れるプルリクエストの計画は、引き続きフラグなしで動く。しかも、kortopi がそうしたフラグを持つかどうかは、それ自体が1つの決定である。

### モード insert のテーブルの値も比べる

- 良い点：空の計画が、宣言したすべての値が一致していると言えるようになる。
- 悪い点：apply が決して書かない値のために、データベースでの作業が増える。しかも `plan --exit-code` は、どの apply も解消しない違いを、ずれとして報告し続ける。
