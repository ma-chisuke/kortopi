# ADR-0013: テーブルごとの設定を1つの TOML ファイルにまとめ、テーブルごとにモードを持たせる

## 背景と課題

マスタテーブルは、テーブルによって扱いを変える必要がある。
都道府県の一覧は宣言の中で完結しており、宣言にない行は削除すべきである。
料金プランのテーブルでは、システムの稼働中に行を足すことがある。宣言にない行をすべて削除すると、そうした行が失われる。
主キー以外のキーで照合するテーブルもある（ADR-0012）。

そのため、テーブルごとに設定が要る。少なくとも、kortopi が行を更新・削除してよいかを決めるモードと、照合キーである。
データファイルには、それらを書ききれない。CSV にはコメントの書き方がなく、1つの SQL ファイルが複数のテーブルを宣言することもある（ADR-0014）。

テーブルごとの設定は、どこに、どの書式で書くか。モードには何があるか。

## 判断の基準

- 特別な扱いの要らないテーブルには、設定が要らない。
- 行の削除は、決して既定にしない。
- 必要の違うテーブルが、同じ実行の中で違うモードを持てる。
- すべてのテーブルの設定が、レビューする人の読める1か所にある。
- 設定の値は、書き方によって型が変わらない。

## 検討した選択肢

- データのディレクトリの最上位に置く1つの TOML ファイルで、テーブルごとにモードを持つ
- すべてのテーブルに1つのモードを、環境ごとに設定する
- データファイルの中のコメントで設定する
- データファイルごとに、隣に設定ファイルを置く
- コマンドラインのフラグだけで設定する

## 決定

採用：「データのディレクトリの最上位に置く1つの TOML ファイルで、テーブルごとにモードを持つ」。すべてのテーブルの設定が1つのファイルにまとまり、既定と違うテーブルだけをそこに書けばよく、テーブルごとに合ったモードを持てるからである。

決まりは次のとおりである。

- 設定は、データのディレクトリの最上位にある1つのファイル `kortopi.toml` に書く。
- このファイルはなくてもよい。ファイルが挙げないテーブルは、モード `upsert` を使い、主キーを照合キーにする。
- 別の設定が要るテーブルは、スキーマとテーブルの名前を付けた節を持つ。

  ```toml
  [tables."facility.room_types"]
  key = ["code"]
  mode = "sync"
  ```

- `mode` は次のどれかである。
  - `insert`：足りない行を足す。更新も削除もしない。
  - `upsert`：足りない行を足し、違う行を更新する。削除はしない。これが既定である。
  - `sync`：さらに、宣言にない行を削除する。この削除には、ADR-0018 の削除の安全策がかかる。
- `key` は、照合キーの列を挙げる（ADR-0012）。
- モードはテーブルごとに設定し、環境ごとには設定しない。
- ファイルの書式は YAML ではなく TOML とする。理由は、ADR-0008 が行について挙げたものと同じであり、YAML では値の書き方によって型が変わるからである。

ファイルのほかのキーは、それを必要とする機能の実装のときに決める。

### 結果

- 良い点：どのテーブルもモード `upsert` を使い、主キーで照合するプロジェクトは、設定を何も書かずに済む。
- 良い点：既定では決して削除しないので、宣言にテーブルを足しても、うっかり行が消えることはない。
- 良い点：同じ実行の中で、都道府県の一覧を `sync` に、料金プランを `upsert` にできる。
- 良い点：レビューする人は、すべてのテーブルのモードとキーを1つのファイルで確かめられる。
- 悪い点：テーブルの設定がその行とは別の場所にあるので、CSV ファイルを読む人は、そのファイルがどう適用されるかを知るために `kortopi.toml` を開く必要がある。
- 悪い点：テーブルのモードは、どの環境でも同じである。開発環境を `sync`、本番を `upsert` にする、といった使い分けはできない。

### 確認の方法

設定を読む処理のテストで、既定、3つのモード、知らないモードのエラーを確かめる。
PostgreSQL 15〜18 に対する結合テストで、各モードが何を挿入・更新・削除するかを確かめる。
これらのテストは、plan と apply の実装とともに加わる。

## 選択肢の長所と短所

### データのディレクトリの最上位に置く1つの TOML ファイルで、テーブルごとにモードを持つ

- 良い点：設定がすべて1つのファイルにあり、テーブルは既定と違うときだけそこに現れる。
- 良い点：TOML の文字列は必ず引用符で囲む。そのため、`mode = "sync"` や `key = ["code"]` のような値が、書き方によって真偽値や数に変わることはない。
- 悪い点：設定がデータファイルとは別の場所にある。

### すべてのテーブルに1つのモードを、環境ごとに設定する

- 良い点：設定は1つで済む。
- 悪い点：テーブルによって必要が違う。完結した一覧は `sync` にしたいが、システムの稼働中に行が増えるテーブルは `upsert` のままにする必要がある。モードが1つだと、すべてのテーブルに安全なほうを強いることになる。

### データファイルの中のコメントで設定する

- 良い点：設定が、それが決める行のすぐ隣にある。
- 悪い点：CSV にはコメントの書き方がない。そのため、大きなテーブルのための書式である CSV のファイルが、設定を持てない。
- 悪い点：1つの SQL ファイルが複数のテーブルを宣言しうるので、コメントは、どのテーブルに当てはまるかも示す必要がある。

### データファイルごとに、隣に設定ファイルを置く

- 良い点：テーブルの設定が、その行のすぐ隣にある。
- 悪い点：ファイルの数が倍になり、設定がツリーのあちこちに散らばる。どのテーブルが行を削除するのかを1つのファイルで見られない。

### コマンドラインのフラグだけで設定する

- 良い点：管理するファイルがない。
- 悪い点：設定が宣言と一緒に保存されないので、kortopi を動かすスクリプトのすべてが、それを繰り返し書く必要がある。プルリクエストの計画と、デプロイで適用されるものが違ってしまうこともある。
- 悪い点：テーブルごとにフラグを渡すと、コマンドラインが長くなる。

## 補足

- [TOML 1.0.0](https://toml.io/en/v1.0.0)
- モード `sync` での削除の安全策は ADR-0018 に、ファイルとテーブルの対応は ADR-0014 にある。
