# ADR-0033: 依存を更新するボットのタイトルは、GitHub が伝える作成者で見分け、長さではなく形を検査する

## 背景と課題

プルリクエストはスカッシュマージされ、そのタイトルが `main` 上のコミットの件名になる。そのため CI は、タイトルをコミットメッセージと同じ決まりで検査する（ADR-0004）。
`make lint-pr-title` は、`commit-msg` フックの中身である `tools/scripts/commit-msg.sh` を実行する。
決まりが求めるのは、`<type>[(<scope>)][!]: <description>` の形であること、説明が小文字で始まり、ピリオドで終わらないこと、件名が72文字以内であることである。

Renovate は、依存を更新するプルリクエストを開く（ADR-0005）。そのタイトルは `build(deps): update module <module path> to v1.20.2 [security]` のような形である。
パスの前後の語が49文字を占めるので、パスが23文字を超えると、タイトルは上限を超える。
`go.mod` のファイルには、61文字に及ぶモジュールパスがある。
実際、パスが29文字のモジュールのセキュリティの修正は、タイトルの長さだけで CI に落ちた。タイトルは78文字で、ほかのチェックはすべて通っていた。

`renovate.json` でタイトルの語は変えられる。しかし、どの言い回しでもモジュールパスは残り、パスだけで72文字のうち61文字を占めることがある。
パスを落としたり切り詰めたりしたタイトルは、どのモジュールが変わったかを示さない。しかも、`main` 上のタイトルは、リリースノートを書く元になる履歴である（ADR-0030）。

検査に落ちたタイトルは、ADR-0005 が自分でマージさせる更新を止め、セキュリティの修正に人の手を待たせる。
しかも、その人はタイトルを直すだけでは済まない。CI が動くのは、プルリクエストを開いたとき、開き直したとき、プッシュしたときであり、タイトルを編集したときではないからである。

人が書く件名には上限を保ちながら、ボットの更新を形だけで通すには、どうすればよいか。

## 判断の基準

- 人が書く件名は、`commit-msg` フックでも CI でも72文字以内に収まる。
- ボットが開き、ほかのチェックをすべて通った更新は、モジュールのパスによらず、ADR-0005 が決めたとおりにマージされる。
- `main` 上のタイトルは、ボットのものも含めて、すべて Conventional Commit の形をしている。
- 上限から外すかどうかは、プルリクエストの作成者には設定できない事実で決まる。作成者が書くものでは決まらない。
- ワークフローの各ステップは `make` だけを呼び（ADR-0004）、ワークフローの式はシェルのコマンドの文面に入らない（ADR-0005）。

## 検討した選択肢

- ボットのタイトルを、GitHub が伝える作成者のログイン名で見分けて、長さの上限から外す
- `renovate.json` でタイトルを短くする
- すべてのタイトルについて、長さの上限を上げる
- ボットのものに見えるタイトル（`build(deps):` で始まるタイトルなど）を、上限から外す
- 長すぎるタイトルを、マージの前に人が手で短くする

## 決定

採用：「ボットのタイトルを、GitHub が伝える作成者のログイン名で見分けて、長さの上限から外す」。ボットのタイトルの長さはモジュールパスで決まり、どの言い回しでも短くならない。一方、作成者のログイン名は、プルリクエストについての事実のうち、作成者自身には書けないものだからである。

決まりは次のとおりである。

- 72文字の上限は、人が書く件名のためのものである。ボットのプルリクエストのタイトルも、ほかのタイトルと同じく形を検査する。検査するのは、type・scope・説明・先頭の文字の大小・最後の文字である。長さは検査しない。
- ボットとは、GitHub がログイン名を `renovate[bot]` と伝える作成者である。これは Renovate のアプリのログイン名である。CI は、ログイン名を `github.event.pull_request.user.login` から読む。この欄は、プルリクエストを開いたアカウントを表し、GitHub が設定する。プルリクエストの作成者が書くのはタイトル・説明・ブランチであり、このログイン名ではない。`[bot]` で終わるログイン名は GitHub App のものであり、人のログイン名は英字・数字・ハイフンだけからなる。そのため、人がアプリのログイン名でプルリクエストを開くことはできない。
- この例外は、ADR-0005 が信頼する以上にアプリを信頼するものではない。アプリは、すでにリポジトリへプッシュできる。
- `.github/workflows/ci.yml` のステップ `make lint-pr-title` は、ログイン名を環境変数 `PR_AUTHOR` に入れ、`PR_TITLE` と並べて `env:` の下で渡す。`run:` には式を書かない。ターゲットはその値を引用符で囲み、`--pr-author <login>` として `tools/scripts/commit-msg.sh` に渡す。スクリプトはそれを、ただの文字列として1文字ずつ `renovate[bot]` と比べる。make もシェルも、その値を評価しない。
- ログイン名が空のとき、`PR_AUTHOR` がないとき、ほかのログイン名のときは、上限がそのまま残る。`renovate` や `Renovate[bot]` のように、ボットのものに似ているだけのログイン名は、別のログイン名である。
- `commit-msg` フックは、`--pr-author` なしでスクリプトを呼ぶ。そのため、手元のコミットは、エージェントのコミットも含めて、すべて上限を保つ。
- `renovate.json` のタイトルの言い回しは変えない。
- `main` の件名に長さを求めるものは、ほかにない。リリースノートは GitHub がプルリクエストのタイトルから書き（ADR-0030）、リリースの道具は件名を読まない。マージのあとに `main` のコミットを検査するチェックもない。`main` では CI が `make check` と `make check-all` を実行するが、その `test-commit-msg` は、決まった見本でスクリプトを試すだけである。したがって、ボットの長い件名が `main` にあっても、何も壊れない。
- この記録は ADR-0004 を細かくする。ADR-0004 の表は、コミットメッセージとプルリクエストのタイトルに、1つのスクリプトで1つの決まりを与えている。スクリプトは引き続き両方を検査し、長さの上限は、ボットのタイトルを除くすべての件名に当てはまる。

### 結果

- 良い点：ボットの更新がタイトルの検査を通るかどうかは、形だけで決まる。そのため、モジュールのパスによらず、パッチの更新は自分でマージされ、セキュリティの修正は人を待たない。
- 良い点：ボットのタイトルの形をまねた人には、引き続き上限がかかる。例外は、タイトルの文面ではなく、GitHub が伝えるログイン名に従うからである。
- 良い点：人が書く件名は、フックでも CI でも上限を保つ。
- 悪い点：`main` の件名の一部は72文字を超える。コミットごとに1行を出すログでは、それらの件名が切れるか、折り返される。
- 悪い点：書き込みの権限を持つ人が、ボットの開いたプルリクエストのタイトルを編集しても、上限はかからない。作成者はボットのままだからである。
- 悪い点：スクリプトは、1つのアプリのログイン名を名指しする。ほかの更新の道具や、アプリの新しいログイン名には上限がかかる。新しい記録がそれを名指しするまで、その長いタイトルはチェックに落ちる。

### 確認の方法

- `make check` は `test-commit-msg`（`tools/tests/commit_msg_test.sh`）を実行する。このテストは、`renovate[bot]` の長いタイトルが通ることと、同じタイトルが、ほかの作成者・空の作成者・作成者なしでは落ちることを確かめる。ボットのものに似たログイン名でも落ちること、ボットのタイトルでも形が誤っていれば落ちることも確かめる。似たログイン名のうち2つは、`renovate[bot]` をシェルのパターンとして読むと一致する文字列である。さらに `make lint-pr-title` も実行し、`PR_AUTHOR` がないときと空のときに上限が残ること、`PR_AUTHOR` の文面がコマンドとして実行されないことを確かめる。
- `make check` は、`run:` の中にあるイベントの式を報告する `lint-actions-security` と、`lint-actions-policy` を実行する。
- レビューでは、`lefthook.yml` が `--pr-author` なしでスクリプトを呼ぶことを確かめる。CI がログイン名を `github.event.pull_request.user.login` から読み、プルリクエストの作成者が書くものからは読まないことも、レビューで確かめる。

## 選択肢の長所と短所

### ボットのタイトルを、GitHub が伝える作成者のログイン名で見分けて、長さの上限から外す

- 良い点：ログイン名は GitHub から来る。プルリクエストの作成者は、アプリのログイン名を名乗れない。
- 良い点：どのタイトルも、引き続き形を検査する。
- 悪い点：上限が、`main` のすべての件名には当てはまらなくなる。

### `renovate.json` でタイトルを短くする

- 良い点：スクリプトに例外を置かずに、どのタイトルも上限に収まる。
- 悪い点：どの言い回しでもモジュールパスは残る。パスが61文字なら、type・動詞・バージョンに残るのは11文字である。
- 悪い点：パスの全体がないタイトルは、どのモジュールが変わったかを示さない。末尾の要素が同じモジュールパスもありうる。

### すべてのタイトルについて、長さの上限を上げる

- 良い点：スクリプトは、どの作成者も同じように扱える。
- 悪い点：最も長いモジュールパスが収まる上限は110文字ほどであり、それでは人が書く件名を短く保てない。しかも、もっと長いパスが現れれば、上限をまた上げることになる。

### ボットのものに見えるタイトル（`build(deps):` で始まるタイトルなど）を、上限から外す

- 良い点：スクリプトは、タイトルのほかに入力を必要としない。
- 悪い点：そのようなタイトルは誰にでも書ける。そのため、それをまねた作成者なら誰でも上限から外れる。

### 長すぎるタイトルを、マージの前に人が手で短くする

- 良い点：決まりは、どのタイトルにも同じままである。
- 悪い点：自分でマージされるはずのパッチの更新（ADR-0005）が、代わりに人を待つ。セキュリティの修正も同じである。
- 悪い点：タイトルを編集しても CI は動かない。そのため、短くしたタイトルでチェックを通すには、CI をもう一度動かす必要もある。

## 補足
