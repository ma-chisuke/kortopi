# ADR-0024: 計画は1つのトランザクションで立ててロールバックし、違うものだけを出力する

## 背景と課題

ADR-0016 は、計画が対象のデータベースを読み、そのテーブルを何も変えず、スキーマの変更を待つテーブルと列に印を付けることを決めた。
2つの細部は実装に任せていた。その印の文言と、まだない列を含む宣言の行をどう読み込むかである。
ADR-0021 はサブコマンド・フラグ・終了コードを決め、`plan` の出力のそれ以外の部分は実装に任せた。

計画は、テスト用のデータベースと同じくらい本番のデータベースに対しても実行する。
計画はそこに一時テーブルを作るので（ADR-0009）、書き込みのできるセッションが要る。しかも、サービスが行を変え続けている間に、多くのテーブルを順に読む。
セッションの動かし方によって、計画がデータベースの1つの状態を見るのか複数の状態を見るのかが決まる。途中で止まったときに何かが残りうるかどうかも決まる。
セッションのロールが何を見られるかも、同じくらい重要である。行単位セキュリティのポリシーのためにロールから見えない行は、計画には存在しない行のように見える。

出力を読むのは3者である。プルリクエストでレビューする人、端末の前の人、終了コードだけを見る定期実行である（ADR-0021）。
宣言は数十のテーブルを持ちうるが、プルリクエストが変えるのは、たいてい1つのテーブルの数行である。
出力は、kortopi が比べたもの・まだ比べられないもの・探さなかったものも、読む人に伝える必要がある。
CI のログはチームの中で広く読まれることが多いので、kortopi が出力するものはパスワードを含んではならない。

計画は、データベースの中でどう動き、何を出力するか。

## 判断の基準

- 計画は、失敗したときも割り込まれたときも、データベースを元のまま残す（ADR-0010、ADR-0016）。
- 計画のすべてのテーブルを、データベースの同じ状態と比べる。
- 計画に要る権限は、スキーマに対する `USAGE` を除けば ADR-0016 が挙げたものだけであり、足りないものをはっきり伝える。
- 計画は、宣言したテーブルのすべての行を見るか、失敗する。
- kortopi が出力するものは、パスワードを繰り返さない。
- 宣言のテーブルが多くても、レビューする人は変わる行をすぐに見つけられる。
- 出力のどの行も意味が1つに決まる。値を NULL と取り違えることはなく、件数が、していない検査をしたように見せることもない。
- 誤りは、1回の実行でできるだけ多く報告する。

## 検討した選択肢

- 計画全体で1つのスナップショットを使い、違うものをテキストで報告する
- テーブルごとにトランザクションを分け、違うものをテキストで報告する
- 計画全体で1つのスナップショットを使い、宣言したすべてのテーブルを報告する
- 計画全体で1つのスナップショットを使い、JSON で報告する

## 決定

採用：「計画全体で1つのスナップショットを使い、違うものをテキストで報告する」。すべてのテーブルをデータベースの1つの状態と比べられ、何も残さないからである。また、レビューする人には変わる行だけを示し、要約ですべてのテーブルを数え上げられる。

決まりは次のとおりである。

セッションについて。

- 計画は接続を1つ開く。環境が別の値を設定しない限り、`application_name` は `kortopi` にする。すべてを分離レベル `REPEATABLE READ` の1つのトランザクションで実行するので、どの問い合わせも同じスナップショットを見る。トランザクションは最後にロールバックする。ADR-0023 の設定は、このトランザクションの中で固定する。
- 宣言したテーブルごとに、一時テーブルをセーブポイントの中で `ON COMMIT DROP` として作り、そのテーブルを比べ終えたらすぐにセーブポイントをロールバックする。データベースの中にある宣言の行は、常に1つのテーブルの分だけである。
- ふつうのテーブルは `ONLY` を付けて読む。そのため、そのテーブルを継承するテーブルの行は、そのテーブルの行に数えない。パーティションテーブルは全体を読む。宣言した名前がビュー・外部テーブル・シーケンスなど、テーブル以外のものを指していればエラーである。
- 割り込みがあると、トランザクションをロールバックして接続を閉じ、計画は `interrupted: the plan was stopped, and the database is as it was` で終わる。
- 計画には、プライマリの書き込みのできるセッションと、データベースに対する `TEMPORARY` 権限が要る。宣言したテーブルのそれぞれについて、そのスキーマに対する `USAGE` と、宣言した列に対する `SELECT` も要る。`SELECT` は、テーブルに対するものでも、それらの列だけに対するものでもよい。ADR-0016 は `TEMPORARY` と `SELECT` を挙げている。この記録は、スキーマに対する `USAGE` を加える。ロールがそもそもテーブルへ届くには、これが要るからである。また、計画はほかの列を読まないので、宣言した列に対する `SELECT` で足りることにする。
- kortopi は、テーブルを読み込む前にこれらをカタログで検査し、足りないものごとに専用のエラーを出す。一時テーブルを作れないセッションには、エラーを1つ出す。エラーはデータベースと理由（スタンバイ、読み取り専用のトランザクション、`TEMPORARY` のないロール）を示し、計画に何が要るかを伝える。`USAGE` や `SELECT` がなければ、スキーマかテーブルとロールを示し、何を与えればよいかを伝えるエラーを出す。
- 宣言したテーブルの行単位セキュリティのポリシーがロールにかかるときは、テーブルとロールを示すエラーにする。これもカタログで見つける。ポリシーが隠す行は、計画からは存在しないように見える。計画はそれらを挿入する行として示し、更新する行や削除する行としては決して示さない。そして、その挿入を適用すると照合キーで失敗する。`BYPASSRLS` を持つロールと、行単位セキュリティを強制していないテーブルの所有者は、すべての行を見られるので計画を立てられる。セッションは `row_security` も off に固定する（ADR-0023）。そのため、ポリシーが絞り込む問い合わせは、少ない行を返さずに失敗する。

作業とエラーの順番について。

- kortopi は、まず `kortopi.toml` と宣言のファイルを読み、設定を宣言したテーブルと照らし合わせ、`--schema` のスキーマに絞る。接続するのはそのあとである。そのため、ファイルの誤りは、データベースなしに報告する。ファイルを並べた順で最初の誤りが、実行を止める。
- 次に、宣言したすべてのテーブルについてまとめてカタログを読み、テーブルごとに照合キー・宣言した列・モードを検査する。どの行を読み込むよりも前に、すべてのテーブルのすべての誤りを1行ずつまとめて報告する。そのため、1回の実行ですべてがわかる。
- そのあと、計画の順にテーブルを1つずつ読み込んで比べる。最初のエラーが、計画を止める。権限の不足、行単位セキュリティ、誤った値、宣言の行の誤り（ADR-0023）、データベースからのほかのエラーがこれにあたる。こうしたエラーは接続やロールから来ることが多く、どのテーブルでも繰り返しうる。それに、ほかのテーブルを読み込んでも、失敗した計画のために対象のデータベースの仕事を増やすだけである。

スキーマの変更を待つテーブルと列について（ADR-0016）。

- データベースにない宣言したテーブルは、`<table>: known after the schema is applied (<n> declared rows)` の1行で示す。SQL ファイルなら、kortopi がその `VALUES` の行を数える。CSV ファイルは、すべての列が `text` の一時テーブルに読み込む。そのため、その書式は PostgreSQL が読んで確かめる。
- テーブルにない宣言した列は、`text` として読み込み、比べずに、`column <name>: known after the schema is applied` と示す。そのテーブルのほかの列は、ふだんどおりに比べる。ADR-0009 は、そうした列は「読み込めない」としている。実際には、行のほかの列を比べられるように、テキストとして読み込む。
- SQL ファイルの値のキャストがまだない型を指すときは、PostgreSQL のエラーで読み込みが失敗する。kortopi はそのエラーにヒントを足す。スキーマの変更がその型を足すなら、先にスキーマを適用するか、キャストを外すように伝える。
- 照合キーに適用待ちの列があればエラーである。スキーマを適用するまで、どの行も照合できないからである。
- `--exit-code` があるときは、適用待ちのテーブルや列も差分に数える（ADR-0021）。

出力について。

- 計画は標準出力に出す。エラーは、1つのエラーにつき1行ずつ、`kortopi: <message>` として標準エラー出力に出す。
- 利用者が求めたヘルプは、標準出力に出して 0 で終わる。`kortopi help plan`・`kortopi plan --help`・`-h` がこれにあたる。誤ったフラグは、エラーと短い使い方を標準エラー出力に出して 1 で終わる。フラグのエラーは、ヘルプと同じくフラグを2つのダッシュ付きで示し、入力された値を決して繰り返さない。
- `--host`・`--user`・`--dbname` と、環境変数 `PGHOST`・`PGUSER`・`PGDATABASE` は名前を受け取り、接続文字列を拒む。接続文字列とは、`://` か `=` を含む値である。libpq はそうした値を名前として読み、接続に失敗したときのエラーがそれをパスワードごと繰り返してしまう。接続文字列に見える引数は、繰り返さずに「a connection string」と示す。
- 示すものがあるテーブルには、ひとまとまりの行を出す。見出し `<schema>.<table> (<mode>, key: <columns>)`、適用待ちの列ごとの行、挿入（`+`）・更新（`~`）・削除（`-`）する行ごとの行、件数の行である。適用待ちの列があって変わる行がないテーブルは、`no changes` と示す。
- 挿入する行はキーと比べる列の値を、更新する行はキーと変わる列だけを `column: old -> new` として、削除する行はキーを示す。種類ごとに、行は照合キーで並べる。並べ方は、キーの型の順である。
- 変更がなく、適用待ちのものもないテーブルは出力しない。末尾の要約は、種類ごとの行の数と計画のすべてのテーブルの数を示す。適用待ちのテーブルと列があればそれを挙げ、示さなかった変更のないテーブルの数も伝える。
- テーブルの件数の行は、そのモードが求める種類だけを示す。`insert` なら挿入、`upsert` なら挿入と更新、`sync` なら3つすべてである。そうしないと、削除をしないモードでも、kortopi が削除する行を探してもいないテーブルに `0 to delete` と出てしまう。要約は、3つの種類すべてを、テーブルの合計として示す。
- 示すものがない計画は、`No changes. The database matches the declaration.` の1行を出す。
- 値は PostgreSQL が出力するとおりに示し、NULL は `NULL` と示す。空の値、`NULL` と読める値、空白・`=`・引用符・表示できない文字を含む値は、Go のエスケープを使って二重引用符で囲む。行は、2つの空白で区切った `column=value` の組の並びである。引用符がなければ、値の中の空白や `=` は次の組と区別できず、空文字列は見えなくなり、文字列の `NULL` は NULL と見分けられない。
- スキーマ・テーブル・列の名前も、出力の形に使う文字を含むときは、同じように二重引用符で囲む。
- 出力は、記号を ASCII に限った色のないテキストであり、kortopi は端末かどうかを調べない。変更の種類は印 `+`・`~`・`-` が表す。端末でも、CI のログでも、プルリクエストのコメントでも、同じバイトが現れる。

### 結果

- 良い点：計画はデータベース全体の1つの状態を見る。そのため、互いを参照する2つのテーブルを、同じ時点で比べられる。
- 良い点：計画のあとには何も残らない。エラーのあとでもロールバックがすべての一時テーブルを消し、接続が切れればサーバーが同じことをする。
- 良い点：1回の実行で、すべてのテーブルのキー・列・モードの誤りをすべて報告し、ファイルの誤りはデータベースなしに報告する。
- 良い点：レビューする人は、変わるテーブルと行だけを読めばよい。変更なしに比べたテーブルの数は、要約が伝える。
- 良い点：出力の行は、2通りには読めない。引用符で囲んだ値・NULL・空文字列は見た目が違い、削除の件数は kortopi が削除する行を探したところにだけ現れる。
- 良い点：ポリシーが隠した行を、計画が挿入する行として示すことはない。計画は失敗し、どのロールなら計画を立てられるかを伝える。
- 良い点：パスワードを誤った場所に渡しても、CI のログに残る kortopi の出力がそれを繰り返すことはない。
- 悪い点：計画の間ずっとスナップショットを持つ。その間、対象のデータベースでは古い行のバージョンの掃除が待たされる。
- 悪い点：計画はデータベースからの最初のエラーで止まる。そのため、3つのテーブルに誤った値がある宣言を直すには、3回の実行がかかる。
- 悪い点：適用待ちの列と適用待ちのテーブルの値は、スキーマを適用するまで、どの型でも検査されない。
- 悪い点：行単位セキュリティのあるテーブルの計画を立てるには、ロールに `BYPASSRLS` が要るか、ロールがテーブルを所有する必要がある。これは読むだけの権限を超える。
- 悪い点：接続先を1つの URL で持っているチームは、それを `--dbname` や `PGDATABASE` に渡せず、libpq の環境変数に分ける必要がある（ADR-0021）。
- 悪い点：テキストは人に向けたものである。行を取り出したい道具は、ADR-0020 の SQL の出力を待つか、テキストを解析する必要がある。

### 確認の方法

- `internal/plan` のレンダラーのゴールデンテスト（`TestRender` と `internal/plan/testdata/` のファイル）で、出力を固める。同じパッケージの単体テストで、検査の順番と、すべてのテーブルの誤りをまとめて報告することを固める。
- `cmd/kortopi` の単体テストで、フラグ・標準出力のヘルプ・終了コード・標準エラー出力のエラー・作業の順番・割り込みのメッセージを確かめる。`TestNoSecretInOutput` は、環境変数にパスワードを置き、フラグ・引数・環境変数に接続文字列を置いてコマンドを実行する。出力がそのどちらかを繰り返せば、このテストは失敗する。
- `make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで、セッションを確かめる。`internal/postgres` では、`TestPlanLeavesNothingBehind` でカタログと行が変わらないことを確かめる。`TestPlanWithLeastPrivileges` で、ADR-0016 の権限で足りることを確かめる。`TestPlanWithoutTemporaryTables` で、読み取り専用のトランザクションと `TEMPORARY` のないロールのエラーを確かめる。`TestPlanWithoutSelect` で、`USAGE` と `SELECT` がないときのエラーと、宣言した列に対する `SELECT` で足りることを確かめる。`TestPlanWithRowLevelSecurity` で、行単位セキュリティのエラーと、`BYPASSRLS` を持つロールと所有者なら計画を立てられることを確かめる。`TestCastToMissingType` で、ない型のヒントを確かめる。ほかのテストで、適用待ちの列、継承とパーティションのテーブル、テーブルでないものを確かめる。`cmd/kortopi` では、`TestPlanCommand` がコマンド全体を各バージョンに対して実行し、出力と終了コードを比べる。
- スタンバイ（テスト用のサーバーがない）と Aurora PostgreSQL（ADR-0019）を対象にするテストは、まだない。

## 選択肢の長所と短所

### 計画全体で1つのスナップショットを使い、違うものをテキストで報告する

- 良い点：どのテーブルも1つの状態と比べ、1回のロールバックでデータベースを元のまま残す。
- 良い点：出力には、レビューする人が読むべきものだけがある。
- 悪い点：長い計画は、実行の間ずっと1つのスナップショットを持つ。

### テーブルごとにトランザクションを分け、違うものをテキストで報告する

- 良い点：トランザクションの1つ1つが短い。
- 悪い点：テーブルを違う時点で比べることになる。2つのテーブルの間にサービスが行を変えると、1つの計画の中で関係するテーブルどうしが食い違いうる。要約も、データベースの違う状態から得た件数を足し合わせることになる。

### 計画全体で1つのスナップショットを使い、宣言したすべてのテーブルを報告する

- 良い点：比べたテーブルが、出力にすべて現れる。
- 悪い点：40のテーブルのうち1つの行を1つだけ変えるプルリクエストでも、変更なしと述べるまとまりが39個並ぶ。その中で、変更は見落としやすい。

### 計画全体で1つのスナップショットを使い、JSON で報告する

- 良い点：道具は、テキストを解析せずに行を読める。
- 悪い点：レビューする人は計画をプルリクエストで読むが、そこでは JSON は長く、目で追いにくい。
- 悪い点：道具のための書式は、変えにくい約束になる。しかも、道具が何を必要とするかを kortopi はまだ知らない。ADR-0021 の `--format` には、あとから書式を足す余地がある。
