# ADR-0043: 割り込まれた実行の文はサーバーでキャンセルし、コミットの応答を待つのをやめるのは2度目の割り込みか接続が死んだときだけにする

## 背景と課題

ADR-0026 は、検査や書き込みの間に割り込まれた apply をロールバックし、何も変わらなかったと伝える。
コミットが始まったら、割り込みでは止めない。その結果を知るためである。応答の返らないコミットは、結果の分からない apply になる。
計画と書き出しも、割り込まれるとロールバックする。

kortopi は、割り込み（SIGINT や SIGTERM）をコンテキストのキャンセルに変え、2度目の割り込みではその場でプロセスを終えていた。
コンテキストがキャンセルされると、ドライバーの pgx は既定ではソケットに期限を設定し、読むのをやめ、裏で接続を閉じる。
キャンセル要求はその裏の処理から送られるが、kortopi が終了すると、その処理も途中で断ち切られる。
そのためサーバーは文を続け、そのロックを持ち続ける。apply どうしを直列にするロックもその1つである。文がみずから終わるまでそれは続く。100万行の更新では、kortopi が終了してから 88 秒と 132 秒続いた。更新が待っていた行をほかのセッションが手放すまで続いた例もある。
その間に kortopi は、何も変わらなかったと伝えていた。次の apply は kortopi のロックを待つか、存在しない「ほかの apply」のせいにするエラーで止まった（issue 42）。

コミットには逆の問題がある（issue 44）。
コミットが応答を待つ間に kortopi とサーバーの間のネットワークが切れると、kortopi は何も出力せずに待つ。キープアライブはランタイムの既定のままで、15 秒後から 15 秒おきに 9 回プローブするので、気付くまでに 150 秒かかる。
1度目の割り込みは黙って後回しにされ、2度目の割り込みは、何のメッセージも出さずに kortopi を終わらせた。変更はコミットされていたにもかかわらずである。

割り込まれた実行はサーバーで何をし、何を伝えるのか。そして、コミットを待つのはどう終わるのか。

## 判断の基準

- 割り込みのあと、サーバーでの kortopi の仕事は、kortopi が終了する前に終わり、そのロックもなくなる。そうでなければ、終わっていないかもしれないことと、その終わらせ方を kortopi が伝える。
- kortopi は、偽りかもしれないときに何も変わらなかったとは言わない。それぞれの場合に分かっていることを伝える。
- 割り込みだけでコミットの結果が分からなくなることはない。kortopi は、割り込みによってメッセージなしに終わることはない。
- サーバーに届かなくなった接続は、決まった時間のうちに待つのを終わらせる。遅くても応答するサーバーは待つ。
- 割り込みのあとに待つのは短くする。ジョブをキャンセルするジョブの実行役は、たいてい最初のシグナルから数秒後にプロセスを強制終了するからである。
- ドライバーが用意する部品を使い、依存を増やさない。

## 検討した選択肢

割り込みのときに動いている文については、次の選択肢を検討した。

- ドライバーが送るプロトコルのキャンセル要求と、ロールバックを、割り込みから5秒以内に行う
- これまでどおり接続を閉じる
- 2つ目の接続から `pg_cancel_backend` か `pg_terminate_backend` を呼ぶ
- サーバーの `client_connection_check_interval` に任せる

コミットの応答を待つことについては、次の選択肢を検討した。

- 黙ったサーバーに約 30 秒で気付く TCP のキープアライブと、キャンセル要求を送らずに待つのをやめる2度目の割り込み
- フラグで与えるコミットの時間の上限
- 2度目の割り込みでコミットにキャンセル要求を送る
- `TCP_USER_TIMEOUT`

## 決定

採用：「ドライバーが送るプロトコルのキャンセル要求と、ロールバックを、割り込みから5秒以内に行う」。こうすればサーバーは、割り込みを次に確かめる時点で文を終え、kortopi はそれを知ることができる。もう1つは「黙ったサーバーに約 30 秒で気付く TCP のキープアライブと、キャンセル要求を送らずに待つのをやめる2度目の割り込み」である。こうすればコミットはサーバーが応答する限り待ち、待つのをいつやめるかは kortopi を動かす人やジョブが決める。そのときのメッセージは、結果について正しいことを伝える。

決まりは次のとおりである。

コミットの前の割り込み：

- 1度目の割り込みは、実行のコンテキストをキャンセルする。するとセッションは、プロトコルのキャンセル要求をその場で送る。送り先はセッション自身のアドレスへの新しい接続で、サーバーがセッションに与えたプロセス ID と秘密鍵を添える。そして応答を読むのに、5秒後の期限を付ける。これは pgx のハンドラー `CancelRequestContextWatcherHandler` を、遅延なしで使ったものである。
- サーバーは、割り込みを次に確かめる時点で文を終え、エラーで応答する。その時点は、スキャン・ソート・ロックの待ち・`pg_sleep` の中なら数ミリ秒のうちに来る。kortopi はそれからトランザクションをロールバックし、接続を閉じる。ロールバックはトランザクションのロックをすべて解放し、kortopi のロックもその中に含まれる。サーバーのプロセスは接続とともに終わる。
- 上限は割り込みから5秒であり、文が終わるのとロールバックとを合わせた時間である。それまでに応答しないサーバーは、ほかのことで手一杯か、届かないところにある。この上限なら、最初のシグナルから数秒待つジョブの実行役より先に終わる。
- サーバーが応答し、ロールバックが返ってきたときのメッセージは、ADR-0026 のものである。`kortopi: interrupted: the apply was stopped` と `kortopi: nothing was changed` であり、計画と書き出しの行もこれまでどおりである。
- そうでなかったときは、kortopi は最後の行の前にそのことを標準エラー出力に書き、終了コード 1 で終わる：

  ```text
  kortopi: interrupted: the apply was stopped
  kortopi: the server did not confirm within 5s that the session of the apply ended: its statement may still run on the server and hold its locks until the server notices that kortopi has gone, although its transaction can no longer commit: find the session in pg_stat_activity, where application_name is "kortopi" and pid is 386, and end it with pg_cancel_backend(386), or with pg_terminate_backend(386) if it does not end
  kortopi: nothing was changed
  ```

- この「nothing was changed」は正しい。kortopi は `COMMIT` を送っておらず、接続も閉じたので、トランザクションはもうコミットできず、セッションが終わるときにサーバーがロールバックする。分からないのはそれがいつかであり、その前の行がそのことを伝える。
- プロセス ID は、セッションの各トランザクションの最初の問い合わせで `pg_backend_pid()` が返すものである。接続の開始時に受け取るプロセス ID は使わない。トランザクションモードのコネクションプーラーは、それをサーバーから受け取らないからである。まだ読んでいないトランザクションは、`application_name` だけで示す。計画と書き出しも、「apply」の代わりに「plan」か「export」として同じことを伝え、計画はこれまでどおり、データベースが元のままであることも伝える。
- 割り込みのあとに始まるはずの文は送らず、ロールバックはセッションを閉じる処理に任せる。その処理は自分のコンテキストを持つ。`BEGIN` やロールバックが応答なしに失敗すると、pgx は接続を壊してしまい、終わっていたセッションが、kortopi には確かめられないセッションになるからである。
- 別の apply を待つ間も同じである。待つのは、それ専用のトランザクションの中の文だからである。

コミット：

- コミットが始まってからは、kortopi からキャンセル要求を送らない。同期スタンバイを待つ間のキャンセルは、サーバーにコミットをローカルで済んだものとして報告させ、遅らせたトリガーの間のキャンセルはコミットをロールバックさせる。結果がコミットのしていたことで決まってしまい、それは割り込む人には見えない。セッションは、キャンセル要求なしにコミットを待つのを終える。さらにセッションの接続処理は、キャンセル要求のための接続を拒む。pgx は、接続を見捨てるときにキャンセル要求を送るからである。
- コミットが始まったあとの1度目の割り込みは後回しにし、kortopi はその場でそのことを標準エラー出力に書く：

  ```text
  kortopi: the commit has started, so the interrupt does not stop it: waiting for the answer of the database, so that the outcome is known: interrupt again to give up the wait
  ```

- 2度目の割り込みは、待つのをその場で終える。セッションは接続に過ぎた期限を設定し、kortopi は応答のないコミットのメッセージを原因とともに出力して、終了コード 1 で終わる：

  ```text
  kortopi: commit the apply: the commit got no answer from the database, so it is not known whether the changes were made: run kortopi plan to see the state of the database (cause: a second interrupt gave up the wait for the answer)
  ```

- そのあとサーバーはコミットを済ませるか、遅らせた制約が失敗すればロールバックする。どちらだったかは `kortopi plan` が示す。
- kortopi は、最初の2回の割り込みで終わることはない。2度目のあとはシグナルを受け取るのをやめるので、3度目はシグナルの既定の動作でプロセスをその場で終える。誰も読まない標準出力のように、ほかの理由で終わらない実行から抜け出す手段である。
- コミットの前の2度目の割り込みも、ロールバックを上限まで待つのをその場で終える。そのときのメッセージは、前半が `kortopi stopped waiting for the server to end the session of the apply` になる。
- 2度目の割り込みが意味するのは「待つのをやめる」であり、「キャンセルしない」ではない。そのため、1度目の直後に来ても、キャンセル要求が送られるのを妨げない。pgx は接続を見捨てるときに裏でキャンセル要求を送る。kortopi は終了する前に、それを最長1秒待つ。プロセスが終わると、その送信も断ち切られるからである。届くところにあるサーバーなら、数ミリ秒で受け取る。コミットが始まってからは、上で述べたとおり、kortopi からキャンセル要求を送らない。

キープアライブ：

- セッションの TCP 接続は、通信のない状態が 10 秒続くとサーバーにプローブを送り始め、5 秒おきに送り、応答のないプローブが4回で接続を落とす。応答しなくなったサーバーには、どの段階でも 30 秒の沈黙のあとに気付き、コミットは結果の分からないメッセージで終わる。ランタイムの既定なら 150 秒かかり、kortopi が設定しなければ2時間かかるシステムもある。
- プローブに応答するサーバーは、コミットがどれほど長くかかっても待つ。遅い同期スタンバイを待つときがそうである。コミットは進行中であり、2度目の割り込みがそこから抜け出す手段である。
- プローブの費用は、通信のない接続で5秒おきに数バイトである。30 秒より短い切断では、実行は終わらない。
- この設定は、Go の接続処理と同じく、できる範囲で行う。システムが拒む値はシステムのままにし、キープアライブは少なくとも有効にし、接続はそのまま使い、何も出力しない。10 バージョン 1709 より前の Windows はプローブの回数の設定を拒み、Linux と macOS は数百万秒の待ち時間を拒む。
- libpq は、`keepalives`・`keepalives_idle`・`keepalives_interval`・`keepalives_count` の設定を接続文字列かサービスファイルから読み、それらの環境変数は持たない。pgx もサービスファイルからそれらを読むが、意味を知らないので、セッションの設定としてサーバーに渡してしまい、サーバーはそれを拒む。kortopi はそれらを取り出し、libpq と同じように適用する。`keepalives` は 0 ならキープアライブを止め、それ以外なら有効にする。ほかの設定の 0 はシステムの値を保ち、libpq が 0 とみなす負の値も同じである。整数でない値は誤りである。システムの値は実際に保たれる。kortopi は pgx の既定の接続処理と同じように接続するが、Go のキープアライブは止めておくからである。止めなければ、Go がまずすべてのソケットに 15 秒・15 秒・9 回を設定してしまう。`tcp_user_timeout` は、ドライバーの扱いのまま、接続のサーバー側についてのサーバーの設定である。
- キープアライブがプローブするのは、確認応答を待つデータのない接続だけである。kortopi が `COMMIT` を送った瞬間、サーバーが確認応答する前に切れたときは、待つのはシステムの再送に委ねられ、Linux では何分も続くことがある。`TCP_USER_TIMEOUT` ならそれも抑えられるが、Go の `net` パッケージはそれを設定せず、Linux にしかない。
- テストではネットワークを切れないので、手で1度だけ測った。Linux 向けのバイナリをコンテナで動かし、別のコンテナの PostgreSQL 18 と専用の Docker ネットワークでつないだ。apply のコミットは、存在しない同期スタンバイを待つようにした。クライアントを `docker network disconnect` してから、サーバーには待つのをやめさせたので、サーバーはコミットした。kortopi は、切断から 30.0 秒後に、原因 `unexpected EOF` とともに結果の分からないメッセージを出力し、終了コード 1 で終わった。ランタイムのキープアライブの設定なら、同じ実行は約 150 秒待ったはずである。こちらは測っていない。

kortopi が受け入れる、分かっている制限：

- キャンセル要求は、その文が終わったあとに届いて、次の文に当たることがある。`BEGIN` や、閉じるときの `ROLLBACK` である。pgx はこれを避けるために、キャンセル要求のたびに 100 ミリ秒待つ。kortopi も、割り込みのあとはロールバックのほかに文を送らない。それでもこれが起きると、kortopi はセッションの終わりを確かめられず、終わっているのに、まだ動いているかもしれないと伝える。メッセージは「かもしれない」と言う。
- `COMMIT` を接続へ書く直前の一瞬に2回の割り込みが来ると、コミットはサーバーに届かない。それでも kortopi は結果が分からないと伝える。送られたコミットと見分けられないので、確かめるよう利用者に促す側を選ぶ。

トランザクションモードのコネクションプーラーを通すとき：

- キャンセル要求は接続のアドレス、つまりプーラーへ送られ、プーラーはそのときクライアントに仕えているサーバーとの接続にそれを転送する。ADR-0026 と同じく、このリポジトリのテストはプーラーを通さない。

これは ADR-0026 の次の決まりを細かくする。

- 「エラーがあったとき、検査や書き込みの間に割り込まれたとき、コミットせずにセッションが閉じたときは、トランザクションをロールバックする。そして、標準エラー出力の最後の行で、何も変えなかったと伝える」。割り込まれたとき、kortopi はまずサーバーに文のキャンセルを求める。セッションが終わったという応答が5秒以内にサーバーからなかったときは、最後の行の前にそう伝える。
- 「コミットの答えが届かないとき（接続が切れた、時間切れになった、サーバーがセッションを終えたとき）、apply は変更がなされたかどうかを知ることができない」。kortopi のキープアライブはそうした時間切れの1つであり、2度目の割り込みもそうである。そのメッセージはそれを伝える。
- 「コミットが始まったら、割り込みでは止めない。その結果を知るためである」。kortopi は割り込みが来たときにそう伝え、2度目の割り込みはコミットではなく、待つことをやめる。

### 結果

- 良い点：割り込まれた実行は、普通は数ミリ秒のうちにサーバーでの仕事を終え、ロックもなくなる。そのため次の apply は、もう誰のためにも働いていないセッションを待たない。
- 良い点：kortopi が「何も変わらなかった」と言うときは、どの場合もそれが正しい。その応答がサーバーからなかったときは、何がまだ動いているかもしれないかと、その終わらせ方を、`pg_stat_activity` が示すプロセス ID とともに伝える。
- 良い点：コミットの間の割り込みにはその場で答え、2度目の割り込みは、何も言わずに死ぬのではなく、結果が分からないというメッセージで kortopi を終える。
- 良い点：切れたネットワークは、コミットの外でも、約 30 秒の沈黙のあとに kortopi の待ちをすべて終わらせる。
- 悪い点：サーバーが応答しないとき、割り込みが終わるまでに最長5秒かかる。以前はその場で終了していた。
- 悪い点：30 秒より長く切れてから戻るネットワークでは、実行は結果の分からないまま終わる。ランタイムの既定なら 150 秒待ち、応答を受け取れたかもしれない。
- 悪い点：まさにコミットの瞬間の切断はシステムの再送に委ねられ、何分も続くことがある。
- 悪い点：キャンセル要求にはサーバーへの2つ目の接続が要る。それを開けないときは、実行は上限まで待ち、セッションがまだ動いているかもしれないと伝える。

### 確認の方法

- `cmd/kortopi` の単体テストは、偽物のセッションでシグナルとメッセージを確かめる。`TestWatchInterrupts`・`TestInterruptedSessionNotEnded`・`TestCommitInterrupted`、そして `TestRunApplyInterruptedUnknownOutcome` である。
- `internal/postgres` の単体テストは、キープアライブ、その libpq の設定、それを持つサービスファイルを確かめる（`TestKeepAliveConfig`・`TestKeepAliveFromTheServiceFile`）。`TestDialKeepAlive` はソケットのオプションを読み、コミットの間に拒まれる接続も確かめる。まだ動いているかもしれないセッションのメッセージは `TestNotEnded` が、待つのをやめたコミットの原因は `TestCommitGivenUp` が確かめる。
- `make check-all` で PostgreSQL 15 から 18 に対して動く結合テストは、2つ目の接続で `pg_stat_activity` と `pg_locks` を読む：
  - `internal/postgres` の `TestInterruptEndsTheStatementOnTheServer`：長い更新の間、行ロックを待つ間、別の apply を待つ間に割り込む。セッションは終わりを確かめ、そのプロセスはロックを持たずに消え、行は何も変わらない。`TestInterruptWithoutAnAnswer`：キャンセルのエラーを捕まえてまた眠るトリガーを使う。セッションは上限のあと、または2度目の割り込みで待つのをやめ、そのエラーはまだ動いているプロセスを挙げる。`TestInterruptDuringTheCommit`：遅らせたトリガーでアドバイザリロックを待つコミットは、1度目の割り込みでは止まらない。2度目は結果の分からないまま待つのを終え、プロセスはサーバーで待ち続け、ロックが空くとコミットは終わる。`TestKeepAliveOfTheSession`：セッションのソケットは、kortopi のキープアライブか libpq の設定によるものを持ち、その設定はサーバーに届かない。`TestSecondInterruptStillCancels`：行ロックを待つ間に2回の割り込みが続けて来る。キャンセル要求は Close が戻る前に送られ、行はまだ持たれたままでも、文はサーバーで終わる。
  - `cmd/kortopi` の `TestInterruptedApplyCommand` と `TestInterruptedCommitCommand` は、同じ3つの場合とコミットの2つのメッセージでコマンドを動かす。
- ネットワークを切るテストはなく、コネクションプーラーを通すテストもない。

## 選択肢の長所と短所

### ドライバーが送るプロトコルのキャンセル要求と、ロールバックを、割り込みから5秒以内に行う

- 良い点：`psql` と libpq が問い合わせをキャンセルするやり方であり、セッションのサーバーのプロセスに直接届き、セッションはロールバックに使えるまま残る。
- 良い点：pgx が、キャンセルされたコンテキストのハンドラーとして用意している。
- 悪い点：短い2つ目の接続を開く。キャンセルのエラーを捕まえる文は続く。

### これまでどおり接続を閉じる

- 良い点：すぐに終わる。
- 悪い点：サーバーが閉じた接続に気付くのは、文が終わって応答しようとしたときであり、何分もかかることがある。それまでロックを持ち続ける。

### 2つ目の接続から `pg_cancel_backend` か `pg_terminate_backend` を呼ぶ

- 良い点：キャンセルのエラーを捕まえる文も終わらせられる。
- 悪い点：完全な2つ目のセッションが要る。認証、空いた接続の枠、ほかのセッションに対する権限である。トランザクションモードのコネクションプーラーを通すと、トランザクションが動いているサーバーのプロセス ID も要る。

### サーバーの `client_connection_check_interval` に任せる

- 良い点：クライアントが何をしていても、クライアントがいなくなるとサーバーはまもなく文を終える。
- 悪い点：サーバーかロールの設定であり、kortopi は制御できない。働くのは閉じた接続に対してだけであり、待っているクライアントには働かない。

### 黙ったサーバーに約 30 秒で気付く TCP のキープアライブと、キャンセル要求を送らずに待つのをやめる2度目の割り込み

- 良い点：遅くても進んでいるコミットを、kortopi 自身が見捨てることはない。
- 良い点：コミットの結果はサーバーに委ねたままであり、メッセージはそれが分からないと伝える。
- 悪い点：30 秒は、一瞬途切れるネットワークと止まったデプロイの間の当て推量である。

### フラグで与えるコミットの時間の上限

- 良い点：スクリプトが実行全体に上限を設けられる。
- 悪い点：スタンバイを待つコミットに合う数はなく、上限は遅いコミットをそれだけで結果の分からないものにしてしまう。

### 2度目の割り込みでコミットにキャンセル要求を送る

- 良い点：サーバーが応答すれば、結果が分かるかもしれない。
- 悪い点：キャンセルが結果を変えてしまう。遅らせたトリガーの中のコミットはロールバックされ、スタンバイを待つコミットはローカルで済んだものになる。

### `TCP_USER_TIMEOUT`

- 良い点：確認応答を待つデータのある接続も抑えられる。
- 悪い点：Go の `net` パッケージはそれを設定せず、Linux にしかない。
