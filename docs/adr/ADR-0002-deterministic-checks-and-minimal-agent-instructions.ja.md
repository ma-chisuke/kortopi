# ADR-0002: コーディングエージェントのハーネスでは決定的なチェックを優先し、指示を最小限に保つ

## 背景と課題

kortopi のコードと文書の多くは、コーディングエージェントが書く。
文章でしか書かれていない決まりは、エージェントが破りうる。決まりを読まないこともあれば、長い作業の途中で見失うことも、読み違えることもある。
そのとき、決まりが破られたことは、エージェントにも、ほかの誰にも伝わらない。

よくある対策は、リポジトリを説明する指示のファイルである。そこには、アーキテクチャ・慣習・すべての決まりを書く。
エージェントはこのファイルを作業のたびに読むので、毎回トークンを消費する。コードが変わるにつれてファイルの中身は古くなり、エージェントがそこに書かれた決まりを破っても何の知らせもない。
ETH Zurich による2026年の「Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?」という研究がある。この研究は、リポジトリの概要を書いたファイルがエージェントの作業の成功率を上げず、費用を2割より多く増やしたと報告している。

kortopi は公開のプロジェクトでもある。
貢献者はそれぞれ別のエージェント製品を使い、何も使わない人もいる。決まりは、そのすべてに同じように効く必要がある。

エージェントにこのリポジトリの決まりを守らせるにはどうすればよいか。また、すべてのエージェントが読む指示には何を書くべきか。

## 判断の基準

- 大事な決まりは、エージェントがそれを読まなかったときも、理解しなかったときも守られる。
- エージェントは、チェックの出力から自分の誤りを人の手を借りずに直せる。
- どのエージェントも作業のたびに指示を読むので、指示の1行1行が費用に見合う。
- 同じ決まりが、どのエージェント製品と人にも効く。
- 指示を変えるときは、推測ではなく、実際に見た失敗に基づく。

## 検討した選択肢

- 決定的なチェックを優先し、指示は最小限にして、実際に見た失敗からだけ増やす
- アーキテクチャとすべての決まりを説明する長い指示のファイル
- ハーネスを作らず、エージェントはコードと README だけを頼りに作業する
- エージェント製品ごとに別々の決まりのファイルを置く

## 決定

採用：「決定的なチェックを優先し、指示は最小限にして、実際に見た失敗からだけ増やす」。チェックはエージェントが何を読んだかに関係なく決まりを守らせ、短い指示のファイルは費用が小さく、古くなりにくいからである。

決まりは次のとおりである。

- 大事な決まりは、`make check` か `make check-all` のチェックで守らせる（ADR-0004）。チェックの指摘は1件1行で、ファイル・行・ルールを示す。このリポジトリが自分で書いたチェックは、直し方と、理由を書いた記録も示す。
- `AGENTS.md` に書くのは、コマンド・ファイルの置き場所・「終える前に `make check` を実行する」という指示・よくある既定から外れる決まりだけである。理由は記録に、手順はスキルとガイドに書く。
- `CLAUDE.md` は `AGENTS.md` を読み込むだけにする。こうして、どのエージェントも同じファイルを読む。
- `AGENTS.md` に指示を足すのは、どのチェックでも捕まえられない失敗を実際に見たあとだけである。指示に照らしてエージェントを評価する仕組みはないので、新しい指示が要るかどうか、チェックで置き換えられないかどうかは、レビューで決める。

ハーネスは次の部品からなる。

- Claude Code のフック。本体は `.claude/hooks/` にあり、`.claude/settings.json` に登録する。エージェントがファイルを編集すると、フックがそのファイルを整形する。編集の前には、`.gitattributes` が印を付けた生成ファイル・外から持ち込んだファイル・ロックファイルへの変更を止め、代わりに実行するものを示す。
- ほかのフックは、`.env` ファイルの読み取り・force push・`main` へのプッシュ・Git のフックを飛ばすコマンドを止め、レビュー役のサブエージェントを読み取りだけに保つ。ターンの終わりには、フックが変更のあったファイルに `make check` を実行し、指摘をエージェントに差し戻す。3回続けて失敗すると、チェックがまだ通らないことを伝えてターンを終えさせる。
- `.claude/settings.json` の権限の設定は、`make` と読み取りだけの Git のコマンドを確認なしで実行させる。`.env` ファイルの読み取り・force push・`main` へのプッシュは拒み、フックの後ろにある2つめの層になる。
- 繰り返す手順のためのスキル（`.claude/skills/`）。`write-adr` は記録を書き、`sync-translation` は対訳を最新にし、`japanese-tech-writing` は日本語の文章規範を持つ（ADR-0003）。
- サブエージェント（`.claude/agents/`）。`design-reviewer` は変更を記録に照らしてレビューし、`translation-reviewer` は対訳を原文と比べる。どちらも読むだけである。`implementer` は、書面の指示から大きな作業を1つ組み上げ、報告の前に検証する。
- lefthook は、人にも同じチェックをかける（`lefthook.yml`）。コミットの前にはステージしたファイルに `make fmt` と `make check` を実行してコミットメッセージを検査し、プッシュの前には `make check` を実行する。

### 結果

- 良い点：エージェントが決まりを読んだかどうかに関係なく、決まりは守られる。エージェントは、決まりを破ったその時点で決まりを知る。
- 良い点：人・エージェント・CI が1つの `make check` を共有するので、エージェント製品ごとの決まりは要らない。
- 良い点：`AGENTS.md` が短いままなので、作業ごとの費用が小さく、古くなる部分も少ない。
- 悪い点：名前の付け方、テストが確かめるべきことを確かめているか、kortopi が記録のとおりに振る舞うかなど、チェックできない決まりもある。それらはレビューと、レビューを担うサブエージェントに頼る。
- 悪い点：記録を示す指摘は少ない。示すのは `lint-adr`・`lint-i18n`・`lint-agents-md` の指摘と、時間の上限を超えたときのメッセージだけである。ほかの道具はルールと、場合によって直し方かリンクを示すだけなので、エージェントはルールの名前から理由を探す必要がある。
- 悪い点：短い `AGENTS.md` で足りるかどうかを測るものがない。この選択は、先の研究と、レビューで見えたことに頼っている。
- 悪い点：フックが動くのは Claude Code の中だけである。ほかのエージェントがチェックを受けるのは、`make check`・lefthook・CI を通してだけである。
- 悪い点：フックが防ぐのは誤りであり、わざとすり抜けようとするエージェントは防げない。フックはシェルのコマンドを簡単なパーサで分けるだけで、サンドボックスではない。

### 確認の方法

- `make check` が関門である。人・エージェント・CI がこれを実行し、フックもターンの終わりにこれを実行する。
- `make check` は `lint-agents-md` を実行する。`lint-agents-md` は、`AGENTS.md` かその対訳が60行より長いと失敗する。
- `make check` は `test-hooks` を実行し、各フックに見本のイベントを与えて、何を止めて何を通すかを確かめる（`tools/tests/hooks_test.sh`）。
- `make check-all` は、`.claude/settings.json` を公開されたスキーマで検証する（`lint-schema-remote`）。
- `AGENTS.md` に足す指示が、実際に見た失敗に応えるもので、どのチェックでも置き換えられないものであることは、レビューで確かめる。

## 選択肢の長所と短所

### 決定的なチェックを優先し、指示は最小限にして、実際に見た失敗からだけ増やす

- 良い点：チェックは、どのエージェントにも、どのモデルにも、どの人にも同じように働く。
- 良い点：失敗したチェックの出力が直すべき点を示すので、エージェントは人の手を借りずに問題を直せる。
- 悪い点：チェックを書いて出力を役に立つ形に保つのは、文を1つ書くより手間がかかる。
- 悪い点：長いファイルなら得られたはずの文脈をエージェントが知らず、それを知るために、失敗するチェックに1ターンを使うことがある。

### アーキテクチャとすべての決まりを説明する長い指示のファイル

- 良い点：すべてが1か所にあり、新しいエージェントも人も、一度読めば済む。
- 悪い点：どのエージェントも作業のたびにこれを読む。この記録で挙げた研究では、そうした概要は成功率を上げずに費用を増やした。
- 悪い点：エージェントがファイルの決まりを破っても、エージェントには何も伝わらない。ファイルが古くなっても、誰にも伝わらない。

### ハーネスを作らず、エージェントはコードと README だけを頼りに作業する

- 良い点：作るものも保守するものもない。
- 悪い点：エージェントは毎回コマンドと決まりを探し直し、見つけられなかった決まりを破り、その始末をレビュー担当者に残す。

### エージェント製品ごとに別々の決まりのファイルを置く

- 良い点：それぞれのファイルで、その製品の機能を使える。
- 悪い点：ファイルどうしの中身がずれていく。あるファイルで決まりを変えても、ほかのファイルでは古い決まりのまま残る。
