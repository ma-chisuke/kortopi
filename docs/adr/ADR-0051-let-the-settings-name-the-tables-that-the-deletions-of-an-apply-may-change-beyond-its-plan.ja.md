# ADR-0051: apply の削除が計画を超えて変えてよいテーブルを設定で挙げられるようにし、そこでしたことを報告し、上限に数える

## 背景と課題

行を削除する apply は、削除のあと、コミットの前に、トランザクションが各テーブルで削除し更新した行を数える。そして、計画が数えなかった行をテーブルが失ったか変えたときに止まる（ADR-0039）。
ADR-0048 から、コミットまで遅らせた制約トリガーはこの検査の前に動くので、それがすることも数に入る。
計画は外部キーをたどるが、トリガーやルールはたどれない。

issue 51 は、意図してほかのテーブルを揃えるトリガーを持つチームにとって、これが何を意味するかを示す。
`shop.categories` の `AFTER DELETE` のトリガーが、そのカテゴリのラベルを `shop.category_labels` から削除し、`shop.totals` の数を1減らす。`shop.category_labels` を結ぶ外部キーはない。
モード `sync` の `shop.categories` の宣言は、もう `games` を持たない。
計画は削除する行を1行示す。削除はさらに2つのラベルを消して数を更新し、apply は次のエラーで止まる。

```text
kortopi: after its first deletion, the database counted 2 deletions in table shop.category_labels for the transaction, and the plan counted 0: a trigger or a rule of a table that the deletions reach, or a constraint trigger deferred to the commit, which the apply runs before this check, did other than the plan shows, so nothing was written: ...
kortopi: nothing was changed
```

既定としてはこれが正しい。計画が示さなかったものは、何もコミットされない。
しかしこのチームにとっては、トリガーを知っていてその働きを望んでいても、`kortopi apply --allow-delete` でカテゴリを1つも削除できないことを意味する。
チームは、自分のセッションで行を手で削除する。それは宣言とそのレビューの外にあり、`--max-delete` の外にもある。あるいは apply の間だけトリガーを無効にする。それにはテーブルの所有者が要り、その間ほかのセッションはトリガーなしで動く。

ほかのすべてについて検査をそのままにしたまま、削除がほかのテーブルを計画を超えて変えることを、チームはどう許せるのか。

## 判断の基準

- apply は既定では止まり続ける。チームがそのテーブルについて許さない限り、計画が示さなかったものは何もコミットされない（ADR-0039）。
- 外すものには名前があり、宣言と一緒にレビューされ、どの実行でも効く。トリガーはスキーマに属し、どの apply でも動く。
- 設定が挙げないテーブルでは、削除のあとの検査は ADR-0039 と ADR-0048 が定めるとおりのままであり、ADR-0039 が挙げる見えないものもそのままである。apply の実行中にほかのセッションの足す外部キーやパーティション、ほかのテーブルに着く新しいトリガーは、今までどおり apply を止める。
- 削除の上限は、誤りがどう広がっても捕まえる（ADR-0039）。トリガーを通して広がっても同じである。
- 計画を超えて起きたことは必ず報告し、どの数も、それが何であるか、つまりトランザクションについてデータベースが数えたものとして伝える。
- 新しい権限も、データベースのオブジェクト（ADR-0010）も要らない。設定を使わない apply には新しい負担がない。

## 検討した選択肢

- 計画を超えて行が変わってよいテーブルを挙げる `kortopi.toml` のキー
- 検査を外すコマンドのフラグ
- すべてのテーブルについて検査を外す
- テーブルの代わりにトリガーを挙げる

## 決定

採用：「計画を超えて行が変わってよいテーブルを挙げる `kortopi.toml` のキー」。
これは既定を保ち、チームが選んだところでだけ検査を外し、ほかでは外さない。プルリクエストがレビューする宣言の隣の、データのディレクトリに置かれる。しかも、検査のエラーがすでに挙げるのと同じテーブルを挙げる。
これは、最後の決まりのとおり ADR-0029・ADR-0039・ADR-0042・ADR-0048 を細かくする。

決まりは次のとおりである。

設定：

- `kortopi.toml` の先頭、最初のセクションより前の `allow_unplanned_changes` は、テーブルの配列である。各テーブルは、ファイルのセクションと同じく `<schema>.<table>` で挙げ（ADR-0013）、大小はデータベースのとおりにする。

  ```toml
  allow_unplanned_changes = ["shop.category_labels", "shop.totals"]

  [tables."shop.categories"]
  mode = "sync"
  ```

- スキーマのない名前、ドットが2つある名前、配列が2回持つ名前、文字列以外を持つ配列は、ファイルの誤りであり、セクションの誤りと一緒に報告する。テーブルのセクションの中に書いたキーは、そのセクションの知らない設定になり、そのエラーはファイルの先頭に書くよう伝える。空の配列はどのテーブルも挙げない。
- ここに挙げたテーブルは、それを宣言するファイルも、自分のセクションも要らない。こうしたテーブルの多くは、宣言が持たないテーブルだからである。
- `allow_unplanned_changes` という名前は、`--allow-delete` と同じく、このキーが何を許すかと、それが許可であることを伝える。「changes」は、計画の「changes」が3つの種類を含むのと同じく、削除した行、更新した行、挿入した行を含む。
- 名前は、通常のテーブル、パーティションテーブル、マテリアライズドビューのどれでもよい。マテリアライズドビューの行も数に含まれ、ビューをリフレッシュするトリガーがそれを変えるからである。
- 挙げたパーティションテーブルは、すべての段のパーティションを含む。検査はリレーションの行を、そのツリーの最上位のパーティションテーブルでまとめて数える（ADR-0039）。そのため、パーティションだけを挙げても何も含まない。計画はそれを伝え、代わりに挙げるテーブルを挙げる。ほかのテーブルを継承するテーブルはパーティションではなく、独立したテーブルである。
- データベースにその名前のテーブルがないこと（まったくない場合も、ビューのような別の種類のリレーションである場合も）は、誤りではない。スキーマの変更がそのテーブルを足すかもしれず、設定が複数の環境に使われるかもしれないからである。計画はそれを伝える。
- スキーマか名前にドットを含むテーブルは、この版では宣言できないのと同じく、挙げられない。

数の中身：

- 検査は、PostgreSQL がトランザクションについて `pg_stat_xact_user_tables` に持つ数を読む（ADR-0039）。それは削除・挿入・更新の回数であり、テーブルが失った行や得た行の数ではない。
  トリガーのブロックが試みてからロールバックしたものも含む。`EXCEPTION` のあるブロックの中で削除に失敗したときがその例である。ほかのパーティションへ動いた行は、削除1回と挿入1回として数える。
- これらの数から行の正確な数は得られない。挙げたテーブルの行を削除の前後で数えると、大きくなりうるテーブルを読むことになる。
  そこで行とエラーは、数をそのまま、トランザクションについてデータベースが数えた削除・挿入・更新として伝え、テーブルが失った行や得た行としては決して伝えない。どのテーブルの件数のエラーも同じである。

削除のあとの検査：

- 挙げたテーブルでは、最初の削除からの数が、計画の数えたものを超えてよい（ADR-0039、ADR-0048）。削除の回数は、計画がそこから削除し削除の波及が数える行より多くてよい。更新は、削除の `SET NULL` と `SET DEFAULT` の動作がしうるより多くてよい。挿入はいくつあってもよい。
  ただし、下回ってはならない。削除の回数は計画の数えた行以上であり、更新は削除の波及が変わると数える行の数以上である。下回るなら、削除は計画の数えたより少ないことをした。それは計画を超えたことではない。
  そのときエラーは、この設定が許すのは、データベースがそのテーブルで計画の数えたより多くの削除・更新・挿入を数えることであり、少なく数えることではないと伝える。
- それ以外は今のままである。削除の波及が数えたすべての行は今までどおり識別子で読み、変わらずに残った数えた行は apply を止める（ADR-0039）。スキーマの比較は先に動き、どの変更でも apply を止める（ADR-0048）。apply の書き込みの行数は厳しいままである（ADR-0042）。そのため、apply の後続の削除が選ぶ行を消すトリガーは、今までどおり apply を止める。コミット前の比較は、今までどおり宣言したすべてのテーブルを比べる（ADR-0042）。そのため、宣言した挙げたテーブルも、宣言のとおりに終わらなければならない。
- 削除の `SET NULL` か `SET DEFAULT` がパーティションキーの列を設定する挙げたテーブルは、今までどおり計画に合わせる。PostgreSQL は、動作がほかのパーティションへ動かした行を削除と挿入として数え、それはトリガーが削除した行と挿入した別の行と見分けられないからである。そのエラーはそれを伝える。
- 設定が挙げないテーブルは、今までどおり apply を止める。テーブルを挙げれば apply が通る場合、件数のエラーは次の句で終わるようになる。

  ```text
  or, if it changes table <table> on purpose, name the table in allow_unplanned_changes of <dir>/kortopi.toml
  ```

  挙げても助けにならない場合、つまり数が計画を下回るときと、削除が行をパーティションの間で動かしうるテーブルでは、この助言をしない。名前にドットを含むテーブルについては、代わりに `allow_unplanned_changes` がそれを挙げられないと伝える。
- 挙げたテーブルでも、数の先にあるものは、どのテーブルとも同じく見えないままである（ADR-0039）。範囲に収まる更新、更新が書く値、トリガーが `TRUNCATE` で空にした行がそれにあたる。

テーブルを挙げることで手放すもの：

- 挙げたテーブルについては、トリガーが残した数えた行を、トリガーのほかの働きと見分けられなくなる。検査は数えた行を識別子の `ctid` で見つける。そのため、`BEFORE DELETE` のトリガーが更新して `NULL` を返して残した行は、もうそこにあるとはみなされない。
  そのとき、その行が残ったことを示すのは削除の回数だけである。挙げたテーブルでは、データベースが数えるほかのどの削除も、それを埋め合わせる。実際の削除でも、トリガーのブロックがロールバックした削除でも同じである。
- そのため挙げたテーブルについては、`Through foreign keys, ...` の行と計画が、そこで起きたより多くを伝えうる。それらが削除したと示す行が、変わって残っていることがある。成り立つのは、削除と更新の回数が計画の数えたものを下回らないことと、変わらずに残った数えた行が apply を止めることである。
- 設定が挙げないテーブルは ADR-0039 の検査を保ち、その記録が挙げる見えないものもそのままである。そこでも、更新の範囲に幅があるときや、トリガーが行を挿入し直すときは、数えた行が残りうる。

検査に要るもの：

- 行を削除する計画で、設定がテーブルを挙げるなら、そのどれがデータベースにあり、どれがパーティションかを1回だけ読む。読むのは `pg_class` と `pg_namespace` で、どのロールも読める。削除のあとの検査は、同じものを自分のトランザクションで読み、そこでは同じスナップショットが見える。数は `pg_stat_xact_user_tables` から読み、検査はそれをすでに読んでいる。権限もオブジェクトも増えない。削除する行のない計画や、設定がテーブルを挙げない計画は、それ以上何も読まない。

`--max-delete`：

- 挙げたテーブルでデータベースが数えた計画を超える削除は、計画の数えた行と一緒に `--max-delete` で数える（ADR-0039）。計画はそれを知りえないので、apply は削除のあとの検査のあと、コミット前の比較の前に、上限をもう一度確かめる。数が上限を超えれば、apply は次のエラーでコミットの前に止まり、何も変えない。

  ```text
  kortopi: the deletions of the apply come to 3, more than the limit of 2: 1 row of shop.categories to delete, and 2 deletions beyond the plan in tables that allow_unplanned_changes names, by the counts of the database (2 in shop.category_labels), so the apply stops before its commit: a count of the database can exceed the rows that are gone, since it holds what a block of a trigger rolled back and both halves of a move between partitions: check the triggers and the rules that delete rows of these tables, and if the deletions are right, raise the limit with --max-delete 3
  ```

  書き込みの前のエラーと同じく、計画の内訳が先に来て、種類ごとに1回、そのテーブルとともに並ぶ。
- この確認はデータベースの数を数えるので、止める側に倒れる。トリガーがブロックの中で削除を試みてロールバックした apply は、消えた行が少なくても止まりうる。エラーは、その数がデータベースの数であり、消えた行を超えうることを伝える。
- 計画を超えた更新は数えない。データベースは更新の回数を数え、合計の数のように1つの行が何回も更新されることがある。そのため更新の回数は行の数ではない。挿入は削除ではない。
- `--max-delete` のヘルプは、`allow_unplanned_changes` のテーブルでデータベースが数えた計画を超える削除も数えることを伝える。
- 書き込みの前の確認は今のままである。

計画が示すもの：

- 行を削除する計画は、削除の波及をまとめる行のあとに、多くとも3行で次を伝える：

  ```text
  The deletion may also delete, update, or insert rows of shop.category_labels and shop.totals beyond what the plan shows, which allow_unplanned_changes in kortopi.toml allows.
  The database has no table shop.archive, which allow_unplanned_changes in kortopi.toml names.
  A partition is checked with the partitioned table at the top of its tree, so allow_unplanned_changes in kortopi.toml does not cover partition audit.log_1 of audit.log: name audit.log instead.
  ```

  ADR-0031 と ADR-0046 が一覧の長さを抑えるのと同じく、各行はテーブルを多くとも5つ挙げ、ほかは `and 3 more tables` のように数える。設定が最上位のパーティションテーブルを挙げるパーティションには、行がない。削除する行のない計画は、これらの行をひとつも出さない。そのときは、この設定の外す検査が動かないからである。
- 挙げたテーブルについて、削除の波及のまとまりとそれをまとめる行が伝えるのは、外部キーだけがするはずのことである。それらが数える行を、トリガーが先に削除することがある。削除を失敗させると数えた行も同じであり、そのとき apply はコミットする。
- apply の計画は計画そのものなので、`--allow-delete` がなくてもこれらの行を示す。
- SQL としての計画（ADR-0029）は、これらの行をヘッダーにコメントとして書く。設定がテーブルを含むときは、さらに次の1行を書く。

  ```text
  The script does not check or report what the deletions change beyond the plan; an apply reports it, and counts its deletions against --max-delete.
  ```

- これらの行は終了コードを変えない。`--exit-code` 付きでは、削除する行を持つ計画は今までどおり 2 で終わる。

apply が報告するもの：

- コミットのあと、ADR-0039 の外部キーの行のあとには、計画を超えたものが数として表れる挙げたテーブルごとの1行が続く。スキーマ、次に名前の順に並ぶ：

  ```text
  Applied: 0 inserted, 0 updated, 1 deleted.
  Unplanned changes in shop.category_labels, by the counts of the database: 2 deletions.
  Unplanned changes in shop.totals, by the counts of the database: 1 update.
  ```

- この行は、計画の数えた行を超える削除、挿入、更新を、トランザクションについてデータベースが数えたとおりに伝える。削除の動作も行を更新しうるテーブルでは、動作がしうる最多を超えた更新だけが確かに計画を超えている。そのため行は、そのときだけ更新を数え、その最多を添える：`7 updates, at most 5 of them by foreign keys`。計画を超えたものが数に表れない挙げたテーブルには、行がない。
- これらの行の数は抑えない。どの行も、コミットした apply がチームの挙げたテーブルにしたことを伝え、多くのテーブルを挙げるチームは、どれが変わったかを知りたいからである。

`--allow-delete` がないとき、削除がないとき：

- `--allow-delete` のない apply は行を削除しない。削除する行をそのまま残すテーブルの確認（ADR-0042）は、挙げたテーブルでも厳しいままである。モード `sync` の宣言したテーブルは、行を失わず、その挿入の行のほかに行を得てはならない。この設定は、apply の削除がほかのテーブルを変えることを許す。何も削除しない apply の書き込みが、実行の残す行を取り去ることは許さない。
- 削除のない apply は件数の検査をしないので、この設定が外すものはない。その計画も、この設定について何も出力しない。

これは ADR-0039 を細かくする。

- 「どのテーブルも、計画がそこから削除し削除の波及が数えた行を失っていなければならず、下の範囲の間で更新されていなければならない」：挙げたテーブルの数はそれらの行と下限を下回ってはならないが、超えてはよい。
- 「行を削除するか、範囲を超えて行を更新するトリガーやルールと、外部キーの無効なトリガーも、そこで apply を止める」：挙げたテーブルにそうするトリガーやルールは止めない。ただし、変更が行をほかのパーティションへ動かしうるテーブルは除く。
- 「`--max-delete` は、実行の削除が消すか変えるすべての行を数える」：挙げたテーブルでデータベースが数えた計画を超える削除も数え、それは削除のあとに確かめる。
- 「コミットのあと、`Applied:` の行はそのままで、削除がほかの行を消すか変えたときは `Through foreign keys, ...` の行が続く」：そのあとに挙げたテーブルの行が続く。挙げたテーブルについては、上で述べたとおり、`Through foreign keys, ...` の行がそこで起きたより多くを伝えうる。
- 見えないもののうち「削除の間にトリガーやルールが挿入する行」：挙げたテーブルでは、そうした挿入を数えて報告する。
- `the apply deleted 1 row of table t.archive, and the plan counted 0` のような件数のエラーは、データベースが数えたものを伝えるようになる。たとえば `the database counted 1 deletion in table t.archive for the transaction, and the plan counted 0` である。設定が挙げないテーブルでも同じである。
- 結果の「悪い点：ADR-0027 で通った実行が止まるようになる」の項目のうち、トリガーやルールが `--allow-delete` 付きの apply をコミットの前に止めるという項目。そうしたトリガーやルールは、ほかのテーブルの行を消すか、削除の動作が更新しうるより多く行を更新する：設定がそのテーブルを挙げなければ、である。

これは ADR-0048 を細かくする。

- 結果の「悪い点：行を削除するか更新する、コミットまで遅らせた制約トリガーは、数がそのしたことを許さないとき、削除する apply を止めるようになる」：設定がそれの変えるテーブルを挙げなければ、である。
- その決まりにある件数のエラーは、上と同じく、データベースが数えたものを伝える。

これは ADR-0042 を細かくする。

- 「`--allow-delete` があっても何も変わらない。削除は厳しい行数を保ち、ADR-0039 の検査が削除のしたことを数える」：ADR-0039 の検査は、挙げたテーブルが計画を超えて変わることを許す。書き込みの行数とコミット前の比較は今のままである。

これは ADR-0029 を細かくする。

- SQL としての計画のヘッダーに、設定の行と、それが伝えることをスクリプトは確かめも報告もしないという注記が加わる。

### 結果

- 良い点：意図してほかのテーブルの行を消すか変えるトリガーを持つチームが、レビューと上限の中で、apply で行を削除できる。
- 良い点：既定が保たれる。設定がテーブルを挙げない apply は今までどおりそこで止まり、挙げることが助けになるときは、エラーがそのテーブルの挙げ方を伝える。
- 良い点：外すのは挙げたテーブルだけで、それも計画の数を上回る方向だけである。apply の実行中にほかのセッションが足す外部キー・パーティション・トリガー、変わらずに残った数えた行、宣言したテーブルは、今と同じ厳しさのままである。
- 良い点：`--max-delete` が、挙げたテーブルでデータベースが数えた削除を数える。そのため、チームの思うより多く削除するトリガーは、コミットの前に apply を止める。
- 良い点：出力が、挙げたテーブルごとに計画を超えてデータベースが数えたものを伝える。計画は、apply が動く前に、どのテーブルが変わりうるかを伝える。
- 悪い点：計画は、トリガーがすることを示せない。レビューする人が見るのはテーブルの名前であって行ではなく、数を知るのはコミットのあとである。
- 悪い点：数はデータベースの数であって行ではない。トリガーのブロックがロールバックしたものと、パーティションの間の移動の両方の半分を含む。そのため出力の行は、どの行も残った削除を数えることもある。上限は、伝えるより少ない行しか削除しなかった apply も止めうる。
- 悪い点：挙げたテーブルでは、トリガーが更新して残した数えた行を、トリガーのほかの働きと見分ける手段を手放す。そうしたテーブルについては、`Through foreign keys, ...` の行と計画が、起きたより多くを伝えうる。
- 悪い点：挙げたテーブルで計画を超えた更新は、行ではなく更新として数え、どの上限にも数えない。挙げたテーブルの多くの行を更新するトリガーは、そのままコミットする。
- 悪い点：削除の `SET NULL` か `SET DEFAULT` が行をパーティションの間で動かしうる挙げたテーブルは、それでも計画に合わせる。
- 悪い点：パーティションを挙げるには、そのツリーの最上位のパーティションテーブルを挙げるしかなく、それはツリーのすべてのパーティションについて検査を外す。名前にドットを含むテーブルは、まったく挙げられない。
- 悪い点：挙げたテーブルは、今までより多くを隠す。計画を超えてその行を削除・更新・挿入するトリガー・ルール・遅らせた制約トリガーは、チームが想定したものに限らず、どれも通る。apply の実行中にほかのセッションが削除の着くテーブルに足したものを止めるのは、スキーマの比較（ADR-0048）だけである。
- 悪い点：この設定はファイルのキーが1つ増えることであり、セクションに置くテーブルの設定と違って、ファイルの先頭に置く。

### 確認の方法

- `internal/config` の単体テストが、このキーを確かめる：`TestLoadUnplannedChanges` と、`TestLoadErrors` のエラー。
- `internal/plan` の単体テストが、計画の行を確かめる。`TestBuildUnplanned`、`TestUnplannedLines`、`TestRender` である。`TestRender` は `internal/plan/testdata/unplanned.golden` を使う。
- `internal/script` のゴールデンテスト `TestWrite` が、SQL としての計画のコメントを確かめる。使うのは `internal/script/testdata/unplanned.golden` と `unplanned_without_tables.golden` である。
- `internal/apply` の単体テスト `TestRunUnplannedChanges` が、検査が受け取るテーブルと削除のあとの上限を確かめる。`TestRenderSummary` が、コミットのあとの行を `internal/apply/testdata/unplanned.golden` で確かめる。
- `cmd/kortopi` の単体テストが、出力と終了コードを確かめる：`TestRunApply` と `TestRunPlan`。
- `make check-all` での PostgreSQL 15〜18 に対する結合テスト：
  - `internal/postgres` の `TestApplyUnplannedChanges`。どのエラーも全体で比べる。issue 51 のトリガーを、設定なしとありで確かめる。設定が挙げないテーブル、`--max-delete` を超える計画を超えた削除も確かめる。
    コミットまで遅らせた制約トリガーを、設定ありとなしで確かめる。トリガーがパーティションに書くパーティションテーブルと、パーティションだけを挙げた場合も確かめる。
    `SET NULL` が行をパーティションの間で動かす場合を、挙げたテーブルと挙げないテーブルで確かめる。トリガーが変えずに残す数えた行と、計画の数えたより少ない更新も確かめる。
    トリガーが更新して残す数えた行を、挙げたテーブルと挙げないテーブルで確かめる。トリガーがリフレッシュするマテリアライズドビューを、設定なしとありで確かめる。名前にドットを含むテーブルも確かめる。
    さらに、トリガーが宣言のとおりに残す宣言したテーブル、宣言から取り去る宣言したテーブル、データベースにその名前のテーブルがない名前を確かめる；
  - `internal/postgres` の `TestUnplanned`：計画が読むカタログを、パーティションテーブル、2つの段のパーティション、マテリアライズドビュー、ビュー、大小の違う名前で確かめる；
  - `TestDeferredTriggerThatChangesAnotherTable`：件数のエラーと、そのテーブルを挙げる助言；
  - `cmd/kortopi` の `TestApplyUnplannedChangesCommand`：コマンドを通した issue 51 を確かめる。計画、SQL としての計画、`--exit-code`、上限と、各 apply のあとにデータベースが持つ行を見る。

## 選択肢の長所と短所

### 計画を超えて行が変わってよいテーブルを挙げる `kortopi.toml` のキー

- 良い点：チームの選んだテーブルについてだけ、どの実行でも検査を外し、ほかでは外さない。
- 良い点：設定は宣言と一緒にレビューされ、検査のエラーが書くべきテーブルを挙げる。
- 悪い点：挙げるのはテーブルであって原因ではない。挙げたテーブルを計画を超えて変えるトリガーは、どれも通る。

### 検査を外すコマンドのフラグ

- 良い点：それを要する実行が、コマンドラインでそう示す。
- 悪い点：トリガーはスキーマに属し、どの apply でも動く。そのためフラグはどの実行でも渡され、すぐにどのパイプラインにも書かれる。
- 悪い点：すべてのテーブルについて一度に検査を外す。apply の実行中にほかのセッションが足す外部キーやトリガーについても外す。

### すべてのテーブルについて検査を外す

- 良い点：どのチームも、自分のトリガーがどのテーブルを変えるかを知らなくてよい。
- 悪い点：検査は計画が示さなかったものを止めるためにあり（ADR-0039）、トリガーやルールのすることを何も止めなくなる。

### テーブルの代わりにトリガーを挙げる

- 良い点：原因を挙げるので、同じテーブルを変える別のトリガーは今までどおり apply を止める。
- 悪い点：データベースの数が伝えるのは、トランザクションが各テーブルでした削除と更新の回数であり、どのトリガーがしたかではない。数からは、あるトリガーのしたことを、別のトリガー、ルール、別のテーブルの遅らせた制約トリガーのしたことと見分けられない。
- 悪い点：ADR-0048 が述べるとおり、トリガーの関数は名前を変えずに変わりうる。そのためトリガーの名前は、見かけほど多くを約束しない。
