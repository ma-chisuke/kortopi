# ADR-0050: 同じ外部キーを繰り返す段を、計画の1行にまとめる

## 背景と課題

計画は、テーブルの削除が外部キーを通じてすることを、テーブルの件数のあとのまとまりで示す（ADR-0039）。
たどる処理の各ステップ、つまり1つの段の1つの外部キーが1つの文になる。n+1 段目のステップは、それが参照するテーブルの行を消す最初の n 段目のステップの下に、2文字深く字下げして置く。
SQL としての計画は同じ行をコメントとして書き、apply は書き込む前に計画を出力する。

issue 58 は、行が連なりをなすテーブルを示す。
`app.steps` の各行は、`ON DELETE CASCADE` で、同じテーブルの別の行のあとに続く。
1つのプランの削除は最初のステップにカスケードし、そこから 300 行の連なりに沿って続くので、たどる処理は 300 段になる。
計画はその1つの削除に 300 行を出力し、どの行も前の行より2文字深く字下げした。最後の行は 602 文字の空白のあとから始まり、出力は 135,856 バイトになった。
数は正しく、`Plan:` のあとの行が合計を示していた。それでも、そのまとまりは端末でもプルリクエストのコメントでも読めなかった。
`ON DELETE CASCADE` で互いを参照する2つのテーブルの循環も、2つのキーが交互に現れて同じことになる。

たどる処理がどれほど深くなっても、まとまりを読めるように保つにはどうするか。しかも正しさを保つには、今の計画が示すどの数も出力から導けて、数えない行が1つもないようにするにはどうするか。

## 判断の基準

- 削除が消す行・変える行・削除を妨げる行は、どれもちょうど1つの行で数える。参照しているテーブルと動作ごとに行の件数を足すと、`--max-delete` とまとめの行が使う件数になる（ADR-0039）。
- どの文も、それが数えるどの行についても正しい。
- まとまりの長さは、データの深さではなく、削除がたどる外部キーの数に応じて増える。
- 1つの道筋に同じキーを2回持たず、5つ目より深い位置の行もないまとまりは、これまでどおりに出力する。ただし、テーブルの名前で誤って置いたステップは除く。
- 上限には、ADR-0031 と ADR-0046 の上限の数を使う。それらは最大で5つの項目を挙げる。しかも、上限はどの件数も隠さない。

## 検討した選択肢

- 親をたどって同じ外部キーを繰り返すステップを、そのキーが最初に現れる行へまとめ、字下げの深さを限る
- 自分自身への外部キーで続く段だけをまとめる
- 最初の何段かを示し、その先の段を1行で数える
- 字下げの上限だけを設ける

## 決定

採用：「親をたどって同じ外部キーを繰り返すステップを、そのキーが最初に現れる行へまとめ、字下げの深さを限る」。
たどる処理が深くなるのは、自分自身を参照するテーブルか循環を通じてキーを繰り返すときである。繰り返すキーをそれが初めて現れた行へまとめれば、まとまりの深さは、1つの道筋の上の異なるキーの数で抑えられる。しかも、各行はその行の件数を正確に数え続ける。

決まりは次のとおりである。

まとまりの行：

- たどる処理のステップは、これまでどおり各段の各外部キーに1つずつであり、上限・まとめの行・削除の前の比較・削除のあとの検査が読む件数を持つ（ADR-0039）。たどる処理は、次の決まりのとおり各ステップに親を加え、まとまりが変わる。
- ステップは親の下に置く。親は、前の段のステップのうち、そのステップの行が参照しうる行を消す最初のステップである。参照しうる行とは、その外部キーが参照するリレーションか、そのパーティションの行である。たどる処理は、前の段の各ステップが消した行を持つリレーションから、各ステップに親を与える。そのステップが参照しうる前の段の行の数も与え、「that row of」と「those rows of」はそれに基づく。
- パーティションが持つキーや、パーティションを参照するキーは、そのステップが参照する行を消したステップとは別のテーブルを名指す。そのため、テーブルの名前を照らし合わせていたまとまりは、そうしたステップを一番上に置き、関係のない行のあとに出していた。
- 親をたどった上の行と同じ外部キーのステップは、新しい行にせず、その行で数える。たどる処理がそのキーをもう一度たどるからである。その下のステップは、その行の下に置く。同じ行の下にある同じキーのステップも、1つの行で数える。2つのステップが同じキーをたどるのは、参照しているテーブル・外部キー・参照されるテーブル・動作が同じで、分からないことについても同じことを示すときである。
- そのため、まとまりの上から下への1つの道筋に、1つのキーは最大で1回しか現れない。削除が複数のキーを通じてたどり着くテーブルには、キーごとに行が残る。1つのキーが2つの異なる行の下に現れることはあり、そのときはそれぞれの下に1行ずつ置く。
- 複数のステップの行は、そのすべての件数を数え、段の数を示す。

  ```text
  1 row of app.steps (plan_code) references it through steps_plan_code_fkey, ON DELETE CASCADE, so the deletion deletes this row too.
    299 rows of app.steps (after_id) reference rows of app.steps that the deletion deletes, through steps_after_id_fkey, ON DELETE CASCADE, at 299 levels, so the deletion deletes these rows too.
  ```

- 複数のステップの行が数える行は、異なる段が消す行を参照する。そのため、そうした行とその下の行は、テーブルの行のうち「that the deletion deletes」（削除が消す）ものを参照すると示す。参照する行が1行なら「a row of」と示す。1つのステップの下にある1つのステップの行は、これまでどおり「that row of」か「those rows of」と示す。文のほかの部分、つまり動作・ステップのすることが分からない理由・あとに続く `ON UPDATE` の動作は変わらない。
- ほかの行の下にない行は、その最初のステップの段の位置に置く。ほかの行の下にある行は、その行より1つ深い位置に置く。1つの行の下の行は、それぞれの最初のステップの順に並べる。これはステップの順であり、段、参照しているテーブル、外部キーの名前、参照されるテーブルの順である（ADR-0039）。

位置と段：

- 行は5つ目の位置より深くは置かない。ADR-0031 と ADR-0046 の一覧が最大で5つの項目を挙げるのに合わせる。それより深い行は5つ目の位置に置く。行はすべて示す。行を隠すと、上限とまとめの行が頼る、テーブルと動作ごとの件数も隠れるからである。
- 行の位置は、その行がたどる処理の中で始まる段である。ただし、上の行が段をまとめると、その下の行の位置は段より浅くなる。5つ目より深い行も5つ目の位置に置く。行は、その位置が始まる段を示さないときは、必ずその段を示す。1つのステップの行なら `at level 6`、複数のステップの行なら `at 3 levels from level 8` のようになる。位置が始まる段を示す、複数のステップの行は `at 3 levels` と示す。

行が現れるところ：

- 計画、apply が書き込む前に出力する計画、SQL としての計画のコメントは、同じ行を書く。
- `Plan:` のあとのまとめの行、`Applied:` の行と削除がさらに消した行を示す行、`--max-delete` のエラーはステップを読むので、変わらない。issue 58 はこれまでどおり 300 行を数え、上限もこれまでどおり `--max-delete 301` である。
- 波及が分からないステップのエラーは、そうしたステップをそれぞれ1回だけ示す。循環を通じて深い段でもう一度出会うキーは、どの段でも同じ文になり、これまでのエラーはそれを段ごとに繰り返していた。
- 削除の前の比較のエラーは、1つのステップをその段とともに挙げ、変わらない。

細かくするもの：

- ADR-0039 の「計画が示すもの」の次の2つ。
  - 「各ステップは1文である」
  - 「n+1 段目のステップは、それが参照するテーブルの行を消す最初の n 段目のステップの下に、2文字深く字下げして置く。そして、それらの行のどれかを参照する行を数える。」

  行は今では、1つのステップか、上のとおりキーを繰り返すステップの集まりであり、5つ目の位置より深くは置かない。ステップは、前の段のステップのうち、そのステップが参照しうる行を消す最初のステップの下に置く。参照しうる行とは、そのキーが参照するリレーションかそのパーティションの行である。それを決めるのはたどる処理であり、テーブルの名前の照合ではない。
- ADR-0039 の「悪い点：2つの外部キーがたどり着く行は、その一方のもとでだけ示す」。これは変わらない。段をまとめた行も、それが数える行を、キーが最初に現れた行の下でだけ示す。

### 結果

- 良い点：issue 58 のまとまりは2行で済み、2つのテーブルの循環はキーごとに1行で済む。データの深さにはよらない。
- 良い点：各行はこれまでどおりその件数を正確に数え、テーブルと動作ごとに行を足すと、まとめの行と上限の数になる。ゴールデンファイルのどの場合についても、テストがこれを確かめる。
- 良い点：1つの道筋に同じキーを2回持たず、5つ目より深い位置の行も、パーティションにあるキーやパーティションへのキーもないまとまりは、これまでどおりに出力する。
- 良い点：パーティションが持つキーや、パーティションを参照するキーのステップは、それが参照する行を消したステップの下に置く。以前は、テーブルの名前がそれを一番上に置いていた。
- 悪い点：複数の段の行は、その行が前の段のどの行を参照するかを示さず、削除が消す行を参照することしか示さない。段ごとの件数も示さない。
- 悪い点：複数の段の行の下にある行や、5つ目より深い行は、位置が段と違うので段を示す。読む人は、木の中の位置を、字下げだけでなく、その段と参照するテーブルから読み取ることになる。
- 悪い点：たどる処理は、これまでどおり段ごとに問い合わせを流す。計画が 300 行の連なりを1行にまとめても、300 段の問い合わせがかかる。

### 確認の方法

- `internal/plan` の単体テスト：
  - `TestRenderEffectsThatRepeatKeys`：次のゴールデンファイルを確かめる。
    - `effect_chain_3` と `effect_chain_300`
    - `effect_tree`：段ごとに広がる行の木と、段ごとに分かれるキー
    - `effect_two_keys`：1つのテーブルから自分自身への、交互に現れる2つのキー
    - `effect_mixed`：`CASCADE` のあとの `SET NULL`、2つの段の `RESTRICT`、1つの段の `NO ACTION`
    - `effect_cycle`：2つのテーブルの循環
    - `effect_deep`：5つ目の位置より深い行
    - `effect_levels_under_a_line_of_several_levels`：2つの段の行の下で位置が段と違う行と、その下で5つ目の位置より深い行
    - `effect_key_on_a_partition` と `effect_key_to_a_partition`：名前が親を示さないステップ
    - `effect_repeated_unknown`
  - `TestEffectLinesCountEveryRow`：これらの場合と ADR-0039 のゴールデンファイル `effect` について、参照しているテーブルと動作ごとの行の件数を足すと、ステップの件数になる。以前の計画はステップごとに1行を出力していた。まとめの行の合計もステップのものであり、上限より深く字下げする行はない。
  - `TestEffectTree`：連なり・循環・段ごとに分かれるキーの行、複数の段の行の下にある行の順、親のないステップを確かめる。同じキーのステップで、分からないこと・あとに続く `ON UPDATE` のキー・そのテーブルのどれか1つだけが違うものは、それぞれ行を分ける。パーティションにあるキーとパーティションへのキーも確かめる。
  - `TestRender`：ADR-0039 のゴールデンファイルは変わらない。
- `internal/apply` の単体テスト：`TestLimitCountsEveryLevelOfADeepCascade` は、300 行の連なりの上限と、その行が出力する件数を確かめる。`TestUnknownEffectsOnceThroughACycle` は、2つの段で分からないキーのエラーを確かめる。
- `internal/postgres` の結合テスト `TestEffectLinesThroughTheWalk` は、PostgreSQL 18 でたどる処理を動かす。対象は、木、段ごとに分かれるキー、テーブルから自分自身への2つのキー、カスケードのあとの `SET NULL`、2つのテーブルの循環である。パーティションが持つキーに沿った連なりと、そのパーティションへのキーのメモも対象である。行は期待どおりであり、その件数はステップとまとめの行に一致する。
- `internal/script` のゴールデンテスト `TestWrite` は、`deletions_through_a_chain` で SQL としての計画のコメントを確かめる。
- `cmd/kortopi` の `TestPlanOfADeepCascadeCommand` は、`make check-all` で PostgreSQL 15 から 18 に対し、issue 58 をコマンドから動かす。計画、SQL としての計画、apply の上限、`--max-delete 301` の apply を確かめる。最後の apply は 300 行を削除し、そう示す。

## 選択肢の長所と短所

### 親をたどって同じ外部キーを繰り返すステップを、そのキーが最初に現れる行へまとめ、字下げの深さを限る

- 良い点：自分自身を参照するテーブルも、どの長さの循環も、段ごとに分かれるキーも、1つの決まりで扱える。
- 良い点：まとまりの深さは1つの道筋の上の異なるキーの数で抑えられる。5つの位置の上限が効くのは、異なるキーが5つより多く連なるときだけである。
- 悪い点：たどる処理が2つの行の下で別々にキーに出会うと、そのキーは2つの行の下に現れる。そのキーの件数を知るには、読む人が2つの行を足すことになる。

### 自分自身への外部キーで続く段だけをまとめる

- 良い点：文で「directly or through each other」（直接に、または互いを通じて）と言え、連なりを正確に表せる。
- 悪い点：キーが交互に現れる、2つ以上のテーブルの循環では、段ごとに行が残る。

### 最初の何段かを示し、その先の段を1行で数える

- 良い点：示す行は、その文をそのまま保てる。
- 悪い点：数える1行は、テーブルと動作をひとまとめにして上限が頼る件数を隠すか、それらを列挙して長さを取り戻すかのどちらかになる。

### 字下げの上限だけを設ける

- 良い点：各行は1つのステップの文のままである。
- 悪い点：issue 58 は、なお 300 行を出力する。
