# ADR-0035: 挿入のときだけ設定する値を、設定に書けるようにする

## 背景と課題

多くのマスタテーブルには、`created_at` のように `NOT NULL` で既定値のない列がある。行を作るときにアプリケーションが値を設定するからである。
kortopi は、宣言が挙げない列には、新しい行でその列の既定値を与える（ADR-0011）。そのため、こうした列は宣言しなければならない。宣言しなければ、挿入する行はどれも失敗する。計画はその列を報告して止まる（ADR-0026）。

宣言すると、その列は管理する列になる（ADR-0011）。
どの環境にも宣言した時刻が入り、それと違う時刻はどの計画にも更新として出る。すでにある行の時刻を kortopi に変えてほしい人はいないにもかかわらずである。
宣言の側からデータベースに時刻を求めることもできない。宣言はどの実行でも同じ意味でなければならないため、`now()` も単語 `now` も拒まれる（ADR-0022）。

「kortopi が行を挿入するときにこの列へ値を与え、そのあとは二度と見ない」と書く手段がない。
新しい行のためだけに値が要る列を、kortopi が管理する対象から外しておくにはどうすればよいか。

## 判断の基準

- 新しい行のためだけに値が要る列は、スキーマが既定値を与えていなくても、比較と更新の対象から外せる。
- 計画は毎回同じ結果を出し、宣言のファイルと設定はコードを持たない（ADR-0013、ADR-0022）。
- どの値も、PostgreSQL がその列の型で読む。宣言した値を読むときと同じである（ADR-0009）。
- スキーマを変えられるチームにとっては、スキーマの既定値が引き続き最初の答えである。
- こうした値の誤りは、計画がどの行も読み込む前に、ほかの誤りとまとめて見つける（ADR-0024）。

## 検討した選択肢

- 機能を足さない：列にスキーマの既定値を与える
- 宣言した列に挿入時だけ設定する印を付け、すべての行に値を書く
- 設定に値を書き、挿入がそれを新しい行すべてに与える
- 設定に SQL の式を書く

## 決定

採用：「設定に値を書き、挿入がそれを新しい行すべてに与える」。設定の1行で、こうした列を宣言の外に置けるうえ、設定にコードを持ち込まず、PostgreSQL がそれぞれの値を宣言した値と同じように読むからである。

決まりは次のとおりである。

設定：

- `kortopi.toml` のテーブルの設定（ADR-0013）は `on_insert` を持てる。`on_insert` は、テーブルの列を値に対応させる。インラインテーブルでも、独立したセクションでも書ける。

  ```toml
  [tables."facility.rooms"]
  key = ["name"]
  on_insert = { created_at = "now" }
  ```

- 値は TOML の文字列に限る。整数・浮動小数点数・真偽値・TOML の日付や時刻・配列・テーブルはエラーであり、エラーは設定ファイルとテーブルと列を挙げ、値を文字列で書くよう告げる。文字列なら、書き方によって型が変わらない。ADR-0013 が設定のすべての値に求めるとおりである。
- 列は、テーブルが持つとおりの名前で書く。値は列の名前の順に並べ、計画も文もこの順で列を挙げる。2回の実行が同じものを出力するようにするためである。
- PostgreSQL は、CSV ファイルの欄を読むときと同じく、列の型で値を読む（ADR-0009）。`timestamptz` の列の `"now"` は挿入するトランザクションの時刻であり、整数の列の `"0"` は 0 であり、`""` は NULL ではなく空文字列である。NULL は書けない。NULL を許す列には値が要らない。計画と apply は、自分が固定する設定で値を読む（ADR-0023）。`"today"` は UTC での日付であり、タイムゾーンのない `timestamp` の列の `"now"` は UTC での時計の時刻である。
- 値は SQL にならない。kortopi が書く文字列リテラルとして PostgreSQL に届き、コードとしては届かない。
- `now`・`today`・`tomorrow`・`yesterday` の各単語は、読んだ瞬間の時刻になるため宣言では拒まれる（ADR-0022）が、ここでは許す。こうした値は比べることがなく、PostgreSQL は行を挿入するトランザクションの中で読むからである。これは ADR-0022 を細かくする。ADR-0022 が拒むのは宣言の値であり、`on_insert` の値ではない。

働き：

- kortopi がテーブルの行を挿入するとき、どのモードでも、挿入は `on_insert` の各列も挙げ、その値を与える。1つの文が挿入する行は、どれも同じ値を得る。
- ほかは何も変わらない。その列は比べず、更新せず、違いとして示さず、管理しない。すでにある行は、持っている値を保つ。
- これは ADR-0011 を細かくする。管理する列は引き続き宣言した列であり、新しい行はほかの列の既定値を得る。ただし `on_insert` の列は、その値を得る。ADR-0013 も細かくする。テーブルの設定は `key`・`mode`・`on_insert` になる。

検査は、すべて計画の中で、どの行を比べるよりも前に行い、テーブルごとのほかの誤りとまとめて報告する（ADR-0024）。検査は次のとおりである。

- テーブルのファイルが宣言してもいる列はエラーであり、2つのどちらかから外すよう告げる。
- 照合キーの列はエラーである。宣言したどの行も、自分のキーを持つからである。
- 生成列と、`GENERATED ALWAYS` の識別列はエラーである。どちらも挿入で値を受け取らない。
- テーブルにない列は、テーブルにない宣言した列と同じに扱う。計画の行を伴ってスキーマの変更を待ち（ADR-0016）、テーブルの列と空白か大小だけが違う名前はエラーであり（ADR-0031）、`--no-pending` があればエラーになり（ADR-0034）、apply はそこで止まる。その名前がデータファイルではなく設定から来たことは、計画の行と apply のエラーが示す。計画の行は `column floor of on_insert in kortopi.toml: known after the schema is applied` であり、apply のエラーは設定ファイルを挙げる。
- 存在するテーブルのほかのすべての値は、挿入する行がないときも含めて PostgreSQL が読む。スキーマの変更を待つテーブルの値は、その宣言した値と同じく読まない（ADR-0016）。その検査は、テーブルができてから行う。PostgreSQL が拒んだ値はエラーであり、エラーは設定ファイル・テーブル・列・引用符で囲んだ値・PostgreSQL のメッセージを挙げる。値を読む文は kortopi が自分で書くので、その文のエラーはどれも、PostgreSQL が値を拒んだことを意味する。`tsquery` の構文エラーや、`regclass` が指す存在しないリレーションも同じである。ただし、接続の切断・ロックの待ちの打ち切り・権限の不足のようなセッションのエラーは除く。セッションのエラーは、データベースのほかのエラーと同じく計画を止める。値は1つずつ、ロールバックする専用のセーブポイントの中で、その列だけを持つ一時テーブルに入れる。一時テーブルの列は、宣言の行の一時テーブルと同じく、型修飾子とドメインを含めてテーブルの列から型を受け継ぐ（ADR-0024）。そのため、拒まれた値は計画を中断させず、ほかの列が値や既定値を得ることはなく、型を名前で探すこともない。この検査はこれらの列の型を読むので、計画と apply には、宣言した列と同じくこれらの列に対する `SELECT` が要る。計画がもともと必要とする `TEMPORARY` 権限も要る。この権限は、どの値を読むよりも前にカタログで確かめる。
- どのファイルも宣言しないテーブルの `on_insert` は、そうしたテーブルのほかの設定と同じくエラーである（ADR-0022）。
- 宣言が挙げない `NOT NULL` で既定値のない列についての ADR-0026 の検査は、`on_insert` の列を除く。そのメッセージは、列を宣言することとスキーマで既定値を与えることに並べて、`on_insert` を解決策として挙げる。

出力と文：

- 計画は、挿入する行のあるテーブルについて、`on insert: created_at="now"` という行を1つ、適用待ちの列の行のあと、行の前に示す。値は、設定が書く文字列のまま、常に二重引用符で囲み、Go のエスケープを使って出す。同じ設定の2つの計画が同じ行を出すようにするためである。挿入する行のないテーブルには、この行を出さない。これは、テーブルの行を列挙する ADR-0024 を細かくする。
- apply の挿入は、宣言した列のあとに `on_insert` の列を挙げ、それぞれの値をキャストのない文字列リテラルで書く。PostgreSQL は、それを受け取る列の型でこのリテラルを読む。apply には、検査のための `SELECT` に加えて、これらの列に対する `INSERT` も要る。apply は最初の書き込みの前にそれを確かめ、文が挿入した行の件数をこれまでどおり確かめる。これは、挿入がキーと比べる列だけを挙げるとする ADR-0026 を細かくする。
- SQL としての計画の `INSERT` もこれらの列を挙げ、スクリプトがあらゆる値に使うリテラルで値を書く（ADR-0029）。文の前の2行のコメントが値を挙げ、PostgreSQL がそれをスクリプトの実行時に、そのセッションの設定で読むことを述べる。したがって `now` のような値は、スクリプトを実行するトランザクションの時刻になる。これは ADR-0029 を細かくする。ADR-0029 のリテラルはどのセッションでも同じに読めるので、スクリプトは3つの設定だけを固定し、セッションのほかの設定には手を出さない。`on_insert` の値はその例外である。計画が出力した値ではなく設定の文字列なので、スクリプトを実行するセッションの `TimeZone` や `DateStyle` のような設定に左右されうる。スクリプトの設定の上のコメントは、設定がこれらの値を固定しないことを述べる。
- まだどのファイルも宣言していないテーブルの書き出しは、生成列に並べて、設定が `on_insert` に挙げる列を除く。新しいファイルと設定がぶつからないようにするためである。書き出し直しは、そのファイルが宣言した列を保つ。これは、新しいファイルが生成列のほかのすべての列を持つとする ADR-0028 を細かくする。

### 結果

- 良い点：`created_at` のように `NOT NULL` で既定値のない列を、宣言の外に置ける。新しい行は値を得て、すでにある行は持っている時刻を保つ。
- 良い点：各環境がそれぞれの行にどんな時刻を与えても、apply のあとの計画はどの環境でも空になる。
- 良い点：設定は文字列を持つだけでコードを持たず、PostgreSQL は宣言した値と同じ規則でそれを読む。
- 良い点：存在するテーブルの値で、挿入が拒むはずのものは、挿入する行がなくても、ほかの誤りとともにプルリクエストの計画を止める。
- 良い点：テーブルの最初の書き出しは、今の設定のまま計画が受け入れるファイルを書く。
- 悪い点：計画と apply は、チームのタイムゾーンではなく、自分が固定する設定で値を読む（ADR-0023）。`today` は UTC での日付であり、タイムゾーンのない `timestamp` の列の `now` は UTC での時計の時刻である。ほかのタイムゾーンにしたいチームは、`timestamptz` の列を使うか、オフセット付きの値を書く。
- 悪い点：kortopi がテーブルに挿入する行は、どれも同じ値を得る。行ごとに違う値が要る列は、引き続き宣言しなければならない。
- 悪い点：データファイルを読む人は、`kortopi.toml` を開かなければ、新しい行が何を得るかが分からない。ADR-0013 がすべての設定について述べるとおりである。
- 悪い点：SQL としての計画は、スクリプトの実行時に、それを実行するセッションの設定で値を読む。`now` は計画の時刻ではなくスクリプトの時刻になる。また、オフセットのないタイムスタンプのように意味が設定に左右される値は、apply とは違う値として読まれることがある。オフセット付きのタイムスタンプのように、どこでも同じに読める値を書けば、後者は避けられる。
- 悪い点：値の検査は、値ごとに一時テーブルを作るので、対象のデータベースの作業が少し増える。
- 悪い点：ロールには `on_insert` の列に対する `SELECT` が要る。kortopi はその列の値を読まないが、検査がその型を読むからである。
- 悪い点：検査は値を型とドメインだけで読む。テーブルの `CHECK` 制約・外部キー・一意キーに値が反することは、apply でしか見つからない。

### 確認の方法

- `internal/config` の単体テスト（`TestLoad`、`TestLoadErrors`、`TestNew`）が、インラインとセクションの書き方、並び順、文字列でない値のエラー、未知の設定が引き続き失敗することを確かめる。
- `internal/plan` の単体テストが、偽のデータベースを使って検査を確かめる。
  - `TestBuildOnInsert` は、計画と要求に渡る値と、スキーマの変更を待つ列を確かめる。
  - `TestBuildOnInsertErrors` は、各検査・1つのテーブルの複数の誤り・大小の違う名前・`--no-pending` を確かめる。
  - `TestBuildOnInsertErrorsOfSeveralTables` と `TestBuildOnInsertDatabaseError` は、複数のテーブルの誤りとデータベースのエラーを確かめる。
  - `TestBuildMissingValues` は、`on_insert` がある場合とない場合の、`NOT NULL` の列の検査を確かめる。
  - `TestRender` のゴールデンファイル `on_insert.golden` が、計画の行を固定する。
- 文・権限・スクリプトのコメント・書き出しの列は、次の単体テストが固定する。
  - `internal/postgres` の `TestInsertColumns`・`TestRefusedValue`・`TestCheckValuesPrivileges`
  - `internal/postgres` の `TestWriteStatements`・`TestCheckWrites`・`TestScriptStatements`
  - `internal/script` の `TestWrite`（`on_insert.golden`）
  - `internal/export` の `TestRun`
- 残りは、`make check-all` で PostgreSQL 15 から 18 に対して動く結合テストが確かめる。
  - `internal/postgres` の `TestCheckValues` と `TestCheckValuesPrivilegesAndApply` は、PostgreSQL の拒む値・そのあともセッションが続くこと・検査の権限を確かめる。
  - `internal/postgres` の `TestOnInsertTypes` は、ドメイン・型修飾子・ほかのスキーマの型を値ごとに検査することと、計画が既定値のシーケンスを動かさないことを確かめる。
  - `internal/postgres` の `TestApplyOnInsert` と `TestApplyOnInsertPrivileges` は、挿入とその権限を確かめる。
  - `cmd/kortopi` の `TestOnInsertCommand` は、CSV と SQL の宣言について各モードで plan と apply を実行する。トランザクションの時刻が、apply の前後に読んだ時計の時刻の間にあることも確かめる。
  - `cmd/kortopi` の `TestOnInsertMistakes` はエラーを確かめる。`TestOnInsertScriptAndExport` は、素の接続で実行した SQL としての計画と、書き出しを確かめる。

## 選択肢の長所と短所

### 機能を足さない：列にスキーマの既定値を与える

- 良い点：kortopi に新しいものは要らず、誰が挿入しても、データベースが新しい行に値を与える。
- 良い点：スキーマを持つチームにとっては、これが引き続き最善の答えである。
- 悪い点：アプリケーションがその列を設定するチームや、別のチームが持つテーブルのスキーマを変えられないチームには、列を宣言して管理するほかに手がない。

### 宣言した列に挿入時だけ設定する印を付け、すべての行に値を書く

- 良い点：各行が、それを宣言するファイルから自分の値を得られる。
- 悪い点：ファイルのすべての行が同じ値を繰り返すことになり、しかも行ごとに違う値が要る場面はまだ見つかっていない。
- 悪い点：比べない宣言した列ができ、宣言が管理する列を挙げるという ADR-0011 の決まりが崩れる。
- 行ごとに違う値が必要になれば、この記録の設定に並べて、あとから足せる。

### 設定に値を書き、挿入がそれを新しい行すべてに与える

- 良い点：設定の1行がテーブルのすべての行に効き、PostgreSQL は宣言した値と同じようにその値を読む。
- 悪い点：新しい行はどれも同じ値を得る。

### 設定に SQL の式を書く

- 良い点：`now()` や `gen_random_uuid()` のような式なら、各行に別々の値を与えられる。
- 悪い点：対象のデータベースで動くコードを設定が持つことになる。ADR-0022 は、理由があってこれを宣言から締め出している。値であれば、設定はコードを持たずに済む。
- 悪い点：式が要る列には、スキーマの既定値のほうが合う。既定値は kortopi の挿入に限らず、あらゆる挿入に効くからである。
