# ADR-0009: 宣言した値の解釈は、一時テーブルの中で PostgreSQL に任せる

## 背景と課題

計画を立てるために、kortopi は宣言した行をデータベースの行と1つずつ組にし、値が等しいかを判定する。
宣言は値を文字列として持つ（ADR-0008）。一方、データベースは値を型付きで持ち、1つの値にはいくつもの書き方がある。
`numeric(10,2)` の列では、`1.5` と `1.50` は同じ値である。
`timestamptz` の列では、`2026-11-19 09:00:00+09` と `2026-11-19 00:00:00+00` は同じ時点である。
`jsonb` の列では、オブジェクトのキーの順番は関係ない。

文字列のまま比べる道具は、こうした値を実行のたびに違うと報告するので、計画が空にならない。
独自の規則で文字列を解析する道具は、PostgreSQL の入力の規則を、すべての型について写し取る必要がある。数値、タイムゾーン付きの日時、JSON、配列、enum、ドメイン、拡張の型である。
写し取りに漏れがあれば、そのたびに、実際にはない差分が出るか、実際にある差分を見逃す。

マスタテーブルには、大きなものもある。たとえば、約12万行の郵便番号のテーブルである。
そうしたテーブルのすべての行を kortopi に読み込んで比べると、メモリと時間がかかる。

宣言した値は誰が解釈し、比較はどこで行うか。

## 判断の基準

- 保存されている値と等しい宣言の値を、書き方が違うというだけで違うと報告しない。
- enum・配列・ドメイン・拡張の型を含め、どの列の型でも、kortopi 独自の規則なしに扱える。
- kortopi は、対象のデータベースのほかにデータベースを必要としない。
- 大きなテーブルを、すべての行を kortopi へ移すことなく比べられる。

## 検討した選択肢

- 対象のデータベースの一時テーブルに入れ、差分を SQL で求める
- 独自の型の規則で、Go で値を解釈して比べる
- 宣言を別の開発用データベースに入れる

## 決定

採用：「対象のデータベースの一時テーブルに入れ、差分を SQL で求める」。宣言の値を、PostgreSQL が本物のテーブルの値と同じ規則で読むからである。そのため、等しい値は等しいと判定され、どの型も扱え、2つ目のデータベースも要らない。

決まりは次のとおりである。

- kortopi は、宣言したテーブルごとに、本物のテーブルの列と同じ型の列を持つ一時テーブルを、自分のセッションに作る。このテーブルはセッションとともに消える（ADR-0010）。
- SQL の宣言は、その INSERT 文として実行する。テーブル名だけを一時テーブルの名前に差し替え、値は書かれたままにする（ADR-0015）。
- CSV ファイルは、CSV 形式の COPY でクライアントから読み込む（`COPY ... FROM STDIN`）。そのため、ファイルをデータベースのサーバーに置く必要はない。
- CSV ファイルは、CSV 形式の COPY の規則に従う。引用符のない空の欄は NULL であり、`""` は空文字列である。文字コードは UTF-8 とする。
- 一時テーブルと本物のテーブルの差分（挿入・更新・削除する行）は、データベースの中で、SQL によって求める。行は照合キーで組にし（ADR-0012）、比べるのは宣言した列だけである（ADR-0011）。

型ごとの比べ方は、原則をこの記録で決め、詳細は plan の実装のときに決める。対象は、numeric の小数点以下の桁数（scale）、`timestamptz`、`jsonb` のキーの順番、配列、enum、NULL と空文字列である。
型ごとの振る舞いはテストで固め、文書に書く。

### 結果

- 良い点：日付・数値・JSON の文書・配列・enum の値は、一時テーブルでも本物のテーブルと同じ形になる。そのため、等しい値を違うと報告しない。
- 良い点：列に入らない値は、計画を立てる前の読み込みの時点で、PostgreSQL 自身のエラーメッセージとともに失敗する。知らない enum のラベル、`2026-02-30` という日付、整数の列に入れた文字列などである。
- 良い点：約12万行の郵便番号のような大きなテーブルも、データベースの中で比べられ、外に出るのは差分だけである。
- 良い点：値をそろえるための2つ目のデータベースが要らない。
- 悪い点：計画を立てるには、対象のデータベースへの接続と、そこで一時テーブルを作れること（データベースに対する TEMPORARY 権限）が要る。
- 悪い点：計画のたびに、宣言したすべての行を対象のデータベースに読み込む。対象は本番のデータベースかもしれず、その仕事の量は宣言の大きさに比例する。
- 悪い点：宣言は、データベースなしには検査できない。値の誤りは、読み込んだときに初めて見つかる。
- 悪い点：CSV は、スプレッドシートの慣習ではなく COPY の規則に従う。空のセルは NULL になるので、空文字列でなければならない値は `""` と書く必要がある。
- 悪い点：本物のテーブルにまだない宣言の列は、読み込めない。計画は、その列に適用待ちのスキーマの変更があることを示す（ADR-0016）。

### 確認の方法

PostgreSQL 15〜18 に対する結合テストで、この決定を確かめる。
テストは、この記録が挙げた型ごとに宣言を読み込み、次のことを確かめる。保存されている値と等しい値を違う書き方で書いても計画が空になること、値を変えれば更新になること、引用符のない空の CSV の欄が NULL として、`""` が空文字列として読み込まれることである。
これらのテストは、型ごとの比べ方の文書とともに、plan の実装で加わる。

## 選択肢の長所と短所

### 対象のデータベースの一時テーブルに入れ、差分を SQL で求める

- 良い点：本物のテーブルと同じく、PostgreSQL 自身の入力の規則が、どの型のどの値も読む。
- 良い点：比較は、行がすでにある場所で行われる。
- 悪い点：計画のたびに、宣言を対象のデータベースに読み込む。
- 悪い点：そのデータベースに対する TEMPORARY 権限が要る。

### 独自の型の規則で、Go で値を解釈して比べる

- 良い点：比べ方を kortopi が自分で決められ、データベースがなくても宣言を検査できる。
- 悪い点：kortopi が、型ごとに PostgreSQL の入力の規則を写し取ることになる。漏れがあれば、そのたびに偽の差分が出るか、差分を見逃す。
- 悪い点：拡張の型のように kortopi が知らない型は、まったく比べられない。
- 悪い点：比べるために、本物のテーブルのすべての行を kortopi に読み込む必要がある。大きなテーブルでは、メモリと時間がかかる。

### 宣言を別の開発用データベースに入れる

- 良い点：値を解釈するのは、やはり PostgreSQL である。
- 良い点：対象のデータベースは、計画のために読まれる以外の仕事をしない。
- 悪い点：2つ目のデータベースを動かし、PostgreSQL のバージョンもスキーマも対象と同じに保つ必要がある。2つの間に違いがあれば、値の読まれ方が変わる。たとえば、片方にしかない enum のラベルである。
- 悪い点：宣言の行と対象の行が2つのデータベースに分かれる。そのため、比較のためには結局、両方の行を kortopi に集めて1行ずつ突き合わせる必要がある。
