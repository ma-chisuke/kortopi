# ADR-0039: 外部キーを通じた削除の波及を計画ですべて求め、行から離して示し、安全策でそのすべてを数える

## 背景と課題

ADR-0027 は、削除する行のあるテーブルごとに、それを参照するほかのテーブルの行を1段目で数える。そして `--max-delete` に、外部キー `ON DELETE CASCADE` がその段で消す行を数えさせる。
深い段まで数えない理由には、段ごとにかかる費用を挙げている。apply が自分で書いた行については、削除の前にもう一度数える。

実際に使うと、削除は計画が示した以上のことを、次の4つの形でした。

- `ON DELETE SET NULL` と `SET DEFAULT` は、数えもせず止めもしなかった。`--allow-delete --max-delete 1` で、1行の削除がほかのテーブルの30行の列を NULL にし、apply は `Applied: 0 inserted, 0 updated, 1 deleted.` と出した。参照しているテーブルを読めないロールでも同じことが起きた。`CASCADE` なら、そうしたテーブルで apply は止まる。
- カスケードは1段目だけを数えた。計画は、注文のテーブルの1行が消えると示した。しかし apply は、既定の上限 100 の範囲で、その注文とその明細5万行、明細のメモ2000行を消した。
- カスケードが、宣言がまだ持つ行を消し、apply はコミットした。モード `sync` のテーブルが行を失い、別の宣言したテーブルの宣言した行がそれを `ON DELETE CASCADE` で参照していた。自分自身を参照するテーブルでも、親が消え、宣言した子が残る宣言で同じことが起きた。次の計画は、宣言した行をもう一度挿入しようとした。ADR-0027 の数え直しは、apply が書いた行しか見ない。
- 参照の行は誤解を招いた。参照の行はテーブルごとに1回、最後の削除する行の下に置いたので、その行に属するように読めた。同じ計画が削除する行や、削除の前に別の行を指すように変える行も数えたので、計画は削除が失敗すると伝え、そのあと apply は成功した。`--max-delete` はそうした行を2回数え、4行を削除するときに `would delete 6 rows` と出した。

計画は、削除がすることをどう知り、どう示し、安全策は何を数えるのか。

## 判断の基準

- apply は、出力が告げていない状態をコミットしない。失敗した apply は何も変えない（ADR-0026）。
- 誤りがどの段まで広がっても、外部キーのどの動作を通じてでも、上限がそれを捉える。
- 自己矛盾する宣言は、何も書く前に計画が見つける誤りである。
- レビューする人は、各削除がすることを、すべての段について計画で読める。どの数も正確であり、どの行も1回だけ数える。
- kortopi が作るのはセッションの一時テーブルだけであり（ADR-0010）、計画はどのテーブルも変えない（ADR-0016）。
- ロールの読めないテーブルがあっても、計画は失敗しない（ADR-0027）。

## 検討した選択肢

- トランザクションの中ですべての外部キーを最後までたどり、たどり着いた行を一時テーブルに控え、そのすべてを数える
- 深い段のカスケードは分からないものとし、apply をそこで止める
- セーブポイントの中で削除し、削除がしたことを測ってロールバックする
- 1つの再帰的な問い合わせで外部キーをたどる

## 決定

採用：「トランザクションの中ですべての外部キーを最後までたどり、たどり着いた行を一時テーブルに控え、そのすべてを数える」。問い合わせだけで、どのテーブルにも書かずに、すべての段とすべての動作について正確な数が得られる。そのため、計画・上限・宣言の検査が、同じ数に基づけるからである。
これは、ADR-0024・ADR-0026・ADR-0027・ADR-0029・ADR-0037・ADR-0038 を文ごとに細かく定める。それらの文は、最後の規則が挙げる。

規則は次のとおりである。

削除の波及：

- kortopi は、テーブルごとに、その削除する行を参照するすべての外部キーをたどる。どのスキーマのどのテーブルからでも、そのテーブル自身からでもたどる。そのテーブルのパーティションを指すキーも、テーブルの上にあるパーティションテーブルを指すキーも同じである。続けて、カスケードが消す行を参照する外部キーを、同じように1段ずつたどる。新しい行を消さない段に着いたら終わる。どの行にも1回しかたどり着かないので、自分自身を参照するテーブルやカスケードの循環でも、たどる処理は終わる。
- PostgreSQL 18 が許す `NOT ENFORCED` の外部キーには、トリガーがない。PostgreSQL はその動作も検査も働かせないので、削除はそれを通じて何もせず、たどる処理はそれを除く。問い合わせが列 `conenforced` を挙げるのは、その列を持つ PostgreSQL 18 以降だけである。
- 外部キーの `ON DELETE` の動作は、消える行を参照する行に、次のことをする。
  - `CASCADE` はそれらを消す。たどる処理は、それらを参照する外部キーへ続く。
  - `SET NULL` と `SET DEFAULT` は、キーの列か、PostgreSQL 15 以降の列の一覧が挙げる列を設定して、それらを変える。変わる行から先はたどらない。
  - `NO ACTION` と `RESTRICT` では、そうした行が残る間、削除が失敗する。そのことを伝えるために数える。
- 計画が自分で削除する行は、波及ではなく、削除が失敗する理由にもならない。
- 参照している行は、apply が削除より先にする挿入と更新のあとの状態で数える（ADR-0026）。宣言した行が照合する保存された行は、更新するモードのテーブルなら、比べる列に宣言した値を持つ。挿入する行は、宣言が外部キーのすべての列を挙げるときに、宣言した値を持つ。そのため、計画が残る行を指すように変える参照は、波及にならない。
- 宣言したテーブルは、参照しているテーブルの行のうち、パーティションの木での `tableoid` が自分に属する行を持つ。参照しているテーブルが、宣言したテーブル自身か、そのパーティションか、その上にあるパーティションテーブルの場合である。そのため、外部キーをパーティションテーブルに定義してそのパーティションを宣言したときも、その逆のときも、宣言した行を宣言した行として数える。これは、計画が削除するか変える行にも、削除とぶつかる宣言した行にもあてはまる。
- どの行も1回だけ数える。カスケードが消す行は、変わる行にも、削除を妨げる行にも数えない。同じ種類の行のあいだでは、最初にたどり着いたステップのもとで数える。最も浅い段が先であり、同じ段では、参照しているテーブル・外部キーの名前・参照されるテーブルの順になる。2つのテーブルの削除がたどり着く行は、計画で先に来るテーブルのものとして数える。
- `SET NULL` や `SET DEFAULT` が、別の外部キーの参照する列を変えると、PostgreSQL はそのキーの `ON UPDATE` の動作を働かせる。kortopi はそれをたどらない。変わる行は数え、そのステップの波及は分からないと印を付ける。

求め方：

- すべてのテーブルを比べたあとで、計画は、削除する行のあるテーブルの削除の波及を、計画の順にまとめて1回だけデータベースに尋ねる。データベースは、計画のトランザクションの中で、外部キーと段ごとに1つずつ問い合わせる。削除は決して実行しない。
- たどり着いた行は、スナップショットでの行の識別子 `tableoid` と `ctid` で、`ON COMMIT DROP` のセッションの一時テーブルに控え、段ごとに統計を取る。削除する行そのものは、計画が見つけるのと同じように、宣言の行で見つけ、識別子では見つけない。宣言した行が照合しない保存された行であり、削除のバッチが照合キーで選ぶ行と同じである（ADR-0037）。
- たどる処理・もう一度たどる処理・削除のあとの検査は、ADR-0023 と ADR-0037 の固定した設定のもとで、書き込みのバッチの合間に実行し、バッチの中では実行しない。どの関数と演算子もスキーマ付きで挙げる。外部キーは、PostgreSQL が行を結び付けるのと同じく、そのキー自身の等価演算子と照合順序でたどる。計画がテキストで比べる型（interval など）でも同じである（ADR-0040）。
- 計画は、apply と同じように、すべてのテーブルの宣言の行を、計画が終わるまで読み込んだままにする。たどる処理が、たどり着いたすべてのテーブルの宣言の行を読むからである。計画の終わりのロールバックが、それらをすべて消す。
- 各段では、外部キーごとに集合単位の問い合わせを1つ使い、参照しているテーブルをそれぞれ1回読む。そのため、参照する側の列にインデックスのない外部キーでは、たどる段ごとに、参照しているテーブル全体を読む。PostgreSQL 自身は、外部キーのトリガーを通じて1行ずつ削除する。そのため削除では、そうしたテーブルを、消える行ごとに1回読む。
- 費用の大きさは、1回の測定で示す。2026-11-22 に、Apple M2 と 8 GB のメモリを持つノートパソコンのコンテナで、PostgreSQL 18.7 に対して `TestEffectsOnLargeTables` を実行した。データ競合の検出器は使わず、書き込みは ADR-0037 のバッチである。1行の削除が 500 行へ、さらに 25000 行へカスケードし、200000 行のテーブルの 100000 行を NULL にする。参照する側の列にインデックスがないとき、波及を含む計画は 0.6 秒かかった。インデックスがあるときは、計画が 0.4 秒、削除が 0.5 秒、削除のあとの検査とコミットが 0.1 秒かかった。インデックスのない削除は、テストでは実行しない。PostgreSQL が、消える 25000 行のそれぞれについて、200000 行のテーブルを1回ずつ読むからである。
- ステップの波及は、次のどれかの理由があれば分からないものとし、その先はたどらない。どの段のステップでも、どの動作でも同じである。apply のエラーは、理由ごとに別の助言を示す。
  - ロールが、参照しているテーブルのスキーマを使えない。
  - ロールが、参照しているテーブル全体を読めない。行の識別子はシステム列であり、列の権限には含まれないからである。宣言したテーブル（自分自身を参照するテーブルなど）でも同じである。計画と apply の書き込みには、その宣言した列だけで足りても変わらない（ADR-0024、ADR-0037）。
  - 参照しているテーブルに、ロールに対する行単位セキュリティがかかる。
  - ロールが、参照される列を読めない。ADR-0027 では、これは要らなかった。宣言したテーブルでは、1段目なら参照される列で足りる。削除する行は、宣言の行で見つけるからである。1段目より先と、宣言したテーブルの上にあるパーティションテーブルでは、たどる処理が参照される行の識別子を読む。そのため、参照されるテーブル全体に対する `SELECT` が要る。
  - 外部キーの動作を担う PostgreSQL のトリガーが無効である。そのため、動作は数えたとおりには動かない。
  - 上のとおり、別のキーの `ON UPDATE` の動作が、そのステップに続く。
- まとめた行は、波及が分からない外部キーを、いくつのテーブルや段がたどり着いても1回だけ数える。

計画が示すもの：

- ADR-0027 の参照の行はなくなる。削除がほかの行に及ぶテーブルには、件数の行のあとに、削除する行から離して、まとまりを置く。

  ```text
  m.plan (sync, key: code)
    - code=legacy
    0 to insert, 0 to update, 1 to delete
    Through foreign keys, the deletion of this row also reaches other rows:
      1 row of t.orders (plan_id) references it through orders_plan_id_fkey, ON DELETE CASCADE, so the deletion deletes this row too.
        50000 rows of t.order_line (order_id) reference that row of t.orders through order_line_order_id_fkey, ON DELETE CASCADE, so the deletion deletes these rows too.
          2000 rows of t.line_note (line_id) reference those rows of t.order_line through line_note_line_id_fkey, ON DELETE CASCADE, so the deletion deletes these rows too.
  ```

- 各ステップは1文である。どのテーブルのどの行が、どの外部キーと動作を通じて、どの行を参照し、削除がそれらに何をするかを述べる。n+1 段目のステップは、それが参照するテーブルの行を消す最初の n 段目のステップの下に、2文字深く字下げして置く。そして、それらの行のどれかを参照する行を数える。数えられなかったステップは、その理由を伝える。
- 件数に行を足さないステップは除く。その外部キーを通じて参照する行がないとき、参照している行を計画が自分で削除するか別の行を指すように変えるとき、それを通じて参照する行をすべて前のステップが数えたときである。
- `Plan:` の行のあとに、すべてのテーブルをまとめた行を、事実ごとに1行ずつ置く。削除がさらに消し、変える行、削除を失敗させる行、そして波及が分からない外部キーの数である。そうした波及のない計画は、これらの行を出さないので、出力は前と変わらない。
- SQL としての計画（ADR-0029）は、参照の行のかわりに、まとまりをテーブルの削除の上にコメントとして書き、まとめた行を冒頭のコメントに書く。
- コミットのあとの `Applied:` の行は変わらない。削除が行を消すか変えたときは、そのあとに `Through foreign keys, the deletions also deleted <n> rows and changed <n> rows.` の行が続く。その数は、削除のあとの検査が確かめたものである。`--allow-delete` がなければ、`Not deleted:` の行が、削除がさらにするはずのことを伝える。

安全策：

- `--max-delete` は、実行の削除が消すか変えるすべての行を数える。宣言したテーブルの削除する行、カスケードがすべての段で消す行、`SET NULL` と `SET DEFAULT` が変える行であり、どれも1回だけ数える。エラーは、それぞれの部分を1回ずつ挙げる。

  ```text
  kortopi: the apply would delete 52004 rows, more than the limit of 100: 1 row of m.plan and 2 rows of m.plan_feature to delete, and 52001 rows that ON DELETE CASCADE deletes with them (2000 rows of t.line_note, 50000 rows of t.order_line, and 1 row of t.orders): check the rows to delete with kortopi plan, and if they are right, raise the limit with --max-delete 52004
  ```

- `--allow-delete` があるとき、`CASCADE`・`SET NULL`・`SET DEFAULT` の波及が分からなければ、どの段のものであれ、apply はどの書き込みよりも前に止まる。エラーは、理由と、与える権限か変えることを伝える。`NO ACTION` と `RESTRICT` では、これまでどおり、削除のときに PostgreSQL が決める。ただし、外部キーのトリガーが無効なら、PostgreSQL はそのキーの動作も検査も働かせないので、どの動作でも apply は止まる。
- `--allow-delete` がなければ、削除は見送り、その波及とともに報告する。その波及は何も止めない。上限も、分からない波及も、apply を止めない。唯一の例外は、下の削除とぶつかる宣言した行である。それは削除の誤りではなく、宣言の誤りだからである。

削除とぶつかる宣言した行：

- 削除の波及が、宣言の持つ行に着くことがある。宣言した行が照合する保存された行か、挿入する行である。カスケードがそれを消すか、`SET NULL` や `SET DEFAULT` がその宣言した列を設定するなら、宣言は自己矛盾している。どの apply も、データベースを宣言どおりにできない。計画も apply も、`--allow-delete` の有無にかかわらず、これを誤りとして報告する。報告は、差分だけが示すほかの誤り（ADR-0026）と一緒に、どの書き込みよりも前にする。エラーは、ファイル・宣言したテーブル・外部キーを挙げ、宣言した行を、消える行を添えて5行まで挙げる。そして、何をすればよいかを伝える。

  ```text
  kortopi: data/m/plan_feature.csv: declared rows of table m.plan_feature reference rows that the deletions remove, through foreign key "plan_feature_plan_id_fkey" (plan_id) to table m.plan, so ON DELETE CASCADE would delete them too, and the declaration contradicts itself: id=2 references code=legacy and id=3 references code=legacy: remove these rows from the declaration too, or point them at rows that stay
  ```

- 更新しないモード（モード `insert`）のテーブルは、保存された行をキーだけで比べる。そのため、その保存された行が削除とぶつかるのは、`SET NULL` か `SET DEFAULT` がそのキーの列を設定し、宣言した行をなくすときだけである。ほかの列の変更は、行を宣言どおりに保つので、波及の変わる行として、ほかの行と同じく数えて示す。挿入する行は宣言した値を得るので、どのモードでも削除とぶつかる。カスケードが消す行も、どのモードでも削除とぶつかる。
- たどる処理は、そうした行から先へは進まない。`NO ACTION` か `RESTRICT` で削除する行を参照する宣言した行は、削除を失敗させ、ほかのテーブルと同じく削除を妨げる行として数える。

`--allow-delete` 付きの apply の順番：

1. 波及を含む計画が先に来る。安全策も、削除とぶつかる宣言した行も、上のとおり、どの書き込みよりも前に apply を止める。
2. どの書き込みよりも前に、apply は、トランザクションが削除し更新した行の数をセッションが数えることを確かめる。削除のあとの検査がその数を読む。PostgreSQL がそれを数えるのは、既定のとおり `track_counts` が on のときだけである。サーバー・データベース・ロール・接続のオプションで `track_counts` が off なら、どの削除も、計画が数えたより少なくしたように見える。そのため apply はここで止まる。エラーはその設定を挙げ、それを on のままにするセッションで適用するか、行を削除せずに適用するよう伝える。削除のない apply には、その数は要らない。
3. apply は挿入し、更新する（ADR-0026）。
4. 最初の削除の直前に、同じ問い合わせで外部キーをもう一度たどり、着いたものを計画とステップごとに比べる。同じ段の同じ外部キー、同じ数、波及が分からない同じ理由である。apply が書いた行に、いまは着くことがある。列の既定値・`on_insert` の値・トリガー・計画のあとに作られたルールが、宣言に現れない参照をその行に与えた場合である。そうした書き込みが働かせる宣言したテーブルのルールは、すでに計画を止める（ADR-0038）。削除がいま消すか変える宣言した行は、それを宣言したファイルとこれらの原因を添えて、削除とぶつかる宣言した行として報告する。そのほかの違いでは、apply は、食い違う最初のステップ・計画の数・いまの数・同じ原因を挙げるエラーで止まる。宣言が挙げない列の変更は、参照を計画が数えたとおりに保つので、そのまま通る。
5. 削除は、参照するテーブルから参照されるテーブルへの順にする。削除する行に別のテーブルからのカスケードが着くテーブルは、そのテーブルより先にする。そうしなければ、カスケードがそれらの行を先に消すので、そのテーブルのバッチの選ぶ行は減り、その文は失敗する。その文は、計画が示す数だけ行を消さなければならないからである（ADR-0026、ADR-0037）。2つの順番が両立しないときは、外部キーの順番のままにする。
6. 削除のあと、コミットの前に、次の規則のとおり波及を検査する。検査は割り込みで止められ、検査の間の割り込みは apply をロールバックする。
7. コミットする。セッションの設定と `COMMIT` は、1つのメッセージで送る（ADR-0037）。検査とコミットの間には、何も実行しない。

削除のあと：

- 削除の波及は、apply のトランザクションの分離レベル `REPEATABLE READ` のスナップショットで数え、削除は同じトランザクションで実行する。
- PostgreSQL は、外部キーの動作を最新の行で実行し、動作が消すか変える行のそれぞれを、トランザクションのスナップショットと照らし合わせる。スナップショットにない行なら、直列化の失敗になる。そのため、スナップショットのあとで別のトランザクションが、たどったテーブルに挿入したか変えた参照している行は、削除を同時の変更のエラー（ADR-0026）で失敗させ、何も書かれない。
- スナップショットのあとで別のトランザクションが削除したか、別の行を指すように変えた参照している行には、外部キーの動作が着かない。そのため、削除がすることは、数えたより少なくなりうる。削除のあとの検査は、波及が消えるか変わると数えた行を、すべて行の識別子で読む。スナップショットにまだある行があれば、apply は止まる。`BEFORE DELETE` か `BEFORE UPDATE` のトリガーが残した行も同じである。
- スナップショットでのカタログの問い合わせには、そのあとで別のトランザクションが足した外部キーやパーティションが見えない。一方、PostgreSQL が外部キーの動作に使うのは最新のカタログである。そのため検査は、トランザクションが最初の削除から各テーブルで削除し更新した行の数も、`pg_stat_xact_user_tables` から読む。数は、各リレーションの一番上のパーティションテーブルでまとめる。どのテーブルも、計画がそこから削除する行と波及が数えた行を失っていなければならず、波及が着かなかったテーブルは、行を失いも変えもしていてはならない。ここで apply を止めるのは、次のものである。別のトランザクションが足した外部キーかパーティション、ほかのテーブルの行を消すか波及が着かなかったテーブルの行を変えるトリガーかルール、外部キーの無効なトリガーである。そのとき、何も書かれない。
- 計画は、apply が働かせる宣言したテーブルのルールで止まる（ADR-0038）。しかし、カスケードは、それが着くテーブルのルールも働かせる。宣言が持たないテーブルのルールと、モードが削除しない宣言したテーブルの `ON DELETE` のルールである。`SET NULL` と `SET DEFAULT` なら `ON UPDATE` のルールである。そうしたルールが消すもの、ほかで変えるもの、残すものは、上の検査が見つける。`DO INSTEAD NOTHING` のように、カスケードの問い合わせを何もしないものに変えるルールでは、PostgreSQL 自身がカスケードを止める。apply はそのエラーをそのまま伝える。
- 見えないまま残るのは、削除の数と、波及が着かなかったテーブルの数では示せないことである。
  - 削除の間にトリガーかルールが挿入する行。
  - 波及が着くテーブルで、波及が数えた行を超えてトリガーかルールが変える行。
  - `SET NULL` のキーと `CASCADE` のキーの両方で削除する行を参照する行について、PostgreSQL がどちらの動作を先に実行するか。計画はその行を消える行として数え、最後には実際に消える。
  - コミットまで遅らせた制約トリガーが消すか変える行。それは、コミットのときに、検査のあとで働く。

細かく定めるもの：

- 前の記録の次の文は、書かれたとおりにはもう成り立たない。
  - ADR-0024：「そのテーブルを比べ終えたらすぐにセーブポイントをロールバックする。データベースの中にある宣言の行は、常に1つのテーブルの分だけである。」計画は、すべてのテーブルの宣言の行を終わるまで保つ。
  - ADR-0026 の作業の順番：「7. 段階 2 は逆の順である。安全策が削除を許すときに削除する。」の前に2回目のたどる処理を置き、削除は上の順番でする。そのあと、「8. コミットする。」の前に検査を置く。「計画は、引き続き、テーブルを比べ終えるとすぐにその行を捨てる」も、もう成り立たない。
  - ADR-0027：上限は、カスケードが消す行を「1段目まで数える」。参照している行を実行が自分でも削除するなら、「その行は2回数える」。上限は、いまはすべての段と変わる行を、どれも1回だけ数える。参照の件数を読めない理由には「キーのどちらかの側の列に対する `SELECT` がないこと」を挙げた。たどる処理には、参照しているテーブル全体に対する `SELECT` が要る。「件数は、テーブルの削除する行の下に、テーブルごとに1回だけ示す」は、まとまりに置き換わる。「テーブルの行を削除する直前に、apply はトランザクションの中で参照をもう一度数える」は、2回目のたどる処理に置き換わる。「apply はほかの変更をし、削除する行は残し」は、`--allow-delete` がないとき、削除とぶつかる宣言した行がなければ今も成り立つ。その確認の方法では、`internal/plan/testdata/effect.golden` が `references.golden` を置き換える。`TestEffectsOfColumnsThatTheRoleMayNotRead` は `TestReferencesToColumnsThatTheRoleMayNotRead` を置き換える。`TestApplyEffectAgainAfterTheWrites` は `TestApplyReferencesAgainBeforeDeletes` を置き換える。
  - ADR-0037：固定した設定のままのものに、「削除の前に参照を数え直すこと（ADR-0027）」を挙げる。それにかわるもう一度たどる処理も、たどる処理も、削除のあとの検査も、固定した設定のままである。書き込みごとに加わる選んだ行の一時テーブルと `on_insert` の値の一時テーブルは、たどる処理の一時テーブルと同じく、検査が読む数から除く。
  - ADR-0038：「モードが決して書かない種類の文のルールは発動しえないので、誤りではない。」ほかのテーブルの削除からのカスケードや `SET NULL` は、それを働かせる。それは計画の誤りではないままとし、それがすることは削除のあとの検査が見つける。「行数の確認は、トリガー、カスケード、計画のあとに作られたルールのために残る」。削除のあとの検査も、それらと、削除が着くテーブルのルールのために残る。
  - ADR-0029：「計画の参照の行（ADR-0027）は、そのテーブルの削除の上にコメントとして置く」の位置には、いまはまとまりを置く。「スクリプトの中には、`--max-delete` を当てはめるものも、参照を数え直すものもない」。外部キーをもう一度たどるものも、削除のあとに波及を検査するものもない。「そのあとに削除を、参照するテーブルから参照されるテーブルへの順に置く」は、上の削除の順番になる。

### 結果

- 良い点：どの段でも、どの動作を通じてでも、上限を超えて消すか変える実行は、何も変えない。そのエラーは、数を作る部分をそれぞれ1回ずつ伝える。
- 良い点：ロールの読めないテーブルの列を設定する削除は、カスケードと同じく、どの書き込みよりも前に止まる。エラーは、理由ごとに何を与えればよいかを伝える。
- 良い点：自分の行が必要とする行を削除する宣言は、コミットのあとではなく、プルリクエストの計画で失敗する。
- 良い点：レビューする人は、削除する行から離して、削除が着くすべての段を読める。数は合う。どの行も1回だけ数え、計画が削除するか変える行は数に入らない。
- 良い点：apply の出力は、削除がほかのテーブルで消し、変えた行を挙げ、apply はそれをコミットの前に確かめた。apply を止めるのは、自分の書き込みが与えた参照・別のトランザクション・新しい外部キーやパーティション・ほかのテーブルの行を消すトリガーやルールであり、そのとき何も書かれない。
- 悪い点：ADR-0027 のもとで通った実行が、いまは止まる。
  - `--max-delete` がカスケードのすべての段と、`SET NULL` と `SET DEFAULT` が変える行を数えるので、上限の内にあった実行が上限を超えうる。注文の明細5万行を下に持つ1行の削除は、`--max-delete 100` で止まる。
  - `SET NULL` か `SET DEFAULT` が、ロールの読めないテーブルか、一部の列しか読めないテーブルに着くと、`--allow-delete` 付きの apply は止まる。
  - 削除とぶつかる宣言した行は、計画と、`--allow-delete` のない apply を止める。その apply は、これまでは削除を見送っていた。
  - 計画の `referenced by` の行や、SQL としての計画のそのコメントを読む道具は、それらを見つけられなくなる。
  - 列の既定値・`on_insert`・トリガー・ルールが、削除の着く行への参照を書くと、`--allow-delete` 付きの apply は止まる。
  - ほかのテーブルの行を消すトリガーやルール、削除が着かないテーブルの行を変えるトリガーやルール、外部キーの無効なトリガーは、`--allow-delete` 付きの apply をコミットの前に止める。
  - `track_counts` が off のセッションは、削除する行のある `--allow-delete` 付きの apply を、どの書き込みよりも前に止める。
  - 削除する行を参照するテーブルを一部の列しか読めないロールは、`--allow-delete` 付きの apply で止まる。自分自身を参照する宣言したテーブルも含む。ADR-0024 と ADR-0037 では、宣言した列だけで適用できた。

  フラグは、変わる行も数えるようになったが、`--max-delete` という名前を保つ。`SET NULL` が変える行は、消える行がすべてを失うのと同じく参照を失い、上限が防ぐのはその両方である。新しい名前は、このフラグを渡すすべてのパイプラインを壊す。
- 悪い点：計画と apply は、削除が着くすべてのテーブルを、すべてのカスケードの最後まで読む。そのため、アプリケーションが使うデータベースで、インデックスのない参照しているテーブルを、段ごとに全体を読む費用がかかる。
- 悪い点：参照しているテーブルをたどるには、テーブルに対する `SELECT` が要る。ADR-0027 で要ったのは、キーの列に対するものだけだった。
- 悪い点：計画は、終わるまで宣言のすべての行を読み込んだままにする。そのため、apply と同じく、一時テーブルの場所とロックを取る。
- 悪い点：`SET NULL` や `SET DEFAULT` が働かせる `ON UPDATE` の動作はたどらず、`--allow-delete` 付きの apply をそこで止める。
- 悪い点：2つの外部キーがたどり着く行は、その一方のもとでだけ示す。そのため、もう一方の行は、それを通じて参照する行より少なく数える。
- 悪い点：計画はトリガーとルールをたどらない。削除のあとの検査は、それらが波及の外で消し、変えるものを止めるが、見えないまま残る行は止めない。apply の更新が働かせる `ON UPDATE` の動作も、これまでどおり示さない（ADR-0027）。
- 悪い点：検査は PostgreSQL の数に頼るので、削除する apply には `track_counts` の on が要る。

### 確認の方法

- `internal/plan` の単体テストが、まとまり・まとめた行・削除とぶつかる宣言した行を確かめる。`TestRender`（`internal/plan/testdata/effect.golden`）・`TestBuildEffects`・`TestBuildConflicts`・`TestTotalsCountUnknownKeysOnce` である。
- `internal/apply` の単体テストが、安全策と apply の順番を確かめる。
  - `TestRun` と `TestRenderSummary`：各部分を1回ずつ挙げる上限、分からない波及での停止、`--allow-delete` のない実行、計画のあとの行。
  - `TestRunEffectAgain`：2回目のたどる処理。別の数、別のステップ、書き込みのあとの削除とぶつかる宣言した行を使う。コミットの前の、削除のあとの検査も確かめる。
  - `TestRunInterruptedDuringTheCheck`：削除のあとの検査の間の割り込み。
  - `TestDeletionOrder` と `TestRunDeletesReachedTablesFirst`：削除の順番。
  - `TestRun` の「the session cannot check the deletions」：`PrepareDeletes` のエラーが、どの書き込みよりも前に apply を止める。
- `internal/script` のゴールデンテスト `TestWrite` が、SQL としての計画のコメントを確かめる。
- `make check-all` の PostgreSQL 15 から 18 に対する結合テストで、`internal/postgres` の次のものが確かめる。
  - `TestEffectsOfEveryAction`：50,000 行への3段のカスケード、列の一覧の有無それぞれの `SET NULL`、`SET DEFAULT`、`NO ACTION`、`RESTRICT`、1段目と2段目のロールの読めないテーブル。
  - `TestEffectsThroughTreesDiamondsAndCycles`：木・ひし形・循環。そのあと削除が消す行を、素の接続で数える。
  - `TestEffectsOfKeysAndPartitions` と `TestReferences`：複合キー・主キーでない一意キー・パーティションテーブル。
  - `TestEffectsOfDeclaredPartitions`：外部キーをパーティションテーブルに定義した、宣言したパーティションと、その逆。
  - `TestEffectsReachOtherDeletions`：削除する行に別のテーブルからのカスケードが着くテーブルと、外部キーの無効なトリガー。
  - `TestEffectsOfNoActionAndRestrict`：`NO ACTION`・`RESTRICT`・コミットまで遅らせた `NO ACTION`。まとめて消える部分木と、残る宣言した行を使う。
  - `TestEffectsThatAnUpdateFollows`：別の外部キーが参照する列の `SET NULL`。
  - `TestReferencesAcrossCollationsAndPartitions`：照合順序と、パーティションを指す外部キー。
  - `TestEffectsOfRowsThatThePlanChanges`：計画が削除するか変える行と、削除とぶつかる宣言した行。挿入する行と、カスケードが着く行も含む。
  - `TestEffectsOfColumnsThatTheRoleMayNotRead`：権限と行単位セキュリティ。それぞれの理由を確かめる。
  - `TestApplyEffectAgainAfterTheWrites`：2回目のたどる処理。
  - `TestApplyEffectAfterConcurrentChanges`：2つ目の接続から、別のトランザクションが参照している行を挿入・削除するか別の行を指すように変え、外部キーとパーティションを足す。行を残すトリガー、PostgreSQL が拒むルール、ほかのテーブルの行を消すトリガーも使う。
  - `TestEffectsOnLargeTables`：大きなテーブルでの費用。最新のバージョンだけで測る。
  - `TestEffectsOfAModeThatDoesNotUpdate`：モード `insert` で、`SET NULL` がキーの外を変える保存された行、`SET DEFAULT` が変えるキー、挿入する行。
  - `TestEffectsLeaveOutKeysNotEnforced`：`CASCADE` と `NO ACTION` の `NOT ENFORCED` のキー。PostgreSQL 18 で確かめる。
  - `TestApplyNeedsTrackCounts`：セッションのオプションとロールの設定で off にした `track_counts`。
  - `TestEffectsOfForeignKeysOfIntervals`：テキストは違うが互いに等しい interval の外部キー。たどる処理がテキストで比べると、このテストは失敗する。
  - ADR-0037 の `TestApplyWhenRowLevelSecurityComesToApply`。いまは削除の前に外部キーをたどる。
- `cmd/kortopi` の `TestApplyEffectOfDeletions`・`TestDeclaredRowsInTheWay`・`TestApplyAfterItsWrites` は、各バージョンに対してコマンドを実行する。`TestApplyDeletesWithSelectOnTheDeclaredColumns` も同じである。上限での `SET NULL` とロールの読めないテーブルへの `SET NULL`、3段のカスケード、SQL としての計画、削除とぶつかる宣言した行、計画が変える参照である。さらに、apply を止める既定値と `on_insert` からの参照、宣言が挙げない列の変更、カスケードが着くテーブルを先に削除することも確かめる。1つの apply での `on_insert` の値を持つ挿入・更新・削除、`track_counts` が off のセッション、宣言したテーブルを宣言した列でしか読めないロールも確かめる。各 apply のあとで、すべてのテーブルの行を素の接続で数え、出力が告げたものと比べる。

## 選択肢の長所と短所

### トランザクションの中ですべての外部キーを最後までたどり、たどり着いた行を一時テーブルに控え、そのすべてを数える

- 良い点：どの段でも、どの動作でも、数が正確であり、同じ数を計画・上限・宣言の検査に使える。
- 良い点：書くのはセッションの一時テーブルだけである。
- 悪い点：費用は削除が着くテーブルとともに増え、段ごとに問い合わせの集まりが要る。

### 深い段のカスケードは分からないものとし、apply をそこで止める

- 良い点：費用は1段目と変わらない。
- 悪い点：カスケードが1段目より先に着く削除は、どれも止まる。そのため、チームは手で削除することを覚える。
- 悪い点：レビューする人は、やはり削除がすることを見られない。

### セーブポイントの中で削除し、削除がしたことを測ってロールバックする

- 良い点：消したものと変えたものを、トリガーも含めて PostgreSQL 自身が伝える。
- 悪い点：計画が対象のデータベースの行を削除することになり、それは ADR-0016 が退ける。着いたすべての行のロックを取り、データベースの外に影響するトリガーを発火させ、計画に `DELETE` が要る。
- 悪い点：文が伝えるのは自分のテーブルの行数だけなので、ほかのテーブルの行は、いずれにせよ前後で数える必要がある。

### 1つの再帰的な問い合わせで外部キーをたどる

- 良い点：1つの文がすべての段をたどる。
- 悪い点：外部キーはそれぞれ、別のテーブルを別の列で、自分の演算子で結び付ける。これを SQL の1つの再帰的な問い合わせで表すには、データベースの中で SQL を組み立てる関数が要り、それは ADR-0010 が退ける。
