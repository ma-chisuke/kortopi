# ADR-0029: 計画を、適用の順に、どのセッションでも同じに読める値で SQL として出力し、削除はコメントにする

## 背景と課題

ADR-0020 は、計画をそのまま実行できる SQL として出力できるとする。データベースを版管理のマイグレーションだけで変えるチームのためである。
その SQL は適用の DML であり、外部キーの順に並び、値を書き出してある。行は照合キーで探し、挿入は宣言した列だけを挙げる。
ADR-0021 は、そのフラグ `kortopi plan --format text|sql` を定める。
どちらの記録も、その SQL の形は決めていない。

SQL は、kortopi の外で実行される。マイグレーションの道具・`psql`・コンソールで、そのセッションの持つ設定のまま実行される。
適用は kortopi が設定を固定したセッションで動き（ADR-0023）、一時テーブルから集合単位の文で書く（ADR-0026）。SQL はどちらにも頼れない。
マイグレーションの道具は、ふつう各ファイルをそれぞれのトランザクションで実行する。
適用は、`--allow-delete` がなければ何も削除せず（ADR-0018、ADR-0027）、どの順序でも書けない外部キーの循環を拒む（ADR-0026）。
テーブルは自分自身を参照できる。PostgreSQL は、遅らせていない外部キーを各文の終わりに検査する。
値と名前はデータベースとファイルから来る。値は改行や `*/` を含みうる。

SQL は何を持ち、どの順に並ぶのか。各値をどう書くのか。削除・スキーマの変更を待つテーブル・拒まれる循環は、どう表れるのか。

## 判断の基準

- 実行するのは、レビューしたものである（ADR-0020）。どの文も読め、読む人の見ていないものは何も実行されない。
- SQL は、同じ計画の適用と同じようにデータベースを変える。自分自身を参照するテーブルでも同じである。
- 値は、どのセッションでも同じ意味になる。その設定やサーバーの版は問わない。
- 誰かが決めない限り、行は削除されない（ADR-0018）。
- SQL は、トランザクションを決めるマイグレーションの道具にも、`psql` にも合う。
- データベースやファイルから来るどんなテキストも、コメントを文に変えられない。
- kortopi の出力するものは、ホスト・ユーザー・パスワードを繰り返さない（ADR-0024）。

## 検討した選択肢

- 適用の順の文。テーブルの変更は種類ごとに1つの文とし、更新だけは行ごとにする。値はどのセッションでも同じに読め、削除はコメントにし、トランザクションの制御は持たない
- 行ごとに1つの文
- 文を `BEGIN` と `COMMIT` で囲む
- 削除の文を、実行される形で書く
- 計画の設定をすべて冒頭で固定し、値は計画の出力するとおりに書く

## 決定

採用：「適用の順の文。テーブルの変更は種類ごとに1つの文とし、更新だけは行ごとにする。値はどのセッションでも同じに読め、削除はコメントにし、トランザクションの制御は持たない」。適用と同じようにデータベースを変え、レビューのためにどの行も1行ずつ立つからである。しかも、値は kortopi の制御しないセッションでも意味を保ち、適用のしないことは、誰かがコメントを外さない限り実行されない。

決まりは次のとおりである。

出力について。

- `kortopi plan --format sql` は、計画のテキストのかわりにスクリプトを標準出力に出す。計画はテキストのときと同じく、同じセッションで立てる（ADR-0024）。スクリプトはそろってから出力するので、失敗した計画は標準出力に何も出さない。
- `--exit-code` は、どちらの形式でも同じ意味で使える。計画が空でなければ終了コードは 2 であり、スキーマの変更を待つテーブルや列も含む（ADR-0021）。
- スクリプトが持つのは、`--` で始まるコメントと文だけである。`BEGIN` も `COMMIT` もない。トランザクションは、実行する人が決める。
- 冒頭のコメントは、kortopi が書いたこと、どのデータのディレクトリから、どのデータベースに対してかを示す。データベースは名前だけを示し、ホスト・ユーザー・パスワードは決して示さない。また、スクリプトが計画した時点の差分であることを示し、件数を挙げ、文を1つのトランザクションで実行するように示す。続けて、スキーマの変更を待つテーブルと列を1つずつ挙げる。
- 空の計画は、することがないと示すコメント1行になる。スキーマの変更を待つテーブルと列しかない計画は、冒頭のコメントと、スキーマを適用するまで実行する文がないと示す行になる。

設定について。

- 冒頭のコメントと、その理由を示すコメントのあと、スクリプトは3つの設定を `SET LOCAL` でトランザクションの終わりまで固定する。`client_encoding` は `UTF8` にする。スクリプトが UTF-8 だからである。`lc_monetary` は、計画が `money` を出力するときの `C` にする。`xmloption` は、計画が `xml` を読むときの `content` にする。この3つはリテラルでは運べない。ASCII でないテキスト・`money` の値・文書全体でなく断片である `xml` の値を、セッションがどう読むかを決めるからである。
- 値の読み方を変えるほかの設定には手を付けない。後述のリテラルは、それらに左右されないからである。

順序は適用の順序である（ADR-0017、ADR-0026）。

- 適用が遅らせる外部キーを、最初に1つの `SET CONSTRAINTS ... DEFERRED` で遅らせる。この文を書く前に、kortopi は適用と同じくそれらの名前を検査する。スキーマのほかのテーブルが、同じ名前の遅らせられない制約を持てば、SQL としての計画は適用と同じエラーで失敗する。
- 次に、参照されるテーブルから参照するテーブルへの順に、挿入か更新する行のあるテーブルごとに、件数のコメント1行・挿入・更新を続ける。
- そのあとに削除を、参照するテーブルから参照されるテーブルへの順に置く。
- 順序と遅らせるキーは、`--allow-delete` のある適用と同じく削除も数えて決める。そのため、削除のコメントを外しても、スクリプトの順序は正しいままである。そのぶん、`--allow-delete` のない適用なら遅らせないキーを遅らせることがある。
- 適用が拒む循環（ADR-0026）も、ここではエラーにしない。そのテーブルは名前の順に書き、その上にコメントを置く。コメントは、テーブルと外部キーを挙げ、どの順序でも一部の文がそのキーで失敗しうると示し、キーの1つを `DEFERRABLE` にするように示す。スクリプトはレビューのためのものであり、そうした循環の行は互いを参照しないことが多い。削除があるときだけ適用がその循環を拒むなら、コメントは、`--allow-delete` のある適用はそれを拒み、ない適用は拒まないと示す。

文について。どの行も、それぞれ1行に立つ。

- テーブルの挿入する行には、`INSERT INTO <table> (<key>, <compared columns>) VALUES` を1つ書く。適用が `OVERRIDING SYSTEM VALUE` を付けるとき、つまりキーに `GENERATED ALWAYS` の識別列があるときは、同じく付ける。
- 更新する行ごとに、`UPDATE [ONLY] <table> SET <changed columns> WHERE <match key>` を1つ書く。設定するのは、値の違う列だけである。適用は比べるすべての列を設定し、違わない列には格納された値を書き戻す（ADR-0026）。どちらでも行は同じになり、スクリプトに要るのは変える列に対する `UPDATE` だけである。
- テーブルの削除する行には、`DELETE FROM [ONLY] <table> AS s USING (VALUES ...) AS d (<key>) WHERE <match key>` を1つ書く。
- 挿入と削除は、適用と同じく、テーブルのすべての行を1つの文で扱う。そうすれば、自分自身を参照するテーブルも、互いを参照する行を得たり失ったりできる。PostgreSQL は、その外部キーを文の終わりに検査するからである。更新は、行ごとに設定する列が違うので、行ごとに1つの文にする。
- ふつうのテーブルの前には、適用と同じく `ONLY` を置く。パーティションテーブルの前には置かない。
- 名前はすべて二重引用符で囲む。スキーマ・テーブル・列・制約・型である。PostgreSQL のある版でそのまま書ける名前が、別の版ではキーワードでありうるからである。

値について。

- 値はどれも文字列リテラルであり、NULL は `NULL` と書く。リテラルのテキストは、固定した設定で PostgreSQL が出力するとおりの値である（ADR-0023）。この形は、セッションの `DateStyle`・`TimeZone`・`IntervalStyle`・`bytea_output`・`extra_float_digits` がどうであれ、同じに読み戻せる。日付と時刻は ISO の形、`timestamptz` はオフセット付き、間隔は符号の要るフィールドすべてに符号付き、`bytea` は16進、浮動小数点数は同じ値に読み戻せる最短のテキストである。
- バックスラッシュも制御文字も含まないテキストは、標準の文字列 `'...'` にし、`'` は2つ重ねる。それ以外のテキストは、エスケープ文字列 `E'...'` にする。バックスラッシュは2つ重ね、制御文字は `\n` や `\x01` のようなエスケープで書く。どちらの形も、`standard_conforming_strings` がどうであれ同じに読め、リテラルはいつも1行である。
- 正しい UTF-8 でない値はエラーである。そうした値は符号化方式 `SQL_ASCII` のデータベースなら持てるが、UTF-8 のリテラルには収まらない。
- 挿入の `VALUES` と `SET` では、リテラルをそのまま置く。PostgreSQL は、それを受け取る列の型で読む。
- 行を探すキーは、スキーマを添えた列の型へキャストする。そして、計画が使った等価演算子で比べる。演算子にもスキーマを添える。たとえば `"code" OPERATOR("pg_catalog".=) 'pro'::"pg_catalog"."text"` である。こうすれば、セッションの検索パスにかかわらず、計画が照合したとおりに行が見つかる。削除の一覧では、最初の行の値にキャストを付け、一覧の列に型を与える。

削除について。

- 削除はコメントにする。その文のどの行も `--` で始め、その上にコメントを置く。コメントは、適用が削除するのは `--allow-delete` のときだけであり、コメントの印を外せば実行されると示す。
- 計画の参照の行（ADR-0027）は、そのテーブルの削除の上にコメントとして置く。
- コメントを外す人が、削除を決める。スクリプトの中には、`--max-delete` を当てはめるものも、参照を数え直すものもない。参照の行は、読むためにある。

コメントと、スキーマの変更を待つテーブルについて。

- コメントの行はどれも、表示できない文字を、改行も含めてエスケープで書く。そのため、どんな名前やパスもコメントを終わらせられない。コメントにした文はどの行もコメントの印で始まり、リテラルはいつも1行である。
- スキーマの変更を待つテーブルには文を書かない。スキーマの変更を待つ列は、計画が比較から除くのと同じく、そのテーブルの文から除く。

これで、ADR-0020 が残した点が決まり、ADR-0020 は次のように細かくなる。

- ADR-0020 は「apply が実行するのと同じ DML」とする。スクリプトは、適用と同じ変更を、同じ順序で、同じキーによってする。挿入と削除がテーブルごとに1つなのも、適用と同じである。ただし、ADR-0026 の集合単位の文は kortopi の一時テーブルを読むが、スクリプトの文は値を持つ。更新も1行ずつである。
- 適用が文の前後でしていることは、スクリプトにはない。ADR-0026 のロック、各文が計画の示す数の行を変えたかの検査、`--max-delete` の上限、削除の前の2回目の参照の件数（ADR-0027）である。
- ADR-0020 は、出力した SQL のあとの計画が空になることを確かめるとする。それが成り立つのは、削除の文も実行したときである。削除をコメントのまま残せば、スクリプトのあとの計画は、その削除だけを示す。

### 結果

- 良い点：レビューする人は、変わるすべての行を1行ずつ読め、行を除いたり削除のコメントを外したりできる。
- 良い点：自分自身を参照するテーブルも、適用と同じく、互いを参照する行を得たり失ったりできる。
- 良い点：スクリプトは、マイグレーションの道具のトランザクションの中でも、`psql --single-transaction` でも、それとぶつかる文なしに動く。
- 良い点：スクリプトが固定する設定は、そのトランザクションとともに終わる。
- 良い点：削除がうっかり実行されることはなく、参照の行が削除のそばに立つ。
- 良い点：どんな値や名前も、コメントやリテラルを終わらせて文として実行されることはない。新しいサーバーのキーワードが、名前の読み方を変えることもない。
- 悪い点：スクリプトは、1つのデータベースの1つの時点からの差分である（ADR-0020）。別のデータベースやあとの時点では、行の見つからない更新や削除は、エラーなしに何も変えない。挿入がキーで失敗することもある。
- 悪い点：文が何行を変えたかを誰も検査しない。そのため、文のすることを変えるトリガーやルールに気づかない。適用なら止まるところである。
- 悪い点：コメントを外した削除は、`--max-delete` の上限なしに実行される。
- 悪い点：`SET LOCAL` が効くのは、トランザクションブロックの中だけである。その外で実行すると、3つの文は警告を出すだけになる。そして、ASCII でないテキスト・`money` の値・`xml` の断片は、そのセッションの設定で読まれる。
- 悪い点：`SET LOCAL client_encoding` が効くのは、クライアントがそのあとに別のメッセージとして送る文である。`psql` はそう送る。スクリプト全体を1つのメッセージで送るクライアントでは、スクリプトはすでにそのクライアントの符号化方式で読まれている。そのため、そうしたクライアントは `client_encoding` を UTF8 にして接続する必要がある。データベースのドライバーは、ふつうそうする。
- 悪い点：テストのサーバーには C と en_US のロケールしかなく、どちらも `money` を同じに書く。そのため、テストが示すのは、`lc_monetary` の固定がそこで害にならないことだけである。
- 悪い点：すべての名前を引用符で囲むので、人の書く SQL より文が読みにくい。
- 悪い点：大きな変更は、長いスクリプトになる。行ごとに1行である。

### 確認の方法

- `internal/script` のゴールデンテスト（`TestWrite` と `internal/script/testdata/` のファイル）で、出力を固定する。冒頭のコメント・順序・遅らせるキー・拒まれる循環のコメント・コメントにした削除・スキーマの変更を待つテーブルと列・空の計画・表示できない文字を含む名前である。`internal/postgres` の単体テスト（`TestLiteral`、`TestScriptStatements`、`TestCommentedStatements`）で、リテラルと文を固定する。
- `make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで確かめる。`internal/postgres` では、次のテストである。
  - `TestScriptLikeAnApply`：設定の違うセッションでふつうの接続からスクリプトを実行する。削除の文も実行すれば `--allow-delete` のある適用と、コメントのままなら `--allow-delete` のない適用と、同じデータベースになることを確かめる。型のテストのすべての型で確かめ、そのあとの計画が何も示さないか、削除だけを示すことも確かめる。
  - `TestCommentedScriptRunsNothing`：値が改行・`*/`・`--` を含んでも、コメントにした文が何も変えないことを確かめる。
  - `TestLiteralsInOtherSessions`：設定の違うセッションで、どのリテラルも同じ値に読み戻せることを確かめる。
- これらのテストの違う設定は、次のとおりである。`standard_conforming_strings` は off、`DateStyle` は `SQL, DMY`、`TimeZone` は `Asia/Tokyo` である。`IntervalStyle` は `sql_standard`、`bytea_output` は `escape`、`extra_float_digits` は 0、`xmloption` は `document` である。
- `cmd/kortopi` の `TestPlanSQLCommand` は、各版に対して `kortopi plan --format sql --exit-code` を実行し、その出力をふつうの接続で実行して、もう一度計画を立てる。`TestRunPlanSQL` で、出力と終了コードを固定する。
- これらが、ADR-0020 の確認の方法が plan の実装とともに来るとしていたテストである。

## 選択肢の長所と短所

### 適用の順の文。テーブルの変更は種類ごとに1つの文とし、更新だけは行ごとにする。値はどのセッションでも同じに読め、削除はコメントにし、トランザクションの制御は持たない

- 良い点：適用の書くものを、人がレビューしてマイグレーションに貼れる形で書く。
- 悪い点：適用が文の前後でする検査はなく、3つの設定にはトランザクションが要る。

### 行ごとに1つの文

- 良い点：どの行もそれだけで1つの文になり、エラーはその行を示す。
- 悪い点：自分自身を参照するテーブルが、互いを参照する行を得ることも失うこともできない。PostgreSQL は外部キーを各文の終わりに検査するので、最初の文が失敗する。

### 文を `BEGIN` と `COMMIT` で囲む

- 良い点：`psql -f` が、オプションなしでスクリプトを1つのトランザクションで実行する。
- 悪い点：ファイルをそれぞれのトランザクションで実行するマイグレーションの道具では、`BEGIN` は警告を出すだけになり、`COMMIT` はマイグレーションの途中でそのトランザクションを終わらせてしまう。

### 削除の文を、実行される形で書く

- 良い点：スクリプトは、手を加えずにデータベースを宣言に合わせる。
- 悪い点：スクリプトを貼るだけで、適用なら `--allow-delete` のときだけ削除する行が削除される。そのため、マイグレーションを使うチームには、ADR-0018 の安全策が効かない。

### 計画の設定をすべて冒頭で固定し、値は計画の出力するとおりに書く

- 良い点：各値を計画が出力するとおりに書け、リテラルの決まりが要らない。
- 悪い点：同じトランザクションにあるマイグレーションの残りが、自分の SQL を読む読み方まで変わる。日付・バックスラッシュを含む文字列・別の `search_path` のもとでのスキーマのない名前である。
- 悪い点：それでも値は設定が効いていることに頼る。トランザクションブロックの外で実行されたスクリプトでは、それを保証できない。
