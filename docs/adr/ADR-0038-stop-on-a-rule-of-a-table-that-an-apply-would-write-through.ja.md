# ADR-0038: apply がルールを通して書くことになる、宣言したテーブルのルールで止まる

## 背景と課題

ADR-0026 は、テーブルの変更の種類ごとに、宣言した行の一時テーブルから集合単位の文を1つ書き、その文が計画の示す数だけ行を変えたかを確かめる。
そして、文の働きを変える「トリガー、ルール、外部キーのカスケード」があれば apply は止まる、としている。

PostgreSQL のルールは、文を実行する前に書き換える。文に別の文を足すか、文を置き換えるか、文をなくす。
書き換えた文は、kortopi が書いた文のテーブルと条件を使う。ルールを書いたチームには、その文は見えない。
行数がどう反応するかは、ルールの種類によって違う。

- `ON INSERT ... DO ALSO INSERT INTO log ...` のルールの動作は、挿入のあとに、同じ問い合わせで動く。kortopi の挿入が取るのは、テーブルがまだ持たない宣言した行である。挿入を終えると、この条件を満たす行はもうないので、kortopi が挿入した行についてルールは何も書かない。PostgreSQL は挿入の行数をいつもどおり報告するので、apply は異常に気付かない。
- `ON UPDATE` と `ON DELETE` の `DO ALSO` のルールの動作は、文の前に、kortopi の文のテーブルと条件で動く。そのため、ルールが何を書くかは、kortopi が文をどう書くかで決まる。
- `DO INSTEAD` のルールは文を置き換える。このとき PostgreSQL が報告するのは、ルールが足した同じ種類の文のうち最後のものの行数か、0 である。別のテーブルを更新する `ON UPDATE DO INSTEAD UPDATE` のルールは、そのテーブルの行数を報告する。計画が1行を更新すると示す apply は、更新した行を1行と報告するが、宣言したテーブルは変わっていない。
- 条件付きのルールは、その条件の否定を文に足すので、文が書く行は減る。

行数の確認は、このうちの一部を捉えるが、挿入の `DO ALSO` と、たまたま計画どおりの行数を報告する `DO INSTEAD` は見逃す。
計画はルールを見ないので、kortopi が書くつもりの行を出力し、apply は別の行を書く。

kortopi は宣言したテーブルのルールを通して書くのか。書かないなら、計画はルールをどう見つけるのか。

## 判断の基準

- apply が計画として出力するものが、apply の書くものである。そうでなければ何も書かない（ADR-0026）。
- 行を読み込む前に見つけられる誤りは、そのときに、すべてのテーブルのほかの誤りとまとめて報告する（ADR-0024）。
- 計画は、ADR-0024 が挙げる権限のほかに権限を必要としない。
- apply の文を書き換えられないルールでは、計画は止まらない。
- 行を書かない書き出しは、これまでどおり動く。

## 検討した選択肢

- テーブルのモードが書く種類の文を書き換えうるルールで止まる
- 宣言したテーブルのルールなら何でも止まる
- 1行ずつ書き、ルールがアプリケーションの挿入と同じように各行を見るようにする
- ルールは行数の確認に任せる
- 計画にルールを示し、ルールを通して書く

## 決定

採用：「テーブルのモードが書く種類の文を書き換えうるルールで止まる」。こうしたルールは、計画が示すのとは別の行を apply に書かせ、しかも行数の確認では捉えきれないことがあるからである。一方、kortopi の文で決して発動しないルールは、何も変えない。

決まりは次のとおりである。

数えるルール：

- ルールを数えるのは、そのルールが宣言したテーブルのものであり、`INSERT`・`UPDATE`・`DELETE` のいずれかを書き換え、`session_replication_role` が `origin` のセッションで発動しうるときである。apply のセッションはそうである（ADR-0026）。発動しうるとは、既定のとおり有効であるか、`ENABLE ALWAYS RULE` で常に有効であることをいう。
- `DISABLE RULE` で無効にしたルールと、`ENABLE REPLICA RULE` でレプリカでだけ発動するルールは、apply の文を書き換えられないので数えない。
- ルールの種類は問わない。`DO ALSO`・`DO INSTEAD`・`DO INSTEAD NOTHING`、そして一部の行で発動する条件付きのルールを、どれも数える。
- ルールを数えるのは、テーブルのモードがその種類の文を書くときである（ADR-0013）。`INSERT` はどのモードでも、`UPDATE` はモード `upsert` と `sync` で、`DELETE` はモード `sync` で書く。モード `sync` のテーブルの計画は、`--allow-delete` の有無で変わらず、このフラグを付けた apply が行う削除を示す。そのためこのモードでは、`DELETE` のルールはどちらの場合も数える。モードが決して書かない種類の文のルールは発動しえないので、誤りではない。モード `upsert` のテーブルの `ON DELETE` のルールは、そのまま残せる。
- 数えるのは、宣言したテーブル自身のルールだけである。パーティションテーブルへの文が発動させるのは、パーティションテーブルのルールであり、そのパーティションのルールではない。テーブルの上のビューのルールや、別のテーブルのルールは、kortopi の文を決して書き換えない。テーブルは `SELECT` のルールを持たない。それを持つのはビューだけで、そのルールは `_RETURN` である。ビューを宣言することは、すでにエラーである（ADR-0024）。

計画が行うこと：

- 数えるルールはそのテーブルの誤りであり、計画と apply は、行を読み込む前に、すべてのテーブルのほかの誤りとまとめて報告する（ADR-0024）。SQL として出力する計画も、計画と同じくここで止まる。
- こうしたルールはそれぞれ1つのエラーになる。エラーは、テーブル、ルール、ルールの種類を挙げ、kortopi はルールを通して書かないと述べ、すべきことを告げる。ルールをトリガーに置き換えるか、テーブルを宣言から外すかであり、`UPDATE` か `DELETE` のルールなら、その種類を書かないモードをテーブルに与える道も示す。

  ```text
  table o.ruled has rule "also_log" ON INSERT, and kortopi does not write through rules, because a rule makes the statements of an apply write other rows than the plan shows: replace the rule with a trigger, or leave the table out of the declaration
  table o.ruled has rule "soft" ON DELETE, and kortopi does not write through rules, because a rule makes the statements of an apply write other rows than the plan shows: replace the rule with a trigger, give the table mode upsert in [tables."o.ruled"] of data/kortopi.toml, which deletes no row, or leave the table out of the declaration
  ```

- トリガーを代わりの道として示すのは、トリガーが文の書く各行について、kortopi の行にもアプリケーションの行にも同じように発動し、行を飛ばすトリガーは行数の確認がなお捉えるからである（ADR-0026）。
- kortopi はルールを、テーブルの説明と一緒にカタログから読む。`pg_class` がルールを持つと記すテーブルについてだけ、1つの問い合わせで読む。`pg_rewrite` はどのロールも読めるので、権限は要らない。
- 書き出しもテーブルの説明を読むが、ルールは確かめない。行を書かないので、ルールを持つテーブルもこれまでどおり書き出せる。

これは ADR-0026 を細かくする。行数の確認はトリガーとカスケードのために残る。しかし行数ではすべてのルールを捉えられないので、ルールはどの行も書く前に計画を止める。ADR-0024 も細かくする。行を読み込む前の段階で報告する誤りが、ルールの分だけ増える。

### 結果

- 良い点：計画が示すのとは別の行を apply に書かせるルールは、プルリクエストの計画を止め、そのルール、種類、すべきことを示す。
- 良い点：何も書かなかった `DO ALSO` のルールや、計画どおりの行数を報告した `DO INSTEAD` のルールを通して、apply がコミットすることはない。
- 良い点：確認に権限は要らず、宣言したテーブルがルールを持つときに問い合わせが1つ増えるだけである。
- 良い点：無効にしたルール、レプリカのルール、モードが決して書かない種類の文のルールでは、計画は止まらない。モード `upsert` のテーブルにある論理削除の `ON DELETE` のルールが、その例である。
- 悪い点：変更の記録などをルールに頼るチームは、ルールをトリガーに置き換えなければならない。そうするまで、kortopi はそのテーブルを書けない。
- 悪い点：モード `upsert` から `sync` に移したテーブルは、その `ON DELETE` のルールでエラーになり始める。
- 悪い点：計画はトランザクションのスナップショットでカタログを読む。そのスナップショットのあと、apply が最初にテーブルを読むまでに別のトランザクションが作ったルールは見えない。apply がテーブルを読んだあとは、ルールの作成は apply を待つ。ルールの作成は、ほかのどのトランザクションとも両立しないロックをテーブルに取るからである。

### 確認の方法

- `internal/plan` の単体テスト（`TestBuildRules`）は、偽物のデータベースで次のことを確かめる。各モードでどのルールが計画を止めるか、そのエラーは何か、そしてエラーがテーブルのほかの誤りと一緒に、どの行を比べるよりも前に出ることである。
- 結合テスト `TestRules`（`internal/postgres`）は、`make check-all` で PostgreSQL 15 から 18 に対して動き、次のことを確かめる。
  - `DO ALSO`・`DO INSTEAD`・`DO INSTEAD NOTHING`・条件付きのルール・無効にしたルール・レプリカのルール・常に有効なルールについて、カタログが報告するもの。
  - パーティションテーブルのルールとパーティションのルール、削除したルール、テーブルの上のビューとそのルールについて、カタログが報告するもの。
  - 数えるルールがあれば、各モードで計画が上のエラーで止まり、なければ計画が進むこと。
  - ルールを持つテーブルの書き出しが、その行を書くこと。

## 選択肢の長所と短所

### テーブルのモードが書く種類の文を書き換えうるルールで止まる

- 良い点：ルールが書き込みを変えうるテーブルだけを、過不足なく止める。
- 悪い点：モードを変えると、エラーが表に出ることがある。

### 宣言したテーブルのルールなら何でも止まる

- 良い点：決まりを短く言える。
- 悪い点：無効にしたルール、レプリカのルール、削除しないテーブルの削除のルールでも計画が止まる。そのどれも、apply の書くものを変えられないにもかかわらずである。

### 1行ずつ書き、ルールがアプリケーションの挿入と同じように各行を見るようにする

- 良い点：`ON INSERT DO ALSO` のルールは、各行を挿入の値として見ることになる。
- 悪い点：ADR-0026 は、行ごとの文を退けている。行の多いテーブルは同じ数の文を要し、計画の条件を別にもう1つ実装しなければならない。
- 悪い点：`DO INSTEAD` と条件付きのルールは、それでも書くものを変え、その行数はやはり誤解を招く。

### ルールは行数の確認に任せる

- 良い点：何も作らずに済む。
- 悪い点：挿入の `DO ALSO` のルールと、計画どおりの行数を報告する `DO INSTEAD` のルールは確認を通り抜け、apply は計画が示さなかったものをコミットする。

### 計画にルールを示し、ルールを通して書く

- 良い点：チームはルールを残せる。
- 悪い点：計画はルールが何を書くかを言えないので、ルールの名前を挙げる行は、apply が何をコミットするかをレビューする人に伝えない。
