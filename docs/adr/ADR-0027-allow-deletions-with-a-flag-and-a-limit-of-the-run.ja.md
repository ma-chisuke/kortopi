# ADR-0027: 削除は `--allow-delete` で許し、`--max-delete` で実行全体を制限し、それを参照する行を数える

## 背景と課題

ADR-0018 は、削除を4つの層で守る。モード `sync`、apply の明示のフラグ、上限、計画の参照の件数である。
次の3点は実装に任せ、あとの記録で定めることにしていた。1つ目はフラグの名前である。2つ目は上限の既定値と、テーブルごとに数えるか実行全体で数えるかである。3つ目は、フラグなしの apply をエラーで止めるか、ほかの変更を適用したうえで見送った削除を報告するかである。
ロールが読めない参照しているテーブルを kortopi がどう報告するかも、決めずに残していた。

削除は、そのテーブルの外にまで及ぶ。
外部キーが `ON DELETE CASCADE` なら、参照している行も消える。そうした行は、注文のように、宣言が管理しない業務の行であることが多い。
マスタの行だけを数える上限では、マスタの3行の削除が、業務の数千行を一緒に消してしまう。

apply は削除の前に行を書く（ADR-0026）。そして、書いた行が、そのあと削除する行を参照することがある。
計画の参照の件数は、それらを書く前に数えたものである。

フラグ・上限・参照の件数は、正確にはどう働くか。

## 判断の基準

- apply を実行する人が削除を求めない限り、どの行も削除しない（ADR-0018）。
- 多くの行を消す誤りは、宣言したテーブルのものもカスケードによるものも、何かが変わる前に止まる。
- 削除を求めないデプロイも、ほかの変更は受け取る。
- レビューする人は、削除がほかのテーブルのどの行にどう及ぶかを計画で読める。
- ロールの読めないテーブルがあっても、計画は失敗しない。
- apply の終了コードは、コミットしたかどうかを表す（ADR-0021）。

## 検討した選択肢

- `--allow-delete` と、1段目のカスケードを含む実行全体の上限。フラグがなければ残りを適用し、0 で終わる
- フラグがなければ、エラーで止める
- テーブルごとの上限
- 宣言したテーブルの行だけを数える上限
- カスケードをすべての段で数える

## 決定

採用：「`--allow-delete` と、1段目のカスケードを含む実行全体の上限。フラグがなければ残りを適用し、0 で終わる」。フラグによって、どの削除も apply を実行する人の判断になる。上限は、誤りがテーブルやカスケードにどう広がっても、それを捉える。しかも、フラグのない apply も、求められた仕事はするからである。

決まりは次のとおりである。

フラグについて。どちらも `kortopi apply` だけが持つ（ADR-0021）。

- `--allow-delete` は、モード `sync` のテーブルで、宣言にない行を削除することを許す。
- `--max-delete <n>` は上限を決める。0 以上の整数であり、既定は 100 である。0 も使え、どんな削除も止める。
- `--allow-delete` のない `--max-delete` は、フラグの誤りである。許しのない上限には効果がないので、利用者はおそらく削除を許すつもりだったか、フラグを読み違えている。

`--allow-delete` がないとき。

- apply はほかの変更をし、削除する行は残し、そのことを要約のあとに伝える。何個のテーブルの何行を削除しなかったかと、それらを削除するフラグである。`DELETE` 権限は要らない。
- 終了コードは 0 である。apply は求められたことをした。削除をしないデプロイが、モード `sync` のテーブルに削除する行があるたびに失敗するわけにはいかない。データベースはまだ宣言と違い、そのずれは `kortopi plan --exit-code` が報告する。
- 違いが削除だけなら、apply は何も書き込まず、コミットもしない。そのときは、書いた行の要約を出さない。削除の行だけを出し、何も書き込まなかったと伝える。

`--allow-delete` があるときの上限について。

- 上限は、テーブルごとではなく、実行のすべてのテーブルの削除する行を合わせて数える。間違ったディレクトリを指した実行は、多くのテーブルから数行ずつ削除し、合計にしか表れないからである。
- 外部キー `ON DELETE CASCADE` がそれと一緒に消す行も、参照の件数が示すとおりに、1段目まで数える。カスケードで消える行が別のカスケードで道連れにする行は数えない。参照している行を、実行が自分の宣言したテーブルからも削除するなら、その行は2回数える。そのため、数は止める側に寄る。
- 数が上限を超えると、apply は何かを書き込む前に止まる。エラーは、数・上限・テーブルごとの行とカスケードごとの行、この apply を通す `--max-delete` の値を示す。すでに出力した計画が、行を示している。
- 削除が、ロールの読めないテーブルへカスケードするときは、その行を数えられない。そのため apply は、外部キーとテーブルを示すエラーで止まる。
- 100 は、マスタデータを意図して整理するときの規模の見当である。そうした整理で数十行より多く削除することはまれである。小さなテーブルは、この上限の中ですべての行を失いうる。その場合は、モード・フラグ・計画が守る。

参照の件数について。

- 削除する行のあるテーブルごとに、計画も apply も、テーブルを指すすべての外部キーについて、削除する行を参照する行を数える。どの外部キーも数える。宣言したかどうかにかかわらずどのテーブルからでも、どのスキーマからでも、そのテーブル自身からでも、テーブルの1つのパーティションを指すキーでも数える。ADR-0018 は「ほかのテーブルごとに」としているが、テーブル自身も含める。
- 件数は、照合キーではなく外部キーの列で結び付ける。PostgreSQL がキーを検査するのと同じく、その外部キー自身の等価演算子と照合順序を使う。
- テーブルから自分自身への外部キーでは、残る行だけを数える。実行が一緒に削除する参照している行は、削除を止めたりカスケードしたりする参照ではないからである。
- 参照している行のない外部キーは除く。件数は、テーブルの削除する行の下に、テーブルごとに1回だけ示す。キーの `ON DELETE` の動作と、その状態で PostgreSQL がすることを添える。削除が失敗する、それらの行も削除する、それらの参照を NULL か既定値にする、のどれかである。
- 参照しているテーブルをロールが読めないときは、件数を数えられなかったと示し、エラーにはしない。読めないとは、スキーマに対する `USAGE` がないこと、キーのどちらかの側の列に対する `SELECT` がないこと、行単位セキュリティがかかることである。これで、ADR-0018 が残した問いが決まる。
- テーブルの行を削除する直前に、apply はトランザクションの中で参照をもう一度数える。この apply の書いた行が、この apply の削除する行を参照していれば、外部キーが削除で何をするかにかかわらず、宣言は自己矛盾している。apply は、外部キーと2つの件数を示すエラーで止まる。

### 結果

- 良い点：ADR-0018 が求めるとおり、削除には設定のモードと apply のときのフラグが要る。そのフラグの名前は、することをそのまま表す。
- 良い点：宣言したテーブルか1段目のカスケードで上限を超えて削除する実行は、何も変えない。そのエラーは、何を削除するはずだったかを伝える。
- 良い点：`--allow-delete` を渡さないデプロイも挿入と更新を受け取る。残した行は、その出力と次の `plan --exit-code` に示される。
- 良い点：レビューする人は、削除する行の下に、それを参照するすべてのテーブル・行の数・削除がそれらに何をするかを見られる。ロールの読めないテーブルがあっても、計画は止まらない。
- 良い点：削除する行への参照を書く宣言は、外部キーが何をするかにかかわらず、削除の前に見つかる。
- 悪い点：`--allow-delete` のない apply は、データベースが宣言とまだ違うまま 0 で終わる。そのずれで失敗させたいパイプラインは、そのあとに `plan --exit-code` を実行する必要がある。
- 悪い点：深い段のカスケードは数えない。そのため、カスケードのカスケードは、上限を超えて行を削除しうる。
- 悪い点：計画が効果を示すのは削除だけである。ほかのテーブルが参照する列を更新すると、それらの `ON UPDATE` の動作が働くが、それを示す件数はない。
- 悪い点：数えるには参照しているテーブルを読む。列にインデックスのない参照しているテーブルは全体を読むことになり、数えるにはそれらに対する `SELECT` が要る。
- 悪い点：100 は小さなマスタテーブルに合う。意図した整理がもっと大きいチームは、その実行でもっと大きな `--max-delete` を渡す。

### 確認の方法

- `internal/apply` の単体テスト（`TestRun`、`TestRunPlanned`、`TestRenderSummary`）で安全策を確かめる。カスケードを含む実行全体の上限、読めないカスケードのエラー、apply が残す削除である。`cmd/kortopi` の単体テスト（`TestParseApply`、`TestRunApply`）で、フラグとその誤りを確かめる。`internal/plan` のゴールデンテスト（`TestRender`、`internal/plan/testdata/references.golden`）で、参照の行を確かめる。
- `make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで、件数を確かめる。`internal/postgres` では、次のテストである。
  - `TestReferences` と `TestReferencesAcrossCollationsAndPartitions`：キーの列での結び付け、照合順序とパーティションをまたぐ場合、自分自身へのキー、`ON DELETE` の動作
  - `TestReferencesToColumnsThatTheRoleMayNotRead`：ロールの読めない参照しているテーブル
  - `TestApplyReferencesAgainBeforeDeletes`：削除の前の2回目の件数
- `cmd/kortopi` の `TestApplyCommand` で、フラグのない apply、カスケードのある場合とない場合の上限、外部キーが止める削除を確かめる。

## 選択肢の長所と短所

### `--allow-delete` と、1段目のカスケードを含む実行全体の上限。フラグがなければ残りを適用し、0 で終わる

- 良い点：ADR-0018 の各層の振る舞いが正確になり、よくある誤りは何かが変わる前に止まる。
- 悪い点：成功の終了でもずれが残りうるので、それは別の計画で報告する必要がある。

### フラグがなければ、エラーで止める

- 良い点：宣言にない行を残したまま apply が終わることはない。
- 悪い点：削除する行のあるモード `sync` のテーブルのデプロイは、誰かがフラグを渡すまで、挿入と更新も含めて毎回失敗する。チームは毎回フラグを渡すことを覚え、この層は形だけになる。

### テーブルごとの上限

- 良い点：大きなテーブルと小さなテーブルが、それぞれの上限を持てる。
- 悪い点：多くのテーブルから数行ずつ消す誤りは、実行全体では多くの行を削除しても、どの上限も通ってしまう。

### 宣言したテーブルの行だけを数える上限

- 良い点：数は、計画が挙げる行とちょうど同じになる。
- 悪い点：カスケードは、それを始めるマスタの行よりはるかに多い業務のテーブルの行を消しうる。上限が守るべきなのは、まさにその行である。

### カスケードをすべての段で数える

- 良い点：上限が、削除が消すすべての行を覆う。
- 悪い点：段ごとに、kortopi が管理しないテーブルへの問い合わせがもう1組要る。深い段の件数は前の段に依存し、その費用はデータベース全体のスキーマとともに増える。
