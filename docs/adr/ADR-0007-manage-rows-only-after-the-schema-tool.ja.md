# ADR-0007: 行だけを扱い、スキーマの道具とは別の道具として、そのあとに動かす

## 背景と課題

マスタテーブルの変わり方は2つある。スキーマ（列・制約・外部キー）が変わることと、行が変わることである。
宣言的なスキーマの道具は、前者をすでに扱っている。宣言したスキーマをデータベースと比べ、その差を埋める DDL を計画にする。
kortopi は、同じことを行について行う。

両方が同時に要る変更もある。
NOT NULL にしたい新しい列は、制約が成り立つ前に、既存のすべての行に値が入っている必要がある。
まだ存在しないマスタの行を指す新しい外部キーは、制約が成り立つ前に、その行を必要とする。
1つの計画に DDL と行の両方を入れると、そうした変更のたびに、道具がすべての DDL の文と行を正しい順に並べなければならない。順番を誤れば、デプロイが失敗する。

kortopi はどこまでを受け持つか。スキーマも変えるのか、スキーマの道具を呼び出すのか、それともスキーマは先に動く別の道具に任せるのか。

## 判断の基準

- チームは、すでに使っているスキーマの道具を、それが何であれ使い続けられる。
- どの計画も DDL と DML を混ぜない。そのため、両者の順番を誤ることがない。
- 適用が失敗しても、データベースは2回目の実行で直せる状態に残る。
- kortopi は小さく保ち、マスタテーブルの行という1つの関心事だけを受け持つ。

## 検討した選択肢

- 行だけを扱う道具にし、スキーマの道具のあとに実行する
- スキーマと行を1つの道具と1つの計画で扱う
- kortopi がスキーマの道具を呼び出し、そのあとで行を適用する

## 決定

採用：「行だけを扱う道具にし、スキーマの道具のあとに実行する」。DDL と DML を別々の計画に分けるので両者の順番を誤ることがなく、デプロイに手順を1つ足すだけで、どのスキーマの道具とも並べて使えるからである。

決まりは次のとおりである。

- kortopi が変えるのは行だけである。テーブル・列・制約などのスキーマのオブジェクトを作ることも、変えることも、消すこともしない。唯一の例外は、1つのセッションの間だけ存在する一時テーブルである（ADR-0009、ADR-0010）。
- kortopi は、スキーマの道具を呼び出さず、組み込みもしない。
- デプロイでは、スキーマの道具が先に動き、kortopi があとに動く。
- 行の適用は、スキーマの変更とは別の、専用のトランザクションで行う（ADR-0017）。
- スキーマの変更と行の両方が要る変更は、拡張と縮小によって2回のデプロイに分ける。1回目のデプロイでは、今の行のままでも満たせる形で、スキーマの道具が新しいものを足す（NULL を許す列や、外部キーをまだ張らない列など）。そのあと、kortopi が新しい行と値を適用する。2回目のデプロイでは、行がすでに満たしている制約（NOT NULL や外部キー）を、スキーマの道具が足す。この手順は README で説明する。
- 行の適用が失敗しても、すでに動いたスキーマの変更はスキーマを広げただけなので、害はない。宣言を直して、もう一度適用すればよい。適用は冪等なので、2回目の実行で行は宣言した状態になる。

### 結果

- 良い点：DDL と DML が同じ計画に入らない。そのため kortopi は、参照先の行より先に外部キーを足すことも、行を変えるついでに制約を消すこともない。
- 良い点：kortopi は、どのスキーマの道具とも、版管理のマイグレーションとも、そのどちらも使わない場合とも組み合わせられる。デプロイで、スキーマの手順のあとに手順を1つ足すだけである。
- 良い点：行で失敗しても、スキーマを戻す必要はない。拡張の手順には害がなく、2回目の実行で行が直る。
- 悪い点：スキーマの変更と行の両方が要る変更には、1回ではなく2回のデプロイがかかる。チームは、拡張と縮小の手順を計画する必要がある。
- 悪い点：デプロイの2つの手順は、別々に失敗しうる。そのため、しばらくの間、データベースが新しいスキーマと古い行を持つことがある。
- 悪い点：まだ実行していないスキーマの変更を前提に、kortopi が行の計画を立てることはできない。プルリクエストの計画は、そうしたテーブルと列に、適用待ちのスキーマの変更があることを示す（ADR-0016）。

### 確認の方法

この決定を守らせるチェックは、まだない。
kortopi がデータベースに送る DDL が一時テーブルを作る文だけであること（ADR-0010）と、kortopi がスキーマの道具を import も実行もしないことは、レビューで確かめる。
拡張と縮小を説明する README の記述は、それが加わるときにレビューで確かめる。

## 選択肢の長所と短所

### 行だけを扱う道具にし、スキーマの道具のあとに実行する

- 良い点：DDL と DML の両方を持つ計画がないので、両者の間に誤りうる順番がない。
- 良い点：どのスキーマの道具とも並べて使え、チームは今の道具を使い続けられる。
- 悪い点：スキーマと行を一緒に変えるには、2回のデプロイがかかる。
- 悪い点：デプロイでは2つの道具を動かし、レビューする人は2つの計画を読む。

### スキーマと行を1つの道具と1つの計画で扱う

- 良い点：宣言を1回変えるだけで、列を足して値を入れるところまでを、1回のデプロイと1つの計画で済ませられる。
- 良い点：1回のレビューで変更の全体を見られる。
- 悪い点：変更のたびに、道具が DDL と DML を正しい順に並べなければならない。新しいテーブル、その外部キー、その行は、制約が受け付ける順に届く必要がある。変更の組み合わせが増えるたびに、順番を誤る機会も増える。
- 悪い点：その道具がスキーマの道具も兼ねる。すでにスキーマの道具を持つチームは、それを置き換えるか、どちらもスキーマに手を出す2つの道具を動かすことになる。

### kortopi がスキーマの道具を呼び出し、そのあとで行を適用する

- 良い点：1つのコマンドが、デプロイの全体を正しい順に動かす。
- 悪い点：kortopi が、対応するスキーマの道具ごとに、フラグ・出力・バージョンを知り、その変更に追いつく必要がある。
- 悪い点：スキーマの道具をライブラリとして組み込むと、kortopi のリリースがその1つの道具に縛られる。
- 悪い点：デプロイのスクリプトに2行書けば済むことに、何も加えない。スキーマの道具はやはり先に専用のトランザクションで動くので、両方が要る変更には、やはり2回のデプロイがかかる。

## 補足

- 適用待ちのスキーマの変更にかかわるテーブルと列を計画でどう扱うかは ADR-0016 に、適用のトランザクションは ADR-0017 にある。
