# ADR-0028: 指定したテーブルだけをテーブルごとのファイルに書き出し、宣言済みのファイルは `--overwrite` のときだけ、その列のまま置き換える

## 背景と課題

ADR-0008 は、既存のデータベースを出発点にできるとする。その行を宣言として書き出せるということである。
ADR-0021 はコマンド `kortopi export [--dir <path>] [--schema <name>]... [--format csv|sql]` を定め、ほかのフラグの名前は実装に委ねている。
書き出しがどう動くかは、まだ決まっていない。

データベースには、マスタテーブル以外のものもある。注文・ユーザー・ログや、ほかのサービスのテーブルである。
チームは kortopi をテーブルごとに取り入れ、データベースで直接変えられた行を取り込むために、あとでまた書き出す。
そのころには、データのディレクトリは人の手で編集されている。kortopi が管理すべきでない列は除かれ（ADR-0011）、テーブルは SQL ファイルへ移され、設定も書かれている。

書き出しが信頼されるには、データベースの行をそのとおりに返す必要がある。直後の計画が違いを見つけないということである。
それは、各値の書き方・行の順序・それを読むセッションで決まる。

テーブルを指定しなかったとき、書き出しは何を書き、どの列を書くのか。ファイルがすでに宣言しているテーブルをどう扱うのか。ファイルをどこに置き、行をどの順に並べ、値を誰が書くのか。どんなセッションが要り、失敗したら何が残るのか。

## 判断の基準

- 書き出しの直後の計画は、計画が比べるどの型でも違いを見つけない。
- 書き出しは、誰も求めていないテーブルを書かない。データベースには、宣言が管理してはならない業務のテーブルがある。
- 書き出しは、求められない限り、人が編集したものを上書きしない。書き出し直しで、管理する列が増えることもない（ADR-0011）。
- 同じ行を2回書き出せば、2つのサーバーからでも同じファイルになる。そのため、レビューには変わった行だけが表れる。
- 書き出しはデータベースの何も変えず、要る権限はできるだけ少ない（ADR-0010）。
- 失敗しても、書きかけのファイルは残らない。

## 検討した選択肢

- テーブルを指定させ、テーブルごとにファイルを書き、宣言済みのファイルは `--overwrite` のときだけ、その列のまま置き換える
- 何も指定されなければ、すべてのテーブルを書き出す
- 宣言済みのファイルを、フラグなしで、テーブルのすべての列で置き換える
- 書き出しは `pg_dump` と `COPY` に任せる

## 決定

採用：「テーブルを指定させ、テーブルごとにファイルを書き、宣言済みのファイルは `--overwrite` のときだけ、その列のまま置き換える」。指定されたものだけを書き、人が編集したものを残し、計画がデータベースの行として読み戻せるファイルを作るからである。

決まりは次のとおりである。

何を書き出すかについて。

- `--table <schema>.<table>` はテーブルを1つ指定し、`--schema <name>` はスキーマのすべてのテーブルを指定する。どちらも繰り返せる。2回指定されたテーブルも、書くのは1回である。これらと後述の `--overwrite` が、ADR-0021 が実装に委ねたフラグである。`export` の `--schema` は書くものを指定する。`plan` や `apply` のように宣言を絞るのではない。
- 2つのフラグのどちらかは必須である。書き出しは、データベースのすべてのテーブルを書くことはない。どちらもなければ、エラーがテーブルの指定のしかたを示す。データのディレクトリがすでにテーブルを宣言していれば、それらを書き出し直す方法も示す。テーブルかそのスキーマを指定し、`--overwrite` を足すことである。
- 指定したテーブルやスキーマが存在しなければエラーである。宣言できる行を持つテーブルが1つもないスキーマを指定しても、エラーである。
- 書き出すのは、ふつうのテーブルとパーティションテーブルだけである。`--schema` は、パーティションテーブルを全体として書き、そのパーティションを単独では書かない。ビューなどほかの種類のリレーションはエラーである。名前にドットを含むものもエラーである。この版の宣言では、そうした名前を指定できないからである（ADR-0022）。

ファイルをどこに置くかについて。

- データのディレクトリは `--dir` で、既定はカレントディレクトリである。ないときは作る。
- どのファイルも宣言していないテーブルには、新しいファイルを作る。`<schema>/<table>.csv` か、`--format sql` なら `<schema>/<table>.sql` である。どちらの形式でも、1つのファイルには1つのテーブルを書く。`--format` の既定は `csv` であり、新しいファイルにだけ効く。
- 既存のファイルの上に新しいファイルを作ることはない。その場所に、そのテーブルを宣言していないファイルがあればエラーである。
- 新しいファイルには、どのファイルシステムもファイルとディレクトリの名前として受け付ける名前が要る。パスの区切り・コロン・制御文字を含む名前や、空白かドットで終わる名前のスキーマやテーブルは、エラーである。そうしたテーブルも、別の名前の SQL ファイルでなら宣言でき、`--overwrite` のある書き出しでそれを書き出し直せる。
- 文字の大小か、名前の Unicode の形だけが違うファイルになる2つのテーブルは、エラーである。既存のファイルやディレクトリとその点だけが違う名前の新しいファイルも、エラーである。大小を区別しないファイルシステムや、名前を正規化するファイルシステムでは、2つが1つのファイルになってしまう。
- 改行を含む列の名前は、CSV ファイルの見出しの行に書けない。そうした列のあるテーブルは、CSV ではエラーになり、SQL でなら書き出せる。
- 書き出しがディレクトリを要する場所にファイルがあれば、エラーである。
- 大小を区別しないファイルシステムや Unicode を正規化するファイルシステムと同じように名前を比べるため、`internal/export` は `golang.org/x/text` を取り込む。大小の畳み込みと NFC の形のためである。このモジュールは、ADR-0025 が選んだドライバーの依存として、すでにバイナリに入っていた。それが、kortopi の直接の依存にもなる。
- 行のないテーブルは、SQL では書き出せない。空の SQL ファイルは、どのテーブルも宣言しないからである。テーブルがすでに SQL ファイルで宣言されていても同じである。CSV なら、そのファイルは見出しの行だけになり、それがテーブルとその列を宣言する。

ファイルがすでに宣言しているテーブルについて。

- `--overwrite` がなければ、そのファイルを示すエラーになる。
- `--overwrite` があれば、書き出しはそのファイルを置き換える。形式はそのファイルの形式、列はそのファイルの宣言した列である。そのため、書き出し直しは、管理する列を増やさずにデータベースの行に追随する（ADR-0011）。ファイルが宣言していなかった行も含め、テーブルのすべての行を書く。
- ほかのテーブルも宣言している SQL ファイルは置き換えない。エラーはそれらのテーブルを挙げ、それぞれのファイルへ移すように示す。ADR-0014 は1つの SQL ファイルに複数のテーブルを宣言させるが、書き出しは1つのファイルに1つのテーブルを書く。そうしたファイルを置き換えれば、ほかのテーブルの行が消えてしまう。
- テーブルにない列や生成列が宣言されていれば、そのファイルを示すエラーになる。
- シンボリックリンクである宣言済みのファイルは置き換えない。書き出しが置き換えるのはリンクであり、リンク先のファイルではないからである。
- ファイルが行のほかに持っていたもの、たとえば SQL ファイルのコメントや体裁は残らない。

列と行について。

- 新しいファイルには、生成列を除くテーブルのすべての列を、テーブルの列の順に書く。識別列も書く。多くの場合、マスタテーブルの ID は、ほかの行から参照されるデータだからである。宣言が管理すべきでない列は、書き出した人が除く。どの列かは、利用者向けの説明に書く。
- 行は、テーブルの照合キーで並べる（ADR-0012）。設定が `kortopi.toml` で `key` を指定していればそれを、なければ主キーを使う。どちらもないテーブルは、書くすべての列で並べる。このとき書き出しは、そのテーブルの計画にはキーが要るという注記を標準エラー出力に出す。
- 列は型の順序で並べ、照合順序を持つ列は照合順序 `"C"`、つまりバイトの順で並べる。そのため、`B` は `a` より前に来る。そうすれば、列の照合順序やそれを提供するライブラリにかかわらず、どのサーバーでもファイルが同じになる。順序のない型の列は、そのテキストを照合順序 `"C"` で並べる。この順序は、計画が行を出力する順序と違うことがある。計画は、列の照合順序で並べるからである。
- 書き出しは、キーを知るために `kortopi.toml` を読む。ただし、設定を宣言と照らし合わせることはしない。ADR-0022 は、どのファイルも宣言していないテーブルの設定をエラーにする。書き出しではそれを許す必要がある。最初の書き出しで、`key` がそのテーブルの行を並べられるようにするためである。書き出しのあとは、ファイルがそのテーブルを宣言している。
- データのディレクトリがどのテーブルを宣言しているかを知るため、書き出しは計画と同じ決まりでそのファイルを読む。ディレクトリがないか、テーブルを1つも宣言していなくても、エラーにはしない。

値について。

- CSV ファイルは PostgreSQL が書く。見出しの行の付いた CSV 形式の `COPY (SELECT <columns> FROM <table> ORDER BY <key>) TO STDOUT` である。そのため、NULL と空文字列は、計画が読むとおりに区別される（ADR-0009）。引用符のない空のフィールドと `""` である。
- ふつうのテーブルは計画と同じく `ONLY` を付けて読み、パーティションテーブルは全体を読む。
- SQL ファイルには、行ごとに `INSERT INTO <schema>.<table> (<columns>) VALUES (...);` を1つ書く。書く列に `GENERATED ALWAYS` の識別列があれば、`OVERRIDING SYSTEM VALUE` を付ける。ADR-0029 の SQL と同じく、名前はすべて二重引用符で囲む。PostgreSQL のある版でそのまま書ける名前が、別の版ではキーワードでありうるからである。
- SQL ファイルの値は、どれも文字列リテラルである。PostgreSQL はそれを列の型で読む。NULL は `NULL` と書く。リテラルは ADR-0029 の決まりに従い、SQL の宣言を読む部分はそれを受け付ける（ADR-0022）。
- どちらの形式も、値は計画が固定する設定で書く（ADR-0023）。`timestamptz` はオフセット付きの UTC、日付は ISO の形、`bytea` は16進である。計画は、同じ設定でそれを読み戻す。
- 正しい UTF-8 でない値は、どちらの形式でもエラーである。そうした値は符号化方式 `SQL_ASCII` のデータベースなら持てるが、宣言は UTF-8 だからである。PostgreSQL はそうした値を UTF-8 のセッションへ送らず、エラーはそのテーブルを示す。

セッションについて。

- 書き出しは、`REPEATABLE READ` かつ `READ ONLY` の1つのトランザクションで、計画と同じ設定を固定して動く。そのため、どのテーブルも1つのスナップショットから読む。トランザクションは最後にロールバックする。
- 書き出しは何も作らず、一時テーブルも作らない（ADR-0010）。要るのは、スキーマに対する `USAGE` と、書く列と行を並べる列に対する `SELECT` である。ADR-0024 は、計画に `TEMPORARY` と書き込みのできるセッションを求める。書き出しはどちらも要らないので、スタンバイでも動くと見込まれる。
- ロールから行を隠す行単位セキュリティは、計画と同じくエラーである（ADR-0024）。書き出しが、隠れた行を落としてしまうからである。
- 書き出しは読むだけなので、ロックを取らない。

ファイルの書き方について。

- すべてのテーブルのすべての検査は、最初のファイルを書く前に行う。すべてのテーブルの誤りはまとめて報告し、1つのテーブルに誤りがあれば何も書かない。
- 各テーブルは、まずそのファイルのディレクトリの一時ファイルに書く。一時ファイルの名前はドットで始めるので、計画が読むことはない。すべてのテーブルを書き終えてはじめて、一時ファイルを1つずつ所定の場所へ移す。
- 置き換えるファイルには、名前の変更で上書きする。新しいファイルは、その名前へリンクする。検査のあとでその場所にファイルが現れていれば、リンクは失敗する。そのため、書き出しが宣言の挙げないファイルを置き換えることはない。
- 行を読む間の失敗では、どのファイルも元のままである。一時ファイルと、書き出しが作ったディレクトリは消し、エラーは `no file was written` で終わる。一部のファイルが置き換わったまま残りうるのは、ファイルを所定の場所へ移す間の失敗だけである。そのときは、エラーがそれらを示す。
- 置き換えたファイルは、そのモードを保つ。新しいファイルとディレクトリのモードは、利用者が作るほかのファイルと同じく、利用者の umask で決まる。
- 標準出力には、ファイルごとに1行 `wrote <path> (<n> rows)` を出し、最後に要約 `Exported <n> tables with <n> rows.` を出す。終了コードは、すべてのファイルを書けたら 0、そうでなければ 1 である（ADR-0021）。

### 結果

- 良い点：書き出し直後の最初の計画は空になる。そのため、チームは何も変えない計画から kortopi を取り入れられる。
- 良い点：うっかり書き出されるものはない。どのテーブルも、単独かスキーマを通じて指定されている。
- 良い点：書き出し直しは、人が選んだ列と形式を保ち、行だけを変える。そのため、レビューでの差分はデータベースのずれそのものである。
- 良い点：同じ行を2回書き出せば、同じバイト列になる。
- 良い点：書き出しは読むだけである。`USAGE` と `SELECT` を持つロールで実行でき、データベースは元のまま残る。
- 悪い点：新しいファイルは、ID やタイムスタンプも含めすべての列を持つ。最初の適用の前に、宣言の管理すべきでない列を、人の手で除く必要がある。`GENERATED ALWAYS` の識別列は、照合キーに含まれない限り除かないと、計画がそこで止まる（ADR-0023）。
- 悪い点：キーのないテーブルも書き出せるが、`kortopi.toml` がキーを指定するまで、その計画は失敗する。
- 悪い点：行のないテーブルは、CSV でしか書き出せない。
- 悪い点：書き出し直しは、テーブルにあとから加わった列を足さない。それは人がファイルに書き足す。
- 悪い点：書き出し直しで、SQL ファイルのコメントや体裁は失われる。
- 悪い点：データのディレクトリに計画の読めないファイルがあると、それを直すまで書き出しも止まる。
- 悪い点：ファイルは1つずつ所定の場所へ移すので、この最後の段階で失敗すると、一部のファイルだけが新しくなりうる。エラーは、新しくなったファイルを挙げる。
- 悪い点：すべてのテーブルの一時ファイルが最後までそろって残る。そのため書き出しには、置き換える古いファイルに加え、新しいファイルすべての分のディスクの空きが要る。
- 悪い点：書き出しの間、スナップショットが古い行のバージョンの掃除を待たせる。計画と同じである。
- 悪い点：スタンバイでの書き出しはテストしていない。

### 確認の方法

- `make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで確かめる。`internal/postgres` では、次のテストである。
  - `TestExportRoundTrip`：型のテストのすべての型・NULL と空文字列・引用符で囲む名前・複合キー・パーティションテーブル・識別列のキーを両方の形式で書き出し、そのファイルの計画が違いを見つけないことを確かめる。
  - `TestExportFiles`：ファイルの中身そのものを確かめる。引用符・型の順序で並ぶ複合キー・バイトの順で並ぶテキスト・パーティションテーブル・`OVERRIDING SYSTEM VALUE`・キーのないテーブルである。
  - `TestExportSession`：`TEMPORARY` を持たず、トランザクションが読み取り専用で、一部の列にだけ `SELECT` を持つロールで書き出す。そして、`USAGE` や `SELECT` の不足・行単位セキュリティ・ビュー・存在しないテーブルやスキーマのエラーを確かめる。
  - `TestExportOfAValueThatIsNotUTF8`：`SQL_ASCII` のデータベースで、正しい UTF-8 でない値のエラーを両方の形式で確かめる。
- `cmd/kortopi` の `TestExportCommand` は、各版に対してコマンドを実行する。スキーマとテーブルを各形式で書き出し、そのファイルの計画が変更を見つけないこと、書き出し直しが宣言した列を保つこと、拒む場合を確かめる。
- `internal/export` には、単体テスト `TestRun`・`TestRunModes`・`TestRunErrors`・`TestRunWriteErrors`・`TestRunFileRules`・`TestRunFileAppears` がある。これらで、ファイル・列・順序・ファイルのモード・エラーを確かめる。ファイル名として使えない名前・同じファイルとみなされる2つのファイル・シンボリックリンク・行のないテーブル・書き出しの間に現れるファイルも確かめる。所定の場所へ移す前の失敗で、ディレクトリが元のままであることも確かめる。`cmd/kortopi` の単体テスト（`TestParseExport`、`TestRunExport`、`TestRunExportInterrupted`）で、フラグ・出力・エラーを確かめる。

## 選択肢の長所と短所

### テーブルを指定させ、テーブルごとにファイルを書き、宣言済みのファイルは `--overwrite` のときだけ、その列のまま置き換える

- 良い点：kortopi が何を管理するかを、人がテーブルごとに決める。
- 悪い点：宣言全体を書き出し直すには、そのテーブルかスキーマをもう一度指定する。その方法は、指定のない書き出しのエラーが示す。

### 何も指定されなければ、すべてのテーブルを書き出す

- 良い点：いちばん短いコマンドで、宣言全体が手に入る。
- 悪い点：業務のテーブル・ログ・ほかのサービスのテーブルまで書く。宣言がそれらの行を持ってはならない。しかも、サービスのユーザーのような行がリポジトリに入ってしまう。

### 宣言済みのファイルを、フラグなしで、テーブルのすべての列で置き換える

- 良い点：書き出し直しがフラグのない1つのコマンドになり、ファイルはいつもテーブル全体を示す。
- 悪い点：書き出し直しのたびに、人の除いた列が戻り、宣言がそれらを管理しはじめる（ADR-0011）。次の適用は、それらをすべての環境に書く。
- 悪い点：テーブル名を打ち間違えると、編集した内容が警告なしに上書きされる。

### 書き出しは `pg_dump` と `COPY` に任せる

- 良い点：何も作らなくてよい。ADR-0008 はすでに `pg_dump --data-only --column-inserts` の出力を受け付けており、`COPY` は CSV を書ける。
- 悪い点：`pg_dump` は、たまたま格納されている順に行を書く。そのため、同じ行の2つのダンプで順序が違いうる。すると、レビューには変わっていない行が表れる。`COPY` が行を並べるのは、テーブルごとに問い合わせを書いたときだけである。
- 悪い点：`COPY` は、実行したセッションの設定で値を書く。タイムゾーンや日付の形式である。そのため、同じ行でも、別の機械では別のファイルになりうる。
- 悪い点：`<schema>/<table>.csv` と宣言した列に合わせて、チームが出力を手で分け、名前を変え、削る必要がある。それを書き出し直しのたびに繰り返す。
