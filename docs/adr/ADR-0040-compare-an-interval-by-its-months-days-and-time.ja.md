# ADR-0040: 期間は月数・日数・時間で比べる

## 背景と課題

ADR-0023 は、計画が宣言の値と保存されている値を列の型の等価性で比べることを決めた。そのため、`numeric` の列の `1.0` と `1.00` のように、1つの値の2つの書き方は変更にならない。
`interval` では、この等価性が値よりも粗い。
PostgreSQL は期間を、月数・日数・マイクロ秒単位の時間という3つの部分として持つ。
その等価性・順序・期間のどの一意インデックスも、1か月を30日、1日を24時間として3つの部分を1つの長さにまとめる。そのため、`1 mon` は `30 days` と等しく、`1 day` は `24 hours` と等しい。
しかし、部分が違えば振る舞いも違う。
`date '2025-01-31' + interval '1 mon'` は 2025-02-28 になり、`30 days` なら 2025-03-02 になる。
`1 day` と `24 hours` を夏時間の切り替えをまたいで `timestamptz` に足すと、1時間ずれた2つの時点になる。

ある列が `30 days` を持ち、宣言がそれを `1 mon` に変えるとする。
`kortopi plan --exit-code` は `No changes. The database matches the declaration.` と表示して終了コード 0 で終わり、適用は何も書かない。
kortopi はこの変更を決してデプロイできず、チームにそれを知らせるものもない。
ADR-0023 は、テストで固めた振る舞いとして「`1 day` と `24 hours` は等しい」まで挙げている。

照合キーの期間には、もう1つ問題がある。
キーの一意インデックスは型の等価性を使うので、テーブルは `1 mon` と `30 days` のどちらか一方しか持てない。
保存されている `30 days` に対して宣言のキーが `1 mon` なら、型の等価性でその行と照合する。計画はキーを決して変えないので、計画が違いはないと示す一方で、保存されているキーは `30 days` のまま残る。

ほかの型の等価性も変更を隠し、チームによってはその変更を適用したいこともある。隠れるのは、桁数を指定しない `numeric` の桁数（`1000.0` と `1000.00`）と、大文字と小文字を区別しない型の値や非決定的な照合順序のもとの値の大文字と小文字である。`-0` と `0` も、`json` の空白・キーの順番・繰り返されたキーも隠れる（計画は `json` を `jsonb` として比べる）。
これらの違いは型がわざわざ無視するものであり、ADR-0023 は型に従うことを選んだ。
期間では、等価性がまとめてしまう部分こそが、アプリケーションの日付の計算にとっての値の意味である。

計画は、期間がどこにあっても2つの期間をどう比べるか。また、型の等価性がそれでも隠す変更について、リファレンスは何を書くか。

## 判断の基準

- 保存されている値と違う宣言の値を、変更なしとは示さない。適用は、その出力が告げなかった状態を決してコミットしない。
- `1.0` と `1.00` のように、型が1つとして扱うように作られた2つの値は、変更なしのままにする（ADR-0023）。この記録が変えるのは期間だけである。
- 比べ方は、PostgreSQL 15〜18 で、列・ドメイン・配列・範囲・複合型のどこにある期間でも厳密であり、テキストの比較より費用がかからない。
- 照合キーは、その一意インデックスと同じように行を組にする（ADR-0012、ADR-0023）。計画は、適用ができない変更を示さない。

## 検討した選択肢

- 期間を、固定した IntervalStyle でのテキストで比べる
- 期間を、`extract` で取り出した部分で比べる
- 期間を、型の等価性で比べる
- すべての値をテキストで比べる

## 決定

採用：「期間を、固定した IntervalStyle でのテキストで比べる」。スタイル `postgres` での期間のテキストは3つの部分だけで決まり、どの2組の部分も区別する。そのため比べ方は厳密になる。配列・範囲・複合型のテキストは要素のテキストから成るので、その中の期間にもこの比べ方が届く。費用は、値ごとに出力関数を1回呼ぶことである。

決まりは次のとおりである。

2つの値の比べ方について。

- 型が期間を含む列の2つの値は、等価性を持たない型の値と同じように、テキストをバイト単位で比べる（ADR-0023）。2つの値は、月数・日数・時間がどれも等しいときに等しい。`1 mon` は `30 days` と違い、`1 day` は `24 hours` と違う。`1 year` は `12 mons` と等しく、`90 minutes` は `01:30:00` と等しく、ISO 8601 の形の `P1M` は `1 mon` と等しい。
- 型が期間を含むとは、その型が `interval` であるか、期間を含む型の上のドメイン、期間を含む型の配列、期間を含む型の列を持つ複合型、部分型が期間を含む範囲、そうした範囲の複数範囲であることをいう。kortopi は、`json` を見つけるのと同じように、型 `interval` そのものを手がかりにカタログからこれらの型を見つける。
- `interval day to second`・`interval hour to minute`・`interval(0)` のような型修飾子は、どの型とも同じく、PostgreSQL が宣言の値を読むときに効く。`interval(0)` の列では、`00:00:00.6` は `00:00:01` になる。`day to second` は値の月数を残すので、この型でも `1 mon` と `30 days` は違う。
- 期間を含む複合型は、全体をテキストで比べる。そのため、ほかの列もテキストで比べることになる。`(1.0,"1 mon")` は `(1.00,"1 mon")` と違う。kortopi は、そうした型を列ごとには比べない。
- 更新は、テキストが違うところに宣言の値を書く。部分が同じ値はテキストも同じなので、保存されている値はそのまま残る。
- ほかのどの型も、ADR-0023 が決めたとおり型の等価性を使う。
- これは ADR-0023 を細かくする。2つの値は列の型の等価演算子が等しいとするときに等しいという ADR-0023 の決まりは、期間を含まないどの型にも引き続き成り立つ。一方、その結果のうち「`interval`：`1 day` と `24 hours` は等しい」は、もう成り立たない。

テキストが部分を区別する理由。

- PostgreSQL は、月数と日数を32ビットの整数として、時間を64ビットのマイクロ秒数として持つ。kortopi のどのセッションも `IntervalStyle` を `postgres` に固定する（ADR-0023）。このスタイルの出力は、まず月数を年と月に分けて書く。分けるには、符号を保つ割り算を使う。次に日数を書き、最後に時間を符号付きの1つの `hh:mm:ss` として書く。秒の端数は6桁までで、末尾の0は書かない。0の部分は書かず、それ以外の部分は `-1 mons +2 days` のように、テキストが必要とする箇所でそれぞれの符号を付ける。3つの部分がどれも0の期間は `00:00:00` になる。
- PostgreSQL 17 からは、期間が `infinity` や `-infinity` になりうる。PostgreSQL はこれらを、どの部分も最大値または最小値にした値として持ち、その語のとおりに出力する。有限の期間がそう出力されることはない。
- したがって、テキストは3つの部分と `IntervalStyle` だけで決まり、部分の組が違えばテキストも違う。年と月からは月数が戻り、日数はそのまま書かれ、時間は符号付きの1つの数である。
- `TestIntervalTextTellsItsPartsApart` は、これを PostgreSQL 15〜18 で確かめる。`IntervalStyle` を `sql_standard` とするデータベースで、kortopi のセッションを使う。部分から1683個の期間を作る。月数は -25 から 25、日数は -31 から 360、時間は -720 時間から 2147483648 時間までである。時間には1マイクロ秒と0.5秒を含め、符号の混じった期間も作る。PostgreSQL 17 からは `infinity` と `-infinity` も加える。そして2つのことを確かめる。1つは、有限の期間ごとに、作ったときの部分を `extract` で読み戻せることである。もう1つは、すべての組で、部分が等しいときに限りテキストが等しいことである。組のうち数千個は、型の等価性では等しい。

照合キーの期間について。

- キーの列は型の等価性を使い続ける。行は、キーの一意インデックスと同じように照合し、型の順序で並べる。保存されている `1 day` に対する `P1D` のように、部分が同じで書き方の違うキーは、これまでどおり照合する。
- 宣言のキーについてこの等価性とテキストが食い違うとき、テーブルは宣言が述べるとおりのものを持てない。そこで計画は、どのモードでも、テーブルを読み込んだあと、値を比べる前に止まる。適用も同じように止まり、何も書かない。
- `1 mon` と `30 days` のように、テキストは違うのに型の等価性が1つのキーとみなすキーを、宣言の行が持つ場合：テーブルはそのうち1行しか持てない。エラーは、そうしたキーの組を10個まで挙げ、各キーを1回だけ宣言するように促す。このエラーは、繰り返されたキーのエラーより前に出る。繰り返されたキーのエラーでは、テキストのうち1つしか示されないからである。
- 保存されている `30 days` に対する `1 mon` のように、宣言のキーが型の等価性で保存されている行と照合するのに、テキストがその行のキーと違う場合：計画はキーを決して変えない。また、宣言のキーを挿入すると一意インデックスに反する。適用は削除の前に挿入するので（ADR-0026）、モード `sync` でも同じである。エラーは、そうしたキーを保存されているキーとともに10個まで挙げる。そして、テーブルが持つとおりにキーを宣言するか、kortopi より前に実行するスキーマの変更の中で `UPDATE` によって保存されているキーを変えるように促す。
- 期間を含む複合型のキーの列は、その配列や範囲のキーの列も含め、値と同じく全体をテキストで比べる。そのため、どちらのエラーも、複合型のほかの列だけが保存されているキーと違う宣言のキーで計画を止める。その違いが、その列の型の無視するものであっても止める。たとえば、保存されている `(1.0,"1 mon")` に対する `(1.00,"1 mon")`、大文字と小文字を区別しない型での大文字と小文字の違い、`-0` と `0` である。こうしたキーはまれであり、kortopi はそれを分解しない。キーは、テーブルが持つとおりに宣言する。
- これは ADR-0012 と ADR-0023 を細かくする。両者のもとでは、宣言のキーは、キーの一意インデックスが同じとみなす保存されている行と照合する。期間では、照合に部分が同じであることも要るようになり、両者が食い違えば計画は止まる。

ほかの型の等価性についてリファレンスが書くこと。

- 型が等しいとみなす2つの値の間で宣言が変更を書いても、その変更は示されず、適用もされない。対象は、桁数を指定しない `numeric` の桁数（`1000.0` と `1000.00`）と、`citext` のような大文字と小文字を区別しない型の値や非決定的な照合順序のもとの値の大文字と小文字（`abc` と `ABC`）である。浮動小数点数の列の `-0` と `0`、`json` の空白・キーの順番・繰り返されたキーも同じである。こうした変更をデータベースに入れたいチームは、スキーマの変更の中に `UPDATE` として書く。変更はそのまま残る。以後の計画は、宣言の値をその値と等しいとみなすからである。
- `docs/reference/comparison.md` は、これらを期間の決まりとともに挙げる。README と `docs/reference/plan.md` は、変更なしについて述べる箇所からそこを指す。

### 結果

- 良い点：期間の月数・日数・時間の変更は、2つの値とともに計画に現れ、適用はそれを書く。
- 良い点：比べ方は 15〜18 のどのバージョンでも厳密であり、配列・範囲・複数範囲・ドメインのために独自の式を要しない。
- 良い点：テーブルが持てない宣言のキーは、キーを示して計画を止める。何も示さない計画にも、一意インデックスで失敗してほかのトランザクションのせいにするエラーを出す適用にもならない。
- 悪い点：データベースが持つのとは違う部分の分け方で期間を書いた宣言は、このバージョンで初めて計画を立てたときに更新を1つ示す。リリースノートには、次の文を書く。

  ```text
  An interval now compares by its months, days, and time: `1 mon` no longer equals `30 days`, nor `1 day` `24 hours`. A declaration that writes an interval in another split of parts than the database stores shows one update, which an apply writes. Such an interval in a match key stops the plan with the keys.
  ```

- 悪い点：期間を含む複合型は、すべての列をテキストで比べる。そのため、ほかの列の型が無視する違い（numeric の桁数など）も、比べる列では変更として現れ、キーの列では計画を止める。
- 悪い点：計画は、照合キーの期間を、部分の別の分け方に変えられない。その変更はスキーマの変更に入れる。
- 悪い点：numeric の桁数のように、ほかの型の等価性が隠す変更は隠れたままであり、それを伝えるのはリファレンスだけである。
- 悪い点：この決まりは、スタイル `postgres` での期間の出力に依っている。期間を別の形で出力する PostgreSQL のバージョンがあれば、この決まりは崩れる。テストは、kortopi が対応するどのバージョンでも実行する。

### 確認の方法

- `internal/postgres` の単体テストで、次のことを確かめる。`TestResolverHoldsInterval` は、どの型が期間を含むかを確かめる。`TestPrepareInterval` は、そうした型の比べる列をテキストで比べ、キーの列では型の等価性を使い続けることを確かめる。`TestSplitColumns` と `TestKeySplitSQL` は、キーの検査が対象とする列と、その問い合わせを確かめる。
- 残りは、`internal/postgres` の結合テストで確かめる。結合テストは、`make check-all` で PostgreSQL 15〜18 に対して実行する。`TestIntervalTextTellsItsPartsApart` は、テキストを部分と照らし合わせる。`TestCompareIntervals` は、部分の違う期間と、部分が同じで書き方の違う期間を、CSV と SQL から計画して適用する。対象は、ふつうの列・配列・ドメイン・型修飾子のある列・範囲・複数範囲・複合型であり、負の部分・符号の混じったもの・秒の端数・PostgreSQL 17 からの `infinity` を含む。そして、テーブルがその後に持つテキストと、次の計画が空であることを確かめる。`TestIntervalKeys` は、1列の期間のキーの照合と、その2つのエラーをどのモードでも CSV と SQL から確かめる。組を10個までにする上限も確かめる。2列のキー・期間の配列のキー・期間を含む複合型のキーのエラーも確かめる。適用がそれで止まることも確かめる。`TestCompareTypes` は、`1 day` と `24 hours` の違いが変更になることを確かめる。`TestEqualByTheTypeIsNoChange` は、リファレンスがほかの型について挙げる例を1つずつ確かめる。変更が出ないこと、適用が保存されているテキストを残すこと、`UPDATE` で書いた値が残ることである。

## 選択肢の長所と短所

### 期間を、固定した IntervalStyle でのテキストで比べる

- 良い点：厳密であり、対応するどのバージョンでもテストがそれを示す。
- 良い点：配列・範囲・複数範囲・複合型は、同じ出力で期間を書く。そのため、1つの決まりですべてを扱える。
- 良い点：kortopi が等価性を持たない型にすでに使っている比べ方であり、費用は値ごとに出力関数を1回呼ぶことである。
- 悪い点：固定した `IntervalStyle` のもとでしか成り立たない。kortopi のどのセッションもそれを固定し、SQL ファイルの文はそれを変えられない（ADR-0022）。
- 悪い点：期間を含む複合型は、ほかの列もテキストで比べる。

### 期間を、`extract` で取り出した部分で比べる

- 良い点：期間のテキストに依らない。
- 悪い点：`extract` は、値の年・月・日・時・分・マイクロ秒を別々に返す。そのため、期間1つに6つの式が要る。また、無限の期間に対する `extract` は部分を返さない。
- 悪い点：配列・範囲・複合型の中の期間は、値ごとに展開する副問い合わせなしには取り出せない。

### 期間を、型の等価性で比べる

- 良い点：何も変わらず、照合キーとその一意インデックスはどの値についても一致する。
- 悪い点：`1 mon` と `30 days`、`1 day` と `24 hours` の間の変更を決してデプロイできず、計画はデータベースが一致すると言う。

### すべての値をテキストで比べる

- 良い点：どの型にも1つの決まりで済む。
- 悪い点：どの型についても ADR-0023 を覆す。numeric の桁数、`citext` の値の大文字と小文字、`-0`、`json` の空白が変更として現れ、照合キーは一意インデックスとは違うように行を組にする。
