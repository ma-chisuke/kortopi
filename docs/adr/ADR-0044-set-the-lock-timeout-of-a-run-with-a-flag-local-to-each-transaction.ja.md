# ADR-0044: 実行のロック待ちの上限は `--lock-timeout` で与え、kortopi の各トランザクションのローカルな設定にする

## 背景と課題

計画・apply・書き出しは、必要なロックをほかのセッションが持っている間、上限なく待つ。`ALTER TABLE` を実行するスキーマの変更、行を持ち続ける長いトランザクション、ほかの apply がその例である。
リファレンスは、実行にロック待ちの上限を `PGOPTIONS` で `-c lock_timeout=10s` のように与えるよう勧めていた。ADR-0037 は、kortopi が固定しない設定として、`lock_timeout` を最後までセッションの値のままにする。

`PGOPTIONS` は接続の起動パラメータである。
ADR-0026 は、apply どうしを直列にするロックについてトランザクションモードのコネクションプーラーに対応する。そうしたプーラーは、この起動パラメータを拒むか、無視するよう設定されていれば何も言わずに捨てる。前者では実行が接続できず、後者では利用者が当てにしている上限なしに実行が待つ（issue 43）。
セッションの設定はどれも同じである。トランザクションモードのプーラーは、クライアントのトランザクションごとに空いているサーバーとの接続を割り当てる。そのため、クライアントがセッションに設定したものは、ほかのクライアントに届くか、どこにも届かない。
`ALTER ROLE ... SET lock_timeout` はそうしたプーラーを通しても働く。しかしロールのすべてのセッションに効き、ロールを共有するアプリケーションのセッションにも効く。しかも、変更のあとでプーラーが開くサーバーとの接続にしか効かない。

kortopi の実行は、そのすべての待ちに効くロック待ちの上限を、トランザクションモードのコネクションプーラーの後ろでも、どうやって得るのか。

## 判断の基準

- 上限は、ロックを待ちうる実行のすべての文に効く。別の apply を待つこと、読み取り、書き込みとそれが発火させるトリガー、そしてコミットである。
- トランザクションモードのコネクションプーラーの後ろでも働き、kortopi 自身のトランザクション以外のセッションを変えない。
- 上限を与えない実行は、これまでどおりに動く。
- 上限が待ちを終わらせたときのエラーは、どの上限がそうしたかを伝える。
- 書き込みは、これまでどおりセッションの設定で動く（ADR-0037）。

## 検討した選択肢

- 各トランザクションの初めに `SET LOCAL` で設定するフラグ `--lock-timeout`
- `kortopi.toml` の設定
- これまでどおりの `PGOPTIONS` か `ALTER ROLE ... SET` と、リファレンスの注記
- 接続のあとにセッションへ `SET lock_timeout` する
- フラグなしの、kortopi 自身のロック待ちの上限
- kortopi 自身の文の時間の上限も設ける

## 決定

採用：「各トランザクションの初めに `SET LOCAL` で設定するフラグ `--lock-timeout`」。トランザクションのローカルな設定は、プーラーがどのサーバーとの接続を割り当ててもトランザクションとともにサーバーに届く。そしてトランザクションとともに終わり、その中のすべての文に効く。しかも、上限を必要とする実行が、それを自分のコマンドラインで指定する。

決まりは次のとおりである。

- `kortopi plan`・`kortopi apply`・`kortopi export` は `--lock-timeout <duration>` を受け取る。値は `10s`・`500ms`・`1m30s` のような Go の時間の長さで、`1ms` から `24h` までである。サーバーは `lock_timeout` をミリ秒の整数で持つので、kortopi はその長さの整数のミリ秒を送る。単位のない数と、この範囲の外の長さはフラグの誤りである。0 と負の長さも範囲の外にある。上限なく待つべき実行は、フラグを付けない。
- 実行のどのトランザクションも、フラグのロック待ちの上限で始まる。計画・書き出し・apply のトランザクションと、apply が別の apply を待つ短いトランザクションの `BEGIN` と、`SET LOCAL lock_timeout = <ミリ秒>` を、1つのメッセージでサーバーに送る。`SET` はスナップショットを取らないので、ADR-0026 のとおり、トランザクションのスナップショットは今も最初の問い合わせが取る。
- apply の書き込みとコミットは、kortopi が固定する設定をセッションの値に戻す（ADR-0037）。`lock_timeout` はそこに含まれない。そのためフラグの値は、書き込みと、それが発火させるトリガーと外部キーの動作に効き、コミットの遅らせたトリガーと制約にも効く。これは ADR-0037 を細かくする。ADR-0037 では、「`lock_timeout` のように kortopi が固定しない設定は、これまでどおり、最後までセッションの値のまま」である。フラグがあれば、`lock_timeout` は kortopi のどのトランザクションでも、最後までフラグの値である。
- kortopi のほかの設定と同じく（ADR-0037）、この設定はトランザクションのローカルなものである。コミットかロールバックで終わるので、同じサーバーとの接続の次のトランザクションは、セッションの設定に戻る。
- フラグがなければ何も変わらない。サーバー・データベース・ロール・`PGOPTIONS` が設定した、セッションの `lock_timeout` が効く。
- 上限が待ちを終わらせたときのエラーは、その上限を値とともに挙げる：

  ```text
  kortopi: update table m.status: canceling statement due to lock timeout: another session holds a lock on a table or on rows that the apply needs, and the apply waited for it as long as --lock-timeout 10s allows: run the apply again once that session has released the lock
  ```

  フラグがなければ `lock_timeout of the session` を挙げ、`or allow the wait more time with --lock-timeout` を足す。別の apply を待つときのエラーは、フラグか `lock_timeout or statement_timeout of the session` を挙げる。そして、止められた apply のセッションがロックを持ったままかもしれないこと、それは `pg_stat_activity` に表れ `pg_terminate_backend` で終わらせられることを足す（ADR-0043）。
- リファレンスは、ロック待ちの上限に `PGOPTIONS` を勧めるのをやめる。フラグを勧め、トランザクションモードのコネクションプーラーの後ろではサーバーに届かないものを伝える。`PGOPTIONS` のような起動パラメータと、セッションの設定全般である。

kortopi 自身の文の時間の上限は、この決定に含めない。長すぎる文は今もセッションの `statement_timeout` が終わらせ、それにはプーラーの後ろで同じ問題がある。同じ種類のフラグは、後の記録で与えられる。

### 結果

- 良い点：トランザクションモードのコネクションプーラーを通すデプロイも、求めたロック待ちの上限を、どの段階でも得る。
- 良い点：フラグはほかのセッションを変えない。ロールも、トランザクションのあとのサーバーとの接続も、アプリケーションも変えない。
- 良い点：エラーは、どの上限が待ちを終わらせたかと、その変え方を伝える。
- 良い点：フラグのない実行は、これまでどおりに動く。
- 悪い点：`PGOPTIONS` に `lock_timeout` を設定していたチームは、プーラーの後ろでそれを得るにはフラグに移さなければならず、スクリプトが変わる。
- 悪い点：フラグは書き込みが発火させるトリガーの待ちにも上限を設ける。それ以外については ADR-0037 のとおりセッションの設定が決めるところを、ここだけフラグが決める。
- 悪い点：プーラーの後ろでの文の時間の上限は、ロールの設定なしには、まだ与えられない。

### 確認の方法

- `cmd/kortopi` の単体テストは、各コマンドのフラグ、その誤り、フラグがセッションに届くことを確かめる（`TestLockTimeoutFlag`・`TestFlagOutput`・`TestHelpListsTheFlags`）。
- `internal/postgres` の単体テストは、トランザクションを始める文（`TestBeginSQL`）とエラー（`TestExplainWait`）を確かめる。
- `make check-all` で PostgreSQL 15 から 18 に対して動く結合テストは、`PGOPTIONS` が与えるのと同じく接続のオプションに 20 秒の `lock_timeout` を置き、フラグを 200 ミリ秒にする：
  - `internal/postgres` の `TestLockTimeoutInEachPhase`：対象は、別の apply を待つこと、計画と apply の読み取り、行ロックを待つ書き込み、遅らせたトリガーがロックを待つコミットである。どれもフラグの時間のあとに止まり、エラーがフラグを挙げる。書き込みとコミットのトリガーはフラグの値を見て、フラグがなければセッションの値を見る。`TestLockTimeoutEndsWithTheTransaction`：トランザクションのあと、接続はセッションの `lock_timeout` を持つ。
  - `cmd/kortopi` の `TestLockTimeoutCommand` は、計画・apply・書き出しをそれぞれの段階で動かす。`TestSettingsFromTheEnvironment` は、フラグがないときのエラーを確かめる。
- コネクションプーラーを通すテストはない。ADR-0037 が書き込みの設定について言うとおり、トランザクションのローカルな設定はそこでも設計上効く。

## 選択肢の長所と短所

### 各トランザクションの初めに `SET LOCAL` で設定するフラグ `--lock-timeout`

- 良い点：トランザクションとともに、どのプーラーも通って届き、往復も増えない。
- 悪い点：それを必要とする実行は、どれもフラグを指定しなければならない。

### `kortopi.toml` の設定

- 良い点：チームは1度書けば済む。
- 悪い点：設定ファイルは宣言の一部であり、どの環境でも同じである。一方、適した上限は、プルリクエストのチェックとデプロイとで違う。

### これまでどおりの `PGOPTIONS` か `ALTER ROLE ... SET` と、リファレンスの注記

- 良い点：kortopi は何も変わらない。
- 悪い点：前者はトランザクションモードのプーラーの後ろではサーバーに届かず、後者はロールのすべてのセッションを変える。

### 接続のあとにセッションへ `SET lock_timeout` する

- 良い点：文が1つで済む。
- 悪い点：トランザクションモードのプーラーの後ろでは、それはサーバーとの1つの接続に残る。次のトランザクションはその接続を得ないかもしれず、その設定を持った接続をほかのクライアントが得る。

### フラグなしの、kortopi 自身のロック待ちの上限

- 良い点：上限なく待つ実行がなくなる。
- 悪い点：長いトランザクションをわざと待っていた実行が失敗するようになり、どのデータベースにも合う既定値はない。

### kortopi 自身の文の時間の上限も設ける

- 良い点：プーラーの後ろでも、長すぎる文に上限を設けられる。
- 悪い点：多くの行に対する apply の文は、正当に何分もかかることがある。上限とそのエラーの選び方は、それ自体の決定に値する。
