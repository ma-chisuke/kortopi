# ADR-0011: 宣言が挙げた列だけを管理する

## 背景と課題

マスタテーブルは、宣言で決めるべきでない列を持つことが多い。
`created_at` や `updated_at` は、`now()` のような既定値を持つか、アプリが値を入れる。
ほかにも、システムの稼働中にアプリや運用者の書き込む列がある。たとえば、行を利用者から隠すためのフラグである。

kortopi がテーブルのすべての列を比べると、そうした列は、実行のたびに差分として現れる。そのため、計画は空にならず、適用はデータベースやアプリが書いた値を上書きしてしまう。
1つの答えは、比較から外す列の一覧を持つことである。
そうした一覧を使うと、宣言が値を決めない列は2回書くことになる。行からは外し、一覧には書く。

kortopi は、テーブルのどの列を比べ、更新するか。

## 判断の基準

- 宣言が値を決めない列を、kortopi は決して変えない。
- 宣言と歩調を合わせて保つべき、2つ目の列の一覧がない。
- 読む人は、宣言だけを見て、kortopi が管理する列がわかる。
- 新しい行でも、宣言が値を決めない列に妥当な値が入る。

## 検討した選択肢

- 宣言が挙げた列
- テーブルのすべての列と、比べない列の一覧
- テーブルのすべての列

## 決定

採用：「宣言が挙げた列」。どの列の値を決めるかは宣言がすでに示しているので、2つ目の一覧が要らず、宣言が挙げない列には手を出さずに済むからである。

決まりは次のとおりである。

- テーブルの管理する列は、その CSV ファイルの見出しの行の列か、その INSERT 文の列の一覧の列である。
- kortopi が比べ、更新するのは、管理する列だけである。宣言が挙げない列は、比べることも更新することもない。
- kortopi が新しい行を挿入するとき、宣言が挙げない列には、データベースがその列に定めた既定値が入る。

次の2つの細部は、SQL を読む処理の実装のときに決める（ADR-0015）。列の一覧のない INSERT 文をエラーにするかどうかと、1つのテーブルに対するすべての INSERT 文が同じ列を挙げなければならないかどうかである。

### 結果

- 良い点：`now()` を既定値に持つ `updated_at` のような列は、設定が要らない。宣言に書かなければ kortopi は比べも上書きもせず、新しい行には `now()` が入る。
- 良い点：システムの稼働中にアプリや運用者の変える列は、宣言から外しておけば、その値が保たれる。
- 良い点：テーブルの宣言が、そのテーブルで kortopi が管理するもののすべてを表す。
- 悪い点：利用者が宣言に書き忘れた列は管理されず、kortopi はそれを報告しない。
- 悪い点：宣言から列を外すと、その列の管理はやめるが、値はそのまま残る。kortopi は、その列を既定値に戻さない。

### 確認の方法

PostgreSQL 15〜18 に対する結合テストで、宣言が挙げない列を比べも更新もしないことと、新しい行ではその列に既定値が入ることを確かめる。
これらのテストは、plan の実装とともに加わる。

## 選択肢の長所と短所

### 宣言が挙げた列

- 良い点：管理する列の一覧は、宣言だけである。
- 良い点：`now()` のような既定値を持つ列には、何もしなくてよい。
- 悪い点：誤って外した列は報告されない。

### テーブルのすべての列と、比べない列の一覧

- 良い点：宣言が書き忘れた列は差分として現れるので、うっかり外れたままになる列がない。
- 悪い点：宣言が値を決めないすべての列を、一覧にも書く必要がある。既定値を持つ新しい列は、宣言するか一覧に書くまで、すべての計画に現れる。
- 悪い点：一覧が行とは別の場所にあるので、宣言だけを見ても、kortopi が何を管理するかはわからない。

### テーブルのすべての列

- 良い点：いちばん単純な決まりである。
- 悪い点：`updated_at` のような列は実行のたびに違うので、計画が空にならない。適用は、データベースやアプリが書いた値を上書きする。
- 悪い点：どの宣言も、データベースやアプリだけが値を決めるべき列を含め、すべての列を持つ必要がある。

## 補足

- どの行を組にするかは照合キーが決める（ADR-0012）。組にした行のどの列を比べるかは、この記録が決める。
