# ADR-0034: `--no-pending` で、データベースにないすべての名前で計画を止められるようにする

## 背景と課題

計画は、データベースにない宣言済みのテーブルや列を、スキーマの適用後に決まるものとして示し、終了コード 0 で終わる（ADR-0016、ADR-0024）。
そのため、プルリクエストはまだ適用していないスキーマの変更の行を宣言しても、計画を得られる。

その代わりに、綴りを誤った名前も同じに見える。
CSV の見出しの行が列 `sort_order` を `sortorder` と書くと、計画は `column sortorder: known after the schema is applied` の行を出して通り、この列は比べられない。
この誤りが表に出るのは、apply がそこで止まったときだけである（ADR-0026）。
ADR-0031 は、データベースの名前と空白か大小だけが違う名前をエラーとし、そのほかの綴りの誤りはそのままにした。すべての適用待ちの名前をエラーにするフラグについては、それ自体が1つの決定であるとした。

スキーマが適用済みだと分かっている実行もある。プルリクエストのスキーマを使い捨てのデータベースに適用してから計画するチェックや、スキーマの道具が動いたあと（ADR-0007）の、デプロイのときの apply の前の段階がそうである。
こうした実行では、データベースにない名前は誤りである。綴りの誤りか、その実行が適用しなかったスキーマの変更である。

こうした実行は、スキーマが適用済みであることをどう kortopi に伝え、綴りを誤った名前で計画を止めるのか。

## 判断の基準

- まだ適用していないスキーマの変更の行を宣言するプルリクエストも、フラグなしで計画を得る（ADR-0016）。
- スキーマが適用済みだと分かっている実行は、綴りを誤った名前で計画を止め、それを宣言したファイルを示させられる。
- 現在動いているどの計画も、出力と終了コードを変えない。
- 1回の実行で、そうした名前をすべて報告する（ADR-0024）。

## 検討した選択肢

- 切り替えを設けない：チェックが宣言を適用し、もう一度計画する
- すべての適用待ちの名前をエラーにする plan のフラグ `--no-pending`
- すべての適用待ちの名前を既定でエラーにし、それを許すフラグを設ける

## 決定

採用：「すべての適用待ちの名前をエラーにする plan のフラグ `--no-pending`」。スキーマが適用済みだと分かっている実行は1つのフラグでそれを伝えられ、スキーマの変更の前のプルリクエスト（kortopi のよくある最初の使い方）は、今の計画をそのまま得られるからである。

決まりは次のとおりである。

- `kortopi plan --no-pending` では、データベースにない宣言済みのテーブルと、そのテーブルにない宣言済みの列が、計画の行ではなくエラーになる。
- そうした名前1つごとに、エラーを1つ出す。エラーはファイルと、宣言が指すテーブル名か列名を挙げる。CSV ファイルなら書いたとおりの名前であり、SQL ファイルなら PostgreSQL が読んだとおりの名前で、引用符のない名前は小文字になる。エラーはさらに、そのテーブルや列がデータベースにないことと、`--no-pending` がなければスキーマの変更を待つことを告げる。これらのエラーは、計画がどの行も読み込む前にまとめて報告する誤りに含まれ（ADR-0024）、計画は終了コード 1 で終わる。
- データベースの名前と空白か大小だけが違う名前は、それ自体のエラー（ADR-0031）を保ち、`--no-pending` のエラーは出さない。`kortopi.toml` が照合キーに挙げた列がテーブルにないときは、その列のエラーだけを出し、スキーマの変更を待つキーの列のエラーは重ねない。
- そうした名前がなければ、出力と終了コードは、フラグなしの計画とまったく同じである。
- このフラグは、`--format text` と `--format sql`、`--exit-code`、`--schema` と組み合わせて使える。`--schema` は、検査の前に宣言済みのテーブルを絞る。
- `apply` には、このフラグはない。apply は、データベースにないテーブルや列があれば必ず止まり、何も変えない（ADR-0026）。`apply --no-pending` と `export --no-pending` には、未知のフラグのエラーを出し、ヒントを添える。apply へのヒントは、apply がスキーマの変更を待つ名前で必ず止まることを述べ、フラグを外すか、apply の前に `kortopi plan --no-pending` を実行するよう告げる。書き出しへのヒントは、書き出しがデータベースにない名前で必ず止まることを述べ、フラグを外すよう告げる。
- これは ADR-0016 と ADR-0024 を細かくする。その計画は、そうした名前をすべてスキーマの適用後に決まるものとして示す。`--no-pending` があれば、どれもエラーになる。
- ADR-0021 も細かくする。ADR-0021 のコマンドラインの形は plan のフラグを挙げており、plan に `--no-pending` が加わる。終了コード 1 は、`--no-pending` があれば、宣言済みのテーブルや列が存在しないことも意味するようになる。`--exit-code` だけなら、そうした名前は違いとして数え、終了コードは 2 である。
- ADR-0031 が別の記録に委ねた決定を、この記録が下す。

### 結果

- 良い点：プルリクエストのスキーマを使い捨てのデータベースに適用するチェックは、綴りを誤ったテーブルや列で、apply より前の計画の時点で止まり、それを宣言したファイルを示す。
- 良い点：現在動いているどの計画も、出力と終了コードを変えない。
- 良い点：エラーはどの行も読み込む前に出て、1回の実行でそうしたテーブルと列をすべて挙げる。
- 悪い点：チームはこのフラグを付けることを知っている必要がある。付けなければ、綴りを誤った名前は引き続きスキーマの変更を待つ名前に見える。
- 悪い点：apply の前では、このフラグは検査を増やさない。apply は同じ名前で止まり、何も変えない。フラグを付けた計画は、より早く止まり、ファイルを示すだけである。
- 悪い点：このフラグは実行が知っていることを述べるものであり、kortopi はそれを確かめられない。スキーマの変更をまだ適用していないデータベースに対して付けると、正しい名前で失敗する。

### 確認の方法

- `internal/plan` の単体テストがエラーを確かめる。`TestBuildNoPending` は、テーブル・列・その両方・複数のテーブル・大小の違う名前・テーブルのほかの誤り・照合キーの列を確かめる。`TestBuildNoPendingWithoutPendingNames` はそうした名前のない宣言を、`TestBuildNoPendingNarrowedBySchema` は `--schema` を確かめる。
- `cmd/kortopi` の単体テストがコマンドを確かめる。`TestParsePlan` はフラグを確かめる。`TestRunPlanNoPending` と `TestRunPlanNoPendingWithoutPendingNames` は、出力の形式・`--exit-code`・`--schema` を確かめる。`TestRun` と `TestFlagOutput` は apply と export のヒントを、`TestHelpListsTheFlags` はヘルプを確かめる。
- `cmd/kortopi` の結合テスト `TestPlanCommandNoPending` は、`make check-all` で PostgreSQL 15 から 18 に対して `kortopi plan --no-pending` を実行する。綴りを誤った列と、データベースにないテーブルを、両方の形式で計画する。そうした名前のない宣言では、出力と終了コードがフラグなしのものと等しいことを確かめる。
- データベースにないテーブルや列で apply が止まることを確かめるテストは、そのまま残る。`internal/apply` の `TestRun`、`cmd/kortopi` の `TestRunApply`、結合テスト `TestApplyCommand` である。

## 選択肢の長所と短所

### 切り替えを設けない：チェックが宣言を適用し、もう一度計画する

- 良い点：kortopi に新しいものは要らない。使い捨てのデータベースへの apply は、綴りを誤った名前があれば必ず止まる（ADR-0016）。
- 悪い点：誤りは、通った計画のあとの apply で初めて表に出る。apply のエラーはテーブルを挙げるが、ファイルは挙げない。
- 悪い点：レビューする人に変更を見せる計画のように、計画するだけで apply しない実行には、綴りを誤った名前で止まる手段がない。

### すべての適用待ちの名前をエラーにする plan のフラグ `--no-pending`

- 良い点：スキーマが適用済みだと分かっている実行がそれを伝え、ほかの実行は何も変わらない。
- 悪い点：フラグは付け忘れやすく、付けない実行は綴りを誤った名前を通す。

### すべての適用待ちの名前を既定でエラーにし、それを許すフラグを設ける

- 良い点：適用待ちの名前を許さないすべての計画が、綴りを誤った名前で止まる。
- 悪い点：自分のスキーマの変更の行を宣言するプルリクエスト（kortopi のよくある最初の使い方）は、フラグを足すまで計画が失敗する。
- 悪い点：適用待ちの名前を示す今のすべての計画が、エラーを出し、別の終了コードで終わるようになる。`--exit-code` でそうした名前を数えるずれの検出も同じである（ADR-0021）。
