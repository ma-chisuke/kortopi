# ADR-0005: サプライチェーンを層を重ねて守り、依存の更新を Renovate に任せる

## 背景と課題

このリポジトリで動くコードの大半は、他人が書いたものである。CI のアクション、各マシンの道具、npm・Python・Go のパッケージがそうである。
どれもソースコードにアクセスできる状態で動き、CI ではトークンにもアクセスできる。
攻撃者がそのどれか1つを乗っ取れば、それを使うすべてのリポジトリに手が届く。
このリポジトリが使う道具も、実際にこの種の攻撃を受けた。2026年3月の攻撃（CVE-2026-33634）では、Trivy v0.69.4 が改ざんされ、GitHub Actions の `trivy-action` と `setup-trivy` のタグが書き換えられた。

kortopi では、危険がさらに大きくなる。
kortopi は、利用者のデプロイのパイプラインの中で、マスタテーブルを変えられるデータベースのロールを持って動く。そのため、バイナリに組み込まれたモジュールが乗っ取られていれば、利用者の本番のデータベースに手が届く。

固定すれば、配布元での変更が気づかれないままこのリポジトリに入ることはない。ただし、固定したものがひとりでに新しくなることもない。
誰も更新しない固定は既知の脆弱性を抱えたままになり、何か月も先送りした更新は移行作業に変わる。

乗っ取られた依存にできることをどう限り、乗っ取られたことにどう気づき、そのうえですべての固定をどう新しく保つか。

## 判断の基準

- kortopi が依存するものの変更は、誰かがレビューできる、このリポジトリへの変更を通してだけ入ってくる。
- 改ざんされたダウンロードは、インストールに失敗する。新しいリリースはインストールの前に一定の期間を待ち、悪意のあるリリースがその間に見つかって取り下げられるようにする。
- どの守りも、人の注意ではなく、チェック・パッケージマネージャー・GitHub のどれかが守らせる。
- 1つの更新の道具が、`mise.toml` を含むすべての種類の固定を扱う。決まりきった更新には人が要らず、危険な更新には人が要る。
- 守りと更新のどちらについても、有料のサービスを必要としない。

## 検討した選択肢

- 固定した道具で層を重ねて守り、すべての更新に Renovate を使う
- 層を重ねて守り、Dependabot のバージョン更新を使う
- 配布元のタグと最新のバージョンを信頼する
- すべての依存をリポジトリに取り込む
- サプライチェーンのセキュリティのための商用プラットフォーム

## 決定

採用：「固定した道具で層を重ねて守り、すべての更新に Renovate を使う」。層ごとに違う種類の攻撃を有料のサービスなしで止められ、しかも Renovate は、このリポジトリのあらゆる種類の固定を `mise.toml` も含めて動かせる唯一の更新の道具だからである。

GitHub Actions には次の決まりを置き、`make check` の pinact・zizmor・ghalint が守らせる。

- どのアクションもコミット SHA の全桁で固定する。タグが動かされても、何も変わらない。リポジトリの設定により、固定していないアクションは GitHub 自身も拒む。
- ワークフローは最上位で権限を何も与えず、各ジョブは必要な権限だけを求める。どのチェックアウトも認証情報を残さない（`persist-credentials: false`）。
- どのジョブにも `timeout-minutes` を書く。

道具には次の決まりを置き、`make setup` が道具を入れるときに mise が守らせる（ADR-0004）。

- mise は、`mise.lock` に書かれたものだけを入れる。配布元が来歴（GitHub の artifact attestations か cosign）を提供している場合、mise はロックを書くときにそれを検証する。
- Trivy は、mise がバージョンとチェックサムを固定して入れる。この記録で述べた攻撃があったため、`trivy-action` と `setup-trivy` のアクションは使わない。

npm のパッケージには、`pnpm-workspace.yaml` の次の設定を pnpm が守らせる。

- 新しいリリースは、公開から3日たつまで入れられない（`minimumReleaseAge`）。バージョンは範囲ではなく、正確な値で保存する（`saveExact`）。
- 推移的な依存のうち、Git リポジトリや tarball の URL のようにレジストリの外から来るものは拒む（`blockExoticSubdeps`）。
- 公開者の信頼の度合いが以前のリリースより下がったリリースは拒む（`trustPolicy: no-downgrade`）。
- `allowBuilds` に載っていない依存は、ビルドのスクリプトを実行しない（`strictDepBuilds`）。この一覧には、何も載っていない。

Python のパッケージには、`pyproject.toml` の次の設定を uv が守らせる。

- `uv.lock` はすべてのパッケージのハッシュを持つ。ロックが合わなければ、`uv sync --locked` は失敗する。
- 公開から3日たっていないリリースは無視する（`exclude-newer`）。uv は mise が入れた Python を使い、別の Python をダウンロードしない。

Go のモジュールには次の決まりを置き、Go のツールチェーンと Makefile が守らせる。

- `go.sum` は、すべてのモジュールのチェックサムを持つ。`GOFLAGS=-mod=readonly` により、コマンドは `go.mod` や `go.sum` を書き換える代わりに失敗する。`GOTOOLCHAIN=local` により、Go は別のツールチェーンをダウンロードしない。
- govulncheck は、実際に呼ばれているコードにある既知の脆弱性を報告する（`make check-all` の `vuln-go`）。
- ADR-0015 が SQL を読むために選ぶモジュールは、タグを付けたリリースを出していない。そのため、`go.mod` はこれを疑似バージョン、つまりコミットで固定する。`go.sum` は、ほかのモジュールと同じようにそのチェックサムを持つ。

Trivy は、ロックファイルをもとに依存をスキャンする（`make check-all` の `scan-deps`）。

- すべての依存について、深刻度が MEDIUM・HIGH・CRITICAL の既知の脆弱性を報告する。開発のための道具も、手元のマシンと CI で動くので対象に含める。
- 脆弱性を報告するのは、修正されたバージョンが出た日からである（`trivy.yaml` の `ignore-unfixed`）。直しようのない指摘は、修正が出るまで、すべてのプルリクエストを失敗させるからである。それまでの間は Dependabot alerts がその脆弱性を一覧に出し、呼ばれている Go のコードが影響を受けるなら govulncheck が失敗する。
- バイナリに入る依存のうち、`trivy.yaml` が禁止するライセンスのものがあれば失敗する（ADR-0006）。

秘密情報については、gitleaks がコミットの前にはステージした変更を、`make check` では作業ツリーを調べる（`lint-secrets`）。GitHub のシークレットスキャンとプッシュ保護は、すべてのプッシュを調べる。

リポジトリには、GitHub の次のサービスを使う。

- CodeQL が、プルリクエストのたび・`main` へのプッシュのたび・週1回、Go のコードとワークフローを解析する（`.github/workflows/codeql.yml`）。
- OpenSSF Scorecard が、リポジトリのセキュリティの慣行を評価し、結果を公開する（`.github/workflows/scorecard.yml`）。
- private vulnerability reporting を使えば、脆弱性を公開せずに報告できる（`SECURITY.md`）。
- Dependabot は、脆弱な依存について警告を出す。プルリクエストは開かない。

Renovate は、`renovate.json` の設定に従って固定を更新する。

- Go のモジュール・npm と Python のパッケージ・`mise.toml` の道具・アクションの SHA を更新する。ワークフローにある mise のバージョンと、`make/repo.mk` のスキーマの URL にある lefthook のバージョンも更新する。
- pnpm や uv と同じく、リリースから3日待ち、待ちが終わるまではプルリクエストを開かない。
- プルリクエストは週1回の予定に沿って開き、ロックファイルは月に1回新しくする。セキュリティの修正は、この予定を待たない。
- patch の更新は、エコシステムごとに1つのプルリクエストにまとめる。一緒に動くべきバージョンもまとめる。textlint のパッケージ群、`mise.toml` の Go とすべての `go.mod` の `go` ディレクティブ、`mise.toml` と `package.json` の pnpm、lefthook とそのスキーマである。
- patch・ダイジェスト・固定の更新は、必須チェックが通れば自分でマージする。minor と major の更新は人を待つ。
- 更新は固定やロックファイルを変えるので、そのプルリクエストのチェックはすべてのファイルを対象にする（ADR-0004）。

kortopi のバイナリをどう公開し、リリースの出どころをどう示すかは、まだ決めていない。後の記録で扱う。

### 結果

- 良い点：タグが動かされても、リリースが差し替えられても、ダウンロードが改ざんされても、そのコードは動く前にインストールの時点で失敗する。
- 良い点：悪意のある npm や Python のリリースが3日以内に見つかって取り下げられれば、このリポジトリには届かない。Renovate も、pnpm や uv が拒むリリースを提案しない。
- 良い点：CI のステップが乗っ取られても、それが持つのはジョブが求めた権限だけであり、それもジョブのタイムアウトまでである。
- 良い点：どの固定も、チェックで検証されるプルリクエストという同じ方法で更新され、patch の更新には人が要らない。
- 悪い点：更新は、セキュリティの修正も含めて3日遅れて届く。人がそのパッケージを待ちから外すまで（`minimumReleaseAgeExclude`・`exclude-newer-package`）、pnpm と uv は公開から3日たっていないリリースを拒む。
- 悪い点：来歴を公開していない道具もあり、Go と Node.js のランタイムもそこに含まれる。それらについては、`mise.lock` はチェックサムしか記録しない。チェックサムが示すのは、どのマシンもロックしたときと同じファイルを受け取ることだけであり、そのファイルが作者のビルドしたものであることまでは示さない。
- 悪い点：人が手で足したバージョンは、`go get` でも `mise.toml` でもすぐに入る。待つのは、Renovate が提案する更新だけである。
- 悪い点：コミットで固定したモジュールには、待ちの起点になるリリースも、変更の大きさを示すバージョンの番号もない。SQL のパーサの更新を Renovate が自分でマージしてよいかは、そのモジュールを加えるときに決める（ADR-0015）。
- 悪い点：自動のマージは、チェックと同じ程度にしか安全でない。テストがカバーしていない振る舞いを壊す patch のリリースは、人を通さずにマージされる。
- 悪い点：プルリクエストは途切れずに届く。まとめて週1回にしても、毎週レビューの時間を取られる。
- 悪い点：Renovate のアプリはリポジトリへの書き込みの権限を必要とするので、信頼する相手が1つ増える。設定を誤ると、ある種類の固定の更新が知らないうちに止まることもある。
- 悪い点：守りのいくつかはファイルではなくリポジトリの設定なので、`make check` からは見えない。

### 確認の方法

- `make check` は、ワークフローに `lint-actions-pins`・`lint-actions-security`・`lint-actions-policy` を、ファイルに `lint-secrets` を実行する。`make check` の `lint-schema` は、check-jsonschema に同梱された Renovate のスキーマで `renovate.json` を検証する。
- `make setup` は、`locked = true` のもとで `mise install` を実行する。`pnpm-workspace.yaml` の設定のもとでの `pnpm install --frozen-lockfile` と、`uv sync --locked` も実行する。CI も同じターゲットを実行する。
- `make check-all` は `scan-deps` と `vuln-go` を実行する。
- CodeQL と Scorecard は、ワークフローとして動く。シークレットスキャン・プッシュ保護・private vulnerability reporting・プルリクエストを開かない Dependabot alerts は、リポジトリの設定である。アクションの固定の義務と、既定で読み取りだけのトークンも設定である。`make github-settings` がこれらを有効にし、`docs/guides/github-settings.md` と違うものがあれば報告する。
- `trivy-action` と `setup-trivy` を使うワークフローがないことは、レビューで確かめる。Renovate がすべての種類の固定を扱っていることも、Renovate の開くプルリクエストのレビューで確かめる。どちらにも、守らせるチェックはない。

## 選択肢の長所と短所

### 固定した道具で層を重ねて守り、すべての更新に Renovate を使う

- 良い点：ほとんどの層は、チェック・パッケージマネージャー・mise が守らせる。残りは設定であり、`make github-settings` とレビューで確かめる。
- 良い点：1つの更新の道具・1つの設定・1つの形のプルリクエストで、すべての固定を扱える。
- 悪い点：設定が多くのファイルに散らばっており、変える前にそれぞれを理解する必要がある。

### 層を重ねて守り、Dependabot のバージョン更新を使う

- 良い点：Dependabot は GitHub に組み込まれており、入れるアプリがない。
- 悪い点：`mise.toml` を更新しないので、道具の固定には別の仕組みが要る。
- 悪い点：自分ではマージしない。自動でマージするには、別にワークフローが要る。

### 配布元のタグと最新のバージョンを信頼する

- 良い点：更新が、手間なしですぐに届く。
- 悪い点：タグが動かされたり悪意のあるリリースが出たりすると、次の実行でこのリポジトリに届く。バイナリを通して、kortopi の利用者のデータベースにも届く。

### すべての依存をリポジトリに取り込む

- 良い点：ビルドの最中に何もダウンロードせず、依存の変更はすべて差分に出る。
- 悪い点：リポジトリがすべての依存の分だけ大きくなり、更新の差分が大きすぎてレビューできない。

### サプライチェーンのセキュリティのための商用プラットフォーム

- 良い点：プラットフォームによっては、勧告が出る前に、悪意のあるパッケージをその振る舞いから見つける。
- 悪い点：オープンソースのプロジェクトは、貢献者に有料のアカウントを求められない。また、そのプラットフォームが、コードにアクセスできる相手として1つ増える。
