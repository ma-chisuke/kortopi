# ADR-0018: 削除に、モード・明示のフラグ・上限・参照の件数という安全策を設ける

## 背景と課題

モードが `sync` のテーブル（ADR-0013）では、apply は、テーブルにあって宣言にない行を削除する。
それがこのモードの目的であり、同時に危うさでもある。

1つの誤りで、多くの行が一度に消えうる。
エディターが CSV ファイルの半分だけを保存した、実行するディレクトリを間違えた、置換で多くの行の照合キーを変えてしまった、などである。最後の場合は、その行のそれぞれが削除と挿入になる（ADR-0012）。
どの場合も、計画は宣言に対しては正しく、チームの意図に対しては誤っている。

マスタの行は、ほかのテーブルから参照される。注文のような業務のテーブルから参照されることも多い。
外部キーによっては、参照されている行の削除は失敗するか、参照している行も一緒に消したり変えたりする（`ON DELETE CASCADE`、`ON DELETE SET NULL`）。
計画を読む人には、どのマスタの行が消えるかは見えても、それを何が参照しているかは見えない。

誤って削除が起きるのを防ぎつつ、意図した削除はできるようにするには、どうすればよいか。

## 判断の基準

- チームがそのテーブルで削除を選ばない限り、何も削除しない。
- 計画が示す削除は、apply のときに誰かが求めた場合にだけ適用する。
- 多くの行を消す誤りは、何かを変える前に止まる。
- 削除がマスタテーブルの外に何を及ぼすかを、計画が示す。
- 削除をしないチームは、安全策の手間を負わない。

## 検討した選択肢

- 4つの層：モード、明示のフラグ、上限、参照の件数
- 管理するテーブルの大きさの上限だけ
- `sync` モードではフラグなしに削除する
- 決して削除しない

## 決定

採用：「4つの層：モード、明示のフラグ、上限、参照の件数」。層ごとに違う誤りを止め、合わせれば、意図した削除はできるようにしたまま、うっかりの削除を防げるからである。

層は次のとおりである。

1. モード。行を削除するのは、モードが `sync` のテーブルだけである（ADR-0013）。`insert` と、既定の `upsert` では、宣言にない行には手を付けない。
2. 明示のフラグ。`sync` でも、apply のフラグで削除を許さない限り、apply は何も削除しない。フラグがなくても計画には削除が示されるので、誰かが削除を許す前に、レビューする人がそれを見られる。
3. 上限。削除する行の数が上限を超えると apply は止まり、データベースは元のままである。
4. 参照の件数。削除する行について、ほかのテーブルごとに、それを参照している行の数を計画が示す。

次の詳細は実装のときに決め、あとの記録で定める。

- フラグの名前。
- 上限の既定値と、削除する行をテーブルごとに数えるか、実行全体で数えるか。
- フラグなしの apply を、エラーで止めるか、ほかの変更を適用したうえで、見送った削除を報告するか。

削除を論理削除（行を消す代わりに印を付ける）に切り替える機能は、あとで加えうるものであり、最初の版には入れない。

### 結果

- 良い点：既定のモードは決して削除しないので、`sync` を選ばないチームが削除に出会うことはない。
- 良い点：削除には、別々のときに下す2つの判断が要る。1度だけレビューする設定のモードと、apply のときのフラグである。
- 良い点：典型的な誤り（途中で切れたファイルや、間違ったディレクトリ）では、多くの行が一度に消える。上限は、まさにそれを止める。
- 良い点：参照の件数によって、削除がどの業務の行に及ぶかを、レビューする人が計画の中で見られる。外部キーが apply を失敗させたり、カスケードが行を消したりする前である。
- 悪い点：参照を数えるには、参照しているテーブルを読む必要がある。計画を立てるロールにはそれらのテーブルの `SELECT` も要り、インデックスのない参照の列で数えると、テーブル全体を読むことになる。読めないテーブルを kortopi がどう報告するかは、実装のときに決める。
- 悪い点：意図して削除するデプロイでは、フラグを渡す必要がある。毎回フラグを渡すチームでは、この層は形だけになる。それでも、上限と参照の件数は働く。
- 悪い点：上限は選ぶべき数である。低すぎれば正当な整理を止め、高すぎれば誤りを通してしまう。

### 確認の方法

- PostgreSQL 15〜18 に対する結合テストで、層ごとに次のことを確かめる。`sync` 以外では削除しないこと、フラグなしでは削除しないこと、上限を超えたら apply が止まって何も変えないこと、計画に参照の件数が出ることである。これらのテストは、apply の実装で加わる。

## 選択肢の長所と短所

### 4つの層：モード、明示のフラグ、上限、参照の件数

- 良い点：層ごとに違う誤りを止める。削除をしないチームは、どの層にも出会わない。
- 悪い点：覚えることが増え、上限という設定も1つ増える。

### 管理するテーブルの大きさの上限だけ

安全策は、kortopi がテーブルごとに管理する行の数の上限だけである。それより多くの行を持つテーブルがあると、実行を止める。

- 良い点：1つの数で、大きなテーブルと大量の削除の両方を防げる。
- 悪い点：制限するのはテーブルの大きさであり、変更の大きさではない。小さなテーブルの行をすべて削除しても通ってしまう。
- 悪い点：削除がほかのテーブルの行に何を及ぼすかについては、何も示さない。

### `sync` モードではフラグなしに削除する

- 良い点：単純であり、意図はモードがすでに示している。
- 悪い点：判断は設定の中で1度だけ下され、そのあとのすべての実行に及ぶ。宣言が壊れた実行にも及ぶ。

### 決して削除しない

- 良い点：どんな誤りでも行は消えない。
- 悪い点：宣言から外した行がデータベースに残り続けるので、ずれが広がる。チームはレビューの外で、手で削除することになる。
