# ADR-0045: apply が列に書いた値の先へ、その列のシーケンスをコミットの直前に進め、決して戻さない

## 背景と課題

識別列や `serial` のキーを持つテーブルは、ID ごと宣言することが多い。ほかのテーブルやほかの環境が同じ ID を参照するからである。一方で、アプリケーションは同じテーブルに、キーのシーケンスから取った ID で行を挿入する。
ADR-0026 は「kortopi はシーケンスを読みも進めもしない」と決め、リファレンスはその帰結を分かっている制限として挙げていた。

issue 29 は、その代償を示す。
`billing.tax_rates` は識別列のキーを、`billing.fees` は `serial` のキーを持ち、アプリケーションはそれぞれのシーケンスから ID 1 と 2 を取っている。
宣言は各テーブルに ID 3 の行を足し、apply は両方の行を挿入してコミットする。
どちらのシーケンスも次に 3 を返すので、アプリケーションの次の挿入は主キーで失敗する。apply が使った ID の数だけ、1回ずつ失敗する。

```text
=# INSERT INTO billing.fees (name, amount) VALUES ('gift', 300);
ERROR:  duplicate key value violates unique constraint "fees_pkey"
DETAIL:  Key (id)=(3) already exists.
```

計画は何も警告しなかった。
回避策は、apply のたびにそうしたテーブルごとの `setval` を、手かデプロイのスクリプトで実行することであり、シーケンスごとに `UPDATE` が要る。あるいは ID を外して自然キーで照合するが、そうすると行の ID は環境ごとに変わる。

シーケンスは行ではない。PostgreSQL は、`nextval` と `setval` がしたことを決して戻さない。それを呼んだトランザクションがロールバックしても同じである。そのため、シーケンスを進めることは、行と違ってコミットを待てない。
また、apply が動いている間も、ほかのセッションはシーケンスから値を取る。

apply はどのシーケンスを、どこまで進めればよいのか。そして、いつどう進めれば、シーケンスを決して戻さず、失敗した apply にも害がないようにできるのか。

## 判断の基準

- シーケンスから値を取る列に apply が明示的な値を書いたあとは、シーケンスの次の値はそのどれでもない。
- シーケンスは決して戻らない。ほかのセッションがそこから値を取っていても同じである。
- 失敗した apply は行を変えず、戻せないことは値を飛ばすだけにとどまる。
- 計画は何も変えない（ADR-0016）。シーケンスを読むが、`nextval` も `setval` も呼ばない。
- シーケンスを進められないロールも行は適用でき、何を付与すればよいかと、シーケンスを手で進める方法を知る（ADR-0026）。
- シーケンスのロックは、計画も apply も長くは止めない。シーケンスに対する文での PostgreSQL のエラーは、それなしなら成功する計画や apply を失敗に変えない。
- 出力は、データベースが読んだとおりにシーケンスの位置を伝える。最後まで終わらなかった進めのあとも同じである。
- SQL としての計画は、計画したロールによる apply と同じことをし（ADR-0029）、シーケンスで失敗しない。計画より遅れて動いても同じである。
- kortopi はオブジェクトを作らず（ADR-0010）、自分の書き込みが求める分だけ進める。

## 検討した選択肢

- apply が値を書く列ごとに、列が所有するシーケンスをコミットの直前に進める。上限までは `nextval` で、それを超えれば `setval` で進める
- 書き込みのあと、そうしたシーケンスを列の最大の値に `setval` で合わせる
- 書き込みの前にシーケンスを進める
- 計画で警告し、進めるのはチームに任せる
- apply のたびに、宣言したすべてのテーブルのシーケンスを進める

## 決定

採用：「apply が値を書く列ごとに、列が所有するシーケンスをコミットの直前に進める。上限までは `nextval` で、それを超えれば `setval` で進める」。次の値を apply が書いた値の先へ運べ、ほかのセッションが値を取っていてもシーケンスを戻さないからである。また、戻せないことが apply の最後の確認より前に起きることはなく、apply が書かなかった列のシーケンスにはどれも触れない。

規則は次のとおりである。

対象のシーケンス：

- 列がそこから値を取るシーケンスを所有するのは、次の2つの場合である。1つは識別列で、そのシーケンスは列に内部の依存を持つ。もう1つは `serial` が作る形である。型が `smallint`・`integer`・`bigint` の列がシーケンスを所有し、列の既定値がそのシーケンスの次の値だけ、つまり `nextval('<schema>.<sequence>'::regclass)` の場合をいう。どちらもカタログの `pg_depend` と `pg_attrdef` が示し、列を読む問い合わせが一緒に読む。権限は要らない。
- apply がそうしたシーケンスを進めるのは、その実行で列に明示的な値を書くときだけである。1つは行を挿入し、その列がキー・比べる列・`on_insert` の列のどれかであるときである。もう1つは行を更新し、更新がその列を変えるときである。
- 範囲の外：列が所有せずに使うシーケンス（複数のテーブルが共有するシーケンスや、宣言したパーティションが使うパーティションテーブルのシーケンスなど）。既定値が次の値を取る以上のことをする列（`nextval(...) * 10` など）。ほかの型の列やドメインの列。apply がその実行で列に明示的な値を書かないテーブル。kortopi の以前の版のあとのようにシーケンスが遅れていても同じであり、列を書く次の apply が進める。宣言が持たないテーブルのシーケンス。

進める先：

- 目標は、シーケンスが次に返す値から増分ずつ進めた値のうち、apply のトランザクションが書き込みのあとに見る列の値の先にある最初の値である。増えるシーケンスなら最大の値の上、減るシーケンスなら最小の値の下である。進めてもシーケンスの値の並びは保つ。`INCREMENT 10` で次の値が 25 のとき、列の最大の値が 41 なら、目標は 42 ではなく 45 である。こうすれば、シーケンスの値を余りで2台のサーバーに分けているチームも、その分け方を保てる。
- シーケンスが次に返す値は、`is_called` が false なら `last_value` である。値を一度も返していないシーケンスや、`setval(..., false)` のあとがこれに当たる。それ以外は `last_value` に増分を足した値である。
- 次の値がすでに列の値の先にあるシーケンスはそのままにし、行も出さない。進めれば値を飛ばすだけの場合も同じである。値を1つも持たない列も、`CYCLE` なしで `MAXVALUE` か `MINVALUE` に達してもう値を返さないシーケンスも、そのままにする。重なりうる値を返さないからである。
- 循環するシーケンスには、列の値の先にずっととどまる位置がない。上限に達すると最初の値をまた返すからである。kortopi はそれをそのままにし、計画はそう伝える。
- 目標が `MAXVALUE` を超えるとき、または減るシーケンスで `MINVALUE` を下回るときは、列の先にあるシーケンスの値がない。kortopi はそれをそのままにし、計画はその上限を挙げて、上げるか下げるよう伝える。上限がシーケンスの型の最大か最小の値であるときは、型にその先の値がないので、代わりにそう伝える。型が `bigint` でなければ、列とそのシーケンスに型 `bigint` を与えるよう伝える。
- 進める値の数は、距離を増分で割った値の床に1を足したものである。文はそれを `div` と `mod` で計算する。どちらも、どの大きさの整数でも正確である。`numeric` の除算は、結果をおよそ 16 桁の有効数字に丸める。`bigint` の上限の近くで `INCREMENT 2`、次の値が 3、列の最大の値が 9223372036854775806 のとき、丸めると目標は 9223372036854775807 ではなく `MAXVALUE` の先になってしまう。

進め方：

- 1つの文が1つのシーケンスを進める。文はまず列を読み、次にシーケンスを読む。シーケンスの `last_value` と `is_called` は、その1行を1回読んで得る。そのあとでシーケンスを進める。文は関数・演算子・型をすべてスキーマ付きで書くので、SQL としての計画は、どのセッションでもその文をそのまま実行できる。
- apply は、その文の前と後に、読むだけの文でシーケンスを読む。そして、後の読み取りからシーケンスの位置を伝える。それは、シーケンスがどのセッションにも次に返す値である。
- 進める値が 100,000 個以下なら、文は `nextval` でそれを1つずつ取り、取った値の次の値が列の先に出たところで止まる。`nextval` は不可分であり、シーケンスを決して戻さない。その間にほかのセッションが取った値は、進めるのにもう要らない値であり、取る数はその分だけ減る。費用の目安として、2026-11-22 に Apple M2 とメモリ 8 GB のノートPC上のコンテナの PostgreSQL 18.7 に対して `psql` で測った値がある。100,000 個の値を順に取るのに 48 ミリ秒、1,000,000 個で 0.57 秒かかった。
- それより長く進めるときは、シーケンスを読んだのと同じ文の中で、次の値が目標になるよう `setval` で設定する。
- 残る窓：値を順に取る方法は、シーケンスを決して戻さない。`setval` がシーケンスを戻すのは、文がシーケンスを読んでから `setval` を呼ぶまでの間に、ほかのセッションが 100,000 個を超える値をそのシーケンスから取った場合だけである。この2点は、サーバー上の1つの文の中にあり、その間に文はほかに何も読まない。その場合、文はシーケンスを、ほかのセッションが最後に取った値より下に設定し、シーケンスはその値をまた返す。ほかのセッション自身の `setval` や `ALTER SEQUENCE ... RESTART` は、いつでもシーケンスを戻しうる。kortopi はそれを防がない。
- `CACHE` が 1 を超えるシーケンスは、各セッションに値をまとめて渡す。シーケンスを進める前に値をキャッシュしたセッションは、進めたあとでそれを渡す。その値は apply が書いた値でありうる。ほかのセッションのキャッシュには、どう進めても届かない。apply が値を順に取るときもひとまとまりを取るので、目標より最大でひとまとまり分だけ多く値を飛ばす。`CACHE 20` で次の値が 3 のとき、4 まで順に取ると、次の値は 23 になる。コミットのあとの行はそれを `next value 3 -> 23` と伝え、計画は `next value 3 -> 4` と伝えていた。`setval` は、`CACHE` によらずシーケンスを目標に設定する。`CACHE` の既定値は 1 である。
- 明示的な値を書いてからシーケンスを進め終えるまでの間に、ほかのセッションがシーケンスから値を取ると、apply が書いた値を得ることがある。その挿入は apply のコミットを待ち、そのあとキーで失敗する。シーケンスを進めなくても同じことが起きる。値を順に取る方法では、この時間はその長さだけ、最大でおよそ 50 ミリ秒続く。

進める時機：

- シーケンスを進めたことは戻らないので、それはコミットの直前の最後の作業とする。書き込み、削除の確認（ADR-0039）、コミット前の比較（ADR-0042）、削除を残すテーブルの件数の確認のあとである。進める前の割り込みは、どのシーケンスももとのままにし、apply はロールバックする。
- シーケンスに対する文は、それぞれ自分のセーブポイントで動く。計画の読み取りも、apply の各読み取りと進める文も同じである。`lock_timeout` は 5 秒とし、セッションの `lock_timeout` がそれより短ければそちらとする。`--lock-timeout` がセッションに設定する値も、これに当たる（ADR-0044）。`set_config` がそれをトランザクションに局所的に設定する。文のあとでセーブポイントをロールバックする。これで `lock_timeout` はもとの値に戻り、文のロックも解放される。`nextval` と `setval` がしたことは残る。そのため、`ALTER SEQUENCE` などでほかのセッションが持つシーケンスのロックは、計画や apply を1つの文につき最大 5 秒しか止めない。
- セッションを使える状態のまま PostgreSQL が計画の読み取りをエラーで終えたときは、計画はシーケンスを読めなかったことと理由を伝えて先へ進む。上の `lock_timeout` がその例である。終了コードは変わらない。apply はそのシーケンスを読み直し、進めようとする。
- PostgreSQL が進める文を終えたときは、apply はシーケンスを読み直す。`nextval` は取った値を返さないので、値を順に取る作業を `statement_timeout` が途中で終えても、シーケンスは取ったところまで進んだままである。コミットのあとの行は、シーケンスの位置とその理由を伝える。次の値まで進めた、エラーとともに途中まで進めた、エラーとともに進めなかった、のどれかである。apply は書いた行をそれでもコミットし、標準エラー出力の注記が、読み直した位置から残りを進める方法を伝える。
- 進める間の割り込みや接続の切断は、シーケンスを読み直す前に apply を止め、ロールバックする。そのシーケンスは前に進んだかもしれないが、値を飛ばすだけである。
- 進めたあとでコミットが失敗したとき、または割り込みが来たときは、行は書かれず、シーケンスは進めたところに残る。値を飛ばすだけである。少しでも進んだシーケンスは、進んだものとして数える。失敗した apply の最後の行は、それを挙げる。割り込みが進める作業を止めたシーケンスは、前に進んだかもしれないものとして挙げる。

  ```text
  kortopi: nothing was changed but the sequences that the apply had moved before its commit, which a rollback does not move back, so they only skip values: billing.fees_id_seq to next value 4, billing.tax_rates_id_seq, which may have moved forward
  ```

- コミットの結果が分からないとき（ADR-0043）は、そのエラーのあとの行が、進んだシーケンスを挙げる。それはコミットされたかどうかによらず進んだままである。

権限：

- シーケンスを読むには、シーケンスの `SELECT` とそのスキーマの `USAGE` が要る。値を順に取るにはシーケンスの `USAGE` か `UPDATE` が要り、`nextval` がそれを確かめる。`setval` には `UPDATE` が要る。計画はこれらをカタログで確かめ、何も進めない。
- 計画は、シーケンスの位置が求める進め方で判断する。`USAGE` と `SELECT` を持つロールは値を順に取ってシーケンスを進め、100,000 個を超える値が要るシーケンスは残す。計画が値を順に取る進め方を示したのに、apply の書き込みが `setval` を求めたときは、進める文が `UPDATE` の不足でセーブポイントの中で失敗する。コミットのあとの行はそう伝え、助言も添える。
- シーケンスを読めないロールや、その進め方を許されないロールも、行は適用でき、終了コードも変わらない。計画は、そうしたシーケンスごとに、進めないこと・その理由・付与するものを伝える。読めるロールには、apply のあとに手作業で進める方法も伝える。その方法は、進められるロールが `nextval` を使い、進める分だけの値を取ることである。これはシーケンスを決して戻さない。それより長く進めるなら、ほかに値を取るものがない間に `setval` で設定する。値を順に取れるロールが `setval` を求められたときは、`UPDATE` を付与するか、許されたロールが `setval` を実行するよう助言する。

  ```text
  sequence billing.fees_id_seq of column id: next value 3, not moved to 4: the role may not take values from the sequence: grant the role USAGE on sequence billing.fees_id_seq, or take 1 value from it as a role that may, with SELECT pg_catalog.nextval('"billing"."fees_id_seq"'::pg_catalog.regclass) FROM pg_catalog.generate_series(1, 1)
  sequence billing.tax_rates_id_seq of column id: not moved: the role may not read the sequence, so kortopi cannot tell where it stands: grant the role SELECT and UPDATE on sequence billing.tax_rates_id_seq
  ```

- 助言は、シーケンスとそのスキーマを、`quote_ident` が書くとおりの SQL の識別子で挙げる。必要なところは引用符で囲むので、そのまま文に貼れる。

計画が示すもの：

- テーブルの下、件数の行のあとで、削除の波及（ADR-0039）の前に、apply が進めるか残すシーケンスごとに1行を出す。行は、シーケンス、列、シーケンスが次に返す値、進めたあとに次に返す値を示す。

  ```text
  billing.fees (upsert, key: id)
    + id=3  name=express  amount=900
    1 to insert, 0 to update
    sequence billing.fees_id_seq of column id: next value 3 -> 4
  ```

- apply が残すシーケンスは、上のように `not moved` と理由を付けた同じ形の行になる。すでに列の先の値を返すシーケンスには行を出さない。
- 計画は、自分のスナップショットで列を読み、apply が書くはずの宣言した値と、挿入する行があるテーブルでは `on_insert` の値も含める。apply が更新や削除をする保存された行は、保存された値で数える。そのため apply は、計画が示すより手前までしか進めないことがある。apply は書き込みのあとで目標をもう一度計算する。
- 計画が読めなかったシーケンスには、そのことと理由を伝える行を出す。

  ```text
  sequence billing.fees_id_seq of column id: could not be read: PostgreSQL ended the read: ERROR: canceling statement due to lock timeout (SQLSTATE 55P03): another session held a lock on the sequence for more than 5s, the longest that kortopi waits for a lock on a sequence: an apply reads it again, and moves it if it can
  ```

- コミットのあと、`Applied:` に続けて、計画の各シーケンスについて1行を出す。apply がシーケンスを、進めるときにあった位置から、読み直した位置へ進めたことを示す。進めなかったときは理由を示す。助言は含めない。

  ```text
  Applied: 2 inserted, 0 updated, 0 deleted.
  Sequence billing.fees_id_seq of billing.fees (id): next value 3 -> 4.
  Sequence billing.tax_rates_id_seq of billing.tax_rates (id): next value 2 -> 40002, not to 100001: the statement that moves it failed: ERROR: canceling statement due to statement timeout (SQLSTATE 57014): statement_timeout of the session, or another session, cancelled the statement.
  ```

  計画のあとでほかのセッションが列の先まで進めたシーケンスは、`not moved: its next value lies beyond the values of the column already` と伝える。
- 続けて、apply が列の値より手前に残したシーケンスと、読めなかったシーケンスごとに、標準エラー出力に注記を出す。export が注記を出すのと同じ形である。注記は、シーケンスの位置とすべきことを、apply が書き込みのあとに読んだ位置から伝える。助言の文で注記を終え、そのあとに句点を置かない。

  ```text
  note: sequence billing.tax_rates_id_seq of column id of table billing.tax_rates: next value 2 -> 40002, not to 100001: the statement that moves it failed: ERROR: canceling statement due to statement timeout (SQLSTATE 57014): statement_timeout of the session, or another session, cancelled the statement: take 59999 values from it, with SELECT pg_catalog.nextval('"billing"."tax_rates_id_seq"'::pg_catalog.regclass) FROM pg_catalog.generate_series(1, 59999)
  ```

SQL としての計画：

- スクリプトは、削除も含むほかのすべての文のあとに、文がすることを伝えるコメント行を置く。その下に、各シーケンスの計画の行をコメントで置く。位置から見て進める必要があるシーケンスと計画が読めなかったシーケンスでは、さらにその下に進める文を置く。文は apply が実行するものと同じであり、スクリプトが動くときに、自分の挿入と更新のあとで列とシーケンスを読む。そのため、アプリケーションがさらに値を取ったあとで、計画より遅れて動いたスクリプトは、シーケンスをそのままにする。
- スクリプトは、計画したロールによる apply と同じことをし、そのロールが実行すればシーケンスで失敗しない。文が実行されるのは、apply が進めると計画が示したシーケンス、つまりそのロールが許された進め方のシーケンスだけである。値を取れるがシーケンスを設定できないロールの文は `setval` を持たず、100,000 個を超える値が要るシーケンスはそのままにする。ほかの文はコメントにして、計画と同じく理由を伝える行の下に置く。実行を許されたロールのためである。SQL の文は、シーケンスを読む前に権限を確かめられない。PostgreSQL は、文のどの部分を実行するよりも前に、文のすべてのリレーションの権限を確かめるからである。そのため、計画が代わりに判断する。
- 循環するシーケンスと、上限が先に来るシーケンスは、コメントの行だけを持ち、文を持たない。

これが細かく定めるもの：

- 以前の記録の次の文は、書かれたとおりには成り立たない。
  - ADR-0026 の「文について」：「kortopi はシーケンスを読みも動かしもしない。」計画は、その apply が明示的な値を書く列のシーケンスを読み、apply は上のとおりそれを進める。
  - ADR-0026 の「作業の順番について」：手順「8. コミットする。」の前に、ADR-0042 の比較のあとで、シーケンスを進める作業を置く。
  - ADR-0026 の結果：「悪い点：kortopi はシーケンスを動かさない。…」これがいま成り立つのは、次のものだけである。上の範囲の外のもの、ロールが進められないシーケンス、ほかのセッションが進める前に取った値とキャッシュに持つ値である。
  - ADR-0042 の「細かく定めるもの」：「いまはその間にコミット前の比較が入る。行を変えるものは何も実行しない。」シーケンスを進める作業も、最後にその間で動く。それは行を変えない。
  - ADR-0029 の、ADR-0020 を細かくする部分：「適用が文の前後でしていることは、スクリプトにはない。…」シーケンスを進める作業は、書き込みのあとの文としてスクリプトに入る。
  - ADR-0022：「…`SELECT pg_catalog.setval(...)` である。kortopi はシーケンスを管理しない。」宣言はダンプの `setval` を引き続き読み飛ばし、どれも実行しない。apply は、自分が書く列のシーケンスを、この記録の規則で進める。
- ADR-0016・ADR-0024・ADR-0010 は、そのまま成り立つ。計画はシーケンスを読んでも何も変えず、ADR-0024 の権限のほかに何も要らず、読めなかったものはそう伝える。kortopi はオブジェクトを作らない。進める作業は、宣言したテーブルの行ではないデータベースのオブジェクト、つまり列が所有するシーケンスを変える。ただし、変えるのは apply が書いた行の求める分だけである。

### 結果

- 良い点：apply のあとのアプリケーションの次の挿入は、デプロイのスクリプトなしで、apply が書いた ID の先の ID を得る。
- 良い点：値を順に取る方法はシーケンスを決して戻さず、`setval` が戻すのは上の狭い窓の中だけである。すでに列の先の値を返すシーケンスには触れない。
- 良い点：進めても、増分ごとのシーケンスの値の並びは保つ。循環するシーケンスと上限が先に来るシーケンスは、理由を付けて残す。
- 良い点：失敗した apply は行を残さない。シーケンスを進めていても値を飛ばすだけであり、最後の行がそう伝える。
- 良い点：シーケンスの権限がないロールも適用でき、何を付与すればよいかを計画が apply の前に伝える。付与するものは、シーケンスに要る進め方で決まる。値を順に取るなら `USAGE`、`setval` なら `UPDATE` である。
- 良い点：シーケンスのロックや、シーケンスに対する文での PostgreSQL のエラーは、計画や apply を最大 5 秒しか止めず、どちらも失敗させない。出力は、データベースが読んだとおりにシーケンスの位置を伝える。
- 良い点：計画したロールが実行すれば、SQL としての計画はシーケンスで失敗しない。
- 悪い点：この変更は既存の利用者に見える。ただし、コマンドの終了コードは変わらず、SQL としての計画をすでに実行していたロールは、以前と同じく実行できる。この変更のプルリクエストのタイトルは、`!` を付けない `feat:` の種類とする。その説明に、利用者にとって変わることを挙げ、メンテナーはそこからリリースノートを書く。
  - apply は、明示的な値を書く識別列や `serial` 列のシーケンスを、コミットの直前で進める。その結果、シーケンスの次の値は書いた値の先に来る。
  - そのあとでコミットが失敗したときや、進める作業のあとや途中で割り込みが apply を止めたときも、シーケンスは apply が進めたところに残る。値を飛ばすだけである。
  - 失敗した apply の最後の行は、`nothing was changed but` に続けてそうしたシーケンスを挙げることがある。結果の分からないコミットのエラーのあとにも、それを挙げる行が続きうる。
  - 計画では、そうしたシーケンスごとにテーブルの下の新しい行が加わる。apply の出力では、`Applied:` のあとにシーケンスごとの行が加わる。列の値より手前で残したシーケンスには、それぞれ標準エラー出力の注記も加わる。
  - SQL としての計画は、そうしたシーケンスの行をコメントで持って終わる。計画したロールが許されたシーケンスには進める文を、許されないシーケンスにはその文をコメントで持つ。
- 悪い点：進めたことは戻せない。そのあとでコミットが失敗すると、シーケンスは進んだまま残り、その値は飛ぶ。PostgreSQL が途中で終えた文も同じである。
- 悪い点：ほかのセッションが 5 秒を超えて、または短い `--lock-timeout` を超えてシーケンスのロックを持つと、そのシーケンスは apply のあとも遅れたまま残る。注記がその進め方を伝える。
- 悪い点：書き込みからシーケンスを進めるまでの間（値を順に取る間なら最大でおよそ 50 ミリ秒）にほかのセッションが取った値と、ほかのセッションがキャッシュに持つ値は、やはり apply が書いた値でありうる。`CACHE` が 1 を超えるシーケンスでは、値を順に取ると、目標より最大でひとまとまり分だけ多く値を飛ばす。
- 悪い点：値を順に取れるがシーケンスを設定できないロールは、100,000 個を超える値が要るシーケンスを、apply でも SQL としての計画でも遅れたまま残す。
- 悪い点：ある実行で apply が列を書かなかったシーケンスは、apply がその列を書くまで遅れたままであり、列が所有せずに使うシーケンスは決して進めない。
- 悪い点：書く行があるテーブルの計画は、そうした列それぞれの最大の値をもう一度読む。キーならインデックススキャンで済むが、インデックスのない列ではテーブルのスキャンになる。apply は、進めるごとにそれを3回読む。進める文の前、文の中、文の後である。

### 確認の方法

- `internal/plan` の単体テストが、計画がデータベースに問い合わせる列と、行と、まとまりの中の順番を確かめる。テストは `TestBuildSequences`・`TestBuildSequencesError`・`TestSequenceText` と `TestRender` である。`TestRender` は `internal/plan/testdata/sequences.golden` を使う。
- `internal/apply` の単体テストが、シーケンスを進めるのはすべての確認のあと、コミットの直前であり、計画が進めると示すか読めなかったシーケンスであることを確かめる。進めるのが失敗したとき、シーケンスが進んだかもしれないとき、コミットが失敗したとき、進める前と進める間に割り込みが来たときに返すものも確かめる。テストは `TestRunMovesSequences`・`TestRunInterruptedAroundTheMoves`・`TestRunMovesEverySequence`・`TestSequenceNotes` である。
- `internal/apply` のゴールデンテスト、`TestRenderSummary` の `internal/apply/testdata/sequences.golden` が、コミットのあとの行を確かめる。
- `internal/script` のゴールデンテストが、スクリプトの中の文の位置、コメントにする文、各文の上のコメントを確かめる。テストは `TestWrite` で、`internal/script/testdata/sequences.golden` を使う。
- `internal/postgres` の単体テストが、残すシーケンスの理由と助言、ロックを待つ上限を確かめる。テストは `TestOwnedSequenceOf`・`TestSequenceStays`・`TestSequenceWait`・`TestSequenceSQL` である。文がどの演算子もスキーマ付きで書き、`div` と `mod` で割り、計画では何も進めないことも確かめる。値を順に取るだけのロールの文が `setval` を持たないことも確かめる。
- `cmd/kortopi` の単体テスト（`TestRunApply`）が、コミットのあとの出力、残すシーケンスの注記、進めたあとで失敗したコミットとシーケンスが進んだかもしれない場合の最後の行、結果の分からないコミットのあとの行を確かめる。
- `make check-all` の PostgreSQL 15〜18 に対する結合テスト、`internal/postgres` で：
  - `TestDescribeSequences`：両方の種類の識別列、`smallserial`、`bigserial`、引用符で囲んだ名前はシーケンスを所有する。共有するシーケンス、既定値が使わない所有されたシーケンス、次の値を掛ける既定値、型が `numeric` の列はそうでない。
  - `TestApplyMovesSequences`：issue 29。計画は何も進めず、apply のあとアプリケーションの次の挿入はどちらのテーブルでも ID 4 を得て、2回目の apply は何も書かない。
  - `TestSequenceMoves`：次の場合のそれぞれで、アプリケーションの次の挿入を素の接続で読む。
    - 増分 10、減るシーケンス、値を一度も返していないシーケンス、`setval(..., false)` で設定したシーケンス
    - すでに列の先にあるシーケンス、100,000 個を超えて進める場合、循環するシーケンス
    - `MAXVALUE` の値と `MINVALUE` を下回る値、`smallint` の最大の値、キーにある `GENERATED ALWAYS` の識別列
    - 列の更新、モード `insert`、`on_insert` の値
    - `CACHE 20`、`bigint` の上限と下限までの増分 2 と -2
  - `TestSequencePrivileges`：シーケンスに `USAGE` と `SELECT`、`UPDATE` と `SELECT`、`USAGE` だけ、`SELECT` だけを持つロールと、何も持たないロール。それぞれの計画、同じロールが実行する SQL としての計画、apply を確かめる。
  - `TestSequenceSetvalNeedsUpdate`：`setval` を求められた、`USAGE` と `SELECT` を持つロール。計画、SQL としての計画、書き込みが値を順に取る進め方を `setval` に変える apply を確かめる。
  - `TestSequenceMovesWhileOthersTakeValues`：2つ目の接続がシーケンスから値を取る間に、値を順に取る方法と `setval` で進める。そのあと次の値は、列の先にも、2つ目の接続が取ったどの値の先にもある。
  - `TestSequencesStayAfterAnInterruptBeforeTheMove`：進める前の割り込み。
  - `TestSequencesStayMovedAfterAFailedCommit`：進めたあとでコミットを失敗させる遅らせた外部キー。
  - 最新のバージョンだけで、次のものを確かめる。
    - `TestSequenceLocks`：計画の間と進める間のシーケンスのロック。5 秒の上限と短い `--lock-timeout` のそれぞれで、かかった時間と、計画のあとの `lock_timeout` を確かめる。
    - `TestSequenceMoveEndedPartWay`：99,999 個の値を順に取る作業を 10 ミリ秒の `statement_timeout` が途中で終える場合と、残りを進める助言の文。
    - `TestSequenceMoveInterrupted`：値を順に取る間の割り込み。
- `cmd/kortopi` では、`TestSequencesCommand` が issue 29 を各バージョンに対して実行する。計画、apply、アプリケーションの次の挿入、そのあとの計画、素の接続で実行する SQL としての計画を確かめる。最後のものは、すぐ実行する場合と、アプリケーションがさらに10個の値を取ったあとに実行する場合であり、後者ではシーケンスはアプリケーションが取った位置のままになる。

## 選択肢の長所と短所

### apply が値を書く列ごとに、列が所有するシーケンスをコミットの直前に進める。上限までは `nextval` で、それを超えれば `setval` で進める

- 良い点：apply のあとの確認がまだ止めうる段階では何も進めず、値を順に取る方法はシーケンスを決して戻さない。
- 悪い点：100,000 個を超えて進めるときは狭い窓が残り、そのあとでコミットが失敗すると値が飛ぶ。

### 書き込みのあと、そうしたシーケンスを列の最大の値に `setval` で合わせる

- 良い点：`pg_dump` が書くように、また issue 29 の回避策が実行するように、1つの文で済む。
- 悪い点：シーケンスを別に読んでからの `setval` は、その間にほかのセッションが値を取るとシーケンスを戻す。また、列の最大の値への `setval` は、すでに列の先の値を返すシーケンスを戻す。
- 悪い点：増分にかかわらず最大の値の次の値をシーケンスに与えるので、値を余りで分ける使い方を壊す。

### 書き込みの前にシーケンスを進める

- 良い点：apply が動く間に、アプリケーションが apply の書く値を得ることがない。
- 悪い点：進めたことは戻らない。そのため、そのあとで確認・キー・トリガーのどれかで失敗した apply はどれも、シーケンスを進めたまま残す。また、目標の根拠は apply が書いた行ではなく計画になる。

### 計画で警告し、進めるのはチームに任せる

- 良い点：kortopi は行のほかに何も触らない。
- 悪い点：アプリケーションがそうしたテーブルに挿入するチームはどれも、同じスクリプトを書いて保つ必要があり、そのスクリプトは2つ目の選択肢の欠点を持つ。

### apply のたびに、宣言したすべてのテーブルのシーケンスを進める

- 良い点：以前の apply が遅らせたままにしたシーケンスも進む。
- 悪い点：apply は、書かなかったテーブルのシーケンスも、書くものがない実行でも変え、そのすべての `UPDATE` を要する。
