# ADR-0021: CLI をサブコマンドの形にする

## 背景と課題

kortopi の操作は4つある。計画の表示、計画の適用、データベースの行を宣言として書き出すこと、ずれの報告である。
人が手で実行するほか、プルリクエストが計画を出し、デプロイが適用し、定期実行がずれを見張る。

操作をいくつか持つコマンドラインの道具の形は、2つに分かれる。
1つは、コマンドが1つで、操作をフラグで選ぶ形である。ドライランのフラグや、書き出しのフラグを持つ。
もう1つは、操作ごとにサブコマンドを持つ形である。

kortopi のコマンドラインはどんな形にするか。データベースをどう見つけるか。終了コードは何を意味するか。

## 判断の基準

- 削除を許すフラグを、誤って渡しにくいこと。
- デプロイのスクリプトを読む人が、変更を示すだけの手順と変更を加える手順を、コマンドから見分けられること。
- 秘密情報がプロセスの引数に現れないこと。
- 定期実行が「データベースがずれた」と「チェックそのものが失敗した」を区別できること。
- 計画とずれの報告が、何が違うかについて食い違わないこと。
- バイナリの依存を少なく保つこと（ADR-0005）。

## 検討した選択肢

- サブコマンド `plan`・`apply`・`export` とし、ずれは `plan` のフラグで知らせる
- サブコマンド `plan`・`apply`・`export` に、ずれのための4つ目のサブコマンドを足す
- コマンドは1つで、フラグで操作を選ぶ

## 決定

採用：「サブコマンド `plan`・`apply`・`export` とし、ずれは `plan` のフラグで知らせる」。操作ごとに、その操作のフラグだけを持てるからである。また、ずれとは空でない計画のことなので、1つのコードが両方の問いに答えられる。

形は次のとおりである。この記録に挙げていないフラグの名前は、それぞれのコマンドの実装のときに決める。

```text
kortopi plan    [--dir <path>] [--schema <name>]... [--format text|sql] [--exit-code]
kortopi apply   [--dir <path>] [--schema <name>]... [flags of the deletion guard]
kortopi export  [--dir <path>] [--schema <name>]... [--format csv|sql]
kortopi version
```

- `--dir` は、宣言と `kortopi.toml` を置いたディレクトリを指す（ADR-0013、ADR-0014）。既定はカレントディレクトリである。
- `--schema` は、対象を指定したスキーマに絞る。繰り返して指定できる（ADR-0017）。
- `plan --format sql` は、計画をそのまま流せる SQL として出力する（ADR-0020）。
- `apply` は変える内容を出力し、確認を求めない。レビューは `plan` の出力で行うものであり、確認を求めるとデプロイが止まるからである。削除の安全策のフラグは `apply` にだけある（ADR-0018）。
- `plan` と `apply` は、同じコードで差分を求める。そのため、宣言とデータベースが同じなら、適用は計画が示したとおりのことをする。

接続先は、libpq の環境変数（`PGHOST`・`PGPORT`・`PGUSER`・`PGPASSWORD`・`PGDATABASE`・`PGSSLMODE`・`PGSERVICE` とパスワードファイル）から決める。
フラグ `--host`・`--port`・`--user`・`--dbname` は、環境変数より優先する。
パスワードのフラグはない。

終了コードは次のとおりである。

| 終了コード | 意味 |
|---|---|
| 0 | コマンドが成功した。`plan --exit-code` では、データベースが宣言と一致している。 |
| 1 | コマンドが失敗した。フラグの誤り、読めない宣言、データベースのエラー、削除の安全策による適用の中止を含む。 |
| 2 | `plan --exit-code` のときだけ使う。計画が空でない。 |

`--exit-code` がなければ、差分を示した計画も 0 で終わる。マスタデータを変えるプルリクエストが、自分の計画で失敗しないようにするためである。
`--exit-code` があるときは、適用待ちのスキーマの変更も差分に数える（ADR-0016）。

フラグは、Go の標準ライブラリの `flag` パッケージで読む。コマンドライン用のライブラリは足さない。

### 結果

- 良い点：削除を許すフラグを `plan` や `export` に渡せない。コマンドが受け付けない。
- 良い点：デプロイのスクリプトにある動詞が、その手順のすることを表す。`kortopi plan` はデータベースを読むだけであり、`kortopi apply` はデータベースを変える。
- 良い点：ずれの報告は計画そのものである。2つが違う差分を示すことはなく、チームが覚える出力は1つで済む。
- 良い点：定期実行は、終了コードだけで3つの結果を区別できる。ずれがない、チェックが失敗した、ずれがある、の3つである。
- 良い点：libpq の環境変数は、チームがすでに持っているものでそのまま使える。`~/.pgpass`、サービスファイル、CI のシークレットである。
- 悪い点：`kortopi plan --exit-code` は、ずれという名前のコマンドより目に付きにくい。README の「ずれを見つける」のところで示す必要がある。
- 悪い点：標準の `flag` パッケージにはシェルの補完がなく、フラグでない最初の引数で解析を止める。どのコマンドも位置引数を取らないので、2つ目は今のところ困らない。
- 悪い点：接続先を1つの URL で持っているチームは、それを環境変数に分ける必要がある。URL のフラグは、この形を壊さずにあとから足せる。

### 確認の方法

- コマンドラインのテストで、サブコマンド、あるサブコマンドのフラグをほかのサブコマンドが受け付けないこと、3つの終了コードを確かめる。テストは、それぞれのコマンドの実装とともに加わる。
- `kortopi plan`・`kortopi apply`・`kortopi version` はすでにあり、そのテストは `cmd/kortopi` にある。`export` は、あとで加わる。

## 選択肢の長所と短所

### サブコマンド `plan`・`apply`・`export` とし、ずれは `plan` のフラグで知らせる

- 良い点：覚える動詞は3つで、それぞれにヘルプがある。
- 良い点：ずれのために2つ目の実装が要らない。
- 悪い点：`--exit-code` の目的を一度は説明する必要がある。

### サブコマンド `plan`・`apply`・`export` に、ずれのための4つ目のサブコマンドを足す

- 良い点：コマンドの名前が、定期実行のしていることを表す。
- 悪い点：4つ目のコマンドは、終了コードが違うだけの `plan` である。常に一致しなければならないコマンドが2つあると、バグの入る場所も2つになる。
- 悪い点：`plan` のフラグをすべて、2つのコマンドが持つことになる。

### コマンドは1つで、フラグで操作を選ぶ

- 良い点：覚えるサブコマンドがない。どの操作も、1つのコマンドのフラグである。
- 良い点：フラグなしのいちばん短い呼び出しが、主な操作をする。
- 悪い点：その主な操作は適用になる。すると、削除を許すフラグがドライランや書き出しのフラグと並ぶ。
- 悪い点：同時に使えないフラグ（`--dry-run` と `--export`）を自前で検査することになり、ヘルプにはすべての操作のフラグがまとめて並ぶ。
