# ADR-0006: kortopi のライセンスを MIT にする

## 背景と課題

kortopi は、チームがデプロイのパイプラインに組み込み、本番のデータベースに対して動かす道具である。
会社がそうした道具をパイプラインや自社でビルドするイメージに入れる前には、誰かがライセンスを確かめる。
法務の担当者とライセンスのスキャナーがすでに知っているライセンスなら、その確認はすぐに終わる。見慣れないライセンスや、道具のまわりのコードに条件を付けるライセンスは、導入そのものを止めることがある。

ライセンスは、kortopi がどの依存をバイナリに組み込めるかも決める。バイナリは、組み込んだ依存のライセンスも一緒に持つからである。

kortopi を導入しやすくするのはどのライセンスか。また、そのライセンスは依存に何を求めるか。

## 判断の基準

- 会社は、ライセンスを見分ける以上の法務の確認なしに、kortopi を動かし、自社のイメージに入れて再配布できる。
- 法務の担当者とライセンスのスキャナーが、そのライセンスを判別できる。つまり、OSI が承認し、SPDX の識別子を持つライセンスである。
- 文面が短く、見慣れている。
- kortopi を動かす人のコード・パイプライン・データベースに、何の条件も付けない。

## 検討した選択肢

- MIT
- MIT-0
- Apache-2.0
- GPL-3.0 や AGPL-3.0 のようなコピーレフトのライセンス

## 決定

採用：「MIT」。短く広く理解されたライセンスで OSI が承認しており、kortopi を複製する人に表示を残すことしか求めないからである。

決まりは次のとおりである。

- `LICENSE` には MIT License の本文を置き、リポジトリの道具の `package.json` には `"license": "MIT"` と書く。
- 2種類のライセンスの依存は、バイナリに含めない。1つは強いコピーレフトのライセンス（GPL や AGPL の系統など）である。もう1つは、ソースは公開していても利用を制限するライセンス（SSPL・BUSL・Commons Clause・NonCommercial の付いた Creative Commons）である。`trivy.yaml` はこれらのライセンスを禁止として並べており、ライセンスのスキャンはこれらでだけ失敗する。
- LGPL や MPL のような弱いコピーレフトのライセンスでは、スキャンは失敗しない。そのライセンスが及ぶのはライブラリそのものであり、それを使うコードには及ばないからである。
- リポジトリに置いた第三者のファイルは、それぞれのライセンスのままにし、ライセンスをファイルの中か隣に書く。`.vale/styles/Google/` にある Vale 用の Google のスタイルは MIT License である。`.claude/skills/japanese-tech-writing/` にある日本語の文章規範は Unlicense である。

### 結果

- 良い点：法務の担当者は MIT License をひと目で見分けられ、スキャナーも SPDX の識別子 `MIT` を判別できる。
- 良い点：誰もが kortopi を動かし、変え、再配布でき、使う会社や製品も問われない。
- 悪い点：MIT License には、Apache-2.0 と違って、特許の明示的な許諾がない。
- 悪い点：変えた kortopi を、変更を公開せずに配ることも、誰にでもできる。
- 悪い点：バイナリを再配布する人は、kortopi の表示と、バイナリに組み込んだ依存の表示を残す必要がある。リリースがそれらの表示をどう集めるかは、リリースと一緒に決める。リリースは後の記録で扱う（ADR-0005）。
- 悪い点：弱いコピーレフトのライブラリはスキャンを通るが、バイナリに組み込むときには、そのライセンスの条件が残る。そうしたライブラリを加えるときは、レビューで条件を見極める。
- 悪い点：禁止したライセンスの依存は使えない。使うには、この記録を置き換える新しい記録と、`trivy.yaml` の変更が要る。

### 確認の方法

- `LICENSE` ファイルがライセンスの本文を持つ。`LICENSE` と `package.json` が MIT を指していることは、レビューで確かめる。
- `make check-all` はターゲット `scan-deps` を実行する。`scan-deps` は、`trivy.yaml` が禁止するライセンスの依存を Trivy が見つけると失敗する。ライセンスのスキャンの対象はバイナリに入るものであり、開発のための依存と `tools/` のモジュールは外す。
- `trivy.yaml` は `license.full: false` を設定している。そのため、Trivy が読むのは各パッケージが宣言したライセンスであり、各ファイルのライセンスの本文は読まない。手でリポジトリにコピーしたファイルは Trivy の対象外なので、そのライセンスがファイルの中か隣に書かれていることをレビューで確かめる。

## 選択肢の長所と短所

### MIT

- 良い点：寛容なライセンスの中で最も広く知られており、本文も短い。
- 悪い点：特許の明示的な許諾がない。
- 悪い点：どの複製にも、著作権表示と許諾表示を付ける必要がある。

### MIT-0

- 良い点：MIT License から、表示を残す義務を除いたものである。
- 悪い点：その自由が役に立つのは、サンプルコードのように、人が自分の製品に写すコードである。kortopi は人が動かす道具であり、写すコードではない。
- 悪い点：MIT ほどには知られておらず、調べる法務の担当者もいる。
- 悪い点：これにも特許の許諾がない。

### Apache-2.0

- 良い点：貢献者の特許を許諾し、その特許をめぐって訴えた者からは許諾を取り上げる。
- 悪い点：文面が長く、条件も多い。複製にはライセンスを含め、表示を残し、変えたファイルに印を付け、`NOTICE` ファイルがあればそれも付ける必要がある。

### GPL-3.0 や AGPL-3.0 のようなコピーレフトのライセンス

- 良い点：配布されたバージョンでの変更は、公開されたままになる。AGPL-3.0 なら、ネットワーク越しに提供されたバージョンでの変更もそうなる。
- 悪い点：会社の方針は、こうしたライセンスを禁じるか、法務の確認に回すことが多い。kortopi は、どの会社のデプロイのパイプラインにも入ることを目指している。

## 補足

- [SPDX License List の MIT](https://spdx.org/licenses/MIT.html)
- ライセンスのスキャンと、そのほかのサプライチェーンの守りは ADR-0005 にある。
