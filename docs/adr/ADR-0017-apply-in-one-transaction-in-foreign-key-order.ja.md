# ADR-0017: 1つのトランザクションで、外部キーの順に適用する

## 背景と課題

apply は、外部キーで互いを参照するテーブルの行を変える。料金プランは機能を参照し、都道府県は地方を参照する。
PostgreSQL は、参照先の行がまだない行を拒む。外部キーに別の定めがない限り、まだ参照されている行の削除も拒む。
そのため、文の順番が問題になる。

スキーマには、循環を含むものもある。
親のカテゴリを参照するカテゴリのように、テーブルが自分自身を参照することがあり、2つのテーブルが互いを参照することもある。
循環は、テーブルの順番だけでは満たせない。

外部キーはスキーマもまたぐ。たとえば、システムの部分ごとに、それぞれのスキーマにテーブルを置く場合である。
1つのスキーマの中だけで求めた順番は、データベース全体で見ると誤っていることがある。

apply は途中で止まることもある。制約が行を拒んだり、接続が切れたりした場合である。
その時点で変更の一部がコミット済みなら、データベースは古い宣言と新しい宣言のどちらにも合わない。

apply は、どの順番で、いくつのトランザクションで行を変えればよいか。

## 判断の基準

- apply は、計画が示すものをすべて変えるか、何も変えないかのどちらかである。
- PostgreSQL はすべての外部キーを検査し、どの変更も外部キーを破らない。
- 順番はデータベースから求める。そのため、スキーマが変われば順番もそれに従う。
- apply には、行を書き込むのに要る権限より強い権限は要らない。
- 1回の実行で、複数のスキーマのテーブルを適用できる。

## 検討した選択肢

- 1つのトランザクションで、外部キーの順に適用する
- テーブルごとに1つのトランザクションにする
- 読み込みの間、トリガーや制約を止める
- 1つのトランザクションで適用し、順番は設定に書く

## 決定

採用：「1つのトランザクションで、外部キーの順に適用する」。すべての外部キーの検査を保ち、特別な権限が要らず、データベースを、すべて適用した状態か元のままかのどちらかにできるからである。

決まりは次のとおりである。

- 1回の apply は1つのトランザクションである。すべての文が成功したときだけコミットし、そうでなければロールバックして、データベースは元のままになる。
- このトランザクションは、スキーマの変更とは別である。スキーマの変更は、kortopi が動く前にスキーマの道具が適用する（ADR-0007）。
- kortopi は、テーブルの間の外部キーを、対象のデータベースのカタログから読む。挿入と更新は、参照されるテーブルから参照するテーブルへの順に流す。削除はその逆で、参照するテーブルから参照されるテーブルへの順に流す。
- 循環は、自分自身を参照するテーブルも含め、`DEFERRABLE` と宣言した制約で扱う。kortopi はその制約をトランザクションの間だけ遅らせ（`SET CONSTRAINTS ... DEFERRED`）、PostgreSQL はコミットのときに検査する。
- 遅らせられる制約のない循環があれば、kortopi は、その循環の制約の名前を挙げたエラーで止まる。正確な振る舞いは実装のときに決める。
- 外部キーはスキーマをまたぐので、1回の実行で複数のスキーマのテーブルを扱う。`--schema` は、実行を指定したスキーマに絞る。絞った実行で、選んだテーブルが参照する、選んだスキーマの外のテーブルをどう扱うかは、実装のときに決める。
- 2つの apply が同時に走らないようにロックを取るかどうかは、実装のときに決める。そのために kortopi 専用のテーブルを使うことは、ADR-0010 が認めていない。

### 結果

- 良い点：失敗した apply は何も残さない。チームは宣言を直してもう一度実行すればよく、結果は初めての実行と同じになる（ADR-0007）。
- 良い点：すべての外部キーが効いたままであり、kortopi が書き込むすべての行を PostgreSQL が検査する。
- 良い点：順番はスキーマから決まるので、設定が要らない。外部キーを足せば、次の実行から順番が変わる。
- 良い点：行を書き込めるロールなら、どの計画にも要る `TEMPORARY` 権限（ADR-0016）があれば apply できる。スーパーユーザーである必要も、テーブルの所有者である必要もない。
- 悪い点：遅らせられる制約のない循環は適用できない。チームは先に、その制約の1つを `DEFERRABLE` と宣言し直す必要がある。
- 悪い点：遅らせた制約はコミットのときにしか検査されない。そのため、循環の中の誤りは、原因になった文ではなく、トランザクションの最後に報告される。
- 悪い点：1つのトランザクションは、変えたすべての行のロックをコミットまで持ち続ける。そのため、大きな apply では、サービスからそれらの行への書き込みが長く待たされる。

### 確認の方法

- PostgreSQL 15〜18 に対する結合テストで、次のことを確かめる。失敗する文があればどのテーブルも元のまま残ること、外部キーをたどった挿入と削除の順番（スキーマをまたぐ場合を含む）、自分自身を参照するテーブル、遅らせられる制約を持つ2つのテーブルの循環である。これらのテストは、apply の実装で加わる。

## 選択肢の長所と短所

### 1つのトランザクションで、外部キーの順に適用する

- 良い点：どの外部キーも検査され、順番はデータベースから求まり、apply は全部か無かのどちらかになる。
- 悪い点：循環には遅らせられる制約が要り、大きな変更ではトランザクションが長くなる。

### テーブルごとに1つのトランザクションにする

- 良い点：トランザクションはそれぞれ短く、ロックを持つ時間も短い。
- 悪い点：あるテーブルで失敗すると、それより前のテーブルは適用済みで、後ろのテーブルは未適用のまま残る。データベースは、どちらの宣言にも合わなくなる。
- 悪い点：2つのテーブルの循環を適用できない。遅らせた制約もテーブルごとのコミットで検査され、その時点ではもう一方のテーブルにまだ行がないからである。

### 読み込みの間、トリガーや制約を止める

- 良い点：順番を気にする必要がなく、循環にも特別な扱いが要らない。
- 悪い点：強い権限が要る。PostgreSQL では、外部キーを検査するトリガーを止めるにはスーパーユーザーが要る。
- 悪い点：外部キーを破る行が、検査なしにコミットされる。あとの変更が、原因から遠く離れたところで失敗する。

### 1つのトランザクションで適用し、順番は設定に書く

- 良い点：循環の順番を、人が明示できる。
- 悪い点：カタログがすでに知っていることを繰り返して書くことになり、スキーマが変わると古くなる。

## 補足

- PostgreSQL 18 の文書の [`SET CONSTRAINTS`](https://www.postgresql.org/docs/18/sql-set-constraints.html) と[制約](https://www.postgresql.org/docs/18/ddl-constraints.html)
- [`ALTER TABLE`](https://www.postgresql.org/docs/18/sql-altertable.html)（制約のトリガーを止めるにはスーパーユーザーが要ると書いている）
