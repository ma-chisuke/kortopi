# ADR-0025: PostgreSQL とは pgx で話し、設定は go-toml で読み、テスト用のサーバーはルートのモジュールの testcontainers-go で起動する

## 背景と課題

`kortopi plan` の最初の実装で、Go のライブラリが3つ加わった。どの記録も、まだそれらを挙げていない。
ADR-0015 は SQL のパーサを選んだが、ほかのライブラリはコードとともに入った。

kortopi は、1つのトランザクションを持つ1つのセッションで PostgreSQL と話す。そのセッションで一時テーブルを作り、各 CSV ファイルをクライアントから `COPY ... FROM STDIN` で一時テーブルへ流し込む（ADR-0009、ADR-0024）。
kortopi は、PostgreSQL の各エラーを、ファイルと行を示すメッセージに変える。そのため、エラーの各フィールドが要る。コード・詳細・ヒント・コンテキスト・位置である。
接続先は、libpq の環境変数・パスワードファイル・サービスファイルから決める（ADR-0021）。
バイナリは cgo なしでビルドする。SQL のパーサは WebAssembly で動き、静的なバイナリなら C のツールチェーンが要らないからである（ADR-0015）。

kortopi は `kortopi.toml` を読む（ADR-0013）。綴りを誤った設定は、黙って無視するのではなく、行を示すエラーにする必要がある。

結合テストには、対応するメジャーバージョンごとに本物の PostgreSQL のサーバーが要る（ADR-0019）。しかも、マシンの環境が何を指していても、ほかのデータベースに届いてはならない。
セッションのテストには、それを持つパッケージの公開していない部分が要る。

どのライブラリも、信頼する相手が1つ増えることを意味する（ADR-0005）。ADR-0004 は、このリポジトリの道具の依存をルートのモジュールの外に置き、kortopi のモジュールグラフが kortopi の使うものだけを持つようにしている。

kortopi は、これらの必要にどのライブラリを使い、テストの依存をどこに置くか。

## 判断の基準

- バイナリは、cgo なしでビルドした1つの静的なプログラムのままである（ADR-0015）。
- CSV ファイルをクライアントから `COPY ... FROM STDIN` へ流し込み、計画のすべての文を1つのセッションと1つのトランザクションで実行する。
- PostgreSQL のエラーのすべてのフィールドが、メッセージに届く。
- 接続の設定は、libpq が読むのと同じ環境変数とファイルから決める。
- `kortopi.toml` の知らないキーは、その行を示すエラーになる。
- 結合テストは、対応するメジャーバージョンごとに、固定したイメージから自分でサーバーを起動する。
- バイナリに入るモジュールは、できるだけ少なくする（ADR-0005）。

## 検討した選択肢

- pgx を直接使い、設定には go-toml を使い、testcontainers-go をルートのモジュールに置く
- pgx を直接使う代わりに、ドライバーの上の標準の `database/sql` インターフェースを使う
- pgx の代わりに、cgo で libpq を使う
- go-toml の代わりに、kortopi 独自の TOML の読み込みを書く
- 結合テストを独立したモジュールに置く
- テスト用のコンテナの代わりに、人や CI がテストの前に PostgreSQL のサーバーを起動する

## 決定

採用：「pgx を直接使い、設定には go-toml を使い、testcontainers-go をルートのモジュールに置く」。pgx は、PostgreSQL のプロトコル・クライアントからの COPY・完全なエラーを、cgo なしに Go で与える。go-toml は、行番号付きで設定を厳しく読む。テスト用のコンテナは、各テストが必要とする本物のサーバーを与える。その代わり、ルートのモジュールがテストだけの依存を持つ。

決まりは次のとおりである。

- kortopi は `github.com/jackc/pgx/v5` で PostgreSQL と話す。`database/sql` は通さず、pgx 自身の接続の型を使う。pgx は PostgreSQL のプロトコルを Go で話し、どんな読み手からでも `COPY ... FROM STDIN` へ流し込める。サーバーが送るすべてのフィールドを持つエラーを返し、libpq の環境変数・パスワードファイル・サービスファイルを読む。
- kortopi は `kortopi.toml` を `github.com/pelletier/go-toml/v2` で読む。go-toml は知らないキーを禁じて読み、知らないキーと構文の誤りのそれぞれについて行を示す。
- 結合テストは、`github.com/testcontainers/testcontainers-go` とその PostgreSQL 用のモジュールでサーバーを起動する。対応するメジャーバージョンごとにコンテナを1つ起動し、イメージはタグとダイジェストで固定した公式のものを使う。Renovate がそれを更新する。サーバーを起動するパッケージ `internal/postgres/pgtest` は、タグ `integration` があるときだけビルドする。このパッケージは、テストを動かす前に、`PG` で始まるすべての変数を環境から取り除く。
- `internal/postgres` のテストは、パッケージの公開していない部分を必要とするので、そのパッケージの中、つまりルートのモジュールにある。そのため、ルートのモジュールの `go.mod` は、コンテナのライブラリとそれが必要とするモジュールを挙げる。テストだけが使う間接のモジュールは、数十にのぼる。
- そのどれも、バイナリには入らない。`make build` は `cmd/kortopi` を cgo なしでビルドする。タグ `integration` なしで kortopi がビルドするパッケージは、どれもコンテナのライブラリを import しない。
- この記録は ADR-0004 を細かくする。ADR-0004 は、kortopi のモジュールグラフが kortopi の使うものだけを持つとしている。この記録により、ルートのモジュールのモジュールグラフは、そのテストの依存も持つ。バイナリは、引き続き kortopi の使うものだけを持つ。
- ADR-0005 のスキャンは、これらのモジュールを違うように扱う。govulncheck（`vuln-go`）は、呼ばれるコードをタグ `integration` なしで解析するので、これらを見ない。Trivy（`scan-deps`）はルートのモジュールの `go.mod` を読むので、これらの脆弱性を報告し、ライセンスもバイナリのものと同じように検査する。このマイルストーンでは、コンテナのライブラリが依存するトレースのライブラリについて脆弱性を報告した。そのモジュールは、直ったバージョンへ上げる必要があった。

### 結果

- 良い点：どんな大きさの CSV ファイルも、クライアントからサーバーへ流し込める。kortopi がその行を抱えることはない。
- 良い点：PostgreSQL のエラーは、詳細・ヒント・位置から求めたファイルの行とともに利用者に届く。
- 良い点：接続には、チームが `psql` のためにすでに持っているものがそのまま使える。libpq の変数・`~/.pgpass`・サービスファイルである。
- 良い点：バイナリは静的なままで、C のツールチェーンなしにクロスコンパイルできる。
- 良い点：`kortopi.toml` の綴りを誤ったキーは、その行を示すエラーになる。
- 良い点：結合テストは、コンテナの実行環境があるどのマシンでも、対応するすべてのバージョンの本物の PostgreSQL に対して動く。しかも、環境が指すデータベースには届かない。
- 悪い点：pgx は libpq の変数を自分のコードで読む。そのため、libpq が知っていて pgx が知らない設定は無視される。kortopi は、pgx が libpq と歩調を合わせ続けることに頼る。
- 悪い点：ルートのモジュールの `go.mod` は、バイナリが使わない多くのモジュールを挙げる。そのため、それを読んでも kortopi が何を配っているかはわからない。
- 悪い点：Trivy は、これらのモジュールの脆弱性を報告し、バイナリにあるかのようにライセンスを検査する。Renovate も、これらの更新を開く。そのため、テストだけの依存にも手間がかかる。このマイルストーンでも、すでに1回の更新が要った。
- 悪い点：結合テストには、コンテナの実行環境と、イメージを取ってくるためのネットワークが要る。そのため、結合テストは `make check` ではなく `make check-all` で実行する。

### 確認の方法

- `go.mod` が3つのライブラリを挙げる。コンテナのライブラリのモジュールがバイナリに入っていないことは、`go version -m bin/kortopi` を使ってレビューで確かめる。これを守らせるチェックはない。
- `make build` は、`CGO_ENABLED=0` でバイナリをビルドする。
- `make check-all` は、コンテナのライブラリが起動する PostgreSQL 15〜18 に対する結合テスト（`test-go-integration`）と、スキャン `vuln-go` と `scan-deps` を実行する。
- `internal/config` の単体テスト（`TestLoadErrors`）で、`kortopi.toml` の厳しい読み方と行番号を確かめる。`internal/postgres` の単体テスト（`TestOptionsConnConfig`）で、接続先が libpq の変数とパスワードファイルから決まることを確かめる。
- 結合テストで、クライアントからの COPY（`TestCSVDetails`、`TestLargeTable`）と、エラーのフィールド（`TestLoadErrorsCSV`、`TestLoadErrorsSQL`）を確かめる。

## 選択肢の長所と短所

### pgx を直接使い、設定には go-toml を使い、testcontainers-go をルートのモジュールに置く

- 良い点：どのライブラリも kortopi が必要とすることをし、バイナリのどこにも cgo が要らない。
- 良い点：テストが、セッションの公開していない部分を使える。
- 悪い点：ルートのモジュールが、テストの依存を持つ。

### pgx を直接使う代わりに、ドライバーの上の標準の `database/sql` インターフェースを使う

- 良い点：コードが1つのドライバーに依存しない。
- 悪い点：`database/sql` には `COPY ... FROM STDIN` がない。そのため、kortopi は結局その下のドライバーに手を伸ばすことになる。
- 悪い点：その接続のプールは、どの接続を渡すかを選ばない。一方、一時テーブルと計画のトランザクションは1つのセッションのものなので、kortopi は接続を自分で固定する必要がある。
- 悪い点：エラーは SQLSTATE・詳細・位置を知らないインターフェースを通る。そのため、kortopi は結局ドライバー自身の型を取り出すことになる。

### pgx の代わりに、cgo で libpq を使う

- 良い点：変数・パスワードファイル・サービスファイルについては、libpq が基準である。
- 悪い点：cgo には、対象のプラットフォームごとに C のツールチェーンと libpq が要る。そのため、ADR-0015 の静的なバイナリをあきらめることになる。

### go-toml の代わりに、kortopi 独自の TOML の読み込みを書く

- 良い点：依存が増えない。
- 悪い点：数行のファイルのために、kortopi が TOML のパーサとそのエラーと行番号を保守することになる。

### 結合テストを独立したモジュールに置く

- 良い点：ルートのモジュールの `go.mod` は、kortopi の使うものだけを挙げる。Trivy も、テストだけのモジュールをほかと分けて報告する。
- 悪い点：別のモジュールのテストは、セッションの公開していない部分に届かない。そのため、テストはパッケージが公開するものしか確かめられないか、パッケージがテストだけに要るものを公開することになる。

### テスト用のコンテナの代わりに、人や CI がテストの前に PostgreSQL のサーバーを起動する

- 良い点：ルートのモジュールに、コンテナのライブラリが要らない。
- 悪い点：人も CI のジョブも、正しいバージョンのサーバーを4つ起動する必要がある。しかも、テストはそのアドレスを環境から読むことになり、環境が本物のデータベースを指すおそれがある。

## 補足
