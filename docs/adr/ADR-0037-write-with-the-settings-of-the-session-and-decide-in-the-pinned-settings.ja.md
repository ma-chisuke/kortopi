# ADR-0037: apply の行はセッションの設定で書き、書く行は固定した設定で決める

## 背景と課題

ADR-0023 は、どの計画でも、ロール・データベース・環境が何を設定していても、トランザクションの中で設定を固定する。`TimeZone` は `UTC`、`DateStyle` は `ISO, MDY`、`search_path` は `pg_catalog`、`row_security` は `off` などである。
これらの設定によって、1つの宣言がどこでも同じ値を意味する。
ADR-0026 は、apply を「計画が固定する設定で」1つのトランザクションとして実行し、テーブルの変更の種類ごとに集合単位の文を1つ書く。

そのため、apply が書いている間も固定は続き、書き込みが発火させるものはすべてその設定で動く。列の既定値、トリガー、外部キーの動作、制約の検査、そしてトリガーが書くテーブルの行単位セキュリティのポリシーである。
その結果、apply が書く行はアプリケーションが書く行と違うものになるか、アプリケーションなら成功するところで apply が失敗する。

- タイムゾーンのない `timestamp` の列への既定値 `now()` は、データベースのタイムゾーンではなく UTC での時計の時刻になる。`TimeZone` が `Asia/Tokyo` のデータベースで、アプリケーション自身の挿入が 19:11 を入れるところに 10:11 が入る。既定値 `current_date` は、UTC から遠いタイムゾーンでは別の日になり、`now()::text` は別の形になる。
- スキーマを付けずにテーブルを挙げるトリガー関数は、`relation "audit_log" does not exist` で失敗する。検索パスが `pg_catalog` だけだからである。
- 行単位セキュリティを持つテーブルに挿入するトリガーは、`row_security` が off なので失敗する。同じロール自身の挿入なら成功するにもかかわらずである。

計画はこれを示せない。計画が比べるのは宣言した列であり、既定値やトリガーが書くものではない。
固定は宣言した値を読み、比べるためのものであり、書き込みはそれを受け継いでいるだけである。
とはいえ、書き込みのために固定を外すのにも代償がある。設定によって結果の変わる比較がある。等価性を持たない型の列はテキストで比べる（ADR-0023）が、そのテキストは `DateStyle`・`TimeZone`・`extra_float_digits` で変わる。ロールの検索パスで動く kortopi の文は、そのパスのスキーマのオブジェクトで変わりうる。`on_insert` の値は固定した設定で読む（ADR-0035）。そしてプーラーは、サーバーとの接続を次のクライアントに渡す。

apply の書き込みはどの設定で動くのか。そして apply は、書く行の決定をどう固定した設定に保つのか。

## 判断の基準

- apply が書く行は、そのテーブルの既定値・トリガー・制約から、同じロール自身の文が得るのと同じものを得る。
- 宣言は、どの環境でも同じ値を意味し（ADR-0023）、`on_insert` の値も同じである（ADR-0035）。
- apply が計画として出力するものが、apply の書くものである（ADR-0026）。どの行のどの列を書くかを決める比較は、すべて固定した設定で行う。
- ロールの検索パスのスキーマにあるオブジェクトが、kortopi の文を変えることはない。
- kortopi が設定したものは、コネクションプーラーを通しても、トランザクションのあとに残らない。
- 書き込みの往復は、これまでより増えない。

## 検討した選択肢

- 固定した設定で行を選んでから、セッションの設定で書く
- 書き込みでも固定した設定を保つ
- 書き込みの文はそのままにして、セッションの設定に戻す
- 書き込みでは `search_path` と `row_security` だけを戻す
- 書き込みの設定を `kortopi.toml` に書かせる

## 決定

採用：「固定した設定で行を選んでから、セッションの設定で書く」。そうすれば、既定値・トリガー・制約が、アプリケーションの行と同じように apply の行にも働く。一方、kortopi が読んで比べる値は、これまでどおりに読んで比べる。

決まりは次のとおりである。

戻す設定とその値：

- この記録は、ADR-0023 が読むために固定する設定を2つ増やす。どちらも、宣言した値の読み方を変えるからである。`array_nulls` は `on` にする。そうすれば、配列の `{NULL}` は、テキスト `NULL` ではなく NULL の要素になる。`timezone_abbreviations` は `Default` にする。そうすれば、値の中のタイムゾーンの略称は、どこでも同じタイムゾーンを意味する。`EST` は、略称の組 `Default` では UTC より5時間遅れたアメリカの東部標準時であり、組 `Australia` では10時間進んだオーストラリアの東部標準時である。
- 書き込みは、ADR-0023 とこの記録が固定する設定のうち `client_encoding` を除くすべてを戻す。戻すのは `search_path`・`TimeZone`・`DateStyle`・`IntervalStyle`・`standard_conforming_strings` である。さらに `extra_float_digits`・`bytea_output`・`xmloption`・`lc_monetary`・`row_security` と、`array_nulls`・`timezone_abbreviations` も戻す。`client_encoding` は固定したままにする。これは kortopi とサーバーの間のバイトについての設定であり、書き込みは一時テーブルから、すでにデータベースの型になった行を取るからである。
- それぞれの値は、kortopi が接続した直後に、どのトランザクションの外でも送る1つの問い合わせへのサーバーの答えである。サーバーの設定・`ALTER DATABASE ... SET`・`ALTER ROLE ... SET`・`PGOPTIONS` などの接続のオプションが、そのセッションに設定したものである。トランザクションモードのコネクションプーラーを通すと、その問い合わせと apply のトランザクションが、サーバーとの別々の接続で動くことがある。値が食い違うのは、そのどちらかに、あるクライアントが `SET` でセッションの設定を残したときだけである。そのモードのプーラーは、そうした設定を接続ごとに分けて保たない。計画と書き出しは何も読まない。
- `lock_timeout` のように kortopi が固定しない設定は、これまでどおり、最後までセッションの値のままである。

対象の文：

- apply の各テーブルの挿入・更新・削除（ADR-0026）と、それらが発火させる既定値・トリガー・制約の検査・外部キーの動作のすべてである。文の終わりに発火するものも含む。
- コミットである。コミットは遅らせた外部キーを検査し、遅らせたトリガーを発火させる。
- それ以外はすべて固定した設定のままである。カタログ、宣言した行の読み込みと比較、計画のすべての検査、`on_insert` の値、削除の前に参照を数え直すこと（ADR-0027）、そして各書き込みの行を選ぶ文である。

書き込みの動き方：

- 1つの書き込みは文のバッチであり、1回の往復でサーバーに送る。
  1. 固定した設定で、1つの文が書き込みの行を選び、セッションの一時テーブルに入れる。条件は計画のものである。挿入なら、保存された行と照合しない宣言した行である。更新なら、比べる列のどれかが違う照合した行であり、比べる列ごとに、違うかどうかを示す印も入れる。削除なら、宣言した行と照合しない保存された行である。宣言した行は、kortopi が持つ宣言の一時テーブルでの識別子 `ctid` で指す。保存された行は照合キーの値で指す。その値を入れる列は、テーブルのキーの列から、型修飾子と照合順序を含めて型を取る。保存された行をテーブルのシステム列で指すことはしない。宣言した列にだけ `SELECT` を持つロールは、システム列を読めないことがある（ADR-0024）。また、外部テーブルであるパーティションは、行の識別子を持たないことがある。`on_insert` の値を持つテーブルへの挿入では、後で述べるとおり、さらに2つの文が値を読む。
  2. `set_config(name, value, true)` で、各設定をセッションでの値にする。
  3. 書き込みは、選んだ宣言した行をその識別子で取り、保存された行をそのキーで取る。キーの比較には、計画が行を照合するのに使う、キーの各列の等価演算子を使う（ADR-0023）。ほかの値は比べない。更新は、比べる列の印が違うと示すところでその列を宣言した値にし、そうでなければ保存された値を戻す（ADR-0026）。
  4. `set_config` で、各設定を固定した値に戻す。apply が次に読むもののためである。
- 書き込みでキーを照らし合わせても、セッションの設定のもとで安全である。演算子は `OPERATOR(<schema>.=)` のようにスキーマ付きで挙げるので、検索パスがそれを選ぶことはない。比べるのはキーの型そのものの値であり、テキストではない。そのため、`DateStyle`・`TimeZone`・`extra_float_digits` のように値の読み方と表示を変える設定は、結果を変えない。そして値は、計画と同じくキーの列の照合順序を持つ。テキストでの比較なら安全ではない。値のテキストはそうした設定で変わるからである。キーの列に等価演算子を持つ型が要り（ADR-0023）、比べる列を書き込みではなく選ぶ文で比べるのは、このためである。
- 選ぶ文は書き込みのときに動く。そのため、apply のそれまでの書き込みが残したとおりの行を見る。ADR-0026 の文が条件を評価したときと同じである。条件は計画のものなので、選ぶのは計画が示す行であり、各書き込みが変えた行の数は、これまでどおり計画と照らし合わせる（ADR-0026）。
- バッチのどの文での PostgreSQL のエラーも、ADR-0026 が書き込みのエラーを報告するのと同じように報告する。エラーはその文がしたことを挙げる。たとえば `pick the rows to update in table app.t` や `read the values of on_insert of table app.t` である。`set the settings of the session to update table app.t` や `update table app.t` もある。PostgreSQL のメッセージ・詳細・ヒント・制約を保ち、その種類の助言を加える。直列化の失敗とデッドロックは、どの文で起きても、もう一度実行すべき競合である。ほかのトランザクションが挿入した行と見なすのは、書き込みそのものでの照合キーのインデックスの違反だけである。これは ADR-0026 を細かくする。ADR-0026 のエラーは、書き込みだけを挙げていた。
- コミットは、1つのメッセージで2つの文を送る。各設定をセッションでの値にする `set_config` と、`COMMIT` である。メッセージを1つにすれば、答えの返らないコミットは、結果の分からない1つの要求のままである（ADR-0026）。コミットの前にトランザクションが失敗していれば、最初の文が失敗し、`COMMIT` は動かない。このとき apply は、PostgreSQL がトランザクションをロールバックし、何も変わらなかったと告げる。`COMMIT` だけを送って `ROLLBACK` が返ったときと同じである。
- どの設定も、`SET LOCAL` と同じくトランザクションの中に限られる。コミットかロールバックで終わる。そのため、同じサーバーとの接続での次のトランザクションは、トランザクションモードのプーラーが接続を渡しても、セッションの設定で始まる。セッション自身の設定が変わることはない。設定がトランザクションの中に限られる以上、コネクションプーラーを通してもこれは成り立つはずである。ただし、このリポジトリのテストは本物のプーラーを通していない（ADR-0026）。

`on_insert` の値：

- ADR-0035 の意味を保つ。PostgreSQL は、固定した設定で、列の型によって値を読む。こうした値を持つテーブルへの挿入では、バッチは `on_insert` の列を持つ一時テーブルを作る。その列は、ADR-0035 の検査と同じく、テーブルの列から型修飾子とドメインを含めて型を取る。バッチは固定した設定でその1行に値を挿入し、挿入はそこから型の付いた値を取る。`now` は、これまでどおりトランザクションの時刻である。
- これは ADR-0035 を細かくする。ADR-0035 の挿入は、各値をキャストのないリテラルとして書いていた。セッションの設定のもとでは、そのリテラルは違うように読まれる。

ロールの検索パス：

- 手順3の文が挙げるのは、スキーマ付きの宣言したテーブル（普通のテーブルなら `ONLY` のあと）、`pg_temp` にある kortopi の一時テーブル、列である。ほかに挙げるのは、それらの一時テーブルのシステム列 `ctid`、`tid` の演算子 `OPERATOR(pg_catalog.=)`、そしてスキーマ付きで挙げるキーの列の等価演算子だけである。真偽値の列は `CASE WHEN` で調べる。関数も型も、ほかの演算子もリテラルも含まない。
- 手順2と4の文、そしてコミットする文は、`pg_catalog.set_config` を呼ぶ。引数はパラメータか、コミットでは `standard_conforming_strings` がどうであれ同じに読めるリテラルである（ADR-0029）。セッションの値を読む問い合わせもセッションの検索パスで動くので、どの関数と型もスキーマ付きで挙げる。
- ほかの文はすべて `search_path` を `pg_catalog` にして動く。このとき PostgreSQL が関数と演算子を探すのは `pg_catalog` だけであり、`pg_temp` は探さない。そのうえ型の演算子はスキーマ付きで挙げる（ADR-0023）。
- そのため、ロールの検索パスのスキーマにあるオブジェクトを kortopi の文が呼ぶことはない。テストは、ロールの検索パスで `pg_catalog` の前にスキーマを置く。そこには `integer`・`text`・`tid`・`oid` の演算子 `=`、`lower`・`num_nulls`・`set_config` という名前の関数、集約 `count` がある。テストは、apply がそのどれも呼ばないこと、そしてスキーマを付けずに `=` を挙げる文ならロールのものを呼ぶことを示す。

行単位セキュリティ：

- 書き込みでは `row_security` も戻す。そのため、ポリシーを持つテーブルに書くトリガーは、アプリケーションの文と同じように動く。
- kortopi 自身の文は、それでもポリシーを越えて書くことはない。触れるのは宣言したテーブルとセッションの一時テーブルだけであり、一時テーブルにはポリシーがない。宣言したテーブルのポリシーがロールに効くなら、計画は止まる（ADR-0024）。計画が使う関数 `row_security_active` は、この設定に左右されない。apply がテーブルを読んだあとに、そのテーブルにポリシーを作ったり有効にしたりはできない。`CREATE POLICY` と `ALTER TABLE ... ROW LEVEL SECURITY` は、ほかのどのトランザクションとも両立しないロックをテーブルに取るからである。
- apply の実行中に、ロールが `BYPASSRLS` を失うことはある。これはそうしたロックを取らない。このとき、次の書き込みの選ぶ文は、`row_security` を off にしてテーブルを読むので失敗する。セッションがロールの変化をまだ見ていなければ、書き込みが計画より少ない行を変え、行数の確認が apply を止める。どちらでも何も書かない。したがって ADR-0024 の検査はなお十分であり、更新や削除から行を隠すポリシーは、行数の確認がなお捉える。

変わらないもの：

- 計画と書き出しはテーブルの行を書かず、すべての設定を固定したままにする。出力は変わらない。
- SQL として出力した計画（ADR-0029）は、それを実行する人のセッションで、スクリプトが固定する3つを除き、そのセッションの設定で動く。そのため、その文が発火させる既定値とトリガーは、そのセッションの設定を見る。apply の書き込みも、いまは自分のセッションで同じようにする。両者は一致する。

これは ADR-0023 を細かくする。`array_nulls` と `timezone_abbreviations` も固定し、固定した設定は読むことと比べることのためのものとする。apply の書き込みは `client_encoding` を除いてセッションの設定で動く。ADR-0026 の次の決まりも細かくする。

- 「apply は、計画が固定する設定で、1つの接続と1つのトランザクションを開く（ADR-0023）」。トランザクションは、書き込みとコミットを除いて固定した設定で動く。apply はその前に、セッションの設定を読む問い合わせを1つ行う。
- 「各文は集合単位であり、計画が比べるのに使った条件で、テーブルの一時テーブルから書く」。各書き込みの前の文がその条件で行を選び、書き込みはその行を取る。保存された行は照合キーで取る。
- 「宣言した行は、トランザクションが終わるまで一時テーブルに置いたままとする」。宣言した行の一時テーブルは、もう apply の唯一の一時テーブルではない。書き込みごとに選んだ行の一時テーブルが1つ加わり、`on_insert` の値を持つ挿入ではもう1つ加わって、コミットまで残る。一時テーブルはどれもコミットまでロックを持ち、apply が読むテーブルも同じである。そのため、数百のテーブルを書く apply は、`max_locks_per_transaction` の既定値が許すより多いロックを要することがある。このとき apply は `out of shared memory` とその設定を上げるヒントで失敗し、何も書かない。
- 「文での PostgreSQL のエラーは、文とテーブルを挙げる」。書き込みのバッチのどの文のエラーも、上で述べたとおり、その文がしたことを挙げる。
- コミットは、セッションの設定と `COMMIT` を1つのメッセージで送る。コミットの前に失敗したトランザクションは、ロールバックしたコミットのメッセージを得る。

### 結果

- 良い点：既定値・外部キーの動作・トリガー、そしてトリガーが書くテーブルのポリシーは、アプリケーションの行と同じものを apply の行にも与える。データベースのタイムゾーンでの時刻、ロールのタイムゾーンでの日付、アプリケーションが見るテキストの形、ロールの検索パスが見つけるテーブルである。
- 良い点：宣言した値と `on_insert` の値は、これまでの意味のままである。オフセットのない `timestamptz` はなお UTC であり、`11/12/2026` はなお11月12日である。
- 良い点：apply のどの決定も固定した設定で行い、書き込みが比べるのは、型の等価性によるキーだけである。そのため、テキストで比べる列についても、apply は出力したとおりの行を書く。
- 良い点：書き込みは、ロールが読めない列を読まない。そのため、ADR-0024 が認めるとおり、宣言した列にだけ `SELECT` を持つロールも適用できる。
- 良い点：ロールの検索パスにあるオブジェクトが、kortopi の文を変えることはない。
- 良い点：トランザクションのあとに残るものはなく、書き込みもコミットも、これまでどおり1回の往復で済む。
- 悪い点：書き込みごとに行の識別子の一時テーブルを作り、`on_insert` の値を持つ挿入ではもう1つ作る。これらはコミットまで残る。また、変更のあるテーブルの条件を2回評価する。計画のために1回、選ぶために1回である。大きなテーブルでは、対象のデータベースの仕事が増える。
- 悪い点：既定値とトリガーが書く値は、アプリケーションの値と同じく、環境ごとの設定で変わるようになる。`timestamp` の列への既定値 `now()` は、CI のデータベースでは UTC を、本番では東京の時刻を持つ。それが狙いではあるが、こうした列で ADR-0023 の UTC を当てにしていたチームには、別の値が見える。
- 悪い点：セッションの設定で失敗するトリガーは、アプリケーションを失敗させるのと同じく、PostgreSQL のエラーで apply を失敗させる。ロールの検索パスがテーブルを見つけられないトリガーがその例である。
- 悪い点：apply は接続するとき、セッションの設定を読むために問い合わせを1つ多く行う。
- 悪い点：選んだ行の一時テーブルの分だけ、apply がコミットまで持つロックが増える。そのため、数百のテーブルの apply では、`max_locks_per_transaction` を上げなければならないことがある。

### 確認の方法

- `internal/postgres` の単体テストは、行を選ぶ文と書く文、書き込みが戻す設定、コミットする文を固定する（`TestWriteStatements`・`TestSettingsOfWrites`）。バッチのどの文が失敗したかの判定とそのエラーも固定する（`TestFailedStatement`・`TestWriteFailure`）。
- `make check-all` で PostgreSQL 15 から 18 に対して動く `internal/postgres` の結合テスト：
  - `TestApplyWritesWithTheSettingsOfTheSession`：設定は3か所に置く。データベースに `TimeZone`、ロールに `search_path` と `DateStyle`、接続のオプションに `IntervalStyle` である。最後のものは、`PGOPTIONS` が与えるのと同じである。
    - 対象は、`timestamp` への既定値 `now()`・`current_date`・`now()::text`・テキストにした interval と、`BEFORE UPDATE` のトリガーである。
    - スキーマを付けずにテーブルを挙げる監査のトリガー、行単位セキュリティを持つテーブルへのトリガー、見た設定を記録するトリガー、外部キーが NULL にする行のトリガーも対象にする。
    - これらが apply の行に与えるものは、同じロール自身の `INSERT`・`UPDATE`・`DELETE` がその行に与えるものと同じである。
    - 宣言した値と `on_insert` の値は UTC と `MDY` で読み、apply のあとの計画は空である。
  - `TestSettingsAroundTheWrites`：各書き込みのあと設定が再び固定されること、トリガーがセッションの設定を見たこと、そしてコミットのあと接続が apply の前と同じセッションの設定を持つことを確かめる。
  - `TestUpdateDecidesInThePinnedSettings`：テキストで比べる列も、固定した設定で違うと決めて更新することを確かめる。
  - `TestWritesInTheSearchPathOfTheRole`：ロールの検索パスで `pg_catalog` の前にあるスキーマのオブジェクトが呼ばれないことを確かめる。
  - `TestSettingsThatChangeHowValuesRead`：ロールは `array_nulls` を off に、`timezone_abbreviations` を `Australia` にしている。それでも計画と apply は、`{NULL}` と `EST` を固定した値のとおりに読む。挿入のトリガーはロール自身の値を見る。
  - `TestCommitWithTheSettingsOfTheSession`：遅らせた制約トリガーは、コミットのときに動く。それがセッションの `TimeZone` と `search_path` を見ることを確かめる。失敗したトランザクションのコミットが、何も変わらなかったと告げることも確かめる。
  - `TestApplyWhenRowLevelSecurityComesToApply` は、選ぶ文のエラーの形も確かめる。
  - `TestApplyWithSelectOnTheDeclaredColumns`：ロールは、宣言した列にだけ `SELECT` と `INSERT` を、比べる列に `UPDATE` を、そして `DELETE` を持つ。このロールが挿入・更新・削除を適用できることを確かめる。
  - `TestApplyWhenRowLevelSecurityComesToApply`：計画のあとに `BYPASSRLS` を失ったロールでは、更新と削除が失敗し、何も書かないことを確かめる。
  - ADR-0026 と ADR-0035 のテストは、apply がこれまでどおりに書くことを確かめる。答えの返らないコミット（`TestCommitWithoutAnAnswer`）も含む。

## 選択肢の長所と短所

### 固定した設定で行を選んでから、セッションの設定で書く

- 良い点：書き込みはアプリケーションのものと同じように働き、決定は計画が行った場所にとどまる。
- 悪い点：書き込みは一時テーブルを要し、計画の条件をもう一度評価する。

### 書き込みでも固定した設定を保つ

- 良い点：何も変わらず、書き込みは計画と同じく予測しやすい。
- 悪い点：テーブルの既定値とトリガーは、アプリケーションが書くところに UTC や別の形を書く。検索パスや行単位セキュリティに頼るトリガーは失敗する。

### 書き込みの文はそのままにして、セッションの設定に戻す

- 良い点：選ぶ文が要らない。ADR-0026 の文がそのまま動く。
- 悪い点：更新は、違う列を自分の文の中で比べる。テキストで比べる列は計画と違う設定で比べることになり、更新は、計画が変わると示す列を変えないまま、正しい行数を報告しうる。
- 悪い点：文の条件が、ロールの検索パスで動く。

### 書き込みでは `search_path` と `row_security` だけを戻す

- 良い点：スキーマを付けずにテーブルを挙げるトリガーと、ポリシーを持つテーブルへのトリガーは動く。
- 悪い点：既定値とトリガーは、なお固定した設定での時刻と形を書き、アプリケーションのものと違う。
- 悪い点：比較は、なおロールの検索パスで動く。

### 書き込みの設定を `kortopi.toml` に書かせる

- 良い点：チームが書き込みの設定を選べる。
- 悪い点：正しい設定はアプリケーションのものであり、それはデータベースとロールがすでに設定している。設定ファイルにもう1つ写しを持てば、それと食い違いうる。
