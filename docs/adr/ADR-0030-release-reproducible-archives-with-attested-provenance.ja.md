# ADR-0030: main 上のタグから再現できるアーカイブをリリースし、サードパーティの表示と構成証明した来歴を添える

## 背景と課題

kortopi には、まだリリースがない。利用者は、このリポジトリから kortopi をビルドしている。
ADR-0005 は、kortopi のバイナリをどう公開し、リリースの出どころをどう示すかを決めずに残した。ADR-0006 は、依存のライセンスが求める表示をリリースがどう集めるかを決めずに残した。

kortopi は、利用者のデプロイのパイプラインの中で、マスタテーブルを変えられるデータベースのロールを持って動く。
途中で誰かが差し替えたバイナリや、乗っ取られたビルドが作ったバイナリは、利用者の本番のデータベースに届く。
kortopi をダウンロードする利用者には、2つの確かめ方が要る。1つは、そのアーカイブが、チェックを通ったコミットからこのリポジトリがビルドしたものだと確かめる方法である。もう1つは、アーカイブがソースと一致すると確かめる方法である。

バイナリには、Go の標準ライブラリと十数個のモジュールが組み込まれる（ADR-0015、ADR-0025）。
それらのライセンスは、バイナリを再配布する者に、著作権とライセンスの表示を残すよう求める。モジュールの中には、go-pgquery の中の PostgreSQL のパーサのように、他者のコードとその表示を含むものもある。

このリポジトリの道具は、固定した道具を使って `make` から動かし、ワークフローのステップは `make` だけを呼ぶ（ADR-0004）。
ワークフローのジョブは、自分が求めた権限だけを持つ（ADR-0005）。

kortopi のリリースを、どうビルドし、どう公開し、どう証明するか。リリースに含まれるものの表示を、リリースはどう添えるか。

## 判断の基準

- アーカイブが、このリポジトリのリリースのワークフローによって `main` 上のタグからビルドされたことを、利用者が手に入れやすいコマンドで確かめられる。
- 同じコミットと同じバージョンの Go からは同じバイトができるので、誰でもリリースをもう一度ビルドして比べられる。
- リリースには、バイナリに組み込まれたものちょうどのライセンスの本文と表示が付く。ライセンスのないモジュールや、ADR-0006 が禁じるライセンスのモジュールがあれば、リリースは止まる。
- メンテナーは、リリースのどのステップも手元のマシンで実行できる。公開せずに GitHub でリリースを試すこともできる。
- 依存のコードを動かすジョブは、書き込めるトークンを持たない。リリースのために新しい道具を固定しない。
- リリースを始められるのはメンテナーだけで、公開したリリースは誰も変えられない。

## 検討した選択肢

- このリポジトリの make のターゲットと Go のプログラムに、GitHub のアーティファクトの構成証明を組み合わせる
- GoReleaser
- slsa-github-generator の SLSA の生成器
- cosign によるキーレスの署名
- チェックサムだけ

## 決定

採用：「このリポジトリの make のターゲットと Go のプログラムに、GitHub のアーティファクトの構成証明を組み合わせる」。固定済みの Go と Trivy でビルドでき、どのステップも手元のマシンで動く `make` のターゲットのまま保て、しかも利用者は `gh` だけでダウンロードを検証できるからである。

ビルドは次の決まりに従う。

- `make release-build VERSION=vX.Y.Z` は、`cmd/kortopi` を Linux・macOS・Windows のそれぞれについて amd64 と arm64 でビルドする。ビルドには `CGO_ENABLED=0`（ADR-0015）と `-trimpath` を使い、バージョンを `-ldflags` で埋め込む。go コマンドがバイナリに記録する環境の設定（`GOAMD64`・`GOARM64`・`GOEXPERIMENT`・`GOFLAGS`）は、既定値に固定する。
- バイナリからシンボルを取り除かない。`go version -m` が読むビルド情報（コミットを含む）と、`govulncheck -mode=binary` が読むシンボルテーブルを残す。
- バージョンは先頭に `v` を付けたセマンティックバージョンで、メジャーバージョンはモジュールのパスが受け付けるものに限る。パスに `/vN` の接尾辞がないあいだは `v0` か `v1` である。`v1.2.3-rc.1` のようにプレリリースの部分を持つバージョンは、GitHub ではプレリリースになる。
- 各バイナリはアーカイブ `kortopi_<version>_<os>_<arch>.tar.gz`（Windows では `.zip`）に入る。同じアーカイブに `LICENSE`・`README.md`・`README.ja.md`・`THIRD_PARTY_NOTICES.txt` も入れる。ファイルは、アーカイブと同じ名前のディレクトリの下に置く。`kortopi_<version>_checksums.txt` には、各アーカイブの SHA-256 を `sha256sum` の形式で書く。
- アーカイブを書くのは、マシンの `tar` や `zip` ではなく、Go のプログラム `tools/cmd/release` である。ファイルは名前の順に並び、モードは 0755 か 0644、所有者は root、時刻はすべてコミットの時刻（`SOURCE_DATE_EPOCH`）とし、gzip のヘッダーには名前も時刻も入れない。そのため、同じコミットと同じ Go からは同じバイトができる。タグの完全なクローンから作っても、浅いクローンから作っても変わらない。

表示は次の決まりに従う。

- `THIRD_PARTY_NOTICES.txt` には、Go の配布物と、バイナリのビルド情報に載るすべてのモジュールを並べる。Go の標準ライブラリとランタイムは、どのバイナリにも入る。ビルド情報に載るモジュールは、`go version -m` が出力するものと同じである。それぞれについて、ライセンスと表示のファイル（`LICENSE`・`COPYING`・`NOTICE`・`PATENTS`・`COPYRIGHT` とその変形）を、サブディレクトリにあるものも含めて収める。ファイルは、`go.sum` が検証したモジュールキャッシュから読む。
- 各モジュールのライセンスは、`scan-deps` と同じく、Trivy が `trivy.yaml` のもとで判定する（ADR-0004、ADR-0006）。バイナリに入るモジュールについて、ルートにライセンスのファイルがないとき、Trivy がライセンスを判定できないとき、`trivy.yaml` がそのライセンスを禁じているときに、ビルドは失敗する。Trivy が判定できないライセンスも失敗にする。ADR-0006 が許すかどうかを誰も判断できないからであり、そうした場合は後の記録で決める。
- このファイルはリリースのたびに生成し、コミットしない。バイナリから生成すれば、バイナリとずれることがない。コミットすると、バイナリに入るモジュールが更新されるたびにファイルが変わる。Renovate は `make gen` を実行できないので、そうした更新を自分でマージできなくなる（ADR-0005）。
- `make check-all` の `make test-release` は、コード・モジュール・リリースの道具が変わるたびに、リリースのビルドを2回実行する。2回のビルドの結果が違うとき、このマシンのバイナリが自分のバージョンを出力しないとき、表示に並ぶモジュールがバイナリのモジュールとちょうど一致しないときに失敗する。そのため、ライセンスのないモジュールや禁じられたライセンスのモジュールは、リリースではなく、それを持ち込むプルリクエストで失敗する。

リリースとその来歴は次の決まりに従う。

- GitHub にタグ `v*` をプッシュすると `.github/workflows/release.yml` が動き、4つのジョブを順に実行する。

  | ジョブ | 権限 | 実行するもの |
  |---|---|---|
  | gate | `contents: read`、`checks: read` | `make release-gate`：タグをチェックアウトしていること、そのコミットが `main` 上にあること、そのコミットで CI のチェック `check` が成功したことを確かめる。 |
  | build | `contents: read` | `make release-build` を実行し、アーカイブを実行のアーティファクトに置く。 |
  | attest | `contents: read`、`id-token: write`、`attestations: write` | `actions/attest` が、アーカイブとチェックサムのファイルについて SLSA のビルドの来歴の構成証明を1つ署名し、リポジトリに保存する。 |
  | publish | `contents: write`、`attestations: read` | `make release-publish`：チェックサムを確かめ、各ファイルの来歴を `gh attestation verify` で検証し、`gh release create --verify-tag --generate-notes` でリリースを作る。 |

- gate は、`make check-all` をもう一度実行せず、CI の結果を信頼する。コミットが `main` に入ったとき、CI はそのコミットのすべてのファイルに `make check-all` を実行しており（ADR-0004）、`main` のルールセットはチェック `check` を必須にしているからである。
- 書き込めるトークンを持つジョブ（attest と publish）は、依存のコードを動かさない。attest が動かすのは GitHub の2つのアクションであり、publish が動かすのは `make`、このリポジトリのスクリプト、`gh` である。依存に対して go コマンドを動かす build は、読み取りだけのトークンを持つ。どのジョブもキャッシュを復元せず、mise もキャッシュを使わずに道具を入れる。そのため、ほかのワークフローが書いたものはリリースに届かない。
- 手で実行（`workflow_dispatch`）すると、ワークフローはドライランになる。選んだブランチを、実行した人が与えるバージョンでビルドし、アーカイブを実行のアーティファクトとして7日間残す。gate、構成証明、リリースは飛ばす。
- このワークフローの次のステップは、`make` のターゲットではなく GitHub のアクションである。ジョブのあいだでアーカイブを受け渡すステップ（`actions/upload-artifact`・`actions/download-artifact`）と、構成証明に署名するステップ（`actions/attest`）である。これらを ADR-0004 の例外に加え、CodeQL や Scorecard と同じ扱いにする。ジョブのあいだでファイルを受け渡す手段はアーティファクトしかなく、構成証明を作れる固定済みの道具もないからである（`gh` は検証しかできない）。
- リポジトリの設定に、ルールセット `release-tags` を加え、変更不可リリースを有効にする。このルールセットのもとでは、タグ `v*` を作成・移動・削除できるのは管理者だけである。変更不可リリースでは、公開したリリースのアセットを誰も変えられず、そのタグも動かせない。GitHub は、リリースの構成証明にも署名する。`make github-settings` が両方を適用する（`docs/guides/github-settings.md`）。

利用者は、ダウンロードしたものを3つの方法で確かめられる。`README.md` にその手順がある。

- チェックサムのファイルを使った `sha256sum --check` で、ダウンロードが欠けていないことがわかる。
- `--repo`・`--signer-workflow`・`--source-ref` を付けた `gh attestation verify` で、このリポジトリのリリースのワークフローがそのタグからファイルをビルドしたことがわかる。`gh release verify-asset` で、そのファイルがそのリリースのアセットであることがわかる。
- タグのきれいなチェックアウトで、そのタグの `mise.toml` が固定する Go を使って `make release-build` を実行すると、同じチェックサムのファイルができる。

`go install github.com/ma-chisuke/kortopi/cmd/kortopi@vX.Y.Z` は、リリースをソースからビルドする方法として正式に扱う。
バイナリはビルド情報のモジュールのバージョンから自分のバージョンを取るので、`kortopi version` は `kortopi vX.Y.Z` を出力する。そのために `cmd/kortopi/main.go` を変える必要はない。
こうしてできたバイナリは利用者の Go がビルドしたもので、構成証明を持たず、リリースのバイトとも一致しない。
文書では、リリースと同じく `CGO_ENABLED=0` を付けるよう求める。C コンパイラーのあるマシンでは cgo が既定で有効になり、ビルドは kortopi が呼ばない pg_query_go の C のパーサもコンパイルしてリンクするからである。

### 結果

- 良い点：アーカイブがこのリポジトリのリリースのワークフローとタグから来たことを、利用者は `gh` だけで確かめられる。ダウンロードが欠けていないことは、チェックサムのファイルだけで確かめられる。
- 良い点：誰でもタグからリリースをもう一度ビルドしてチェックサムを比べられる。そうすれば、アーカイブがソースのとおりの内容で、それ以外のものを含まないことがわかる。
- 良い点：表示はいつもバイナリと一致する。ライセンスのないモジュールや禁じられたライセンスのモジュールは、それを持ち込むプルリクエストで失敗する。
- 良い点：メンテナーはどのステップも手元のマシンで実行でき（`make release-build`、`make release-gate`、`make release-verify`）、GitHub ではドライランでワークフローを試せる。
- 良い点：リリースに新しい道具は要らない。使うのは、`mise.toml` がすでに固定している Go・Trivy・`gh`・`jq` と、GitHub のサービスである。
- 良い点：ビルドの最中に乗っ取られた依存が動いても、公開や構成証明ができるトークンは手に入らない。
- 悪い点：来歴が達するのは SLSA の Build Level 2 であり、3 ではない。ビルドと署名は、このリポジトリが管理する1つのワークフローのジョブで動く。そのため、ワークフローのファイルやビルドのステップが乗っ取られれば、自分でビルドしたものに署名できてしまう。`--signer-workflow` と `--source-ref` を付けた検証とタグのルールセットにより、それができるのはメンテナーだけに絞られる。
- 悪い点：来歴を確かめるには、`gh`（あるいは Sigstore の別のクライアント）とネットワークが要る。チェックサムのファイルはアーカイブと同じ場所から来るので、それだけではダウンロードが欠けていないことしかわからない。
- 悪い点：リリースは GitHub に依存する。構成証明の保存先、Sigstore の公開インスタンス、変更不可リリースである。
- 悪い点：ワークフローの3つのステップはアクションであり、手元のマシンでは動かない。手元で実行する `make release-publish` は、ワークフローがすでに構成証明を作ったものしか検証できない。
- 悪い点：リリースをもう一度ビルドするには、タグのきれいなチェックアウトと同じ Go が要る。作業ツリーに変更があったり、タグのないチェックアウトだったりすると、違うバイトになる。バイナリがチェックアウトの状態を記録するからである。
- 悪い点：バイナリには、macOS と Windows のための署名がない。そのため、ブラウザーでダウンロードしたバイナリは、OS に実行を止められる場合がある。
- 悪い点：`make test-release` は6つのバイナリを2回ずつビルドする。Go のコードを変えると、`make check-all` が1分ほど長くなる。
- 悪い点：Trivy が判定できないライセンスは、記録で決めるまでリリースを止める。例外の一覧は、まだない。
- 悪い点：gate は、そのコミットで CI が成功していることを必要とする。CI の実行中にタグをプッシュすると gate は失敗し、メンテナーは CI が成功してからワークフローをもう一度実行する。

### 確認の方法

- `make check-all` は `make test-release` を実行する。リリースを2回ビルドしてバイトを比べ、このマシンのバイナリを動かし、表示を `go version -m` と比べる。ルートにライセンスのファイルがないモジュールと、ライセンスが禁じられているか判定できないモジュールでは失敗する。自己テストにも、そのケースがある。
- `tools/internal/release` と `tools/cmd/release` の単体テストが、次のことを確かめる。アーカイブがファイルの順序・ディスク上のモード・タイムゾーンに左右されないこと、どのファイルを表示として扱うか、Trivy のレポートの読み方、表示についてどの指摘を出すかである。
- `make check` は、リリースのワークフローに `lint-actions`・`lint-actions-security`・`lint-actions-policy`・`lint-actions-pins` を実行する。アクションの固定、ジョブごとの権限、タイムアウトを確かめる。
- `make release-publish` は、公開の前にすべてのファイルの来歴を検証する。`make release-verify` は、公開したリリース、その来歴、リリースの構成証明を検証する。
- `make github-settings` は、ルールセット `release-tags` と変更不可リリースが有効かどうかを報告する。
- attest と publish のジョブが依存のコードを動かさないこと、リリースのワークフローのどのジョブもキャッシュを復元しないことは、レビューで確かめる。

## 選択肢の長所と短所

### このリポジトリの make のターゲットと Go のプログラムに、GitHub のアーティファクトの構成証明を組み合わせる

- 良い点：どのステップも手元のマシンで動く `make` のターゲットであり、道具はすでに固定してある。
- 良い点：構成証明は GitHub が保存し、`gh` が検証するので、利用者はほかの道具を必要としない。
- 悪い点：アーカイブを作り、表示を書くコードを、このリポジトリが保守する。

### GoReleaser

- 良い点：広く使われており、1つの設定ファイルで、ビルド・アーカイブ・チェックサム・署名・公開ができる。再現できるビルドのための設定もある。
- 悪い点：新しい道具であり、このリポジトリで `make`・go コマンド・`gh` がすでにしていることを肩代わりするので、1つの関心事に道具を1つだけ使う決まり（ADR-0004）に反する。ワークフローのステップも、`make` ではなくこの道具を呼ぶことになる。
- 悪い点：モジュールの表示には、それでも別のステップが要る。

### slsa-github-generator の SLSA の生成器

- 良い点：SLSA の Build Level 3 に達する。来歴を生成するのは、ビルドが影響を与えられない再利用可能なワークフローである。
- 悪い点：検証器が来歴を受け付けるには、ワークフローがこれをコミット SHA ではなくタグで呼ぶ必要があり、ADR-0005 の固定と衝突する。
- 悪い点：利用者は来歴を slsa-verifier で検証することになり、入れる道具が1つ増える。

### cosign によるキーレスの署名

- 良い点：Sigstore のどのクライアントでも検証でき、GitHub の外でも検証できる。
- 悪い点：cosign は、ワークフローでは新しく固定する道具になり、利用者にとっても道具が1つ増える。一方、アーティファクトの構成証明はすでに Sigstore で署名しており、`gh` がそれを検証する。

### チェックサムだけ

- 良い点：署名するものも、それ以上検証するものもない。
- 悪い点：チェックサムのファイルはアーカイブと同じ場所から来るので、わかるのはダウンロードが欠けていないことだけで、誰がビルドしたかはわからない。
