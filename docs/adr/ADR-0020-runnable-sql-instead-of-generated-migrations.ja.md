# ADR-0020: 版管理のマイグレーションを生成する代わりに、計画をそのまま流せる SQL として出力する

## 背景と課題

多くのチームは、版管理のマイグレーションだけでデータベースを変える。
スキーマの変更もデータの変更も、番号の付いたファイルであり、各環境で1度だけ実行される。
そうしたチームにとって、行を自分で適用する道具は、データベースを変える2つ目の経路になる。チームの手順が、それを認めないこともある。

宣言の変更からマイグレーションを生成するには、変更の前の状態、つまり、それまでのマイグレーションを流した後の行が要る。
その状態を知るには、それまでのマイグレーションをデータベースで流し直すしかない。それには、データベースと、マイグレーションの道具ごとのファイルの流し方の知識が要る。

その仕組みを持たずに、版管理のマイグレーションを使うチームに kortopi をどう役立てるか。

## 判断の基準

- 版管理のマイグレーションを使うチームが、自分たちの手順を捨てずに kortopi を使える。
- 実行されるものは、レビューしたものとまったく同じである。
- SQL は、ID が環境ごとに違っても流せる。
- 最初の版を小さく保つ。機能は、利用者が必要とするまで待つ。

## 検討した選択肢

- 計画を、そのまま流せる SQL として出力する
- 宣言の変更から、版管理のマイグレーションのファイルを生成する
- 計画を、人が読むためだけに出力する

## 決定

採用：「計画を、そのまま流せる SQL として出力する」。版管理のマイグレーションを使うチームに、apply が流すのとまったく同じ文を渡せ、しかも、生成に要るマイグレーションの流し直しが要らないからである。

決まりは次のとおりである。

- 計画は、そのまま流せる SQL としても出力できる。中身は apply が流すのと同じ DML であり、外部キーの順に並び（ADR-0017）、値は書き出してある。そのため、流すのに kortopi もその一時テーブルも要らない。
- `WHERE` 句は、照合キーで行を見つける（ADR-0012）。新しい行の `INSERT` は宣言した列だけを挙げるので（ADR-0011）、データベースが振る ID は含まない。そのため、ID が環境ごとに違っても SQL を流せる。
- 例外は、宣言した参照の値が、参照先の行の UUID のように環境ごとに違う ID であるテーブルである。参照を自然キーで書く仕組みは後回しにしたので、そうしたテーブルの SQL は、それらの ID が同じ環境でしか流せない。
- 版管理のマイグレーションを使うチームは、この SQL をマイグレーションのファイルに貼れる。
- 宣言の変更からマイグレーションのファイルを生成する機能は、最初の版に入れない。この機能には、マイグレーションを流し直して前の状態を組み立てる仕組みが要り、要望が出るまで待つ。
- SQL をどう求めるかは、コマンドラインの形の問題である（ADR-0021）。

### 結果

- 良い点：版管理のマイグレーションを使うチームは、ほかのマイグレーションと同じように文をレビューし、実行できる。それでも、あるべき行を示すのは宣言のままである。
- 良い点：SQL は apply の DML そのものなので、kortopi が変更を求める方法は、2つではなく1つで済む。
- 良い点：SQL はデータベースが振る ID に頼らないので、先の例外を除き、1つのマイグレーションをどの環境でも流せる。
- 悪い点：SQL は、計画が読んだ1つのデータベースとの差分である。行がそれと違う環境では、文が一意キーで失敗したり、次の計画に出るずれを残したりしうる。
- 悪い点：生成ならしてくれることを、チームが手で行う。マイグレーションが作るのと同じ状態のデータベースに対して計画を立て、その出力をファイルに写す。
- 悪い点：貼ったマイグレーションは、それ以降の宣言の変更に追随しない。宣言をあとで変えたら、新しい計画と新しいファイルが要る。

### 確認の方法

- PostgreSQL 15〜18 に対する結合テストで、次のことを確かめる。出力した SQL をデータベースの複製に流すと apply と同じ状態になること、そのあとの計画が空になることである。これらのテストは、plan の実装で加わる。

## 選択肢の長所と短所

### 計画を、そのまま流せる SQL として出力する

- 良い点：計画のほかにわずかなコードを足すだけで、版管理のマイグレーションを使うチームの役に立つ。
- 悪い点：SQL をマイグレーションのファイルに移すのは、人の手作業である。

### 宣言の変更から、版管理のマイグレーションのファイルを生成する

- 良い点：宣言の変更が、手作業なしにマイグレーションのファイルになる。
- 悪い点：既存のマイグレーションをデータベースで流し直して前の状態を組み立てる必要があり、マイグレーションの道具ごとの決まりも知る必要がある。
- 悪い点：要望があるかはまだわからない。この機能は、そのまま流せる SQL の上に、あとからでも足せる。

### 計画を、人が読むためだけに出力する

- 良い点：そのまま流せる SQL という制約なしに、読みやすい形の出力にできる。
- 悪い点：版管理のマイグレーションを使うチームは、計画を見ながら文を手で書くことになる。
