# ADR-0049: `NOT ENFORCED` の外部キーを、apply の順序から除く

## 背景と課題

apply は、実行のテーブルを、その間の外部キーの順に書く。PostgreSQL はどの外部キーも検査し、書き込みはどれも破れないからである（ADR-0017）。
2つ以上のテーブルの循環では、`DEFERRABLE` なキーを遅らせる。それを除いても残る循環は、そのうち2つ以上のテーブルに書く行があれば、どの書き込みよりも前に断る（ADR-0026）。

PostgreSQL 18 からは、外部キーを `NOT ENFORCED` にできる。
そうしたキーにはトリガーがない。PostgreSQL はそれを検査せず、その動作も働かせない。カタログでは `pg_constraint.conenforced` が false になる。
削除をたどる処理は、すでにそうしたキーを除いている。削除はそれを通じて何もしないからである（ADR-0039）。
書き込みの順序は、それを除いていなかった。

issue 57 がその例を示す。
`app.members` は PostgreSQL が検査するキーで `app.teams` を参照し、`app.teams` は `NOT ENFORCED` のキーで `app.members` を参照する。
互いを参照するチームとそのリーダーを宣言すると、apply は2つのテーブルを、どの順序でも書けない循環として断り、何も変えなかった。

```text
kortopi: tables app.members and app.teams reference each other through foreign keys that are not deferrable, "members_team_id_fkey" of app.members and "teams_lead_id_fkey" of app.teams, and tables app.members and app.teams have rows to write, so no order of these tables can write their changes: declare one of these foreign keys DEFERRABLE
```

ところが、`app.teams` を先に書けば、PostgreSQL はこれらの行を受け入れる。
エラーが勧める回避策は、検査されないキーを `DEFERRABLE` と宣言することだった。そうすると kortopi は、遅らせるものが何もないキーを遅らせていた。

apply の書き込みを順序づけるのはどの外部キーか。PostgreSQL が検査しないキーは、順序・遅らせるキー・循環に何をもたらすか。

## 判断の基準

- 順序があるのは、PostgreSQL がキーを検査するからである（ADR-0017）。検査するキーは書き込みを順序づけ、検査しないキーはその必要がない。
- apply が断るのは、PostgreSQL が断るものだけである。どれかの順序で書ける循環に、スキーマの変更は要らない。
- SQL としての計画は apply の順に書き、apply が何を遅らせ何を断るかを伝える（ADR-0029）。
- PostgreSQL 15 から 17 では、また PostgreSQL が検査するどのキーについても、何も変わらない。
- 順序はどのデータベースでも同じであり、`internal/apply` にある。カタログの事実は DB ごとの部品が渡す（ADR-0019・ADR-0036）。

## 検討した選択肢

- データベースが検査しないキーに印を付け、順序・遅らせるキー・循環から除く
- そうしたキーを、外部キーを読む問い合わせから除く
- 順序があるところではそうしたキーで順序づけ、循環の中でだけ外す
- これまでどおりどのキーでも順序づけ、エラーでキーが検査されないことを伝える

## 決定

採用：「データベースが検査しないキーに印を付け、順序・遅らせるキー・循環から除く」。
PostgreSQL が検査しないキーは、どの順序でも書き込みを失敗させられない。印を使えば、この決まりは、どのデータベースにも共通の順序を決めるコードに置け、単体テストで確かめられる。DB ごとの部品は、カタログにあることを伝えるだけで済む。

決まりは次のとおりである。

- 宣言したテーブルの間の外部キーには、それぞれ、データベースが検査するかどうかが付く。PostgreSQL 18 以降では、`pg_constraint.conenforced` が false のキーを、検査しないキーとする。PostgreSQL 18 より前では、どのキーも検査するキーであり、問い合わせはその列を挙げない。その版にはこの列がないからである。`NOT VALID` のキーは検査するキーである。PostgreSQL は保存された行をそれに照らして検査していないが、書き込みが渡す行はどれも検査する。そのため、ほかのキーと同じくテーブルを順序づける。
- 検査しないキーは、次のとおりである。
  - 挿入と更新の順序も、削除の順序も決めない。
  - `DEFERRABLE` であっても遅らせない。
  - 循環を作らず、循環のエラーに挙がらない。
- ほかのキーは、ADR-0026 のとおりにテーブルを順序づけ、遅らされ、循環を作る。
- SQL としての計画も apply に従う。文は同じ順に並び、`SET CONSTRAINTS` と循環のコメントはそうしたキーを除く。
- 計画は、そうしたキーについて何も出力しない。計画はテーブルの順序を見せず、削除のまとまりはすでにそうしたキーを除いている（ADR-0039）。PostgreSQL が無視するキーごとに1行を出しても、その行は apply のすることを何も表さない。

変わらないもの：

- `SET CONSTRAINTS` は制約をスキーマと名前で指す。スキーマの中で、`NOT ENFORCED` で遅らせられない制約が同じ名前を持てば、その名前を断る。遅らせられないほかの制約を断るのと同じであり、テストが PostgreSQL 18 で示している。そのため、遅らせる前の名前の検査は、そうした制約も数え続ける（ADR-0026）。
- 削除をたどる処理は、これまでどおりそうしたキーを除く（ADR-0039）。
- apply は最初の書き込みの前に、宣言したテーブルの各外部キーが参照するテーブルを読む。ほかのセッションがそのテーブルを書き直したあとにキーが書き込みを断ったときの、エラーのためである（ADR-0047）。そこでは検査しないキーも読み、そのうちスナップショットが `NOT ENFORCED` と見せるキーも読む。後述のエラーのためである。格納の比較は、どのキーとも同じく、そうしたキーにも成り立つ。

apply の実行中に、ほかのセッションがそうしたキーを変えたとき：

- `ALTER TABLE ... ALTER CONSTRAINT ... ENFORCED` は、参照する側のテーブルに `ACCESS EXCLUSIVE` を取る。ADR-0048 が PostgreSQL 15 から 18 で `ALTER CONSTRAINT` について確かめたとおりである。しかも、そのテーブルのすべての行をキーに照らして検査する。PostgreSQL 18 では、テーブルを読んだトランザクションを待ち、キーを破る行があると失敗した。
- 宣言したテーブルの間のキーでは、参照する側のテーブルは宣言したテーブルである。apply は外部キーを読む前にそのテーブルを読み、終わるまでその `ACCESS SHARE` を持つ。そのため、その読み取りまでにコミットしていない変更は apply を待ち、そのあとで、apply がコミットした行を検査する。
- apply のスナップショットのあと、その読み取りより前にコミットした変更は、スナップショットのカタログには入らない。カタログはキーを `NOT ENFORCED` のまま見せ、PostgreSQL は最新のトリガーを動かす。そうした変更は、apply より前に始まっていることもある。apply がスナップショットを取るとき、変更は参照する側のテーブルの `ACCESS EXCLUSIVE` を持っている。apply は、そのテーブルを初めて読むときにそのロックを待ち、変更がコミットすると先へ進む。そのため、この期間は apply のスナップショットから参照する側のテーブルを初めて読むまでである。apply の始まりにロックを持っている変更も、この期間の中でコミットする。
- そうした変更のあと、apply はキーを除いてテーブルを順序づけ、PostgreSQL は書き込みでキーを検査する。コミットまで遅らせたキーなら、コミットで検査する。スナップショットが `NOT ENFORCED` と見せるキーには、そこではトリガーがない。外部キーが拒むものは、書き込み・コミットまで遅らせた制約の検査・コミットのどれかである。その検査は、削除の終わりとシーケンスを進める前に動く（ADR-0048、ADR-0045）。PostgreSQL のエラーが挙げるテーブルと制約で探したキーを、スナップショットが `NOT ENFORCED` と見せるなら、ほかのセッションがそのキーを検査するキーへ変えたか、同じ名前の検査するキーで置き換えたことを意味する。
- エラーはそう伝え、apply がそのキーを除いて書き込みを計画したことと、apply をもう一度実行することを、PostgreSQL のエラーより前に伝える。存在しない行を参照する行への助言は付けない。その助言は、正しい宣言を変えるよう求めることになるからである。格納の比較が見つけた、参照されるテーブルの書き直しも挙げる（ADR-0047）。apply はロールバックし、何も書かない。次の apply はそのキーでテーブルを順序づけるか、循環を断る。
- 削除が着くテーブルについては、削除のあとのスキーマの比較が各キーを検査するかどうかを読み、文を拒まなかったそうした変更で apply を止める（ADR-0048）。
- 逆の変更、つまりスナップショットのあとの `ALTER CONSTRAINT ... NOT ENFORCED` で apply に残るのは、もう要らない順序や遅らせるキーか、今はどれかの順序で書ける循環を断ることである。キーを破るコミットにはならない。

細かくするもの：

- ADR-0017 の「kortopi は、テーブルの間の外部キーを、対象のデータベースのカタログから読む。挿入と更新は、参照されるテーブルから参照するテーブルへの順に流す。」これは、PostgreSQL が検査する外部キーについて成り立つ。
- ADR-0026 の「参照されるテーブルを、それを参照するテーブルより前に置く」と「遅らせられるキーを除いても残る循環がエラーになる」。前者は PostgreSQL が検査するキーについて成り立ち、循環はそうしたキーの循環である。
- ADR-0047 の次の文。対象は、宣言したテーブルの外部キーが参照するテーブルである。

  「このテーブルは、そのキーが apply の書き込みを拒んだときに確かめる。コミットまで遅らせたキーがコミットで拒んだときも同じである。」

  今では、apply がコミットより前に動かす、コミットまで遅らせた制約の検査（ADR-0045、ADR-0048）をそのキーが拒んだときも確かめる。しかもエラーは、上のとおり、スナップショットが `NOT ENFORCED` と見せるキーを挙げる。

### 結果

- 良い点：`NOT ENFORCED` のキーが閉じる循環は、スキーマを変えずに、PostgreSQL が受け入れる順で適用できる。issue 57 の apply はコミットする。
- 良い点：`NOT ENFORCED` で `DEFERRABLE` なキーはもう遅らせないので、その名前が、同じ名前の制約で遅らせるのを失敗させることもなくなる。
- 良い点：どのキーが働くかについて、順序・遅らせるキー・循環・削除をたどる処理が一致する。
- 悪い点：apply のスナップショットから参照する側のテーブルを読むまでの間で、ほかのセッションがキーを検査するキーへ変えてコミットすると、apply は失敗する。apply がそのロックを待つ間も同じである。エラーはその変更を挙げ、何も書かず、apply をもう一度実行することになる。
- 悪い点：ほかのセッションがそうしたキーを検査するキーに変えたあとで SQL としての計画を流すと、そのキーで失敗しうる。計画は、計画の時点のスキーマに向けて書いたものだからである（ADR-0029）。1つのトランザクションで流せば、そのとき何も変えない。

### 確認の方法

- `internal/postgres` の単体テスト `TestEnforcedError` は、参照されるテーブルの変更がある場合とない場合について、エラーを確かめる。
- `internal/apply` の単体テストは順序を確かめる。`TestOrder` は、検査しないキーを確かめる。対象は、単独のキー、2つと3つのテーブルの循環の中のキー（`DEFERRABLE` かどうかを問わない）、検査するキーの循環の横のキーである。`TestOrderIsDeterministic`・`TestArrangeCycles`・`TestDeletionOrder` も順序を確かめる。`TestRun` の場合「a cycle closed by a key that is not enforced」は、apply の呼び出しの順を確かめる。
- `make check-all` で PostgreSQL 15 から 18 に対して動く結合テスト：
  - `internal/postgres` の `TestOrderLeavesOutKeysNotEnforced`：issue 57 のテーブルを使う。`ForeignKeys` が伝えること、SQL としての計画、挿入して削除する apply を確かめる。検査するキーはどの版でも断り、`DEFERRABLE` なキーは遅らせる。PostgreSQL 18 では、`NOT ENFORCED` のキー、`DEFERRABLE NOT ENFORCED` のキー、`NOT ENFORCED` のキーの横にある検査するキーの循環も確かめる。
  - `TestOrderLeavesOutKeysNotEnforced` は、`NOT VALID` のキーが検査するキーであることも確かめる。そのキーは issue 57 の循環を作り、apply はどの版でもそれを断る。`DEFERRABLE` なら遅らせる。`TestOrderFollowsKeysNotValid` は、そのキーが2つのテーブルを名前の順に逆らって順序づけることを確かめる。
  - `TestApplyAfterAnotherSessionEnforcesAKey`：PostgreSQL 18 で確かめる。スナップショットのあと最初の読み取りの前で、キーを検査するキーへ変える。変えるセッションは、apply が動く前にコミットするか、apply の始まりにロックを持っていて apply がそれを待つ間にコミットする。コミットまで遅らせたキーも確かめる。どれも、その変更を挙げるエラーで apply を失敗させ、何も書かせない。
  - `TestApplyAfterAnotherSessionEnforcesAKeyAndRewritesItsTable`：PostgreSQL 18 で、実行の外のテーブルへのキーを検査するキーに変え、そのテーブルを書き直す。どちらもスナップショットのあとである。エラーは両方を挙げる。
  - `TestDeferWithAConstraintNotEnforcedOfTheSameName`：PostgreSQL 18 で確かめる。`NOT ENFORCED` の制約が同じ名前を持てば、`SET CONSTRAINTS` と `Defer` はその名前を断る。
  - `cmd/kortopi` の `TestApplyLeavesOutKeysNotEnforcedCommand`：PostgreSQL 18 で issue 57 をコマンドから確かめる。PostgreSQL 15 から 17 では、検査するキーを持つ同じテーブルを、これまでと同じエラーで断る。
- 最初の読み取りのあとで apply が待つ間にキーを検査するキーに変えるテストはない。その変更が apply を待つことは、ADR-0048 と、PostgreSQL 18 での手作業のテストが示している。

## 選択肢の長所と短所

### データベースが検査しないキーに印を付け、順序・遅らせるキー・循環から除く

- 良い点：決まりは、順序の共通のコードの中で、遅らせられるキーと自分自身を参照するキーの決まりの横に置かれる。その単体テストにデータベースは要らない。
- 良い点：DB ごとの部品はカタログをそのまま伝え、キーを検査しないことがありうる別のデータベースにも同じ印が使える。
- 悪い点：外部キーを渡すどこもが印を付けなければならない。印のゼロ値は、データベースが検査するキーであり、以前のどのキーとも同じである。

### そうしたキーを、外部キーを読む問い合わせから除く

- 良い点：変更は1つの問い合わせの1つの条件で済む。削除をたどる処理と同じである（ADR-0039）。
- 悪い点：共通の順序からはそうしたキーが見えなくなり、決まりは DB ごとの部品にしか残らない。しかも、遅らせる前の名前の検査はそうした制約を数えなければならず、それには別の問い合わせが要る。

### 順序があるところではそうしたキーで順序づけ、循環の中でだけ外す

- 良い点：循環のないスキーマでは、順序がこれまでと変わらない。
- 悪い点：PostgreSQL が検査しないキーが課す順序は何も守らない。しかも決まりは「そうしたキーは働かない」より言い表しにくい。

### これまでどおりどのキーでも順序づけ、エラーでキーが検査されないことを伝える

- 良い点：順序は何も変わらない。
- 悪い点：apply は、PostgreSQL が受け入れる行をなお断る。しかも助言は、何も守らないスキーマの変更を求める。
