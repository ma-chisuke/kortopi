# ADR-0010: kortopi 自身のオブジェクトをデータベースに作らない

## 背景と課題

データベースを変える道具は、自分の状態をそのデータベースに持つことが多い。
版管理のマイグレーションの道具は、実行した手順の履歴をテーブルに残す。2つの実行が重ならないよう、ロック用のテーブルを持つ道具もある。
kortopi も同じことができる。適用ごとに何を変えたかの履歴、宣言が変わっていないテーブルを計画で飛ばすための、宣言したテーブルごとのハッシュ、それにロックである。

しかし kortopi は、宣言的なスキーマの道具と並べて使う（ADR-0007）。
スキーマの道具は、データベースのスキーマを自分の宣言と比べる。
自分の宣言にないテーブルは、スキーマの道具から見れば消すべきテーブルである。そのため、kortopi 自身のテーブルは、kortopi を使うどのプロジェクトでも、スキーマの道具の計画に消す対象として現れる。

kortopi は、データベースに何かの状態を持つか。

## 判断の基準

- kortopi は、どの宣言的なスキーマの道具とも、その設定で何も除外せずに並べて使える。
- 計画が比べる相手は、今のありのままのデータベースであり、kortopi が以前に何をしたかの記録ではない。
- kortopi に要る権限は、マスタテーブルの読み書きと、一時テーブルを作ることだけである。

## 検討した選択肢

- 自分用のオブジェクトは作らず、一時テーブルだけを使う
- 履歴・ハッシュ・ロックのテーブルを、マスタテーブルの隣に置く
- それらのテーブルを置く、kortopi 専用のスキーマ
- 状態を、データベースの外のファイルに持つ

## 決定

採用：「自分用のオブジェクトは作らず、一時テーブルだけを使う」。kortopi 自身の残り続けるオブジェクトは、どれも宣言的なスキーマの道具の計画に消す対象として現れる。しかも、宣言とデータベースを比べるのに、保存した状態は要らないからである。

決まりは次のとおりである。

- kortopi は、テーブル・ビュー・関数・スキーマなど、セッションより長く残るオブジェクトを作らない。
- kortopi が作るオブジェクトは、ADR-0009 の一時テーブルだけである。一時テーブルはセッションの間だけ存在し、セッションが終わると消える。
- どの計画も、宣言をその時点のありのままのデータベースと比べる。

### 結果

- 良い点：宣言的なスキーマの道具からは、自分が管理するスキーマに kortopi のものが何も見えない。そのため、その設定で何かを除外する必要はなく、その計画も変わらない。
- 良い点：手で直した行のように kortopi の外で行われた変更は、次の計画にずれとして現れる。kortopi の履歴が、テーブルは最新だと誤って示すこともない。
- 良い点：kortopi には、残り続けるオブジェクトを作る権限が要らない。
- 悪い点：kortopi が何をいつ適用したかの記録は、データベースに残らない。その記録は、デプロイのログや宣言の Git の履歴など、ほかの場所に残る。
- 悪い点：何も変わっていなくても、計画のたびに、宣言したすべてのテーブルを読み込む。保存したハッシュでテーブルを飛ばすことはできない。
- 悪い点：2つの適用が同時に動くのを、テーブルに置いたロックで止めることはできない。ほかの種類のロックを取るかどうかは、apply の実装のときに決める（ADR-0017）。

### 確認の方法

kortopi が一時テーブルのほかにオブジェクトを作らないことは、レビューで確かめる。
PostgreSQL 15〜18 に対する結合テストで、計画と適用のあと、それまでなかったオブジェクトがカタログに現れないことを確かめる。
これらのテストは、plan と apply の実装とともに加わる。

## 選択肢の長所と短所

### 自分用のオブジェクトは作らず、一時テーブルだけを使う

- 良い点：スキーマの道具の計画に、kortopi のものが何も現れない。
- 良い点：状態は、今のありのままのデータベースだけである。
- 悪い点：履歴も、保存したハッシュも、ロック用のテーブルもない。

### 履歴・ハッシュ・ロックのテーブルを、マスタテーブルの隣に置く

- 良い点：版管理のマイグレーションの道具の履歴テーブルと同じく、何をいつ適用したかがデータベースに残る。
- 良い点：保存したハッシュがあれば、宣言の変わっていないテーブルを計画で飛ばせる。ロック用のテーブルがあれば、2つの適用が同時に動かないようにできる。
- 悪い点：宣言的なスキーマの道具は、これらのテーブルを自分の宣言にないものとみなし、消す計画を立てる。kortopi を使うすべてのチームが、スキーマの道具の設定でこれらを手で除外しない限り、そうなる。
- 悪い点：ハッシュが記録するのは kortopi が適用した内容であり、今テーブルが持つ内容ではない。そのため、ハッシュを信じる計画は、手で変えた行を見逃す。

### それらのテーブルを置く、kortopi 専用のスキーマ

- 良い点：アプリのスキーマだけを管理するスキーマの道具は、このスキーマを見ない。
- 悪い点：スキーマの道具がデータベースのほかのスキーマを見るかどうかは、道具とその設定によって決まる。そのため、各チームが自分のスキーマの道具を調べ、場合によっては設定する必要がある。
- 悪い点：kortopi にスキーマを作る権限が要る。行を適用するロールは、その権限を持っていないかもしれない。

### 状態を、データベースの外のファイルに持つ

- 良い点：データベースには、kortopi のものが何も残らない。
- 悪い点：kortopi を動かすすべてのマシンの間で、そのファイルを保存し共有する必要がある。しかも、ファイルがデータベースと食い違うことがある。
- 悪い点：データベースと比べれば済むことに、何も加えない。今の行は、データベースがすでに持っている。

## 補足

- kortopi がスキーマの道具を兼ねずに、その隣で動く理由は ADR-0007 にある。
- 一時テーブルと、そこに読み込むものは ADR-0009 にある。
