# ADR-0012: 行を主キーか、テーブルごとに選んだ一意キーで照合する

## 背景と課題

計画を立てるために、kortopi は宣言した行を、データベースの行と組にする。組になる行は、あっても1つだけである。
計画の内容は、テーブルのモード（ADR-0013）の範囲で、この組が決める。相手のない宣言の行は挿入し、管理する列（ADR-0011）が違う組は更新する。モード `sync` では、相手のないデータベースの行を削除する。
組を作るための列が、照合キーである。

すぐに思いつく照合キーは主キーである。
しかし、マスタテーブルの多くは、既定値を持つ UUID のように、データベースが振る代理の主キーを持つ。
そうしたキーで照合すると、宣言は振られた ID を持つ必要がある。ファイルを編集する人にとって、その ID には意味がない。
ID は環境ごとに違うこともある。2つの環境で別々に作った同じ行は、それぞれ違う ID を持つので、1つの宣言では両方に合わせられない。
こうしたテーブルは、たいてい `code` のような一意な業務のコードも持っている。

主キーで照合するのがいちばんよいテーブルもある。
主キーがそのまま業務のコードであるテーブルである。公式のコードを主キーにした都道府県のテーブルがその例である。
アプリが ID をコードの中に定数として持つテーブルもそうである。ID は固定されており、どこでも同じだからである。

kortopi は、どの列で宣言の行とデータベースの行を組にするか。

## 判断の基準

- データベースが振る ID は、宣言に書かなくてよい。
- 振られた ID が環境ごとに違っても、1つの宣言でどの環境とも照合できる。
- 照合があいまいにならない。宣言の各行と組になるデータベースの行は、あっても1つだけである。
- 主キーに意味のあるテーブルは、設定が要らない。

## 検討した選択肢

- 既定は主キーで、テーブルごとに一意キーを選べる
- 主キーだけ
- 宣言したすべての列をまとめてキーにする

## 決定

採用：「既定は主キーで、テーブルごとに一意キーを選べる」。宣言から振られた ID を外して環境をまたいで照合でき、しかも主キーに意味のあるテーブルには設定がまったく要らないからである。

決まりは次のとおりである。

- テーブルの照合キーは主キーである。ただし、`kortopi.toml` のそのテーブルの設定が `key` でほかの列を挙げたときは、その列を使う。たとえば `key = ["code"]` である（ADR-0013）。
- 選んだ列には、それを対象とする UNIQUE 制約と、NOT NULL 制約がなければならない。そうでなければ、照合があいまいになるので、kortopi はエラーで止まる。
- 主キーも選んだキーもないテーブルは、エラーである。
- 主キーが業務のコードであるテーブルや、アプリが ID を定数として持つテーブルは、主キーで照合する。
- 照合キーの値を変えると、計画には古い行の削除と新しい行の挿入として現れる。kortopi は、名前の変更をまだ見分けない。
- マスタテーブルどうしの参照は、当面、参照先の行の ID で書く。参照を自然キーで書く仕組みは、あとの記録に回す。それまでの間、主キーが UUID のテーブルを参照する宣言は、その UUID を持つ。

### 結果

- 良い点：UUID を振るテーブルを、コードだけで宣言できる。新しい行の ID は、列の既定値から得られる。
- 良い点：振られた ID が違う環境どうしでも、1つの宣言で照合できる。
- 良い点：UNIQUE と NOT NULL の検査が、組が当て推量になる計画を止める。
- 悪い点：振られた ID を持つテーブルを参照するテーブルは、やはりその ID を宣言する。そのため、ID が環境ごとに違えば、自然キーでの参照ができるまでは、1つの宣言ですべての環境をまかなえない。
- 悪い点：キーの値の変更は、更新ではなく削除と挿入になる。行は新しい ID を得て、古い行を参照するほかのテーブルの行が影響を受ける（ADR-0018）。削除をしないモード `upsert` では、古い行が新しい行の隣に残る。
- 悪い点：NULL になりうる列は照合キーに含められない。そのため、コードが省略可能なテーブルは、主キーで照合するしかない。

### 確認の方法

PostgreSQL 15〜18 に対する結合テストで、この決定を確かめる。
テストが扱うのは、主キーによる照合と選んだキーによる照合、選んだキーに UNIQUE 制約がない場合と NULL になりうる列を含む場合のエラー、どちらのキーもないテーブルのエラーである。
これらのテストは、plan の実装とともに加わる。

## 選択肢の長所と短所

### 既定は主キーで、テーブルごとに一意キーを選べる

- 良い点：主キーに意味のあるテーブルは設定が要らず、それ以外のテーブルも1行で済む。
- 良い点：振られた ID を宣言の外に置ける。
- 悪い点：キーを選ぶテーブルでは、正しく書くべき設定が1つ増える。

### 主キーだけ

- 良い点：設定が要らない。主キーは、定義により一意であり NOT NULL である。
- 悪い点：UUID を振るテーブルは、その UUID を宣言する必要がある。すると、ID が違う環境どうしでは宣言も違ってくる。
- 悪い点：ある環境では手で、別の環境では kortopi が作った行は、2つの違う ID を持ち、決して照合できない。

### 宣言したすべての列をまとめてキーにする

- 良い点：設定が要らず、主キーのないテーブルにも使える。
- 悪い点：どの値の変更も、更新ではなく削除と挿入になる。そのため、ID が変わり、参照が壊れる。
- 悪い点：等しい2つの行を見分けられない。

## 補足

- 設定 `key` は、ADR-0013 の設定ファイルの一部である。
- 自然キーでの参照ができれば、宣言は行を ID ではなくコードで参照できる。この仕組みは後回しにしてあり、あとの記録で決める。
