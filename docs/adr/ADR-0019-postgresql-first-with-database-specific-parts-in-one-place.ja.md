# ADR-0019: まず PostgreSQL に対応し、データベースごとに違う部分は1か所にまとめる

## 背景と課題

kortopi には、ほかの何よりもデータベースに左右される部分がいくつかある。
kortopi は、SQL の宣言を PostgreSQL のパーサで読み（ADR-0015）、宣言した行を一時テーブルに読み込む（ADR-0009）。値の比較はデータベースに任せ、外部キーの循環は遅らせられる制約で扱い（ADR-0017）、計画と apply のための DML を書く。

kortopi が次に対応しようとしているデータベースは MySQL であり、MySQL はまさにこれらの部分で違う。

- ADR-0015 のパーサは、PostgreSQL の文法しか読まない。
- MySQL 8 の既定の照合順序 `utf8mb4_0900_ai_ci` は、大文字と小文字もアクセントも区別せずに文字列を比べる。そのため、PostgreSQL が区別する2つの値が、MySQL では等しくなりうる。
- MySQL には遅らせられる制約がない。InnoDB は外部キーを、1行ずつ、すぐに検査する。
- クライアントからの一括の読み込み `LOAD DATA LOCAL INFILE` は、止められていることが多い。サーバーの変数 `local_infile` は MySQL 8 では既定で無効であり、クライアントの側でも許す必要がある。

両方のデータベースにきちんと対応するには、これらの部分をそれぞれ2回作ることになる。汎用の設計にすれば、どちらにも中途半端になる。

最初の版はどのデータベースに対応し、ほかのデータベースを足せるように、コードをどう分けておけばよいか。

## 判断の基準

- 最初の版は、対応するデータベースで正しく動き、対応するバージョンはそれぞれ本物のサーバーでテストする。
- 最初の版は、どのデータベースにも共通することではなく、そのデータベースが得意なことを使う。
- あとで MySQL を足すときは、データベースごとに違う部分を差し替え、残りはそのままにする。

## 検討した選択肢

- まず PostgreSQL に対応し、データベースごとに違う部分を内部の1つの境界の内側に置く
- 最初から PostgreSQL と MySQL の両方に対応する
- `database/sql` の上に、どのデータベースにも共通することだけを使う汎用の層を作る
- PostgreSQL だけに対応し、境界を設けない

## 決定

採用：「まず PostgreSQL に対応し、データベースごとに違う部分を内部の1つの境界の内側に置く」。最初の版が PostgreSQL の得意なことに頼れ、MySQL を足す手間を1つのパッケージの中に収められるからである。

決まりは次のとおりである。

- 最初の版は、PostgreSQL 15〜18 と Aurora PostgreSQL に対応する。PostgreSQL 15〜18 は、この記録の日付の時点で PostgreSQL のコミュニティが保守しているメジャーバージョンである。PostgreSQL 14 は、2026年11月12日に保守が終わった。
- Aurora PostgreSQL は、一時テーブルと `COPY FROM STDIN` に対応しているので、動くと見込んでいる。これは、まだ Aurora PostgreSQL のクラスターで確かめていない。
- MySQL には、最初の版のあとで対応する。その時期は決めていない。
- データベースごとに違う部分（DB ごとの部品）は、内部の1つの境界の内側、1つのパッケージに置く。対象は、SQL の宣言のパーサ、一時テーブル、一括の読み込み、値の比べ方、DML の書き方である。ほかにもデータベースごとに違う部分が見つかれば、同じ場所に加える。
- kortopi のほかの部分は、これらの部分をその境界を通してだけ使う。そのため、MySQL を足すことは、2つ目の DB ごとの部品を足すことであり、ほかの部分を変えることではない。
- テストは、コンテナで動かす本物の PostgreSQL のサーバーに対して実行する。サーバーは、対応するメジャーバージョンごとに1つである。

### 結果

- 良い点：最初の版は、PostgreSQL 自身のパーサ、`COPY`、遅らせられる制約、PostgreSQL 自身の値の比べ方に、十分に頼れる。
- 良い点：MySQL を足すときは DB ごとの部品を差し替えればよく、計画、外部キーの順番、削除の安全策はそのまま残る。
- 良い点：メジャーバージョンごとにテスト用のサーバーがあるので、バージョンの間の違いを、利用者より先に見つけられる。
- 悪い点：MySQL を使うチームは、MySQL に対応するまで kortopi を使えず、その時期は決まっていない。
- 悪い点：境界は1つのデータベースだけを見て設計するので、MySQL を足すときに変える必要が出るかもしれない。たとえば、MySQL には遅らせられる制約がないので、外部キーの循環には別のやり方が要る。
- 悪い点：Aurora PostgreSQL への対応は、確かめるまでは、その文書だけを根拠にしている。
- 悪い点：メジャーバージョンごとにサーバーを動かすので、結合テストが遅くなる。しかも、PostgreSQL が毎年メジャーバージョンを1つ出し1つ保守を終えるので、対象のバージョンの一覧も毎年変わる。

### 確認の方法

- 結合テストは、PostgreSQL 15・16・17・18 をそれぞれコンテナで動かして実行する。このテストが、対応するすべてのバージョンの振る舞いを確かめる。これらのテストは、データベースとやり取りする最初の実装で加わる。
- Aurora PostgreSQL を対象にするテストは、まだない。
- データベースごとに違うコードを DB ごとの部品のパッケージの中にとどめるのは、レビューで確かめる。境界を守らせるチェックは、まだない。

## 選択肢の長所と短所

### まず PostgreSQL に対応し、データベースごとに違う部分を内部の1つの境界の内側に置く

- 良い点：最初の版を早く出せて、PostgreSQL に十分に頼れ、MySQL を足す場所がはっきりする。
- 悪い点：2つ目のデータベースで試されるまでは、境界の形は1つのデータベースだけで決まる。

### 最初から PostgreSQL と MySQL の両方に対応する

- 良い点：境界の形を2つのデータベースで決められ、MySQL を使うチームも最初の版から使える。
- 悪い点：最初のリリースの前に、データベースごとに違う部分をすべて2回作る必要がある。しかも難しいのは MySQL の側である。大文字と小文字を区別しない照合順序での比較、遅らせられる制約のない循環、止められていることの多い一括の読み込みがある。

### `database/sql` の上に、どのデータベースにも共通することだけを使う汎用の層を作る

- 良い点：1つのコードで、どのデータベースにも対応できる。
- 悪い点：設計が頼っているもの（PostgreSQL のパーサ、`COPY`、遅らせられる制約）を手放すことになる。`database/sql` も MySQL も、これらを備えていない。
- 悪い点：照合順序のような違いは、それでも結果を変える。汎用の層は違いを隠すだけで、なくしはしない。

### PostgreSQL だけに対応し、境界を設けない

- 良い点：コードがいちばん少ない。
- 悪い点：PostgreSQL に固有のコードがプログラム全体に散らばり、MySQL を足すときには、それをあちこちで探して書き直すことになる。
