# ADR-0022: 宣言のファイルは、意味が1つに決まり、値が定数であるものだけを受け付ける

## 背景と課題

ADR-0008・ADR-0014・ADR-0015 は、宣言の書式、ファイルとテーブルの対応づけ、SQL を PostgreSQL 自身のパーサで読むことを決めた。
次の細部は、読み込む処理の実装に任せていた。

- SQL ファイルをデータのディレクトリの下のどこに置けるか、スキーマのないテーブル名をどう扱うか（ADR-0014）。
- 列の一覧のない `INSERT` をエラーにするか、1つのテーブルのすべての `INSERT` が同じ列を挙げる必要があるか（ADR-0011）。
- 行の前後のどの文を読み飛ばし、`INSERT ... VALUES` の中のどの句を受け付けるか。最近の `pg_dump` が書く `\restrict`・`\unrestrict`・`OVERRIDING SYSTEM VALUE` や、`standard_conforming_strings` などの設定もここに含まれる（ADR-0015）。

読み込む処理を書くうちに、同じ種類の問いがさらに出てきた。
ADR-0015 は `INSERT` の値を書かれたまま PostgreSQL に送るが、値は `now()` や `nextval('...')` のような式でもありうる。こうした式は、実行のたびに違う結果を返すか、シーケンスを進める。
定数でさえ時計に左右されることがある。`date` の列の文字列 `'today'` を、PostgreSQL は読んだ日の日付として読む。
ファイルの先頭の `SET TimeZone = 'Asia/Tokyo'` のような `SET` は、そのファイルの日付や時刻の読み方を変えうる。
ファイルの名前を誤ることもある。`rooms.csv` を `rooms.CSV` としたり、ディレクトリを1段深く置いたりする場合である。
スキーマやテーブルの名前がドットを含むこともある。一方、`kortopi.toml` と計画は、テーブルを `<schema>.<table>` と書く。

どの問いにも答えが2つある。
1つは、PostgreSQL のセッションがそのファイルを実行したときと同じように、ファイルが決めていないことを kortopi が補う答えである。
もう1つは、ファイルを拒み、何を書けばよいかを示す答えである。
同じ宣言を、プルリクエストで計画に使い、環境ごとに適用し、その後の計画のたびに読み直す。
意味がセッションや時点によって変わるファイルからは、互いに食い違う計画が出る。

kortopi は、宣言のファイルをどこまで厳しく読むか。

## 判断の基準

- 1つの宣言は、どの環境でも、どのロールでも、何度実行しても同じ意味になる。
- 計画はデータベースの何も変えず、毎回同じ結果を返す（ADR-0016）。
- `pg_dump --data-only --column-inserts` の出力を、手を加えずに使える（ADR-0008）。
- ファイルの誤りによって、行やテーブルが計画から黙って消えることはない。
- エラーはファイルと行を示し、代わりに何を書けばよいかを伝える。

## 検討した選択肢

- 意味が1つに決まるものだけを受け付け、残りはエラーにする
- PostgreSQL が受け付けるものを受け付け、残りはセッションと同じように補う
- kortopi が理解できるものを受け付け、残りは警告を出して読み飛ばす

## 決定

採用：「意味が1つに決まるものだけを受け付け、残りはエラーにする」。宣言は多くのセッションと環境で読まれ、そのすべてで同じ意味になるのは、セッションに何も委ねないファイルだけだからである。

決まりは次のとおりである。

データのディレクトリについて。

- 最上位の `kortopi.toml` に設定を書く（ADR-0013）。このファイルはなくてもよい。
- CSV ファイルは、ちょうど `<schema>/<table>.csv` に置く。それ以外の深さにある `.csv` ファイルは、パスがテーブルを示さないのでエラーである。
- `.sql` ファイルは、どの深さに置いてもよい。パスに意味はなく、テーブルはファイルの文が示す。
- 拡張子が大文字を含む `.csv` や `.sql` のファイル（`rooms.CSV` など）はエラーである。無視すると、そのファイルのテーブルが黙って消えるからである。それ以外のファイルは無視する。名前がドットで始まるファイルとディレクトリも読み飛ばす。
- ディレクトリへのシンボリックリンクはエラーである。kortopi はそれをたどらないので、その中のファイルが黙って抜け落ちるからである。
- 名前がドットを含むスキーマやテーブルは、この版ではエラーである。CSV のパス、`INSERT`、`kortopi.toml` のどれでも同じである。`<schema>.<table>` という書き方があいまいになるからである。
- 2つのファイルで宣言したテーブルはエラーであり、エラーは両方のファイルを示す。1つの SQL ファイルが、同じテーブルへの `INSERT` 文をいくつ持ってもよい。
- `kortopi.toml` が挙げたテーブルをどのファイルも宣言していなければ、エラーである。名前の綴りを誤ったテーブルが、既定の設定のまま残ることはない。
- テーブルを1つも宣言していないデータのディレクトリと、存在しないデータのディレクトリはエラーである。
- ファイルはパスを並べた順に読む。そのため、結果も最初のエラーも毎回同じになる。

CSV ファイルについて。

- 文字コードは UTF-8 である。先頭のバイトオーダーマークは読み飛ばす。
- 1行目は見出しの行である。宣言した列を、データベースでの名前のとおり、大文字と小文字も同じに挙げる。見出しの行のないファイル・空の1行目・名前のない列・2回挙げた名前・改行を含む名前は、どれもエラーである。
- kortopi が読むのは見出しの行だけである。行は PostgreSQL が COPY で読み（ADR-0009）、`HEADER match` によって見出しの行と列をもう一度照らし合わせる。
- PostgreSQL 18 より前では、引用符の外にあって `\.` だけからなる行はエラーであり、エラーはその行を示す。これらのバージョンの COPY は、そうした行をデータの終わりとみなし、ファイルの残りをエラーなしに捨てる。そのため、計画は行を見落としてしまう。PostgreSQL 18 はその行をデータとして読み、引用符で囲んだ `"\."` はどのバージョンでもデータである。

SQL ファイルについて。

- 文字コードは UTF-8 であり、NUL バイトを含まない。先頭のバイトオーダーマークは読み飛ばす。
- kortopi が受け付ける文は `INSERT INTO <schema>.<table> (<columns>) VALUES (...), (...)` である。`VALUES` の前の `OVERRIDING SYSTEM VALUE` は許す。
- テーブル名はスキーマを持つ。スキーマのない名前はエラーであり、エラーはスキーマを書くよう伝える。そうしないと、セッションの検索パスがテーブルを決めてしまう。データベースの部分を持つ名前もエラーである。
- 列の一覧は必須である。列の一覧は列の全体を1回ずつ挙げ、各行はそれぞれの列に1つずつ値を持つ。
- 1つのテーブルのすべての `INSERT` は、同じ列の集まりを挙げる。順番は問わない。そうしないと、1つのテーブルに、ある列の値を決める行と、その列を既定値に任せる行が混ざる。
- 値として受け付けるのは定数と `NULL`、1回以上キャストした定数（`'x'::t`・`CAST('x' AS t)`・`t 'x'`）、数の前の符号、それらを並べた `ARRAY[...]` と `ROW(...)` である。それ以外はすべてエラーである。関数の呼び出し（`now()` や `nextval(...)` を含む）・副問い合わせ・列の参照・パラメータ・演算子がこれにあたる。エラーは理由を示す。計画はデータベースを変えてはならず、毎回同じ結果を返さなければならない。
- 同じ理由で、日付や時刻の型へのキャストの下にある文字列は、`now`・`today`・`tomorrow`・`yesterday` のどれかを含めばエラーである。大文字と小文字は問わない。`'now'::timestamptz` や `date 'today'` がその例である。PostgreSQL はこれらの語を読んだ時点として読むので、値が計画ごとに変わってしまう。日付や時刻の型とは、`date`・`time`・`timetz`・`timestamp`・`timestamptz` とその配列、日付やタイムスタンプの範囲と複数範囲である。そうしたキャストのない値と CSV ファイルのすべての値は、型が日付や時刻の型である列について、読み込んだあとに検査する（ADR-0023）。
- 受け付ける文の中にあっても、次のものはエラーである。`WITH`・テーブルの別名・`DEFAULT VALUES`・`INSERT ... SELECT`・`UNION` などの集合演算・`ORDER BY`・`LIMIT`・`OFFSET` である。`FOR UPDATE`・`ON CONFLICT`・`RETURNING`・`OVERRIDING USER VALUE`・値としての `DEFAULT` もエラーである。
- `OVERRIDING SYSTEM VALUE` を受け付けるのは、`GENERATED ALWAYS` の識別列に対して `pg_dump` がこれを書くからである。このとき、ファイルの値がそのまま行の値になる。`OVERRIDING USER VALUE` は、その値を捨ててしまう。
- ダンプが行の前後に書くものは、読み飛ばし、どれも実行しない。読み飛ばすのは、すべての `SET` 文・`SET CONSTRAINTS`・`SELECT pg_catalog.set_config(...)`・`SELECT pg_catalog.setval(...)` である。kortopi はシーケンスを管理しない。psql のメタコマンド `\restrict` と `\unrestrict` の行も読み飛ばす。
- 読み飛ばす文のうち、次の設定を計画が固定する値（ADR-0023）以外にする文はエラーである。`SET NAMES`・`SET TIME ZONE`・`pg_catalog.set_config` を使った場合も同じである。対象は、`standard_conforming_strings`（on）と `client_encoding`（UTF8）である。`TimeZone`（UTC・`Etc/UTC`・オフセット 0）、`DateStyle`（ISO だけか、ISO と MDY）、`IntervalStyle`（postgres）も対象である。どの設定も、ファイルの文字列・日付・時刻・期間の意味を変える。しかも kortopi はそれを実行しないので、ファイルは、書いた人が想定したのとは違う設定で読まれてしまう。エラーは、代わりに値をどう書けばよいかを伝える。たとえば、各タイムスタンプにオフセットを書く。
- `RESET`、ほかの psql のメタコマンド、それ以外のすべての文はエラーであり、エラーは文の種類を示す。`COPY ... FROM stdin` には専用のエラーがあり、`--column-inserts` か CSV ファイルを使うよう伝える。

大きなテーブルは CSV ファイルで宣言する。
SQL のパーサは WebAssembly で動く（ADR-0015）。
1回の実行で最初に使うときは1秒近くかかる。実装のときの計測では、25 MB の SQL ファイルを読むのに約10秒と約1 GB のメモリがかかった。
CSV ファイルは COPY へそのまま流し、kortopi は解析しない。
大きすぎるファイルでパーサが失敗したときは、エラーがそう伝え、CSV を勧める。

### 結果

- 良い点：宣言は、どこで読んでも同じ意味になる。テーブルも列も値も、検索パス、テーブルの列の順番、シーケンス、時計に左右されない。
- 良い点：計画は読むだけにとどまる。宣言の値が、データベースを変える関数を呼ぶことはない。
- 良い点：名前を誤ったファイル、置き場所を誤った CSV ファイル、綴りを誤ったテーブルの設定はエラーになる。そのため、テーブルが気付かれないまま計画から抜け落ちることはない。
- 良い点：PostgreSQL 15〜18 の `pg_dump --data-only --column-inserts` の出力が、そのまま使える。
- 悪い点：正しい SQL でも拒むものがある。`now()` や `gen_random_uuid()`、列の一覧のない `INSERT` を使った手書きの初期データのスクリプトは、定数と列の一覧で書き直さないと宣言にできない。
- 悪い点：UUID の主キーのようにデータベースが振る値を、`DEFAULT` や関数の呼び出しでデータベースに任せることはできない。代わりにその列を宣言から外し（ADR-0011）、テーブルは別のキーで照合する（ADR-0012）。
- 悪い点：名前がドットを含むスキーマやテーブルは、この版では宣言できない。
- 悪い点：`today` のような語が読み込む処理に見えるのは、組み込みの日付や時刻の型へのキャストの下だけである。`date` の上のドメインへのキャストは、その語を読み込む処理から隠す。しかも、読み込んだあとの検査に見えるのは、キャストがすでに作った日付だけである（ADR-0023）。
- 悪い点：`TimeZone`・`DateStyle`・`IntervalStyle` の `SET` に頼るファイルは、書き直す必要がある。タイムスタンプにはオフセットを付け、日付は ISO の形で書き、期間は postgres の形で意味が通るように書く。
- 悪い点：SQL ファイルに書いた大きなテーブルは、読むのが遅く、メモリを多く使う。大きなテーブルを SQL でダンプしているチームは、CSV に移す必要がある。

### 確認の方法

- `internal/declaration` と `internal/postgres` の単体テストで、それぞれの決まりとエラーを確かめる。データのディレクトリの構成、CSV ファイルの見出しの行、受け付ける文・句・値と拒む文・句・値、読み飛ばす文、固定する設定ごとに受け付ける書き方、現在の時刻と読まれる語、メタコマンド、エラーが示す行と桁である。
- `internal/config` の単体テストで、`kortopi.toml` のエラーを確かめる。`cmd/kortopi` のテストで、ファイルの誤りがデータベースへの接続より前に報告されることを確かめる。
- 残りは、`make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで確かめる。`TestDumpRoundTrip` は、各バージョンの `pg_dump --column-inserts` の出力が宣言として読み込め、元のテーブルとの差分が出ないことを確かめる。`TestEndMarkerLine` は、各バージョンでの `\.` の行を確かめる。

## 選択肢の長所と短所

### 意味が1つに決まるものだけを受け付け、残りはエラーにする

- 良い点：どのテーブル、どの列、どの値かを、宣言だけで決められる。セッションから来るものは何もない。
- 良い点：どのエラーも、代わりに何を書けばよいかを伝える。
- 悪い点：PostgreSQL 自身なら実行できる SQL の一部を、利用者は書き直すことになる。

### PostgreSQL が受け付けるものを受け付け、残りはセッションと同じように補う

- 良い点：`psql` で実行できる `INSERT` なら、どれも宣言として使える。
- 悪い点：スキーマのないテーブル名は、セッションの検索パスで決まる。検索パスは、ロールや環境によって違うことがある。
- 悪い点：列の一覧のない `INSERT` は、データベースごとの列の順番に左右される。この順番は、スキーマの変更で変わりうる。
- 悪い点：`now()` は実行のたびに違う値を返すので、計画が空にならない。`nextval(...)` は、計画の間に対象のデータベースのシーケンスを進めてしまう。

### kortopi が理解できるものを受け付け、残りは警告を出して読み飛ばす

- 良い点：変わった文が1つあるファイルでも、計画を立てられる。
- 悪い点：読み飛ばした `INSERT` や名前を誤ったファイルの行は、宣言から抜け落ちる。モード `sync` では、それらの行が削除として現れる（ADR-0013）。
- 悪い点：長い CI のログの中の警告は、見落としやすい。
