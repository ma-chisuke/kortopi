# ADR-0016: 計画は対象のデータベースを読んで立て、スキーマの変更を待つものには印を付ける

## 背景と課題

マスタデータを変えるプルリクエストは、マージで適用される計画を示す。各テーブルでどの行が増え、減り、変わるかである。
kortopi は、宣言と対象のデータベースの行を一時テーブルを通して比べ、計画を求める（ADR-0009）。

スキーマの道具は kortopi より先に動く（ADR-0007）。そして、プルリクエストはスキーマと行を一緒に変えることが多い。
列を足して値を入れたり、マスタテーブルとその行を足したりする。
そのプルリクエストで計画を立てる時点では、対象のデータベースはまだ古いスキーマのままである。新しいテーブルも新しい列も、まだない。

対象は、本番のデータベースであることが多い。
計画がそこで何をするにしても、本物のテーブルはそのまま残す必要があり、サービスを待たせるロックを取るわけにもいかない。

スキーマが宣言に追いついていないデータベースについて、それを変えずに計画を立てるにはどうすればよいか。

## 判断の基準

- 計画は、対象のデータベースの本物のテーブルを決して変えない。
- 計画は、サービスを待たせるロックを取らない。そのため、本物のテーブルに DDL を実行しない。
- スキーマと行を一緒に変えるプルリクエストにも、役に立つ計画が出る。
- 計画に2つ目のデータベースは要らない（ADR-0009）。
- 計画に見えない誤りも、マージの前に見つかる。

## 検討した選択肢

- 対象のデータベースを読み、スキーマの変更を待つものに印を付ける
- 適用待ちの DDL をトランザクションの中で実行し、計画を立ててからロールバックする
- 新しいスキーマで作ったシャドーデータベースに対して計画を立てる
- 宣言したテーブルや列がない間は、計画を失敗させる

## 決定

採用：「対象のデータベースを読み、スキーマの変更を待つものに印を付ける」。対象のデータベースで DDL を実行することも、2つ目のデータベースを用意することもなく、プルリクエストに計画を示せるからである。

決まりは次のとおりである。

- 計画は、対象のデータベースのどのテーブルも変えず、そのテーブルに DDL を実行しない。計画が作るのは自分のセッションの一時テーブルだけであり（ADR-0009、ADR-0010）、それはセッションとともに消える。
- 対象のデータベースにない宣言したテーブルは、スキーマの適用後に決まるものとして示し、宣言した行の数を添える。
- テーブルにない宣言した列も同じように示し、その列の名前を添える。そのテーブルのほかの列は、ふだんどおりに比べる。
- それ以外の差分は、すべてふだんどおりに示す。
- まだないテーブルや列についての型や制約の誤りは計画から見えないので、CI で見つける。CI では、新しいスキーマを適用したあとに行を適用する。適用先は、使い捨ての PostgreSQL である。この実行はふつうの apply であり、kortopi の側に特別な仕組みは要らない。
- 出力での印の文言と、まだない列を含む宣言の行をどう読み込むかは、plan の実装のときに決める。

### 結果

- 良い点：プルリクエストの計画は、いまのスキーマで求められる差分をすべて示し、スキーマの変更を待つものも名前で示す。そのため、レビューする人は変更の全体を見られる。
- 良い点：対象のデータベースで DDL を実行しないので、計画が `ALTER TABLE` の強いロックを取ることはない。
- 良い点：計画に要るのは、対象のデータベースだけである。
- 悪い点：まだないテーブルや列の値は、計画では検査できない。PostgreSQL は値を列の型で解釈するからである（ADR-0009）。そこにある誤った値は、使い捨ての PostgreSQL での CI の実行で見つかる。遅くとも apply が失敗してロールバックしたときにはわかる（ADR-0017）。
- 悪い点：テーブルや列の名前の綴りの誤りは、スキーマの変更を待つものと同じに見える。使い捨ての PostgreSQL での CI の実行がそれを見つけ、印を読むレビューでも見つかる。
- 悪い点：それでも計画は一時テーブルを作る。PostgreSQL では、読み取り専用のトランザクションもホットスタンバイも、一時テーブルの作成を許さない。そのため、計画には書き込みのできるプライマリへのセッションが要る。そのロールには、データベースに対する `TEMPORARY` 権限（既定では `PUBLIC` に与えられている）と、テーブルに対する `SELECT` が要る。リードレプリカに対しては計画を立てられない。
- 悪い点：プルリクエストの CI に、対象のデータベースへの接続と、そこでのロールが要る。

### 確認の方法

- PostgreSQL 15〜18 に対する結合テストで、次のことを確かめる。計画がデータベースのどのテーブルも元のまま残すこと、ないテーブルとない列に決めたとおりの印が付くこと、テーブルに対する `SELECT` とデータベースに対する `TEMPORARY` だけを持つロールで計画を立てられることである。読み取り専用のセッションで計画が何を報告するかも確かめる。これらのテストは、plan の実装で加わる。

## 選択肢の長所と短所

### 対象のデータベースを読み、スキーマの変更を待つものに印を付ける

- 良い点：対象のデータベースでの DDL も、2つ目のデータベースも要らない。
- 悪い点：スキーマの変更を待つテーブルや列の値を、計画は検査しない。

### 適用待ちの DDL をトランザクションの中で実行し、計画を立ててからロールバックする

- 良い点：計画から新しいスキーマが見えるので、どの値も本当の型で検査できる。
- 悪い点：`ALTER TABLE` の多くの形は `ACCESS EXCLUSIVE` ロックを取り、ロールバックまで持ち続ける。そのため、プルリクエストの計画が本番のサービスを待たせてしまう。
- 悪い点：kortopi が、スキーマの道具の DDL を手に入れて実行する必要がある。ADR-0007 は、スキーマの道具を別にしている。

### 新しいスキーマで作ったシャドーデータベースに対して計画を立てる

- 良い点：マージの前に、新しい型と制約で値を検査できる。
- 悪い点：どのパイプラインにも2つ目のデータベースが要る。しかも kortopi は、スキーマの道具を実行して、そこに新しいスキーマを作る必要がある。ADR-0007 は、スキーマの道具を別にしている。
- 悪い点：シャドーデータベースには対象の行が1つもない。そのため、計画は結局対象も読み、2つのデータベースから得たことを組み合わせることになる。

### 宣言したテーブルや列がない間は、計画を失敗させる

- 良い点：単純で、一部だけの計画を示すことがない。
- 悪い点：マスタテーブルや列を足すプルリクエストには、計画がまったく出ない。レビューする人が計画をいちばん必要とするのは、まさにそのときである。

## 補足

- PostgreSQL 18 の文書の[読み取り専用のトランザクション](https://www.postgresql.org/docs/18/sql-set-transaction.html)と[ホットスタンバイ](https://www.postgresql.org/docs/18/hot-standby.html)（それぞれが拒むコマンドを挙げており、`CREATE` もその1つである）
- [権限](https://www.postgresql.org/docs/18/ddl-priv.html)（データベースに対する `TEMPORARY` 権限と、その既定）
