# ADR-0003: 文書は英語で書き、どの文書にも日本語の対訳を隣に置く

## 背景と課題

kortopi は公開の道具であり、使う人・issue を書く人・ほかの道具と比べる人の多くは英語を読む。
一方、メンテナーはすべての文書をレビューし、そのレビューを日本語で行う。
kortopi の文書は、利用者のデータベースの行に kortopi が何をするかを伝える。そのため、レビューで見逃した誤りは、利用者に誤った適用をさせるおそれがある。

2つの言語で文書を書くと、別の危険が生まれる。2つの文面が食い違ったとき、どちらが正しいのか、どちらが古いのかを見分ける手段がない。

どちらの言語を原文とし、もう一方の言語をどこに置き、2つの文面がまだ一致していることを読み手はどうやって知るか。

## 判断の基準

- 公開の道具の利用者が、すべての文書を読める。
- メンテナーが、すべての文書を日本語でレビューできる。
- 2つの文面が食い違ったとき、どちらか一方が正となる。
- 古くなった対訳は、読み手ではなくチェックが見つける。
- コード・kortopi のメッセージ・道具への指示は1つの言語で書き、そこには対訳を必要としない。

## 検討した選択肢

- 英語を原文とし、どの文書にも日本語の対訳を隣に置く
- 英語だけ
- 日本語だけ
- 日本語を原文とし、どの文書にも英語の対訳を隣に置く
- 対訳を別のツリー（`docs/ja/`）に置く
- 必要なときに機械翻訳し、何もコミットしない

## 決定

採用：「英語を原文とし、どの文書にも日本語の対訳を隣に置く」。利用者は対訳ではなく原文を読め、メンテナーは日本語でレビューでき、文書がコードと同じ言語になり、しかも2つの文面がずれたことをチェックで見つけられるからである。

決まりは[対訳のガイド](../guides/translation.ja.md)のとおりである。

- `foo.md` は英語で、これが原文である。`foo.ja.md` はその日本語の対訳で、同じディレクトリに置く。
- 2つのファイルは同じコミットで変える。
- 対訳の最後の行に、訳した英語版のファイルの SHA-256 ハッシュを書く。この行は `make i18n-stamp` が書く。
- コード・コメント・コミットメッセージと、kortopi が出力するメッセージは、英語だけで書く。
- `.claude/` と `.github/` の下のファイルは道具への指示なので、英語だけで書く。`.i18nignore` は、これらと、Markdown に対訳の要らないほかのパスを並べる。たとえば `CLAUDE.md` は `AGENTS.md` を読み込むだけなので、この一覧に入る。
- 第三者のファイルは、公開されたときの言語のまま置く。`.claude/skills/japanese-tech-writing/` にある日本語の文章規範がその例である。
- 英語の文章は Vale が Google の開発者向け文書のスタイルに照らして検査し、日本語の文章は textlint が検査する。対訳は、日本語の文章規範と、ガイドにある用語の表に従う。

### 結果

- 良い点：どちらの言語の読み手も、要約ではなく文書の全文を読める。
- 良い点：2つの文面が食い違ったときは、英語の文面で決まる。
- 良い点：2つのファイルが並んでいるので、相対リンクがどちらでも同じように働き、両方への変更が1つの差分に出る。
- 良い点：道具とエージェントは英語の指示だけを読むので、食い違いうる2つの版を持つ指示がない。
- 悪い点：文書を変えるたびに2回書く必要があり、レビューの時間も延びる。
- 悪い点：日本語を書かない貢献者は、自分だけでは対訳を更新できない。スキル `sync-translation` か、メンテナーの手助けが要る。`make i18n-stamp` を実行すれば `make check` は通るが、対訳は古いまま残る。
- 悪い点：ハッシュが示すのは、原文が変わったあとに誰かが `make i18n-stamp` を実行したことだけである。対訳を更新したことも、意味が一致していることも示さない。意味はサブエージェント `translation-reviewer` が比べるが、違いを見落とすこともある。
- 悪い点：メンテナーがレビューするのは原文ではなく対訳である。そのため、英語の文面だけにある誤りはレビューを通り抜けうる。
- 悪い点：日本語しか読まない利用者は、文書を日本語で読めても、kortopi のメッセージは英語で読むことになる。

### 確認の方法

- `make check` は `lint-i18n` を実行する。`lint-i18n` が失敗するのは、対訳のない文書があるとき、英語版のない対訳があるとき、対訳の最後の行がないか別のファイルを指しているとき、対訳のハッシュが英語版と違うときである。指摘はどれもこの記録を示す。
- `make check` は、英語の Markdown に Vale を（`lint-prose-en`）、日本語の Markdown に textlint を（`lint-prose-ja`）実行する。
- 意味は、サブエージェント `translation-reviewer` が対訳と原文を比べて確かめ、その見落としはレビューで補う。
- コード・コメント・コミットメッセージと kortopi のメッセージが英語であることは、レビューで確かめる。言語を守らせるチェックはない。

## 選択肢の長所と短所

### 英語を原文とし、どの文書にも日本語の対訳を隣に置く

- 良い点：どちらの読み手も全文を読める。
- 良い点：どちらの文面が正なのかがはっきりしている。
- 悪い点：書く手間が2倍になる。

### 英語だけ

- 良い点：文面が1つなので、そろえるものがない。
- 悪い点：メンテナーが日本語でレビューできない。

### 日本語だけ

- 良い点：メンテナーのレビューする文面と、利用者の読む文面が同じである。
- 悪い点：公開の道具の利用者の多くが読めない。

### 日本語を原文とし、どの文書にも英語の対訳を隣に置く

- 良い点：正となる文面を、メンテナーが書いてレビューできる。
- 悪い点：利用者が読むのは対訳である。対訳の質が低いところでは、公開される文面の質も低くなる。
- 悪い点：コード・コメント・コミットメッセージはどのみち英語なので、文書だけが、説明する対象のコードと違う言語になる。

### 対訳を別のツリー（`docs/ja/`）に置く

- 良い点：英語のツリーには英語しか置かれない。
- 悪い点：対訳が原文から離れた場所にあるので、片方だけを変えてしまいやすい。相対リンクも2つのツリーで変わる。
- 悪い点：README や `AGENTS.md` のように `docs/` の外にある文書には、別の仕組みが要る。

### 必要なときに機械翻訳し、何もコミットしない

- 良い点：何も2回書かずに済む。
- 悪い点：読み手が読む文面を誰もレビューしない。用語も訳すたびに変わる。
- 悪い点：メンテナーが対訳をレビューしても、その跡がリポジトリに残らない。

## 補足

- [Vale](https://vale.sh/)・[Google developer documentation style guide](https://developers.google.com/style)・[textlint](https://textlint.org/)
- スキル `sync-translation` とサブエージェント `translation-reviewer` は、ADR-0002 のハーネスの一部である。
