# ADR-0026: apply は1つのスナップショットで、トランザクションのロックのもとで、集合単位の文で実行する

## 背景と課題

ADR-0017 は、apply を1つのトランザクションとし、行を外部キーの順に書き、循環の制約を遅らせることを決めた。
いくつかの点は実装に任せていた。2つ目の apply に対してロックを取るかどうか、遅らせられる制約のない循環の正確な振る舞い、`--schema` で絞った実行がその外のテーブルをどう扱うかである。
apply を書くうちに、同じ種類の問いがさらに出てきた。

apply は計画を出力し、それから書き込む。その間も、サービスはデータベースを変え続けている。
もし apply が、出力したものより新しい状態から書き込めば、その出力を読んだ人は、ある変更を読んで別の変更を受け取ることになる。

2つの apply が同時に始まることもある。たとえば、2つのデプロイのジョブからである。
ADR-0010 は、それらを分けるための kortopi 専用のテーブルを認めていない。
多くのチームは、トランザクションモードのコネクションプーラーを通して PostgreSQL につなぐ。プーラーは、クライアントのトランザクションごとに、空いているサーバーの接続を割り当てる。そのため、サーバーのセッションに属するロックは、それを取ったクライアントより長く残ったり、別の接続で解放されたりしうる。

書く行は、計画が比べたとおりに書く必要もある。同じ等価性で、同じ宣言の行から書き、宣言が挙げない列は変えない（ADR-0011）。
テーブルのトリガーやルールは、文のすることを変えうる。ロールが、ある種類の変更の権限だけを欠くこともある。

apply はデータベースの中でどう動き、書き込む前とあとに何を検査するか。

## 判断の基準

- apply が計画として出力するものは、apply が書き込むものそのものである。そうでなければ、何も書き込まない。
- 1つのデータベースで2つの apply が入り混じることはない。データベースには kortopi のオブジェクトを置かず（ADR-0010）、コネクションプーラーを通しても同じである。
- 計画と apply は、どの行が違うかを同じコードで決める（ADR-0021）。
- 最初の書き込みより前に見つけられる誤りは、その前に見つける。
- apply に、行を書き込む権限より強い権限は要らない（ADR-0017）。
- どんな失敗のあとでも、データベースは元のままであり、利用者は変更がなされたかどうかを知ることができる。

## 検討した選択肢

- トランザクションのロックのもとで、`REPEATABLE READ` の1つのトランザクションで、読み込んだ行から集合単位の文で書く
- 読むときに保存されている行をロックする、`READ COMMITTED` の1つのトランザクション
- `SERIALIZABLE` の1つのトランザクション
- トランザクションの前後で持ち続けるセッションのロック
- kortopi が計画から組み立てる、行ごとの文

## 決定

採用：「トランザクションのロックのもとで、`REPEATABLE READ` の1つのトランザクションで、読み込んだ行から集合単位の文で書く」。スナップショットによって、出力した計画が書き込む計画になる。ロックはどんなプーラーを通しても2つの apply を分け、トランザクションとともに終わる。文は計画の条件を使い回すので、計画が示す行だけをちょうど変えるからである。

決まりは次のとおりである。

トランザクションとロックについて。

- apply は、接続を1つ開き、分離レベル `REPEATABLE READ` のトランザクションを1つ開く。そこでは、計画が固定する設定（ADR-0023）を使う。そのトランザクションの中で読み・読み込み・比べ・書き込む。そのため、出力する計画と書き込む行は、1つのスナップショットから来る。
- apply のスナップショットのあとに、apply が書き込む行を別のトランザクションが変えると、PostgreSQL は直列化の失敗かデッドロックを報告する。宣言したキーの行を別のトランザクションが同時に挿入した場合は、照合キーのインデックスの違反を報告する。どれも、別のトランザクションが行を変えたので apply をもう一度実行するように、と伝える1つのエラーになる。何も書き込まない。
- トランザクションの最初の文は、kortopi の決まった1つのキーで `pg_try_advisory_xact_lock` を試みる。このロックはサーバーのロックであり、データベースのオブジェクトではない。コミットとロールバックのどちらでも、トランザクションとともに終わる。セッションのロックは使わない。トランザクションモードのプーラーを通すと、トランザクションが終わったあともサーバーの接続に残ってしまうからである。
- 別の apply がロックを持っているときは、apply はロールバックし、別の apply を待つという1行を標準エラー出力に出す。そして、自分の短いトランザクションでロックを待ち、新しいスナップショットでやり直す。自分のトランザクションの中では待たない。そうすると、スナップショットが別の apply の変更より前のものになってしまうからである。スナップショットとロックの間のわずかな時間は、同時の変更のエラーで補う。
- `session_replication_role` が `origin` でなければ、apply は始めない。`replica` や `local` では外部キーのトリガーが発火せず、apply がそれを破る行をコミットしうるからである。kortopi はこの設定を読むが、変えない。
- 文は宣言の行から書き込む。そのため、宣言の行は、トランザクションが終わるまで一時テーブルに残しておく。計画は、引き続き、テーブルを比べ終えるとすぐにその行を捨てる（ADR-0024）。

作業の順番について。

1. kortopi は、計画と同じようにファイルと設定を読み、接続する。
2. `kortopi plan` のコードで計画を求める。計画は、どの行を読み込むよりも前にすべてのテーブルを検査し、それからテーブルを1つずつ読み込んで比べる（ADR-0024）。そのあと、挿入する行が、値の要るどの列にも値を得られることを検査する（後述）。
3. データベースにまだない宣言したテーブルや列は、apply のエラーであり、すべてをまとめて報告する。先にスキーマの変更を適用する必要がある（ADR-0016、ADR-0007）。計画はそれらに印を付けるが、apply はそれらを書き込めない。
4. 削除の安全策と最初の書き込みより前に、計画を標準出力に出す。そのあと apply が失敗しても、何をしようとしていたかが出力に残る。
5. 削除の安全策（ADR-0027）と外部キーの循環を検査する。
6. 段階 1 は外部キーの順、つまり参照されるテーブルから参照するテーブルへの順である。テーブルごとに、足りない行を挿入し、それから違う行を更新する。テーブルの中で挿入を更新より先にするのは、更新した行が、同じテーブルに加わる行を参照できるようにするためである。
7. 段階 2 は逆の順である。安全策が削除を許すときに削除する。
8. コミットする。

差分でしか分からない宣言の検査について。

- `NOT NULL` で既定値がなく、宣言が挙げない列は、新しい行で値を得られない。そのため、そのテーブルの挿入する行はどれも失敗する。計画は、したがって apply も、挿入する行のあるすべてのテーブルについて、そうした列を報告する。報告するのはテーブルを比べたあと、計画を出す前であり、すべてをまとめて報告する。比べるのを止めたデータベースのエラーがあれば、その前に置く。ここでの既定値とは、列かそのドメインの既定値、`serial`、どちらの種類の識別列、生成列である。
- これは ADR-0023 を細かくする。ADR-0023 は、計画が検査しない制約に「宣言が挙げない列の NOT NULL」を挙げている。計画は今や、それが影響する唯一の行である挿入する行について、これを検査する。ADR-0024 も細かくする。ADR-0024 の誤りの順番では、どの行を読み込むよりも前に、すべてのテーブルのすべての誤りを報告する。この誤りは差分によってしか見つからないので、比べたあとに来る。

外部キーの順について。

- kortopi は、実行の対象のテーブルの間の外部キーをカタログから読む。参照されるテーブルを、それを参照するテーブルより前に置く。同じ順位のものはスキーマ、名前の順に並べるので、順番は毎回同じになる。
- テーブルから自分自身への外部キーは、テーブルの順番を決めず、遅らせもしない。PostgreSQL は遅らせていないキーを各文の終わりに検査し、apply はテーブルの変更を種類ごとに1つの文で書くからである。これは ADR-0017 を細かくする。ADR-0017 は「自分自身を参照するテーブルも含め、循環」を遅らせることで扱うとしている。
- 2つ以上のテーブルの循環では、遅らせられる外部キーはテーブルの順番を決めない。そのキーを `SET CONSTRAINTS ... DEFERRED` で遅らせるのは、循環の中の2つ以上のテーブルに書く行があるときだけである。それより少なければ、循環のどの文もほかの文に頼らないので、何も遅らせない。不要な遅らせ方は避ける。壊れたキーのエラーが文からコミットへ移ってしまい、しかも `SET CONSTRAINTS` が無関係な同名の制約で失敗しうるからである。
- 遅らせられるキーを除いても残る循環がエラーになるのは、その中の2つ以上のテーブルに書く行があるときだけであり、最初の書き込みより前に報告する。エラーは、テーブル・制約・書くテーブルを挙げ、キーの1つを `DEFERRABLE` と宣言するよう伝える。これで、ADR-0017 の「遅らせられる制約のない循環」のエラーが正確になる。テーブルが一緒には書かない循環は、エラーではない。
- `SET CONSTRAINTS` は制約をスキーマと名前だけで指すので、そのスキーマにあるその名前のすべての制約に効く。そのスキーマの別のテーブルに、同じ名前で遅らせられない制約があれば、apply は、どちらかの名前を変えるよう伝えるエラーで止まる。
- `--schema` は、計画と同じく、実行を指定したスキーマの宣言したテーブルに絞る。実行の外のテーブルへの外部キーは、順番に影響しない。行がそうしたキーを破れば、PostgreSQL のエラーをテーブルと制約とともに報告する。これで、ADR-0017 が残した点が決まる。

文について。

- どの文も集合単位であり、テーブルの一時テーブルから、計画が比べるのに使った条件で書き込む。照合キー、保存されているどの行とも組にならない行、違う列という条件である。ふつうのテーブルは、読むときと同じく `ONLY` を付けて書く。
- 挿入はキーと比べる列だけを挙げるので、ほかの列には既定値が入る（ADR-0011）。キーが `GENERATED ALWAYS` の識別列を含むときは、`OVERRIDING SYSTEM VALUE` を付ける。kortopi はシーケンスを読みも動かしもしない。
- 更新は、違う行の比べる列をすべて設定し、値が違わない列には保存されている値を戻す。そのため、等しいとみなす値は、保存されているテキストを保つ。たとえば、宣言の `1.00` に対する `1.0` である。
- 削除は、どの宣言の行とも組にならない保存されている行を消す。
- 各文のあと、文が変えた行の数は、そのテーブルとその種類について計画が示す数と等しくなければならない。違えば apply は止まる。トリガー・ルール・カスケードが、文のすることを変えたからである。
- 文の中の PostgreSQL のエラーは、文とテーブルを示し、メッセージ・詳細・ヒント・制約を保ち、よくある場合には何をすればよいかを足す。外部キー、照合キー以外の一意キー、`CHECK` 制約、値のない列、権限の不足である。

権限と、それぞれを検査する時点について。

- apply には、計画に要るもの（ADR-0024）と、テーブルの変更の種類に応じた `INSERT`・`UPDATE`・`DELETE` が要る。
- 挿入する行のあるテーブルではキーと比べる列に対する `INSERT` を、更新する行のあるテーブルでは比べるすべての列に対する `UPDATE` を、各テーブルを比べるときにカタログで検査する。どちらも、最初の書き込みより前である。`UPDATE` が比べるすべての列について要るのは、更新がそのすべてを挙げるからである。
- `DELETE` は、最初の削除の直前に、削除する行のあるすべてのテーブルについて検査する。そのため、`--allow-delete` のない apply には `DELETE` は要らない。

コミットについて。

- apply は、すべての文が成功したあとでだけコミットする。エラーがあったとき、検査や書き込みの間に割り込まれたとき、コミットせずにセッションが閉じたときは、トランザクションをロールバックする。そして、標準エラー出力の最後の行で、何も変えなかったと伝える。
- PostgreSQL がコミットを拒んだとき（たとえば遅らせた外部キーが失敗したとき）も、何も変わっていない。
- コミットの答えが届かないとき（接続が切れた、時間切れになった、サーバーがセッションを終えたとき）、apply は変更がなされたかどうかを知ることができない。apply はそう伝え、何も変えなかったとは言わず、状態を見るために `kortopi plan` を実行するよう伝える。終了コードは 1 である。
- コミットが始まったら、割り込みでは止めない。その結果を知るためである。
- 書くものがない apply は、何も書き込まず、コミットもしない。

apply がデータベースに残すものについて。

- コミットのあと、カタログには PostgreSQL 自身の一時スキーマ `pg_temp_N` と `pg_toast_temp_N` が空のまま残る。PostgreSQL は、サーバーのセッションが初めて一時テーブルを作るときにこれらを作り、使い回すために残す。ロールバックはその作成を取り消すが、コミットは取り消さない。これらは kortopi のオブジェクトではなく、kortopi のものを何も持たない。これは ADR-0010 を細かくする。ADR-0010 は、kortopi がセッションより長く残るオブジェクトを残さないとしている。kortopi のオブジェクトは何も残らないが、PostgreSQL 自身のこれらのスキーマは残りうる。計画は常にロールバックするので、何も残さない。

### 結果

- 良い点：apply が出力する計画は、apply がコミットする変更そのものである。その間に誰かが変更すれば、apply は別のものを書かずに失敗する。
- 良い点：1つのデータベースの2つの apply は、トランザクションモードのプーラーを通しても順に動き、2つ目は1つ目が書いた行と比べる。
- 良い点：ファイル・キー・安全策・循環の誤り、挿入する行が値を得られない列、読む・挿入する・更新する権限の不足は、何かを書き込む前に apply を止める。`DELETE` の不足は最初の削除の前に apply を止め、ロールバックがそれまでに書いたものを取り消す。
- 良い点：文は計画の条件を使い回すので、計画が示さなかった行を apply が変えることはない。
- 良い点：文の効果を変えるトリガーやルールがあれば、思いがけないものをコミットせずに apply が止まる。
- 良い点：失敗した apply は何も残さない。結果が不明な apply は、何も変わっていないと言い張らず、不明だと伝える。
- 悪い点：apply は、実行のすべての宣言の行をコミットまで読み込んだままにし、変えたすべての行のロックも同じ間持つ。そのため、大きな apply は一時テーブルの領域を使い、サービスからそれらの行への書き込みを待たせる。
- 悪い点：同じ行が同時に変わると apply が失敗し、チームはもう一度実行する必要がある。
- 悪い点：更新は、違う行の比べる列をすべて書く。そのため、`UPDATE OF` のトリガーは値の変わらない列についても発火し、ロールにはそのすべての列に対する `UPDATE` が要る。
- 悪い点：kortopi はシーケンスを動かさない。`serial` や識別列に明示の値を挿入する apply のあと、シーケンスは元の位置のままであり、アプリのあとの挿入が apply の書いた行とぶつかりうる。
- 悪い点：`session_replication_role` を `replica` にしたセッションでは、チームが意図してそうしていても apply できない。
- 悪い点：コミットは PostgreSQL 自身の一時スキーマをカタログに残す。そのため、apply の前後でデータベースのすべてのスキーマを比べる検査は、それらを除く必要がある。

### 確認の方法

- `internal/apply` の単体テストで、テーブルの順番、循環の遅らせ方、循環のエラー、作業の順番を確かめる。テストは `TestOrder`・`TestOrderIsDeterministic`・`TestRun`・`TestRunPlanned`・`TestRunInterrupted`・`TestRunUnknownOutcome` である。
- `internal/postgres` の単体テストで、文と書き込みのエラーを確かめる。テストは `TestWriteStatements`・`TestWriteError`・`TestCheckWrites`・`TestCommitOutcome` である。
- `cmd/kortopi` の単体テストで、フラグ・出力・終了コードを確かめる。テストは `TestParseApply`・`TestRunApply`・`TestRunApplyInterrupted`・`TestRunApplyInterruptedUnknownOutcome` である。
- 残りは、`make check-all` で実行する PostgreSQL 15〜18 に対する結合テストで確かめる。`internal/postgres` では、次のテストである。
  - apply のあとの宣言どおりの状態（`TestApplyBringsTheDeclaredState`）と、何も変えない失敗（`TestApplyFailureChangesNothing`）
  - スキーマをまたぐ順番（`TestApplyOrderOfForeignKeys`）と、自分自身を参照するテーブルと循環（`TestApplySelfReferenceAndCycle`）
  - 行の数の検査（`TestApplyRowCount`）と、権限（`TestApplyPrivileges`、`TestApplyNeedsMessages`）
  - ロック（`TestApplyWaitsForAnotherApply`）と、同時の変更（`TestApplyConcurrentChange`、`TestApplyConcurrentInsertIntoAPartition`）
  - ロールバックとコミットのあとのカタログ（`TestApplyLeavesNothingBehind`）と、PostgreSQL のエラー（`TestApplyErrors`）
  - 答えのないコミット（`TestCommitWithoutAnAnswer`）と、同じ名前の制約（`TestDeferWithAConstraintOfTheSameName`）
  - `session_replication_role`（`TestApplyNeedsTheOriginReplicationRole`）
- `cmd/kortopi` では、`TestApplyCommand` がコマンドを各バージョンに対して実行する。
- スタンバイ、Aurora PostgreSQL、本物のコネクションプーラーを対象にするテストはない。

## 選択肢の長所と短所

### トランザクションのロックのもとで、`REPEATABLE READ` の1つのトランザクションで、読み込んだ行から集合単位の文で書く

- 良い点：計画と書き込みが、1つのスナップショットと1組の条件を共にする。
- 良い点：ロックに、オブジェクトもセッションとの結び付きも要らない。
- 悪い点：同時の変更は、apply が避けて通るものではなく、もう一度実行すべきエラーになる。

### 読むときに保存されている行をロックする、`READ COMMITTED` の1つのトランザクション

- 良い点：保存されている行を同時に変えようとするトランザクションは、apply を失敗させずに apply を待つ。
- 悪い点：文ごとに新しいスナップショットを取る。計画を出力したあとで別のトランザクションの挿入した行が、文のすることを変えうる。そのため、出力した計画は、もう書き込む変更ではない。
- 悪い点：計画を求める間、宣言したすべてのテーブルの保存されているすべての行をロックする。そのため、apply が変えるかもしれない行のために、サービスを待たせることになる。

### `SERIALIZABLE` の1つのトランザクション

- 良い点：apply とほかのトランザクションの間のあらゆる異常を、PostgreSQL が見つける。
- 悪い点：その述語ロックは、apply が書くどの行にも関わらない同時の作業でも apply を失敗させる。宣言したすべてのテーブルを読むので、そうなりやすい。
- 悪い点：`REPEATABLE READ` でも、apply が書き別のトランザクションが変えたどの行でも失敗する。問題になるのは、その場合である。

### トランザクションの前後で持ち続けるセッションのロック

- 良い点：apply はトランザクションを始める前にロックを待てるので、やり直しが要らない。
- 悪い点：トランザクションモードのプーラーを通すと、ロックはトランザクションのあともサーバーの接続に残り、解放は別の接続で実行されうる。そのため、ロックが漏れ、あとの apply を止めてしまいうる。

### kortopi が計画から組み立てる、行ごとの文

- 良い点：エラーが、失敗した1行を示せる。
- 悪い点：どの値も PostgreSQL から kortopi に戻り、もう一度 SQL に書かれる。これは ADR-0009 が避けていることであり、条件も計画のものと並ぶ2つ目の実装になる。
- 悪い点：行の多いテーブルでは、同じ数の文と往復が要る。
