# ADR-0008: 行を SQL の INSERT 文と CSV ファイルで宣言する

## 背景と課題

kortopi は、マスタテーブルのあるべき行をファイルから読む。このファイルが宣言である。
宣言の書式は、利用者がいちばん多く書き、レビューするものであり、利用者がファイルを書いたあとでは変えにくい。

マスタデータの出どころは、チームによって違う。
SQL で持っているチームがある。初期データのスクリプトや、既存のデータベースのダンプである。
スプレッドシートで持っているチームもある。開発者でない人が編集していることも多い。

マスタデータの多くは、コードである。国のコード、都道府県のコード、状態や種類のコードなどである。
値の書き方から型を推測する書式では、kortopi が値を受け取る前に、そうしたコードが別の値に変わりうる。

利用者は、どの書式で行を宣言するか。

## 判断の基準

- PostgreSQL を知っている人は、新しく覚えることがない。
- 既存のデータベースを出発点にできる。その行を宣言として書き出せる。
- 値は、見た目にかかわらず、その列の型のまま扱われる。
- 1つの行の変更が、プルリクエストでは1行の変更として見える。
- 開発者でない人も、大きなテーブルをスプレッドシートで編集できる。
- 書式は少なくする。書式ごとに、読み込む処理を書き、テストし、文書にする必要があるからである。

## 検討した選択肢

- SQL の INSERT 文と CSV ファイル
- YAML
- JSON
- kortopi 独自の書式（DSL など）

## 決定

採用：「SQL の INSERT 文と CSV ファイル」。どちらも利用者と道具がすでに書いている書式であり、どちらでも kortopi が値の型を推測しないからである。どの値も、PostgreSQL がその列の型に照らして読む（ADR-0009）。

決まりは次のとおりである。

- 宣言は、データのディレクトリの下にある SQL ファイルと CSV ファイルの集まりである。どのファイルがどのテーブルを宣言するかは ADR-0014 で決める。
- SQL ファイルには `INSERT ... VALUES` の文を書く。マスタテーブルを対象にした `pg_dump --data-only --column-inserts` の出力を、出発点にできる。kortopi が SQL をどう読み、どの文を受け付けるかは ADR-0015 で決める。
- CSV ファイルは、1つのテーブルを宣言する。1行目は列の名前を並べた見出しの行であり、続く各行が1つの行である（引用符で囲んだ値が改行を含む場合を除く）。書き方は PostgreSQL の COPY の CSV 形式の規則に従い、文字コードは UTF-8 とする（ADR-0009）。
- どちらの書式でも、宣言した列は、ファイルが挙げた列である。CSV ファイルなら見出しの行の列、INSERT 文なら列の一覧の列である（ADR-0011）。
- kortopi は、ほかの書式を読まない。YAML も、JSON も、独自の書式も読まない。

### 結果

- 良い点：チームは、今あるデータベースから始められる。マスタテーブルを INSERT 文としてダンプするか、CSV として保存すれば、その時点で宣言がデータベースと一致する。
- 良い点：スプレッドシートで管理しているマスタデータは、CSV として保存すれば、そのまま宣言にできる。1つの行の変更は、プルリクエストでは1行の変更になる。
- 良い点：kortopi が、値の書き方から型を決めることはない。SQL ではリテラルが PostgreSQL 自身の規則に従い、CSV ではどの値も、PostgreSQL が列に読み込むまでは文字列である。
- 悪い点：書式が2つあるので、チームはテーブルごとにどちらかを選ぶことになり、kortopi は読み込む処理を2つ保守する。
- 悪い点：どちらの書式にも、テーブルの設定を書く場所がない（CSV にはコメントがない）。そのため、設定は別のファイルに置く（ADR-0013）。
- 悪い点：CSV には型も独自の NULL もなく、COPY の規則で決まる。引用符のない空の欄は NULL、`""` は空文字列である。スプレッドシートを CSV として保存する人は、これを予期していないかもしれない。
- 悪い点：`jsonb` の列に入れる JSON の文書のような入れ子の値は、CSV では扱いにくい。引用符で囲み、中の引用符をすべて二重にする必要がある。
- 悪い点：SQL ファイルはすべて SQL のパーサを通るが（ADR-0015）、CSV ファイルはパーサを通らずに COPY で入る。そのため、大きなテーブルは CSV で宣言するほうがよい。

### 確認の方法

両方の書式の見本の宣言を使った読み込みのテストと、それを PostgreSQL 15〜18 に読み込む結合テストで、この決定を確かめる。
これらのテストは、plan の実装とともに加わる。
新しい書式は、この記録を置き換える新しい記録がない限り、レビューで受け入れない。

## 選択肢の長所と短所

### SQL の INSERT 文と CSV ファイル

- 良い点：SQL なら新しく覚えることがなく、`pg_dump` がすでに書き出せる。
- 良い点：CSV はスプレッドシートで開け、差分では1行が1つの行になる。
- 良い点：どちらの書式でも、kortopi は型を推測しない。値を読むのは PostgreSQL である。
- 悪い点：文書にし、テストし、保守する書式が2つある。
- 悪い点：CSV にはコメントも型もない。

### YAML

- 良い点：設定や初期データでよく使われ、コメントを書ける。
- 良い点：入れ子の値を書きやすい。
- 悪い点：値の書き方で型が変わる。今も多くのパーサが従う YAML 1.1 では、国のコード `NO` は真偽値の false になり、`0123` は8進数の 83 になり、バージョンの `1.10` は数の 1.1 になる。マスタデータは、こうしたコードであふれている。
- 悪い点：1つの行が何行にもなるので、大きなテーブルは長くて読みにくく、スプレッドシートでは編集できない。

### JSON

- 良い点：どの言語でも読め、文字列は必ず引用符で囲むので、型がはっきりしている。
- 良い点：`jsonb` の列に入れる文書のような入れ子の値を、自然に書ける。
- 悪い点：型が文字列・数・真偽値・null しかない。日付・タイムスタンプ・numeric・enum は、結局どれも文字列になる。しかも、JSON 自身の型は、PostgreSQL の規則と並ぶもう1組の規則になる。
- 悪い点：スプレッドシートで編集する人はいない。オブジェクトの配列にすると、どの行にもすべての列の名前が繰り返し現れ、差分が読みにくくなる。

### kortopi 独自の書式（DSL など）

- 良い点：型・設定・参照を1か所に書けるよう、マスタデータに合わせて設計できる。
- 悪い点：利用者は誰もが新しく覚える必要があり、この書式を書き出す道具もない。既存のデータベースやスプレッドシートは、先に変換する必要がある。
- 悪い点：kortopi が、構文・型の規則・エラーメッセージを定め、安定して保つ必要がある。これは道具の仕事の大きな部分を占める。

## 補足

- [`pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html)（オプション `--data-only` と `--column-inserts`）
- [COPY](https://www.postgresql.org/docs/current/sql-copy.html)（CSV 形式の規則）
- [YAML 1.1 の真偽値の型](https://yaml.org/type/bool.html)（false の書き方として `no` や `NO` を挙げている）
